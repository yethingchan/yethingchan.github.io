### 一、Domain 层：业务逻辑的纯净内核

Domain 层是整个架构的基石，它是一个**纯 C# 类库**，不引用任何 NuGet 包（除 System 包外），这意味着它可以在任何 .NET 环境中运行，没有任何框架绑定。

```
│   ├── BaseEvent.cs            ← 领域事件的基类（继承 MediatR.INotification）
│   └── ValueObject.cs          ← 值对象基类，实现值相等语义
```

**关键设计点 1：BaseEntity 与领域事件**

```csharp
public abstract class BaseEntity
{
    public int Id { get; set; }

    private readonly List<BaseEvent> _domainEvents = new();

    [NotMapped]
    public IReadOnlyCollection<BaseEvent> DomainEvents => _domainEvents.AsReadOnly();

    public void AddDomainEvent(BaseEvent domainEvent) => _domainEvents.Add(domainEvent);
    public void RemoveDomainEvent(BaseEvent domainEvent) => _domainEvents.Remove(domainEvent);
    public void ClearDomainEvents() => _domainEvents.Clear();
}
```

`_domainEvents` 是一个私有列表，通过 `AddDomainEvent` 方法添加。`[NotMapped]` 特性告诉 EF Core 不要将其映射到数据库列。这种设计让实体可以在修改自身状态时"记录"发生了什么，然后在持久化时由 Infrastructure 层统一分发。

**关键设计点 2：值对象 Colour**

```csharp
public class Colour(string code) : ValueObject
{
    public static Colour From(string code)
    {
        var colour = new Colour(code);
        if (!SupportedColours.Contains(colour))
            throw new UnsupportedColourException(code);
        return colour;
    }

    public static Colour Red => new("#E05C4D");
    public static Colour Blue => new("#5C6BC0");
    // ... 更多预定义颜色

    public static implicit operator string(Colour colour) => colour.ToString();
    public static explicit operator Colour(string code) => From(code);

    protected override IEnumerable<object> GetEqualityComponents()
    {
        yield return Code;
    }
}
```

Colour 展示了值对象的三个核心特征：不可变性（`Code` 的 setter 是 private 的）、基于值的相等性（通过 `GetEqualityComponents` 实现）、以及工厂方法模式（`From` 方法进行验证，预定义静态属性提供合法值）。隐式转换运算符让 Colour 可以无缝地在需要 string 的地方使用。

**关键设计点 3：实体中的领域事件触发**

```csharp
public class TodoItem : BaseAuditableEntity
{
    private bool _done;
    public bool Done
    {
        get => _done;
        set
        {
            if (value && !_done)  // 仅在从 false → true 时触发
            {
                AddDomainEvent(new TodoItemCompletedEvent(this));
            }
            _done = value;
        }
    }
}
```

这里展示了一个精妙的设计：`Done` 属性的 setter 不仅设置值，还在状态变化时自动注册领域事件。只有当值从 `false` 变为 `true` 时才触发，避免了重复事件。这是 DDD 中"充血模型"的典型体现——实体不仅仅是数据容器，还包含行为。

### 二、Application 层：用例编排的指挥中心

Application 层是整个系统最"厚"的一层，它不关心数据怎么存（那是 Infrastructure 的事），也不关心请求怎么来（那是 Web 的事），它只关心**业务流程如何编排**。

**核心组织原则：按功能（Feature）而非按类型分组**

注意 Application 层的目录结构不是 `Controllers/`、`Services/`、`Validators/` 这种按技术类型分组，而是按业务功能（TodoItems、TodoLists）分组，每个功能下再按操作类型（Commands、Queries）细分，每个操作有自己的文件夹。

这种组织方式的好处是：当你需要修改"创建待办项"的功能时，相关的 Command、Handler、Validator、DTO 都在同一个文件夹里，不需要在多个目录之间跳转。

**关键设计点：命令/处理器/验证器同文件**

在较新版本的 CleanArchitecture 中，一个 Command 的完整定义（Command record、Handler class、Validator class）被放在同一个 `.cs` 文件中。这种设计减少了文件数量，同时保持了内聚性：

```csharp
// CreateTodoListCommand.cs —— 一个文件包含三个类
public record CreateTodoListCommand : IRequest<int>
{
    public string? Title { get; init; }
}

public class CreateTodoListCommandValidator : AbstractValidator<CreateTodoListCommand>
{
    public CreateTodoListCommandValidator(IApplicationDbContext context)
    {
        RuleFor(v => v.Title)
            .NotEmpty().WithMessage("Title is required.")
            .MaximumLength(200).WithMessage("Title must not exceed 200 characters.")
            .MustAsync(BeUniqueTitle(context))
                .WithMessage("'{PropertyName}' must be unique.")
                .WithErrorCode("UNIQUE_TITLE");
    }
    // ...
}

public class CreateTodoListCommandHandler 
    : IRequestHandler<CreateTodoListCommand, int>
{
    private readonly IApplicationDbContext _context;
    
    public CreateTodoListCommandHandler(IApplicationDbContext context)
    {
        _context = context;
    }

    public async Task<int> Handle(CreateTodoListCommand request, 
        CancellationToken cancellationToken)
    {
        var entity = new TodoList { Title = request.Title };
        _context.TodoLists.Add(entity);
        await _context.SaveChangesAsync(cancellationToken);
        return entity.Id;
    }
}
```

**关键设计点 1：EF Core 配置与值对象映射**

Infrastructure 层通过 Fluent API 配置实体映射，特别是值对象的处理：

```csharp
public class TodoListConfiguration : IEntityTypeConfiguration<TodoList>
{
    public void Configure(EntityTypeBuilder<TodoList> builder)
    {
        builder.Property(t => t.Title)
            .HasMaxLength(200)
            .IsRequired();

        builder.OwnsOne(t => t.Colour);  // 值对象映射为 OwnsOne
    }
}
```

`OwnsOne` 告诉 EF Core `Colour` 是 `TodoList` 的"拥有类型"，它的属性会被映射到 `TodoList` 对应的表中（列名为 `Colour_Code`），而不是创建一个独立的表。这是 EF Core 处理 DDD 值对象的标准方式。

**关键设计点 2：审计拦截器**

```csharp
public class AuditableEntityInterceptor : SaveChangesInterceptor
{
    private readonly IUser _user;
    private readonly TimeProvider _dateTime;

    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData, InterceptionResult<int> result,
        CancellationToken cancellationToken = default)
    {
        UpdateEntities(eventData.Context);
        return base.SavingChangesAsync(eventData, result, cancellationToken);
    }

    public void UpdateEntities(DbContext? context)
    {
        foreach (var entry in context.ChangeTracker.Entries<BaseAuditableEntity>())
        {
            if (entry.State is EntityState.Added or EntityState.Modified 
                || entry.HasChangedOwnedEntities())
            {
                var utcNow = _dateTime.GetUtcNow();
                if (entry.State == EntityState.Added)
                {
                    entry.Entity.CreatedBy = _user.Id;
                    entry.Entity.Created = utcNow;
                }
                entry.Entity.LastModifiedBy = _user.Id;
                entry.Entity.LastModified = utcNow;
            }
        }
    }
}
```

这个拦截器的巧妙之处在于 `HasChangedOwnedEntities` 扩展方法：即使 `BaseAuditableEntity` 本身没有变化，但如果它拥有的值对象发生了变化（比如修改了 `TodoList` 的 `Colour`），也需要更新 `LastModified` 字段。这确保了审计数据的完整性。

**关键设计点 3：领域事件分发拦截器**

```csharp
public class DispatchDomainEventsInterceptor : SaveChangesInterceptor
{
    private readonly IMediator _mediator;

    public override async ValueTask<int> SavedChangesAsync(
        DbContextEventData eventData, int result,
        CancellationToken cancellationToken = default)
    {
        await DispatchDomainEvents(eventData.Context);
        return await base.SavedChangesAsync(eventData, result, cancellationToken);
    }

    private async Task DispatchDomainEvents(DbContext? context)
    {
        var entities = context.ChangeTracker
            .Entries<BaseEntity>()
            .Where(e => e.Entity.DomainEvents.Any())
            .Select(e => e.Entity);

        var domainEvents = entities
            .SelectMany(e => e.DomainEvents)
            .ToList();

        entities.ToList().ForEach(e => e.ClearDomainEvents());

        foreach (var domainEvent in domainEvents)
            await _mediator.Publish(domainEvent);
    }
}
```

注意事件是在 `SavedChangesAsync`（保存之后）而不是 `SavingChangesAsync`（保存之前）分发的。这确保了当事件处理器收到事件时，触发事件的数据变更已经持久化了。同时，分发前先 `ClearDomainEvents()` 避免了事件的重复处理。

### 四、Web 层：HTTP 入口与端点发现

**关键设计点：基于约定的端点发现**

项目没有使用传统的 Controller 模式，而是采用了 Minimal API + 自定义端点发现机制：

```csharp
public class TodoLists : IEndpointGroup
{
    public static void Map(RouteGroupBuilder groupBuilder)
    {
        groupBuilder.RequireAuthorization();

        groupBuilder.MapGet(GetTodoLists);
        groupBuilder.MapPost(CreateTodoList);
        groupBuilder.MapPut(UpdateTodoList, "{id}");
        groupBuilder.MapDelete(DeleteTodoList, "{id}");
    }

    [EndpointSummary("Get all Todo Lists")]
    public static async Task<Ok<TodosVm>> GetTodoLists(ISender sender)
    {
        var vm = await sender.Send(new GetTodosQuery());
        return TypedResults.Ok(vm);
    }

    [EndpointSummary("Create a new Todo List")]
    public static async Task<Created<int>> CreateTodoList(
        ISender sender, CreateTodoListCommand command)
    {
        var id = await sender.Send(command);
        return TypedResults.Created($"/{nameof(TodoLists)}/{id}", id);
    }
}
```

`IEndpointGroup` 接口是一个标记接口，`EndpointRouteBuilderExtensions` 会在启动时通过反射扫描所有实现了 `IEndpointGroup` 的类，自动调用它们的 `Map` 方法并注册路由。路由规则约定：类名 `TodoLists` 对应路由前缀 `/api/TodoLists`，方法名对应具体的路由后缀。

这种设计的好处是：添加新端点只需创建一个新类实现 `IEndpointGroup`，无需修改任何路由配置或启动代码。

**关键设计点：TypedResults 替代 IActionResult**

注意端点方法的返回类型使用了 `TypedResults`（如 `Ok<T>`、`Created<int>`、`NoContent`），而不是传统的 `IActionResult`。这是 ASP.NET Core 的现代做法，好处是：编译器可以检查返回类型是否匹配，OpenAPI 文档可以自动生成准确的响应 schema。

### 五、Shared 层：前后端共享的契约

```
src/Shared/
└── (前后端共享的 DTO、常量、枚举等)
```

Shared 层是一个独立的项目，被 Web 层和前端项目同时引用。它包含了 DTO 定义、常量等需要在前后端之间共享的类型。这种设计确保了前端和后端使用相同的类型定义，减少了因手动同步导致的不一致。


### 七、文件组织的设计原则总结

通过以上分析，可以提炼出 CleanArchitecture 项目文件组织的几条核心原则：

1. **按功能分组优于按类型分组**：`TodoItems/Commands/CreateTodoItem/` 优于 `Commands/TodoItems/CreateTodoItemCommand.cs`。
2. **高内聚文件**：相关的 Command、Handler、Validator 放在同一个文件中，减少文件碎片。
3. **依赖注入集中管理**：每一层都有自己的 `DependencyInjection.cs`，负责注册该层的服务。
4. **全局 using 简化引用**：`GlobalUsings.cs` 文件统一管理常用的 `using` 声明，减少每个文件头部的重复。
5. **配置与实现分离**：EF Core 的 `IEntityTypeConfiguration` 放在 `Configurations/` 文件夹，而不是和 `DbContext` 混在一起。

### 一、MediatR 管道行为（Pipeline Behaviors）全解析

MediatR 的管道行为是本项目最精妙的设计之一。它通过 AOP（面向切面编程）的思想，将横切关注点（日志、异常、验证、授权、性能监控）从业务逻辑中抽离出来，形成可组合的管道。

#### 1.1 管道行为的执行顺序

管道行为的注册顺序决定了执行顺序，这在 `DependencyInjection.cs` 中配置：

```
请求进入 → LoggingBehaviour → UnhandledExceptionBehaviour 
         → AuthorizationBehaviour → ValidationBehaviour 
         → PerformanceBehaviour → Handler → 响应返回
```

这个顺序是经过精心设计的：日志行为在最外层确保所有请求都被记录；异常处理紧随其后确保后续行为抛出的异常都能被捕获；授权在验证之前执行，因为未授权的请求没必要进行验证；性能计时在最内层，只计算实际业务处理的时间。

#### 1.2 验证行为（ValidationBehaviour）

```csharp
public class ValidationBehaviour<TRequest, TResponse> 
    : IPipelineBehavior<TRequest, TResponse>
    where TRequest : notnull
{
    private readonly IEnumerable<IValidator<TRequest>> _validators;

    public ValidationBehaviour(IEnumerable<IValidator<TRequest>> validators)
    {
        _validators = validators;
    }

    public async Task<TResponse> Handle(TRequest request, 
        RequestHandlerDelegate<TResponse> next, CancellationToken cancellationToken)
    {
        if (_validators.Any())
        {
            var context = new ValidationContext<TRequest>(request);

            var validationResults = await Task.WhenAll(
                _validators.Select(v => v.ValidateAsync(context, cancellationToken)));

            var failures = validationResults
                .Where(r => r.Errors.Any())
                .SelectMany(r => r.Errors)
                .ToList();

            if (failures.Any())
                throw new ValidationException(failures);
        }
        return await next();
    }
}
```

几个值得注意的技术细节：

**并行验证**：使用 `Task.WhenAll` 并行执行所有验证器，而不是逐一执行。当有多个验证器时（比如一个验证字段格式，另一个验证唯一性），并行执行可以显著减少延迟。

**无验证器时跳过**：`if (_validators.Any())` 确保当某个 Command 没有对应的 Validator 时，管道行为直接跳过，不会抛出异常。

**聚合所有错误**：不是遇到第一个错误就抛异常，而是收集所有验证错误后一次性抛出，让客户端可以同时修复所有问题。

#### 1.3 性能行为（PerformanceBehaviour）

```csharp
public class PerformanceBehaviour<TRequest, TResponse> 
    : IPipelineBehavior<TRequest, TResponse> where TRequest : notnull
{
    private readonly Stopwatch _timer;
    private readonly ILogger<TRequest> _logger;
    private readonly IUser _user;
    private readonly IIdentityService _identityService;

    public async Task<TResponse> Handle(TRequest request, 
        RequestHandlerDelegate<TResponse> next, CancellationToken cancellationToken)
    {
        _timer.Start();
        var response = await next();
        _timer.Stop();

        var elapsedMilliseconds = _timer.ElapsedMilliseconds;

        if (elapsedMilliseconds > 500)
        {
            var requestName = typeof(TRequest).Name;
            var userId = _user.Id ?? string.Empty;
            var userName = string.IsNullOrEmpty(userId) 
                ? string.Empty 
                : await _identityService.GetUserNameAsync(userId);

            _logger.LogWarning(
                "CleanArchitecture Long Running Request: {Name} ({ElapsedMilliseconds}ms) {@UserId} {@UserName} {@Request}",
                requestName, elapsedMilliseconds, userId, userName, request);
        }
        return response;
    }
}
```

性能行为记录超过 500 毫秒的请求，并将请求名称、耗时、用户 ID、请求内容全部结构化输出。使用 Serilog 的结构化日志特性（`{@Request}`），日志可以被 ELK 或 Seq 等系统索引和查询。

#### 1.4 授权行为（AuthorizationBehaviour）

授权行为通过反射读取 Command 上的 `[Authorize]` 特性来实现声明式授权：

```csharp
public async Task<TResponse> Handle(TRequest request, 
    RequestHandlerDelegate<TResponse> next, CancellationToken cancellationToken)
{
    var authorizeAttributes = request.GetType().GetCustomAttributes<AuthorizeAttribute>();

    if (authorizeAttributes.Any())
    {
        // 1. 认证检查：用户必须已登录
        if (_user.Id == null)
            throw new UnauthorizedAccessException();

        // 2. 角色授权：用户必须属于指定角色之一
        var authorizeAttributesWithRoles = authorizeAttributes
            .Where(a => !string.IsNullOrWhiteSpace(a.Roles));
        if (authorizeAttributesWithRoles.Any())
        {
            var authorized = false;
            foreach (var roles in authorizeAttributesWithRoles.Select(a => a.Roles.Split(',')))
            {
                foreach (var role in roles)
                {
                    var isInRole = _user.Roles?.Any(x => role == x) ?? false;
                    if (isInRole) { authorized = true; break; }
                }
            }
            if (!authorized) throw new ForbiddenAccessException();
        }

        // 3. 策略授权：基于 ASP.NET Core 的 Policy 机制
        var authorizeAttributesWithPolicies = authorizeAttributes
            .Where(a => !string.IsNullOrWhiteSpace(a.Policy));
        if (authorizeAttributesWithPolicies.Any())
        {
            foreach (var policy in authorizeAttributesWithPolicies.Select(a => a.Policy))
            {
                var authorized = await _identityService.AuthorizeAsync(_user.Id, policy);
                if (!authorized) throw new ForbiddenAccessException();
            }
        }
    }
    return await next();
}
```

这种设计的精妙之处在于：授权逻辑完全在 Application 层，不需要依赖 ASP.NET Core 的中间件。这意味着同一个 Command 无论是通过 HTTP API、gRPC 还是消息队列触发，授权逻辑都会生效。

### 二、EF Core 高级用法

#### 2.1 IApplicationDbContext 接口：数据访问的抽象

```csharp
public interface IApplicationDbContext
{
    DbSet<TodoList> TodoLists { get; }
    DbSet<TodoItem> TodoItems { get; }
    
    Task<int> SaveChangesAsync(CancellationToken cancellationToken);
}
```

这个接口只暴露 `DbSet<T>` 和 `SaveChangesAsync`，不暴露 EF Core 的 `ChangeTracker`、`Database` 等底层 API。Application 层的 Handler 通过这个接口操作数据，在单元测试时可以用内存集合模拟 `DbSet<T>`。

#### 2.2 SaveChangesInterceptor 链

项目注册了两个拦截器，它们在 `SaveChanges` 调用前后按顺序执行：

```csharp
builder.Services.AddDbContext<ApplicationDbContext>(options =>
{
    options.AddInterceptors(
        new AuditableEntityInterceptor(user, timeProvider),
        new DispatchDomainEventsInterceptor(mediator)
    );
});
```

执行顺序：
1. `AuditableEntityInterceptor.SavingChangesAsync` — 填充审计字段
2. EF Core 执行 INSERT/UPDATE/DELETE SQL
3. `DispatchDomainEventsInterceptor.SavedChangesAsync` — 分发领域事件

这保证了审计字段在数据保存前被设置，而领域事件在数据保存后才被分发。

#### 2.3 OwnsOne 映射值对象

```csharp
public class TodoListConfiguration : IEntityTypeConfiguration<TodoList>
{
    public void Configure(EntityTypeBuilder<TodoList> builder)
    {
        builder.OwnsOne(t => t.Colour);
    }
}
```

`OwnsOne` 是 EF Core 处理值对象的方式。它会在 `TodoLists` 表中创建一个名为 `Colour_Code` 的列（`{属性名}_{值对象属性名}`）。值对象没有自己的主键，也不能独立存在，这与 DDD 的语义完全一致。

#### 2.4 全局查询过滤器

```csharp
builder.HasQueryFilter(e => !e.IsDeleted);  // 软删除过滤
```

项目使用全局查询过滤器实现软删除。所有查询自动附加 `WHERE IsDeleted = false` 条件，避免了在每一处查询中手动过滤的繁琐和遗漏。如果确实需要查询已删除的数据，可以使用 `IgnoreQueryFilters()` 方法。

### 三、全局异常处理与 ProblemDetails

Web 层使用 `ProblemDetailsExceptionHandler` 将不同类型的异常映射为标准的 RFC 9110 ProblemDetails 响应：

```csharp
public class ProblemDetailsExceptionHandler : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(HttpContext httpContext, 
        Exception exception, CancellationToken cancellationToken)
    {
        // ValidationException → 400 Bad Request
        // UnauthorizedAccessException → 401 Unauthorized
        // ForbiddenAccessException → 403 Forbidden
        // NotFoundException → 404 Not Found
        // 其他异常 → 500 Internal Server Error
    }
}
```

ProblemDetails 是 ASP.NET Core 推荐的标准错误响应格式，包含 `type`（错误类型 URL）、`title`（简短描述）、`status`（HTTP 状态码）、`detail`（详细信息）等字段。使用标准格式的好处是前端和 API 客户端可以用统一的方式解析错误。

### 四、依赖注入的组织方式

每一层都有自己的 `DependencyInjection.cs`，只注册该层负责的服务：

**Application 层的依赖注入：**
```csharp
public static class DependencyInjection
{
    public static IServiceCollection AddApplicationServices(this IServiceCollection services)
    {
        services.AddAutoMapper(Assembly.GetExecutingAssembly());
        services.AddValidatorsFromAssembly(Assembly.GetExecutingAssembly());
        services.AddMediatR(cfg => {
            cfg.RegisterServicesFromAssembly(Assembly.GetExecutingAssembly());
            cfg.AddBehavior(typeof(IPipelineBehavior<,>), typeof(UnhandledExceptionBehaviour<,>));
            cfg.AddBehavior(typeof(IPipelineBehavior<,>), typeof(ValidationBehaviour<,>));
            cfg.AddBehavior(typeof(IPipelineBehavior<,>), typeof(PerformanceBehaviour<,>));
            cfg.AddBehavior(typeof(IPipelineBehavior<,>), typeof(AuthorizationBehaviour<,>));
            cfg.AddBehavior(typeof(IPipelineBehavior<,>), typeof(LoggingBehaviour<,>));
        });
        return services;
    }
}
```

**Infrastructure 层的依赖注入：**
```csharp
public static class DependencyInjection
{
    public static IServiceCollection AddInfrastructureServices(
        this IServiceCollection services, IConfiguration configuration)
    {
        services.AddDbContext<ApplicationDbContext>(...);
        services.AddScoped<IApplicationDbContext>(provider => 
            provider.GetRequiredService<ApplicationDbContext>());
        services.AddScoped<ApplicationDbContextInitialiser>();
        services.AddIdentityServices(...);
        return services;
    }
}
```

**Web 层的 Program.cs 组合所有层：**
```csharp
builder.Services
    .AddApplicationServices()
    .AddInfrastructureServices(builder.Configuration)
    .AddWebServices();
```

这种分层注册的 pattern 使得每层的依赖注入逻辑是内聚的，添加新服务时只需修改对应层的 `DependencyInjection.cs`，不影响其他层。

### 五、.NET Aspire 云原生集成

从 v10 开始，项目引入了 .NET Aspire 作为编排和可观测性层：

**AppHost 项目** 是整个应用的启动入口，它编排了 Web 应用和数据库服务：

```csharp
var builder = DistributedApplication.CreateBuilder(args);
var database = builder.AddSqlServer("sql").AddDatabase("CleanArchitectureDb");
builder.AddProject<Projects.Web>("web")
    .WithReference(database)
    .WaitFor(database);
builder.Build().Run();
```

**ServiceDefaults 项目** 提供了所有服务共享的默认配置，包括健康检查端点（`/health` 和 `/alive`）、OpenTelemetry 追踪、弹性策略（重试和断路器）等。

引入 Aspire 的意义在于：项目从一开始就具备了生产级别的可观测性。分布式追踪、指标收集和日志聚合不需要后期"补"，而是开箱即用的。

### 六、自定义授权特性（Security 设计）

项目定义了自己的 `[Authorize]` 特性，放在 Application 层：

```csharp
namespace CleanArchitecture.Application.Common.Security;

[AttributeUsage(AttributeTargets.Class, AllowMultiple = true, Inherited = true)]
public class AuthorizeAttribute : Attribute
{
    public string Roles { get; set; } = string.Empty;
    public string Policy { get; set; } = string.Empty;
}
```

注意这个特性是放在 Application 层而不是 Web 层的，这意味着授权策略是业务逻辑的一部分。当 `PurgeTodoLists` 命令标记了 `[Authorize(Roles = "Administrator")]` 时，这个授权约束无论是在 HTTP 管道中还是在单元测试中都是有效的。

### 七、AutoMapper 的使用与争议

项目使用 AutoMapper 来处理 Entity ↔ DTO 的映射：

```csharp
public class MappingConfigurations : IProfileExpression
{
    public void Configure()
    {
        CreateMap<TodoList, TodoListDto>();
        CreateMap<TodoItem, TodoItemDto>();
        CreateMap<TodoList, TodoListDto>()
            .ForMember(d => d.Items, opt => opt.MapFrom(s => s.Items));
    }
}
```

AutoMapper 在这个项目中用于 Query 的返回结果映射。值得注意的是，Command 的输入不使用 AutoMapper，而是手动创建实体——这是因为 Command 的输入通常需要精确控制，不适合自动映射。

近年来 AutoMapper 在 .NET 社区引发了争议，其作者 Jimmy Bogard 本人也承认大多数场景下手动映射更好。如果你在自己的项目中犹豫，可以考虑仅在 Query 返回结果中使用 AutoMapper，在 Command 输入中手动映射。

### 八、IUser 接口：当前用户的抽象

```csharp
public interface IUser
{
    string? Id { get; }
    string[]? Roles { get; }
}
```

`IUser` 接口是对当前请求用户的抽象。在 ASP.NET Core 中，它通过 `HttpContext.User` 的 Claims 来实现。将当前用户抽象为接口的好处是：Application 层不需要知道 ASP.NET Core 的存在，测试时也可以轻松模拟当前用户。

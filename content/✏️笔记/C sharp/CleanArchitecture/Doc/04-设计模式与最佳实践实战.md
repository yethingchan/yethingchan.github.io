### 一、CQRS（命令查询职责分离）的落地实践

CQRS 是本项目最核心的架构模式。它的核心思想是：**修改数据的操作（Command）和读取数据的操作（Query）应该使用不同的模型**。

#### 1.1 为什么需要 CQRS

在传统的 CRUD 架构中，同一个 Service 方法既要处理查询也要处理修改，导致模型越来越复杂。一个 `GetTodoList` 查询可能需要关联 5 张表做 JOIN，而一个 `CreateTodoList` 命令只需要 INSERT 一条记录。如果用同一个模型，要么查询模型携带了大量不必要的字段，要么修改模型缺少了查询需要的关联数据。

CQRS 通过分离两者来解决这个问题：Command 模型关注写操作（验证、业务规则、持久化），Query 模型关注读操作（投影、分页、关联查询）。

#### 1.2 Command 与 Query 的区分

在本项目中，Command 和 Query 通过 MediatR 的接口来区分：

```csharp
// Command：修改数据，返回 ID 或无返回值
public record CreateTodoListCommand : IRequest<int>     // 返回新实体的 ID
public record UpdateTodoListCommand : IRequest           // 无返回值
public record DeleteTodoListCommand : IRequest           // 无返回值

// Query：读取数据，返回 ViewModel
public record GetTodosQuery : IRequest<TodosVm>         // 返回视图模型
public record GetAllTodoItemsQuery : IRequest<TodoItemsVm>
```

`IRequest<T>` 表示需要返回 `T` 类型的结果，`IRequest`（无泛型参数）表示不需要返回值。

#### 1.3 Command 的完整处理流程

以 `CreateTodoListCommand` 为例，一个 Command 从定义到执行经历以下步骤：

**定义层（同文件内）：**
```csharp
// 1. Command 定义（C# record 类型）
public record CreateTodoListCommand : IRequest<int>
{
    public string? Title { get; init; }
}

// 2. Validator 定义（FluentValidation）
public class CreateTodoListCommandValidator 
    : AbstractValidator<CreateTodoListCommand>
{
    public CreateTodoListCommandValidator(IApplicationDbContext context)
    {
        RuleFor(v => v.Title)
            .NotEmpty().WithMessage("Title is required.")
            .MaximumLength(200).WithMessage("Title must not exceed 200 characters.")
            .MustAsync(BeUniqueTitle(context))
                .WithMessage("'{PropertyName}' must be unique.")
                .WithErrorCode("UNIQUE_TITLE");
    }

    private static Func<string?, CancellationToken, Task<bool>> BeUniqueTitle(
        IApplicationDbContext context)
    {
        return async (title, cancellationToken) =>
            !await context.TodoLists.AnyAsync(l => l.Title == title, cancellationToken);
    }
}

// 3. Handler 定义
public class CreateTodoListCommandHandler 
    : IRequestHandler<CreateTodoListCommand, int>
{
    private readonly IApplicationDbContext _context;

    public async Task<int> Handle(CreateTodoListCommand request, 
        CancellationToken cancellationToken)
    {
        var entity = new TodoList { Title = request.Title };
        _context.TodoLists.Add(entity);
        await _context.SaveChangesAsync(cancellationToken);
        return entity.Id;
    }
}
```

**调用层（Web 端点）：**
```csharp
public static async Task<Created<int>> CreateTodoList(
    ISender sender, CreateTodoListCommand command)
{
    var id = await sender.Send(command);
    return TypedResults.Created($"/{nameof(TodoLists)}/{id}", id);
}
```

这个流程展示了 CQRS 的三个核心原则：Command 只负责写（Handler 中只有 Add + SaveChanges），Query 只负责读（Handler 中只有 SELECT），两者通过不同的 Handler 实现，互不干扰。

#### 1.4 异步验证（Async Validation）

注意 `BeUniqueTitle` 方法使用了 `MustAsync` 进行异步验证。这是因为它需要查询数据库来检查标题的唯一性。FluentValidation 支持同步和异步两种验证方式，涉及 I/O 操作时应始终使用异步方式以避免阻塞线程。

### 二、DDD 战术模式的运用

虽然项目没有完全遵循 DDD 的战略设计（限界上下文、上下文映射等），但在战术设计层面运用了多个 DDD 模式。

#### 2.1 实体（Entity）与值对象（Value Object）

**实体** 通过 `BaseEntity` 实现，拥有唯一标识（`Id`）和生命周期。**值对象** 通过 `ValueObject` 基类实现，没有唯一标识，通过属性值判断相等性。

```csharp
// 值对象基类的核心——基于值的相等性
public abstract class ValueObject : IEquatable<ValueObject>
{
    protected abstract IEnumerable<object> GetEqualityComponents();

    public override bool Equals(object? obj)
    {
        if (obj == null || obj.GetType() != GetType()) return false;
        var other = (ValueObject)obj;
        return GetEqualityComponents()
            .SequenceEqual(other.GetEqualityComponents());
    }

    public override int GetHashCode()
    {
        return GetEqualityComponents()
            .Select(x => x?.GetHashCode() ?? 0)
            .Aggregate((x, y) => x ^ y);
    }

    public bool Equals(ValueObject? other) => Equals((object?)other);
}
```

值对象的相等性通过 `GetEqualityComponents()` 实现，子类只需声明哪些属性参与相等性比较。`Colour` 值对象只比较 `Code` 属性：两个 Colour 对象只要 Code 相同就是相等的，即使它们是不同的对象实例。

#### 2.2 聚合根（Aggregate Root）

`TodoList` 是一个聚合根，`TodoItem` 是聚合内的实体。外部不能直接操作 `TodoItem`，必须通过 `TodoList` 来进行。这在 Application 层的 Command Handler 中体现为：所有对 `TodoItem` 的操作都通过 `IApplicationDbContext.TodoItems` 来进行，而不是绕过聚合根。

#### 2.3 领域事件（Domain Event）

领域事件是 DDD 中最强大的模式之一。它允许实体在不直接调用其他服务的情况下"通知"系统发生了什么。

```csharp
// 1. 实体在属性 setter 中注册事件
public bool Done
{
    get => _done;
    set
    {
        if (value && !_done)
            AddDomainEvent(new TodoItemCompletedEvent(this));
        _done = value;
    }
}

// 2. 事件定义
public class TodoItemCompletedEvent : BaseEvent
{
    public TodoItemCompletedEvent(TodoItem item)
    {
        Item = item;
    }
    public TodoItem Item { get; }
}

// 3. 事件处理器（Application 层）
public class TodoItemCompletedEventHandler 
    : INotificationHandler<TodoItemCompletedEvent>
{
    private readonly ILogger<TodoItemCompletedEventHandler> _logger;

    public Task Handle(TodoItemCompletedEvent notification, 
        CancellationToken cancellationToken)
    {
        _logger.LogInformation("Todo Item ({Id}) was completed.", 
            notification.Item.Id);
        return Task.CompletedTask;
    }
}
```

领域事件的价值在于**解耦**。TodoItem 不需要知道"完成"后需要做什么（发通知？更新统计？触发后续流程？），它只需要声明"我完成了"。所有关心这个事件的地方都可以通过实现 `INotificationHandler<TodoItemCompletedEvent>` 来响应，而不需要修改 TodoItem 的代码。

#### 2.4 领域异常（Domain Exception）

项目在 Domain 层定义了领域特有的异常类型，如 `UnsupportedColourException`。这些异常在 Web 层的 `ProblemDetailsExceptionHandler` 中被映射为对应的 HTTP 状态码。领域异常的存在让业务规则违反有了明确的信号。

### 三、中介者模式（Mediator Pattern）与 MediatR

MediatR 是本项目的"神经系统"，负责将请求从发送者路由到处理器。

#### 3.1 ISender vs IPublisher

MediatR 提供两个核心接口：

- `ISender.Send()` —— 用于 Command/Query，请求只会被路由到一个 Handler
- `IPublisher.Publish()` —— 用于 Notification（领域事件），请求会被路由到所有 Handler

在本项目中，Web 端点使用 `ISender` 发送 Command/Query，`DispatchDomainEventsInterceptor` 使用 `IPublisher` 发布领域事件。

#### 3.2 为什么用 MediatR 而不是直接调用 Service

直接调用 Service 的方式：
```csharp
// 传统方式
public class TodoListsController
{
    private readonly ITodoListService _service;
    
    public async Task<int> Create(CreateTodoListDto dto)
    {
        _logger.LogInformation("Creating...");           // 日志
        _validator.Validate(dto);                         // 验证
        await _authorizationService.AuthorizeAsync(...); // 授权
        var id = await _service.CreateAsync(dto);        // 业务逻辑
        _performanceLogger.LogElapsedTime(...);           // 性能
        return id;
    }
}
```

使用 MediatR 的方式：
```csharp
// Clean Architecture 方式
public static async Task<Created<int>> CreateTodoList(
    ISender sender, CreateTodoListCommand command)
{
    var id = await sender.Send(command);
    return TypedResults.Created($"/{nameof(TodoLists)}/{id}", id);
}
```

日志、验证、授权、性能监控全部由管道行为自动处理，端点方法只需一行 `sender.Send(command)`。这就是 MediatR 的价值：它把横切关注点从业务代码中抽离出来，让每个 Handler 只关心业务逻辑。

### 四、依赖倒置原则（DIP）的实际运用

DIP 是 SOLID 原则中最难理解也最有价值的一条。本项目的 DIP 运用可以用一张图概括：

```
Application 层定义接口        Infrastructure 层提供实现
─────────────────────        ────────────────────────
IApplicationDbContext    →   ApplicationDbContext
IUser                    →   CurrentUser（从 HttpContext 提取）
IIdentityService         →   IdentityService（调用 ASP.NET Identity）
```

关键点是：这些接口定义在 Application 层，但实现在 Infrastructure 层。这意味着 Application 层是"策略制定者"（定义需要什么能力），Infrastructure 层是"执行者"（提供具体实现）。

这种设计带来了一个重要的好处：Application 层的单元测试不需要真实的数据库、不需要真实的身份认证服务，只需要提供 Mock 实现即可。

### 五、测试策略：金字塔模型

项目的测试组织遵循测试金字塔：

```
           ▲
          / \        Web.FunctionalTests (少量)
         /   \       → 完整 HTTP 管道 + 真实数据库
        /─────\
       /       \     Application.FunctionalTests (适量)
      /         \    → MediatR Handler + 真实数据库
     /───────────\
    /             \  Application.UnitTests (大量)
   /               \ → Handler + Mock DbContext
  /─────────────────\
 /                   \ Domain.UnitTests (最多)
/                     \ → 纯逻辑，零 I/O
```

**Domain 层测试示例：**
```csharp
[Test]
public void TodoItem_Done_ShouldRaiseCompletedEvent()
{
    var item = new TodoItem();
    item.Done = true;
    item.DomainEvents.Should().ContainSingle()
        .Which.Should().BeOfType<TodoItemCompletedEvent>();
}

[Test]
public void Colour_From_ShouldThrowForUnsupportedColour()
{
    FluentActions.Invoking(() => Colour.From("#FFFFFF"))
        .Should().Throw<UnsupportedColourException>();
}
```

**Application 层测试示例：**
```csharp
[Test]
public async Task ShouldRequireUniqueTitle()
{
    var command = new CreateTodoListCommand { Title = "Shopping" };
    await _sender.Send(command);  // 第一次创建成功
    
    // 第二次创建同标题应该失败
    await FluentActions.Invoking(() => _sender.Send(command))
        .Should().ThrowAsync<ValidationException>()
        .Where(ex => ex.Errors.ContainsKey("Title"));
}
```

### 六、SOLID 原则在项目中的体现

| 原则 | 体现 |
|------|------|
| **S - 单一职责** | 每个 Handler 只做一件事，每个 Validator 只验证一个 Command |
| **O - 开闭原则** | 新增 Command 不需要修改管道行为，管道行为通过泛型自动适用 |
| **L - 里氏替换** | `BaseEntity` 的所有子类可以无差别地被 EF Core 持久化 |
| **I - 接口隔离** | `IUser`、`IIdentityService` 接口方法精简，只包含必要操作 |
| **D - 依赖倒置** | Application 层定义接口，Infrastructure 层提供实现 |

### 七、C# Record 类型在 CQRS 中的运用

项目大量使用 C# 的 `record` 类型来定义 Command 和 Query，这是经过深思熟虑的选择：

```csharp
public record CreateTodoListCommand : IRequest<int>
{
    public string? Title { get; init; }
}

public record UpdateTodoListCommand : IRequest
{
    public int Id { get; init; }
    public string? Title { get; init; }
}
```

Record 类型的优势在这个场景下得到了充分体现：不可变性（`init` setter 意味着创建后不能修改）、值相等性（两个相同内容的 Command 是相等的）、简洁的声明语法。不可变性对于 Command 尤其重要——一旦 Command 被创建并通过管道处理，它的内容不应该被中途修改。

### 八、端点路由的约定式设计

Web 层的端点发现系统是一个值得学习的设计模式：

```csharp
// 标记接口
public interface IEndpointGroup { }

// 反射扫描 + 自动注册
public static IEndpointRouteBuilder MapGroupEndpoints(
    this IEndpointRouteBuilder builder, string groupName)
{
    var assembly = typeof(Program).Assembly;
    var endpointGroupTypes = assembly.GetTypes()
        .Where(t => t.IsClass && !t.IsAbstract 
            && t.GetInterfaces().Contains(typeof(IEndpointGroup)));

    foreach (var type in endpointGroupTypes)
    {
        var groupRoute = $"/api/{type.Name}";
        var groupBuilder = builder.MapGroup(groupRoute)
            .WithGroupName(type.Name)
            .WithTags(type.Name);

        var mapMethod = type.GetMethod("Map", 
            BindingFlags.Public | BindingFlags.Static);
        mapMethod?.Invoke(null, new object[] { groupBuilder });
    }
    return builder;
}
```

这个设计的巧妙之处在于完全基于约定和反射：创建一个实现了 `IEndpointGroup` 的类，定义一个静态的 `Map` 方法，系统就会自动注册路由。添加新功能不需要修改任何启动代码，完全符合开闭原则。

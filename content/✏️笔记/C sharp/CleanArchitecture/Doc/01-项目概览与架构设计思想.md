### 一、为什么选择这个项目

JasonTaylorDev/CleanArchitecture 是 .NET 生态中最具影响力的 Clean Architecture 参考实现。它不是微软官方的 eShop 那样的"大而全"微服务演示，而是一个聚焦于**单体后端系统如何做到极致整洁**的标杆项目。它的技术深度体现在每一个文件夹、每一个类的设计上，而不是靠庞大的业务复杂度来堆砌。

这个项目适合以下人群深入学习：想从"能跑就行"进化到"工程化思维"的 C# 开发者，想理解 DDD/CQRS/MediatR 在真实项目中如何落地的架构师，以及正在寻找一个高质量脚手架来启动新项目的团队。

### 二、Clean Architecture 核心理念

Clean Architecture 由 Uncle Bob（Robert C. Martin）在 2012 年提出，核心思想可以用一句话概括：**依赖方向必须从外向内，内层（Domain）不依赖任何外层**。

把这个理念画成同心圆：

```
    ┌─────────────────────────────────────────┐
    │            Web / API 层                  │  ← 最外层：HTTP、中间件、序列化
    │  ┌───────────────────────────────────┐   │
    │  │        Infrastructure 层           │   │  ← 数据库、文件、外部服务
    │  │  ┌─────────────────────────────┐   │   │
    │  │  │      Application 层          │   │   │  ← 用例编排：CQRS、验证、授权
    │  │  │  ┌───────────────────────┐   │   │   │
    │  │  │  │     Domain 层         │   │   │   │  ← 最内层：实体、值对象、领域事件
    │  │  │  └───────────────────────┘   │   │   │
    │  │  └─────────────────────────────┘   │   │
    │  └───────────────────────────────────┘   │
    └─────────────────────────────────────────┘
```

每层之间的依赖关系是严格单向的：Web → Infrastructure → Application → Domain。Domain 层是一个"纯净"的 C# 类库，不引用任何第三方包（连 EF Core 都不引用），这让业务逻辑可以被独立测试和复用。

### 三、项目采用的关键架构决策

这个项目有三个被明确记录的 Architecture Decision Records（ADR），理解它们是深入分析的前提。

**ADR 1：EF Core 不使用 Repository 模式。** 这是一个反直觉的决策。传统 DDD 教程几乎都会给每个聚合根配一个 Repository 接口和实现。但本项目认为 EF Core 的 `DbContext` 本身就是一个 Unit of Work，`DbSet<T>` 就是一个 Repository。再加一层抽象只是增加了样板代码而没有实际收益。项目通过 `IApplicationDbContext` 接口来解耦，Application 层依赖这个接口，Infrastructure 层提供 `ApplicationDbContext` 实现。

**ADR 2：采用 .NET Aspire 进行编排。** 从 v10 开始，项目引入了 .NET Aspire 来管理服务编排、健康检查和可观测性。这意味着项目不仅仅是"能跑"，还考虑了云原生环境下的部署和监控。

**ADR 3：MediatR.Contracts 放在 Domain 层。** 通常通知（Notification）类会被放在 Application 层。但本项目将领域事件的契约定义放在 Domain 层，使得 Domain 层可以直接发布领域事件，而不需要向上依赖 Application 层。这是一个实用的折衷。

### 五、项目分层架构总览

整个解决方案包含 6 个核心项目和 6 个测试项目：

```
CleanArchitecture.sln
├── src/
│   ├── Domain/          ← 纯 C# 类库，零外部依赖
│   ├── Application/     ← MediatR + FluentValidation + AutoMapper
│   ├── Infrastructure/  ← EF Core + Identity + 外部服务适配
│   ├── Web/             ← ASP.NET Core Minimal API
│   ├── AppHost/         ← .NET Aspire 编排宿主
│   ├── ServiceDefaults/ ← Aspire 默认服务配置
│   └── Shared/          ← 前后端共享的 DTO / 常量
└── tests/
    ├── Domain.UnitTests/
    ├── Application.UnitTests/
    ├── Application.FunctionalTests/
    ├── Infrastructure.IntegrationTests/
    ├── Infrastructure.Data.SQLite.FunctionalTests/
    └── Web.FunctionalTests/
```

注意测试项目的命名约定：`UnitTests` 只测纯逻辑（无 I/O），`FunctionalTests` 会启动真实的 HTTP 管道（有数据库、有网络），`IntegrationTests` 介于两者之间。这种命名方式清晰地表达了测试的"重量级"。

### 六、数据流：一个请求的完整生命周期

理解架构最好的方式是追踪一个请求从进入到返回的全过程。以"创建 TodoList"为例：

1. **Web 层接收 HTTP 请求**：`POST /api/TodoLists` 被路由到 `TodoLists.CreateTodoList` 端点方法。该方法通过 `ISender`（MediatR 的发送接口）发出 `CreateTodoListCommand`。

2. **MediatR 管道启动**：Command 经过一系列 `IPipelineBehavior`，依次是：`LoggingBehaviour` → `UnhandledExceptionBehaviour` → `AuthorizationBehaviour` → `ValidationBehaviour` → `PerformanceBehaviour`。

3. **验证行为介入**：`ValidationBehaviour` 发现 `CreateTodoListCommand` 有对应的 `CreateTodoListCommandValidator`，执行验证。如果验证失败，抛出 `ValidationException`。

4. **命令处理器执行**：`CreateTodoListCommandHandler` 创建 `TodoList` 实体，通过 `IApplicationDbContext` 保存到数据库。

5. **EF Core 拦截器触发**：`AuditableEntityInterceptor` 在 `SaveChanges` 之前自动填充 `CreatedBy`、`Created` 等审计字段。

6. **领域事件分发**：如果实体上附加了领域事件，`DispatchDomainEventsInterceptor` 会在保存后通过 MediatR 发布这些事件。

7. **响应返回**：Handler 返回新创建的 `TodoList` 的 ID，Web 层包装成 `Created<int>` 响应返回给客户端。

这条数据流展示了 Clean Architecture 的核心价值：每一层只做自己擅长的事，层与层之间通过明确的契约（Command/Query 对象、接口）通信，而不是直接调用。

### 七、与传统三层架构的本质区别

很多开发者第一次看到 Clean Architecture 会觉得"不就是三层架构加了几个文件夹吗"。但本质区别在于依赖方向的控制。

在传统的三层架构（Controller → Service → Repository）中，Service 层通常会直接引用 EF Core，这意味着你的业务逻辑与数据访问技术耦合了。如果你想从 EF Core 切换到 Dapper，或者从 SQL Server 切换到 MongoDB，你需要修改 Service 层的代码。

在 Clean Architecture 中，Application 层通过 `IApplicationDbContext` 接口访问数据，这个接口完全由 Infrastructure 层实现。如果未来要换 ORM，只需在 Infrastructure 层提供一个新实现，Application 层一行代码都不用改。这就是依赖倒置原则（DIP）的实际价值。

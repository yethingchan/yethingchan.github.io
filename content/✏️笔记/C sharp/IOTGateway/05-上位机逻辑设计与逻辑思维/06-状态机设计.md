## 为什么上位机需要状态机

在工业控制中，"当前处于什么状态"决定了"应该做什么动作"。

一台设备的生命周期不是简单的"开/关"两态。它有上电初始化、建立连接、正常通信、暂停采集、断开连接等多个阶段。每个阶段有不同的允许操作和禁止操作。如果你不显式地建模这些状态，代码中就会充满 `if (已连接 && 未暂停 && 变量不为空)` 这样的嵌套条件判断 — 这就是"状态机"思维的缺失。

### 6.1 IoTGateway 中的状态层次

IoTGateway 的状态管理分布在三个层次：

```
层次1: 设备级状态 — 设备整体是否在线
        ↓
层次2: 驱动级状态 — 通信连接是否建立
        ↓
层次3: 变量级状态 — 每个变量的读取结果
```

### 6.2 驱动级状态：IsConnected

IDriver 接口定义了最基础的连接状态：

```csharp
// IDriver.cs
public interface IDriver : IDisposable
{
    public bool IsConnected { get; }
    // ...
}
```

以 Modbus 驱动为例，`IsConnected` 的实现考虑了多种传输介质：

```csharp
// DeviceModBusMaster.cs
public bool IsConnected
{
    get
    {
        switch (MasterType)
        {
            case MasterType.Tcp:
            case MasterType.RtuOnTcp:
            case MasterType.AsciiOnTcp:
                return _tcpClient != null
                    && _master != null
                    && _tcpClient.Connected;

            case MasterType.Udp:
            case MasterType.RtuOnUdp:
            case MasterType.AsciiOnUdp:
                return _udpClient != null
                    && _master != null
                    && _udpClient.Client.Connected;

            case MasterType.Rtu:
            case MasterType.Ascii:
                return _serialPort != null
                    && _master != null
                    && _serialPort.IsOpen;

            default:
                return false;
        }
    }
}
```

**设计洞察**：`IsConnected` 不只是一个布尔值，它是"连接对象存在 + 主站对象存在 + 底层通道打开"三个条件的交集。这保证了状态的准确性 — 如果只是创建了 `TcpClient` 对象但实际未连接，`IsConnected` 仍然返回 `false`。

### 6.3 设备级状态：DeviceThread 的隐式状态机

虽然 IoTGateway 没有显式定义一个 `DeviceState` 枚举，但 `DeviceThread.CreateThreadAsync` 的逻辑流程隐含了一个完整的状态机：

```
         ┌──────────────┐
         │   Created    │ (构造函数完成，AutoStart=true)
         └──────┬───────┘
                │ 启动 CreateThreadAsync
                ▼
         ┌──────────────┐
    ┌───→│  Connected   │◄───────────┐
    │    │  (读取变量)   │            │ Connect() 成功
    │    └──────┬───────┘            │
    │           │                     │
    │    IsConnected?                 │
    │     ↓Yes    ↓No                │
    │    继续   ┌──────────┐         │
    │    读取   │Disconnected│───────┘
    │           │(尝试重连) │
    │           └─────┬────┘
    │                 │ Connect() 失败
    │                 │ → 等待 MinPeriod 后重试
    │                 │
    │    全部Bad>60s  │
    │    ┌────────┐   │
    └────┤ForceDisconnect│
         │(Close+Dispose)│
         └───────────────┘
```

这个隐式状态机的转换条件：

| 当前状态 | 触发条件 | 下一状态 | 动作 |
|---------|---------|---------|------|
| Created | AutoStart=true | Connected | 启动采集循环 |
| Connected | IsConnected=false | Disconnected | 上报离线，尝试重连 |
| Disconnected | Connect()成功 | Connected | 上报在线 |
| Disconnected | Connect()失败 | Disconnected | 等待后重试 |
| Connected | 全部Bad超60秒 | ForceDisconnect | Close+Dispose |
| ForceDisconnect | 下一轮循环 | Disconnected | IsConnected=false |

### 6.4 变量级状态：VaribaleStatusTypeEnum

每个变量都有独立的状态跟踪：

```csharp
// VaribaleStatusTypeEnum.cs
public enum VaribaleStatusTypeEnum
{
    Good = 0,           // 读取成功，值有效
    AddressError,       // 地址解析错误
    MethodError,        // 驱动方法调用失败
    ExpressionError,    // 表达式计算错误
    Bad,                // 通信失败
    UnKnow,             // 初始状态/未确定
    Custome1,           // 驱动自定义状态1
    Custome2,           // 驱动自定义状态2
    Custome3,           // 驱动自定义状态3
    Custome4,           // 驱动自定义状态4
    Custome5            // 驱动自定义状态5
}
```

**状态转换图**：

```
                ┌───────┐
     初始状态 → │UnKnow │
                └───┬───┘
                    │ 首次读取
           ┌────────┼────────┐
           ▼        ▼        ▼
      ┌──────┐ ┌───────┐ ┌──────────┐
      │Good  │ │Bad    │ │XxxError  │
      └──┬───┘ └───┬───┘ └──────────┘
         │         │
    下次读取   下次读取
         │         │
    ┌────┴────┐ ┌──┴──┐
    ▼         ▼ ▼     ▼
  Good      Bad    Good
 (持续正常)(持续故障)(恢复)
```

变量状态的独立性很重要 — 一台设备上的 20 个变量，可能 18 个 Good、1 个 AddressError、1 个 Bad。你需要知道具体是哪个变量出了问题。

### 6.5 设备状态枚举：DeviceStatusTypeEnum

```csharp
// SendModel.cs — 设备状态类型
public enum DeviceStatusTypeEnum
{
    Good,       // 所有变量正常
    PartGood,   // 部分变量正常
    Bad,        // 全部变量异常
    UnKnow      // 未知
}
```

在 DeviceThread 中，当一轮采集完成后：

```csharp
// DeviceThread.cs — 设置设备状态
payLoad.DeviceStatus = DeviceStatusTypeEnum.Good;
```

**注意**：当前实现中 `DeviceStatus` 固定设为 `Good`，只要进入了 Connected 分支。更精确的做法是根据变量状态的分布来设置：

```csharp
// 改进思路：根据变量状态分布确定设备状态
var goodCount = group.Count(x => x.StatusType == VaribaleStatusTypeEnum.Good);
var totalCount = group.Count();

if (goodCount == totalCount)
    payLoad.DeviceStatus = DeviceStatusTypeEnum.Good;
else if (goodCount > 0)
    payLoad.DeviceStatus = DeviceStatusTypeEnum.PartGood;
else
    payLoad.DeviceStatus = DeviceStatusTypeEnum.Bad;
```

### 6.6 ProtectType：变量的操作权限状态

```csharp
// ProtectTypeEnum.cs
public enum ProtectTypeEnum
{
    ReadOnly,   // 只读：参与采集，不可写入
    ReadWrite,  // 读写：既采集又可写入
    WriteOnly,  // 只写：不采集，只可写入
}
```

这个枚举控制了变量在不同操作中的参与资格：

```csharp
// 轮询时：排除 WriteOnly
.Where(x => x.ProtectType != ProtectTypeEnum.WriteOnly)

// RPC写入时：排除 ReadOnly
if (deviceVariable != null
    && deviceVariable.ProtectType != ProtectTypeEnum.ReadOnly)
```

**状态机视角**：`ProtectType` 是变量的一个"静态状态" — 它在配置时确定，运行时不会改变。但它决定了变量在动态状态机中的"可达路径"。

### 6.7 如何设计更完整的设备状态机

如果我们要将 IoTGateway 的隐式状态机显式化，可以这样设计：

```csharp
public enum DeviceState
{
    Created,        // 已创建，未启动
    Initializing,   // 正在初始化（上传属性）
    Connected,      // 已连接，正常采集
    ReadingPaused,  // 采集暂停（RPC写入进行中）
    Reconnecting,   // 正在重连
    Disconnected,   // 已断开，等待重连
    Stopping,       // 正在停止
    Disposed        // 已释放
}
```

**完整的状态转换矩阵**：

```
Created ──(AutoStart)──→ Initializing
Initializing ──(属性上传完成)──→ Connected
Connected ──(IsConnected=false)──→ Disconnected
Connected ──(全部Bad>60s)──→ Reconnecting
Connected ──(RPC写入)──→ ReadingPaused
ReadingPaused ──(写入完成)──→ Connected
Disconnected ──(Connect成功)──→ Connected
Disconnected ──(Connect失败)──→ Disconnected
Reconnecting ──(Close完成)──→ Disconnected
Connected ──(StopThread)──→ Stopping
Disconnected ──(StopThread)──→ Stopping
ReadingPaused ──(StopThread)──→ Stopping
Stopping ──(Cancel完成)──→ Disposed
```

显式状态机的好处：
- **代码可读性**：一看就知道设备可能处于哪些状态
- **转换验证**：可以明确检查"从状态 A 是否允许转换到状态 B"
- **动作绑定**：每个转换都可以绑定明确的动作（日志、通知等）
- **调试便利**：打印当前状态就知道设备在做什么

### 6.8 用枚举组合表示复合状态

在实际项目中，一个设备的"状态"往往不是一个枚举能表达的。它是多个维度的组合：

```
设备状态 = 连接状态 × 采集状态 × 报警状态
```

例如：
- 连接正常 + 采集中 + 无报警 = "正常运行"
- 连接正常 + 暂停 + 无报警 = "写入中"
- 连接断开 + 重连中 + 通信报警 = "通信故障"

IoTGateway 通过多个独立的状态字段组合来表达复合状态：

```
Driver.IsConnected           → 连接维度
_resetEvent.IsSet            → 采集维度（Set=采集中，Reset=暂停）
变量 StatusType 的分布        → 健康维度
_lastGoodTime 距今多久        → 稳定性维度
```

### 6.9 状态转换中的副作用

每次状态转换都可能触发"副作用"（Side Effect）。IoTGateway 中的典型副作用：

| 状态转换 | 副作用 |
|---------|--------|
| Disconnected → Connected | 上报在线状态到云平台 |
| Connected → Disconnected | 上报离线状态到云平台 |
| Good → Bad（变量级） | 变量状态变为异常 |
| 全部Good → 有Bad | 可能触发设备离线通知 |
| Created → Initializing | 延迟5秒后开始上传属性 |

**设计原则**：状态转换和副作用应该一一对应。不要在随机的代码位置触发副作用，而应该在状态转换的"入口"处集中处理。

### 6.10 状态持久化 vs 运行时状态

IoTGateway 将状态分为两类：

**持久化状态**（存在数据库中）：
- 设备配置（AutoStart、CgUpload、CmdPeriod 等）
- 变量配置（地址、数据类型、表达式等）

**运行时状态**（只在内存中）：
- 当前连接状态
- 变量当前值和历史值
- 最后成功时间
- 暂停/恢复状态

```csharp
// DeviceVariable.cs — [NotMapped] 标记运行时状态
[NotMapped] public object Value { get; set; }
[NotMapped] public object CookedValue { get; set; }
[NotMapped] public string Message { get; set; }
[NotMapped] public DateTime Timestamp { get; set; }
[NotMapped] public VaribaleStatusTypeEnum StatusType { get; set; }
[NotMapped] public object[] Values { get; set; } = new object[3];
[NotMapped] public object[] CookedValues { get; set; } = new object[3];
```

这种分离是合理的 — 运行时状态不需要持久化，程序重启后会重新初始化。但有一个例外：如果你需要"记住"设备的最后一次状态（用于故障分析），那就需要将关键运行时状态定期写入数据库或日志。

### 6.11 状态机设计的思维提炼

**思维一：状态即约束**
每个状态都定义了"在这个状态下允许做什么、禁止做什么"。如果你发现代码中有大量的条件判断，考虑是否应该用状态机来组织。

**思维二：转换即事件**
状态之间的转换不是被动的"变化"，而是主动的"事件"。每次转换都应该有明确的触发条件、执行动作和日志记录。

**思维三：层次化状态**
设备级状态、驱动级状态、变量级状态 — 不同层次的状态相互影响但不混为一谈。一个变量是 Bad 不等于设备是断开的。

**思维四：显式优于隐式**
虽然 IoTGateway 使用隐式状态机（通过代码流程隐含），但在更复杂的系统中，建议使用显式的状态枚举和转换表。显式状态机更容易理解、测试和维护。

**思维五：不可达状态的检测**
设计完状态机后，检查是否存在"不可达状态"（没有任何路径能到达的状态）和"死锁状态"（进入后无法离开的状态）。这两种情况都是设计缺陷。

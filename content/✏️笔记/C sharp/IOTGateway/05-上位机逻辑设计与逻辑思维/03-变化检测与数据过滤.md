## 工业场景中的数据爆炸问题

想象一个真实的工业场景：一台 PLC 有 200 个变量，每 3 秒采集一次，每次采集后都上报到云平台。

计算一下数据量：200 变量 × 20 次/分钟 × 60 分钟 × 24 小时 = **288 万次/天**。

但实际上，在产线稳定运行时，大部分变量的值几乎没有变化 — 室温维持在 25°C，电机转速恒定在 1500rpm，阀门开度一直是 60%。这些"没变化的数据"占了总数据量的 80% 以上。

上传这些冗余数据不仅浪费网络带宽和存储空间，还会增加云平台的处理压力，更重要的是 — 淹没了真正有价值的变化数据。

**变化检测**就是解决这个问题的核心策略。

### 3.1 IoTGateway 的变化检测设计

IoTGateway 提供了两个关键配置参数来控制数据上报行为：

```csharp
// Device.cs — 设备模型中的变化检测配置
[Comment("变化上传")]
public bool CgUpload { get; set; }           // 是否启用变化检测

[Comment("归档周期ms")]
public uint EnforcePeriod { get; set; }      // 强制上报间隔（毫秒）
```

这两个参数的组合定义了一套灵活的上报策略：

| CgUpload | EnforcePeriod | 行为 |
|----------|--------------|------|
| false | 忽略 | 每次都上报（全量模式） |
| true | 60000 | 值变化时上报，但最长不超过 60 秒 |
| true | 300000 | 值变化时上报，但最长不超过 5 分钟 |
| true | 0 | 只在值变化时上报（纯变化模式，危险！） |

### 3.2 CanPubTelemetry：变化检测的核心算法

```csharp
// MessageService.cs — 变化检测与强制上报的完整逻辑
private bool CanPubTelemetry(
    string deviceName, Device device,
    Dictionary<string, List<PayLoad>> sendModel)
{
    try
    {
        var newTelemetry = sendModel[deviceName];
        var newPayload = newTelemetry[0];

        // 情况1：没有历史数据 → 必须上报（首次数据）
        if (!_lastTelemetrys.TryGetValue(deviceName, out var lastTelemetry)
            || lastTelemetry == null || lastTelemetry.Count == 0)
        {
            _lastTelemetrys[deviceName] = newTelemetry;
            return true;
        }

        var lastPayload = lastTelemetry[0];

        // 情况2：启用了变化检测
        if (device.CgUpload)
        {
            // 条件A：时间是否超过强制上报周期
            bool isTimeExceeded =
                (newPayload.TS - lastPayload.TS) > device.EnforcePeriod;

            // 条件B：值是否发生了变化
            bool isValueChanged =
                !newPayload.Values.SequenceEqual(lastPayload.Values);

            if (isTimeExceeded || isValueChanged)
            {
                _lastTelemetrys[deviceName] = newTelemetry;
                return true;
            }

            // 既没超时也没变化 → 不上报
            return false;
        }

        // 情况3：未启用变化检测 → 每次都上报
        _lastTelemetrys[deviceName] = newTelemetry;
        return true;
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, "Error in CanPubTelemetry");
        return true; // 异常时选择保守发布
    }
}
```

这个算法虽然简短，但包含了几个重要的设计决策：

### 3.3 双保险机制：变化触发 + 时间兜底

```
┌─────────────────────────────────────────────┐
│              每次采集后判断                    │
│                                              │
│  ┌── 值变化了？──┐     ┌── 超过EnforcePeriod？┐
│  │    Yes        │     │     Yes              │
│  │    ↓          │     │     ↓                │
│  │   上报        │ OR  │   上报               │
│  └───────────────┘     └──────────────────────┘
│         │                       │              │
│         └─────── Both No ───────┘              │
│                 ↓                              │
│               不上报                            │
└─────────────────────────────────────────────┘
```

**为什么需要 EnforcePeriod 兜底？**

假设一个温度传感器稳定在 25.0°C 不变。如果只有变化检测，这个值可能几天都不会上报。但云平台需要定期收到数据来确认"这个设备还活着"。EnforcePeriod 就是这个"心跳" — 即使值没变，每隔一段时间也要上报一次，告诉云端"我还在正常工作"。

**为什么 EnforcePeriod 不能太短？**
如果设成 1 秒，就变成了全量上报，失去了变化检测的意义。

**为什么 EnforcePeriod 不能太长？**
如果设成 1 小时，设备在这 1 小时内断线了，云平台要等 1 小时后才能发现。

典型的设置：
- 关键设备（安全相关）：10-30 秒
- 一般设备：60-300 秒
- 慢变化设备（环境温度）：300-600 秒

### 3.4 值比较的实现：SequenceEqual

```csharp
bool isValueChanged = !newPayload.Values.SequenceEqual(lastPayload.Values);
```

`SequenceEqual` 对两个字典做键值对的逐项比较。这里有一个隐含的设计选择 — 它比较的是**CookedValue**（计算后的值），而不是 RawValue（原始值）。

为什么比较计算后的值？

假设一个压力传感器的原始值是 16 位整数，经过表达式 `$v / 100.0` 转换。原始值可能从 `2567` 变成 `2568`（差 1），但转换后是 `25.67` 和 `25.68`（差 0.01）。如果业务上 0.01 的差别不重要，你可以在表达式中加入量化处理：

```
Math.Round($v / 100.0, 1)  // 只保留一位小数
```

这样，只有当计算值在小数点后一位发生变化时，才会触发上报。

### 3.5 内部 MQTT 推送的变化检测

除了对外的上报变化检测，IoTGateway 在内部也有一套独立的变化检测机制，用于前端 UI 的实时刷新：

```csharp
// DeviceThread.cs — 内部 MQTT 推送的变化检测
if (JsonConvert.SerializeObject(item.Values[1])
    != JsonConvert.SerializeObject(item.Values[0]) ||
    JsonConvert.SerializeObject(item.CookedValues[1])
    != JsonConvert.SerializeObject(item.CookedValues[0]))
{
    var msgInternal = new InjectedMqttApplicationMessage(
        new MqttApplicationMessage()
        {
            Topic = $"internal/v1/gateway/telemetry/{Device.DeviceName}/{item.Name}",
            PayloadSegment = Encoding.UTF8.GetBytes(
                JsonConvert.SerializeObject(ret))
        });
    mqttServer.InjectApplicationMessage(msgInternal);
}
```

这里比较的是**当前值（Values[0]）**和**前次值（Values[1]）**，通过 JSON 序列化后做字符串比较。虽然这不是最高效的比较方式（序列化有性能开销），但它有一个优势：可以处理任意类型的值（数字、字符串、布尔值等），不需要为每种类型写比较逻辑。

**思维要点**：内部推送和外部上报使用了不同的变化检测策略，这体现了"关注点分离"的设计原则 — 内部推送追求实时性（每次变化都推），外部上报追求经济性（过滤冗余数据）。

### 3.6 数据过滤的设计模式

IoTGateway 的变化检测只是数据过滤的一种方式。在工业上位机开发中，常见的数据过滤模式还包括：

**模式一：死区过滤（Deadband）**
```csharp
// 只有变化超过死区值才认为"真的变了"
bool HasSignificantChange(object newVal, object oldVal, double deadband)
{
    if (newVal is double nd && oldVal is double od)
        return Math.Abs(nd - od) > deadband;
    return !Equals(newVal, oldVal);
}
```

适用场景：传感器有微小抖动（如 ±0.1°C），不希望这些噪声触发上报。

**模式二：限速过滤（Rate Limiting）**
```csharp
// 即使值一直在变，也最多每 N 秒上报一次
private DateTime _lastPublishTime = DateTime.MinValue;

bool CanPublish(TimeSpan minInterval)
{
    if (DateTime.UtcNow - _lastPublishTime >= minInterval)
    {
        _lastPublishTime = DateTime.UtcNow;
        return true;
    }
    return false;
}
```

适用场景：高频变化的变量（如振动数据），不需要每次都上报。

**模式三：事件驱动过滤**
```csharp
// 只在特定事件发生时上报（如报警触发、报警恢复）
bool ShouldPublish(double value, double alarmHigh, double alarmLow)
{
    bool wasAlarm = _lastValue > alarmHigh || _lastValue < alarmLow;
    bool isAlarm = value > alarmHigh || value < alarmLow;
    return wasAlarm != isAlarm; // 报警状态发生了变化
}
```

适用场景：只需要知道"什么时候出了问题"，正常运行时不需要数据。

**模式四：聚合过滤**
```csharp
// 不逐条上报，而是聚合为统计值
var stats = new
{
    Max = values.Max(),
    Min = values.Min(),
    Avg = values.Average(),
    Count = values.Count
};
```

适用场景：高频采样但只关心统计特征（如每分钟的振动峰值）。

### 3.7 IsUpload 标志：变量级别的过滤

除了设备级别的变化检测，IoTGateway 还支持变量级别的上传控制：

```csharp
// DeviceThread.cs — 只有 IsUpload = true 的变量才会上报
var payLoad = new PayLoad()
{
    Values = group
        .Where(x => x.StatusType == VaribaleStatusTypeEnum.Good
                 && x.IsUpload)
        .ToDictionary(x => x.Name, x => x.CookedValue),
    DeviceStatus = payLoadTrigger.DeviceStatus
};
```

这个设计的实际意义：

- 有些变量只用于内部计算（如中间结果），不需要上报
- 有些变量是诊断信息（如通信计数器），运维时才需要
- 有些变量值很大（如字符串），上报成本高

通过 `IsUpload` 标志，可以精细控制哪些变量值得上报到云平台。

### 3.8 ProtectType 的过滤作用

```csharp
// DeviceVariable.cs — 变量保护类型
public enum ProtectTypeEnum
{
    ReadOnly,   // 只读 — 参与采集，不参与写入
    ReadWrite,  // 读写 — 采集和写入都参与
    WriteOnly,  // 只写 — 不参与采集！
}
```

```csharp
// DeviceThread.cs — WriteOnly 变量不参与轮询
.Where(x => x.ProtectType != ProtectTypeEnum.WriteOnly)
```

WriteOnly 变量是一个有趣的设计 — 它存在于设备配置中，但永远不被读取。典型场景是"控制指令"类的变量，你只需要往设备写值，不需要读回来。

### 3.9 _lastTelemetrys 的线程安全性

```csharp
// MessageService.cs — 使用 ConcurrentDictionary 保证线程安全
private readonly ConcurrentDictionary<string, List<PayLoad>> _lastTelemetrys = new();
```

由于多个 DeviceThread 可能同时调用 `CanPubTelemetry`，缓存字典必须是线程安全的。`ConcurrentDictionary` 提供了原子级的 `TryGetValue` 和索引器赋值操作。

但注意：`ConcurrentDictionary` 只保证字典操作的原子性，不保证"读取-比较-写入"这个复合操作的原子性。在高并发场景下，理论上存在极小的竞态窗口。对于工业场景来说，这种极小的竞态不会造成严重后果（最多重复上报一次），所以是可以接受的。

### 3.10 变化检测的异常处理策略

```csharp
catch (Exception ex)
{
    _logger.LogError(ex, "Error in CanPubTelemetry for device: {DeviceName}",
        deviceName);
    return true; // 出现异常，选择保守发布
}
```

**关键决策**：异常时选择"上报"而不是"不上报"。

这是工业软件开发中的一条重要原则：**在不确定性面前，选择更安全的行为**。如果变化检测逻辑本身出了问题，宁可多发一些冗余数据，也不能漏发重要数据。漏发可能导致云平台认为设备在线而实际上已经故障。

### 3.11 变化检测的思维提炼

**思维一：数据不等于信息**
数据是原始数字，信息是对决策有价值的数据。变化检测的本质是"数据→信息"的过滤器 — 它帮你筛除没有信息量的数据。

**思维二：双保险原则**
单一条件的过滤可能有漏洞。变化触发 + 时间兜底 的组合，确保了"该上报的不会被遗漏"。这种"双保险"思维在工业软件中非常常见。

**思维三：分层过滤**
IoTGateway 的过滤发生在多个层次：
- 变量级：IsUpload 标志
- 设备级：CgUpload + EnforcePeriod
- 通信级：MQTT QoS 和消息队列

每一层都在减少数据量，最终到达云平台的是最有价值的数据。

**思维四：保守策略**
当你不确定是否应该上报时，选择上报。冗余数据的代价远小于丢失数据的代价。

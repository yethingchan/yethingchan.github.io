## 为什么轮询是上位机的核心动作

在工业通信中，绝大多数场景是"主从模式" — 上位机（主站）主动向 PLC/仪表（从站）发起读取请求，从站被动响应。这与互联网 API 的"推模式"截然不同：不是等设备推送数据给你，而是你要不断地去"问"设备。

这就产生了上位机开发中最基本也最重要的逻辑结构 — **轮询循环**。

一个上位机程序可以没有 UI，可以没有数据库，但不能没有轮询循环。它是数据采集的心脏。

### 1.1 IoTGateway 的轮询架构

IoTGateway 为每台设备创建独立的 `DeviceThread`，每个线程内部运行一个 `async while` 循环。关键设计决策是**每设备一线程**，而不是所有设备共享一个线程。

```
IoTBackgroundService (启动入口)
    └── DeviceService (设备管理)
         ├── DeviceThread[设备A] → while循环: 读变量1, 读变量2, ...
         ├── DeviceThread[设备B] → while循环: 读变量1, 读变量2, ...
         └── DeviceThread[设备C] → while循环: 读变量1, 读变量2, ...
```

为什么不用线程池或 Task 并行？因为每台设备的通信参数不同 — 波特率、超时时间、最小通信周期都不一样。如果共享线程，一台慢设备会拖慢所有设备。独立线程保证了隔离性。

### 1.2 CreateThreadAsync：轮询主循环的完整解剖

这是整个 IoTGateway 最核心的方法。我们逐段分析：

**阶段一：启动延迟与属性上传**

```csharp
private async Task CreateThreadAsync(CancellationToken token)
{
    try
    {
        // 等待 5 秒再开始，给系统其他组件初始化的时间
        await Task.Delay(5000, token);

        // 上传客户端属性（设备配置信息）
        foreach (var group in Device.DeviceVariables!.GroupBy(x => x.Alias))
        {
            var deviceName = string.IsNullOrWhiteSpace(group.Key)
                ? Device.DeviceName : group.Key;
            var configDict = Device.DeviceConfigs
                .Where(x => x.DataSide == DataSide.ClientSide
                         || x.DataSide == DataSide.AnySide)
                .ToDictionary(x => x.DeviceConfigName, x => x.Value);
            await _messageService.UploadAttributeAsync(deviceName, configDict);
        }
```

**思维要点**：启动时为什么延迟 5 秒？因为系统启动时，MQTT 客户端可能还没连上服务器、数据库迁移可能还没完成。这是一个典型的"启动时序"问题 — 你不能假设所有组件都已就绪。

**阶段二：主循环 — 已连接状态下的变量读取**

```csharp
        while (!token.IsCancellationRequested)
        {
            // 如果有 RPC 写入正在进行，这里会阻塞等待
            _resetEvent.Wait(token);

            try
            {
                if (Driver.IsConnected)
                {
                    // 按 Alias 分组，每组独立发布
                    foreach (var group in Device.DeviceVariables
                        .Where(x => x.ProtectType != ProtectTypeEnum.WriteOnly)
                        .GroupBy(x => x.Alias))
                    {
                        // ... 读取并处理变量
                    }
                }
                else
                {
                    // 连接断开，尝试重连
                    if (Driver.Connect())
                    {
                        // 重连成功，上报在线状态
                    }
                }
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, $"线程循环异常,{Device.DeviceName}");
            }

            // 关键：循环间隔由 MinPeriod 控制
            await Task.Delay(Device.DeviceVariables!.Any()
                ? (int)Driver.MinPeriod : 10000, token);
        }
```

**阶段三：循环间隔 — MinPeriod 的作用**

注意最后一行 `await Task.Delay((int)Driver.MinPeriod, token)`。`MinPeriod` 是驱动层面定义的"最小通信周期"，不同协议差异很大：

| 协议 | 典型 MinPeriod | 原因 |
|------|---------------|------|
| Modbus TCP | 100-500ms | 以太网速度快 |
| Modbus RTU | 1000-3000ms | 串口速度慢，需要等待帧间隔 |
| OPC UA | 500-2000ms | 会话管理开销 |
| S7 (西门子) | 100-500ms | 以太网直连 |

这个设计体现了一个重要的逻辑思维：**时间约束是由最慢的环节决定的**。你不能让轮询周期快过协议本身允许的速度。

### 1.3 CmdPeriod：变量间的呼吸间隔

在主循环内部，每读取一个变量之后，都有一个 `CmdPeriod` 的延迟：

```csharp
private async Task ReadVariablesAsync(
    List<DeviceVariable> variables, PayLoad payLoad,
    MqttServer mqttServer, CancellationToken token)
{
    foreach (var item in variables.OrderBy(x => x.Index))
    {
        // ... 读取变量、表达式计算、状态更新 ...

        // 每个变量读取后，等待 CmdPeriod 毫秒
        await Task.Delay((int)Device.CmdPeriod, token);
    }
}
```

`CmdPeriod` 是设备级别的配置，表示"两条指令之间的最小间隔"。这个设计解决了一个非常实际的工业问题：

**串口通信的帧间隔问题**

Modbus RTU 协议规定，两帧之间必须有至少 3.5 个字符时间的静默间隔。在 9600 波特率下，这大约是 4ms。但实际上，很多设备的固件实现不够严格，如果你连续发送请求太快，设备可能来不及处理上一条就收到下一条，导致数据错乱。

设置 `CmdPeriod = 100ms` 就是给设备留出"消化"时间。

**TCP 通信的流量控制**

即使是 TCP 连接，连续快速读取也可能导致问题 — PLC 的通信处理能力有限，如果请求堆积过多，可能触发 PLC 的通信保护机制，主动断开连接。

### 1.4 顺序读取 vs 并行读取

IoTGateway 选择了**顺序读取**：

```csharp
foreach (var item in variables.OrderBy(x => x.Index))
{
    // 按 Index 排序后，一个一个读
}
```

这是一个有意的设计决策。为什么不用 `Task.WhenAll` 并行读取？

**原因一：协议限制**

Modbus 是半双工协议 — 同一时刻只能有一个请求在传输。即使你用多线程同时发请求，底层也会串行化。并行读取不仅不能提速，反而会导致帧冲突。

**原因二：设备保护**

PLC 的通信处理器通常优先级低于控制处理器。如果你同时发起多个读取请求，PLC 需要额外调度资源来响应，可能影响其核心控制任务。

**原因三：确定性**

顺序读取保证了变量读取的时序是确定的。如果你需要分析变量 A 和变量 B 的相关性（例如 A 是阀门开度，B 是流量），你需要确保它们的读取时间尽可能接近。顺序读取保证了这一点。

### 1.5 触发器变量：条件采集策略

IoTGateway 支持一种更精细的采集策略 — **触发器变量**（Trigger Variable）：

```csharp
// 先读取触发器变量
var triggerVariables = group.Where(x => x.IsTrigger).ToList();
await ReadVariablesAsync(triggerVariables, payLoadTrigger, _mqttServer, token);
var triggerValues = triggerVariables.ToDictionary(x => x.Name, x => x.CookedValue);

// 只有当触发器值为 true（或没有触发器变量）时，才读取其他变量
if (triggerValues.Values.Any(x => x is true) || !triggerVariables.Any())
{
    var nonTriggerVars = group
        .Where(x => !triggerVariables.Select(y => y.ID).Contains(x.ID))
        .ToList();
    await ReadVariablesAsync(nonTriggerVars, payLoadUnTrigger, _mqttServer, token);
    canPub = true;
}
```

这个设计的工业意义：

假设你有一条包装线，正常运行时所有传感器都在变化。但当产线停机时，温度、压力等值都不再有意义。你可以设置一个"产线运行状态"变量作为触发器 — 只有当产线运行时才采集其他数据。这样既节省了通信带宽，又避免了停机时上报无意义的数据。

### 1.6 批量读取优化：ReadMultiple + ReadFromCache

对于 Modbus 协议，IoTGateway 提供了一个精妙的批量读取优化：

```csharp
// DeviceModBusMaster.cs — 多地址读取
[Method("多地址读取", description: "多地址读取缓存")]
public DriverReturnValueModel ReadMultiple(DriverAddressIoArgModel ioArg)
{
    var args = ioArg.Address.Split(',');
    var func = args[0];            // 功能码
    var startAddress = ushort.Parse(args[1]);  // 开始地址
    var length = ushort.Parse(args[2]);        // 读取字数
    var cacheKey = args[3];        // 缓存字典名

    // 一次 Modbus 请求读取多个连续寄存器
    switch (func)
    {
        case "3":
            var holdingRs = _master.ReadHoldingRegisters(
                slaveId, startAddress, length);
            _cache[cacheKey] = holdingRs;
            break;
        // ...
    }
}

// 后续变量从缓存中取值，无需再次通信
[Method("从缓存读取", description: "从缓存读取")]
public DriverReturnValueModel ReadFromCache(DriverAddressIoArgModel ioArg)
{
    // 计算在缓存中的偏移量
    int startIndex = ushort.Parse(ioArg.Address) - _cacheStart[cacheName];
    var cacheBuffers = (ushort[])_cache[cacheName];
    var rawBuffers = cacheBuffers.Skip(startIndex).Take(wordLen).ToArray();
    // ...
}
```

**思维模式**：这是"空间换时间"的经典应用。如果 10 个变量分布在连续的寄存器地址（如 40001-40020），正常方式需要 10 次 Modbus 请求，而批量读取只需要 1 次请求 + 9 次数组索引操作。

**设计权衡**：
- 优势：通信次数大幅减少，采集速度提升
- 代价：需要额外的缓存管理，地址计算逻辑更复杂
- 适用场景：变量地址连续或密集分布
- 不适用：变量地址分散在不同功能码区域

### 1.7 Alias 分组：一台物理设备映射为多个逻辑设备

```csharp
foreach (var group in Device.DeviceVariables
    .Where(x => x.ProtectType != ProtectTypeEnum.WriteOnly)
    .GroupBy(x => x.Alias))
{
    var deviceName = string.IsNullOrWhiteSpace(group.Key)
        ? Device.DeviceName : group.Key;
    // ...
}
```

在工业现场，一台物理 PLC 可能连接了多个子设备 — 例如一台 PLC 同时控制 3 台电机。通过 Alias 机制，可以将一台物理 PLC 的数据分成 3 组，分别以不同的设备名上报到云平台。

这种"物理设备 → 逻辑设备"的映射，是上位机设计中非常重要的抽象能力。

### 1.8 轮询策略的选择指南

| 策略 | 适用场景 | IoTGateway 实现 |
|------|---------|----------------|
| 等间隔全量轮询 | 变量少，通信速度快 | 默认模式，CmdPeriod = 0 |
| 带延迟的顺序轮询 | 串口通信、慢速设备 | CmdPeriod > 0 |
| 触发式轮询 | 有条件采集需求 | IsTrigger = true |
| 批量读 + 缓存取值 | 地址连续的 Modbus 变量 | ReadMultiple + ReadFromCache |
| 只写不读 | 控制类变量 | ProtectType = WriteOnly |

### 1.9 轮询逻辑的思维提炼

**模式一：心跳式轮询**
轮询就像心跳 — 稳定、有节奏、不能停。MinPeriod 决定了心跳的频率，CmdPeriod 决定了每次心跳内部的节拍。

**模式二：隔离式设计**
每台设备独立线程，故障不会扩散。这和"微服务"的思想是一致的 — 但这里的隔离不是通过网络，而是通过线程。

**模式三：渐进式降级**
正常情况下全量采集 → 触发条件不满足时跳过部分变量 → 通信失败时只上报状态 → 长时间失败后断开重连。这是"优雅降级"思维在采集层的体现。

**模式四：时间就是语义**
在工业数据采集领域，"什么时候读的"和"读到了什么"同样重要。时间戳、采样间隔、时序关系 — 这些都是数据的一部分。

## 从原始字节到云端数据：一条完整的管线

一个温度值从传感器出发，到达云平台仪表板，中间经历了多少个处理环节？

```
传感器 → PLC寄存器 → 通信帧 → 上位机原始字节 → ushort[]
→ 字节序转换 → 数据类型转换 → 原始值(RawValue)
→ 表达式计算 → 计算值(CookedValue)
→ 环形缓冲区入队 → 变化检测
→ JSON序列化 → MQTT发布 → 云平台
```

这条链路有**至少 10 个处理阶段**，每个阶段都可能出错，每个阶段都有设计决策。理解这条完整的管线，是上位机开发者建立"系统观"的关键。

### 8.1 IoTGateway 的数据管线总览

让我们用一张图来展示 IoTGateway 的完整数据管线：

```
┌─────────────────────────────────────────────────────────────┐
│                    DeviceThread 轮询循环                     │
│                                                             │
│  ┌──────────┐  ┌───────────┐  ┌──────────┐  ┌───────────┐  │
│  │ 1.读取    │→│ 2.字节序   │→│ 3.类型    │→│ 4.入队     │  │
│  │ (Driver)  │  │ (驱动内)  │  │ 转换     │  │ (缓冲区)  │  │
│  └──────────┘  └───────────┘  └──────────┘  └───────────┘  │
│       ↓                                         ↓           │
│  ┌──────────┐  ┌───────────┐  ┌──────────┐  ┌───────────┐  │
│  │ 9.MQTT   │←│ 8.变化     │←│ 7.入队    │←│ 5.表达式  │  │
│  │ 发布     │  │ 检测      │  │ Cooked   │  │ 计算      │  │
│  └──────────┘  └───────────┘  └──────────┘  └───────────┘  │
│       ↓                                                     │
│  ┌──────────┐                                               │
│  │10.内部   │ (变量值变化时推送给前端)                        │
│  │ MQTT推送 │                                               │
│  └──────────┘                                               │
└─────────────────────────────────────────────────────────────┘
```

### 8.2 阶段一：驱动读取

```csharp
// DeviceThread.cs — 通过委托调用驱动方法
if (!MethodDelegates.TryGetValue(item.Method, out var methodDelegate))
{
    ret.StatusType = VaribaleStatusTypeEnum.MethodError;
}
else
{
    try
    {
        ret = methodDelegate(ioarg);
    }
    catch (Exception ex)
    {
        ret.StatusType = VaribaleStatusTypeEnum.MethodError;
    }
}
```

驱动方法通过反射预编译为委托，存储在 `MethodDelegates` 字典中：

```csharp
// DeviceThread.cs — 构造函数中缓存方法委托
foreach (var methodInfo in Driver.GetType().GetMethods()
    .Where(x => x.GetCustomAttribute(typeof(MethodAttribute)) != null))
{
    var del = (Func<DriverAddressIoArgModel, DriverReturnValueModel>)
        Delegate.CreateDelegate(
            typeof(Func<DriverAddressIoArgModel, DriverReturnValueModel>),
            Driver, methodInfo);
    MethodDelegates[methodInfo.Name] = del;
}
```

**设计思维**：反射调用虽然灵活（支持运行时动态发现驱动方法），但性能较差。通过 `Delegate.CreateDelegate` 将反射结果缓存为委托，后续调用性能接近直接方法调用。这是"启动时付出一次代价，运行时持续获益"的思维模式。

### 8.3 阶段二-三：字节序转换与数据类型转换

这两个阶段在驱动内部完成，对 DeviceThread 是透明的。以 Modbus 驱动为例：

```csharp
// DeviceModBusMaster.cs — 读取 + 字节序 + 类型转换
var rawBuffers = _master.ReadHoldingRegisters(
    slaveAddress, startAddress, count);         // 阶段2前：原始读取

ushort[] retBuffers = ChangeBuffersOrder(
    rawBuffers, ioArg.EndianType);              // 阶段2：字节序转换

// 阶段3：数据类型转换
if (ioArg.ValueType == DataTypeEnum.Float)
{
    var bytes = new[]
    {
        (byte)(retBuffers[1] & 0xff),
        (byte)((retBuffers[1] >> 8) & 0xff),
        (byte)(retBuffers[0] & 0xff),
        (byte)((retBuffers[0] >> 8) & 0xff)
    };
    ret.Value = BitConverter.ToSingle(bytes, 0);
}
```

**管线边界**：驱动返回的 `DriverReturnValueModel.Value` 就是"原始值"（RawValue），它是一个 C# 对象（可能是 int、float、string 等），已经完成了字节级处理。

### 8.4 阶段四：原始值入队（环形缓冲区）

```csharp
// DeviceThread.cs
ret.Timestamp = DateTime.Now;
item.EnqueueVariable(ret.Value);  // 存入 3 槽环形缓冲区
```

```csharp
// DeviceVariable.cs — 环形缓冲区实现
public void EnqueueVariable(object value)
{
    Values[2] = Values[1];   // 前前次 ← 前次
    Values[1] = Values[0];   // 前次 ← 当前
    Values[0] = value;       // 当前 ← 新值
}
```

**为什么在这里入队而不是在最后？**

因为表达式引擎需要用到历史值（`$pv`、`$ppv`）。如果在表达式计算之后才入队，那 `$pv` 拿到的是"上一次的计算值"而不是"上一次的原始值"。两者在语义上不同：

```
原始值序列: 100, 101, 103
表达式: $v - $pv

如果在原始值入队前计算:
$pv 是上一次 CookedValue（可能经过了不同的表达式）

如果在原始值入队后计算:
$pv 是上一次的原始值 101
结果 = 103 - 101 = 2 (变化量)
```

### 8.5 阶段五：表达式计算

```csharp
// DeviceThread.cs — 表达式计算
if (ret.StatusType == VaribaleStatusTypeEnum.Good
    && !string.IsNullOrWhiteSpace(item.Expressions?.Trim()))
{
    expressionText = item.Expressions.GetExpressionText(
        item.Values,
        variables.DistinctBy(x => x.Name)
            .ToDictionary(x => x.Name, x => x.Value));
    ret.CookedValue = _interpreter!.Eval(expressionText);
}
else
{
    ret.CookedValue = ret.Value;  // 无表达式，直接使用原始值
}
```

**管线边界**：这个阶段将 `RawValue`（原始值）转换为 `CookedValue`（计算值）。后续的过滤和发布都基于 `CookedValue`。

### 8.6 阶段六-七：CookedValue 入队

```csharp
// DeviceThread.cs
item.EnqueueCookedVariable(ret.CookedValue);
payLoad.Values[item.Name] = ret.CookedValue;
```

CookedValue 也存入 3 槽环形缓冲区。这让你可以在前端同时展示原始值趋势和计算值趋势。

### 8.7 阶段八：变化检测

```csharp
// MessageService.cs — 变化检测
private bool CanPubTelemetry(
    string deviceName, Device device,
    Dictionary<string, List<PayLoad>> sendModel)
{
    // ... 比较当前 Payload 与上次 Payload ...
    if (device.CgUpload)
    {
        bool isTimeExceeded =
            (newPayload.TS - lastPayload.TS) > device.EnforcePeriod;
        bool isValueChanged =
            !newPayload.Values.SequenceEqual(lastPayload.Values);
        return isTimeExceeded || isValueChanged;
    }
    return true;  // 未启用变化检测
}
```

变化检测是管线中的"阀门" — 它决定数据是否继续流向下一阶段。如果值没有变化且未超时，数据在这里被"拦截"，不会进入 MQTT 发布阶段。

### 8.8 阶段九：MQTT 发布

```csharp
// DeviceThread.cs — 构建发布数据
var payLoad = new PayLoad()
{
    Values = group
        .Where(x => x.StatusType == VaribaleStatusTypeEnum.Good
                 && x.IsUpload)
        .ToDictionary(x => x.Name, x => x.CookedValue),
    DeviceStatus = DeviceStatusTypeEnum.Good
};
payLoad.TS = (long)(DateTime.UtcNow - _tsStartDt).TotalMilliseconds;

sendModel[deviceName] = new List<PayLoad> { payLoad };
await _messageService.PublishTelemetryAsync(
    deviceName, Device, sendModel);
```

**过滤条件**：只有同时满足以下条件的变量才会出现在发布的 Payload 中：
- `StatusType == Good`（读取成功）
- `IsUpload == true`（配置为上传）
- 通过了变化检测（`CanPubTelemetry` 返回 true）

### 8.9 阶段十：内部 MQTT 推送

与对外发布不同，内部推送是每个变量独立触发的：

```csharp
// DeviceThread.cs — 变量值变化时推送给前端
if (JsonConvert.SerializeObject(item.Values[1])
    != JsonConvert.SerializeObject(item.Values[0]) ||
    JsonConvert.SerializeObject(item.CookedValues[1])
    != JsonConvert.SerializeObject(item.CookedValues[0]))
{
    var msgInternal = new InjectedMqttApplicationMessage(
        new MqttApplicationMessage()
        {
            Topic = $"internal/v1/gateway/telemetry/"
                  + $"{Device.DeviceName}/{item.Name}",
            PayloadSegment = Encoding.UTF8.GetBytes(
                JsonConvert.SerializeObject(ret))
        });
    mqttServer.InjectApplicationMessage(msgInternal);
}
```

这条内部管线直接绕过变化检测和 EnforcePeriod，实现了对前端的低延迟推送。

### 8.10 管线中的错误传播

每个阶段的错误都会影响后续阶段：

```
MethodError → 不执行字节序转换 → 不执行表达式 → Value 为空 → 不上报
Bad(通信失败) → 同上
ExpressionError → RawValue 有效，CookedValue 无效 → 以 RawValue 上报？
```

当前实现中，如果表达式出错，`StatusType` 变为 `ExpressionError`，该变量不会出现在最终 Payload 中（因为只选 `Good` 的变量）。这是一个合理的设计 — 宁可不上报一个变量，也不上报一个可能错误的值。

### 8.11 管线设计的扩展点

IoTGateway 的数据管线有几个天然的扩展点：

**扩展点一：自定义预处理**
在表达式计算之前插入自定义处理逻辑，例如：
- 异常值过滤（超出量程的值直接标记为 Bad）
- 中值滤波（取多次采样的中间值）
- 死区处理（变化太小视为不变）

**扩展点二：自定义后处理**
在表达式计算之后、变化检测之前：
- 数据分级（根据值判断报警等级）
- 单位附加（在值后面加上单位字符串）

**扩展点三：自定义过滤器**
在变化检测阶段：
- 更复杂的比较逻辑（如百分比变化）
- 基于时间窗口的聚合

**扩展点四：多路输出**
当前只有两路输出（MQTT 发布 + 内部推送），可以增加：
- 本地数据库存储
- 文件日志
- WebSocket 推送
- 消息队列（Kafka/RabbitMQ）

### 8.12 管线的性能瓶颈分析

每个阶段的性能开销：

| 阶段 | 开销 | 瓶颈 |
|------|------|------|
| 驱动读取 | 网络/串口 I/O | **最大瓶颈** — 毫秒到秒级 |
| 字节序转换 | 内存操作 | 微秒级，可忽略 |
| 类型转换 | 位运算 | 微秒级，可忽略 |
| 缓冲区入队 | 数组赋值 | 纳秒级，可忽略 |
| 表达式计算 | 字符串解析 + 求值 | **中等瓶颈** — 微秒级 |
| 变化检测 | 字典比较 | 微秒级，但随变量数增长 |
| JSON 序列化 | 字符串构建 | 微秒级 |
| MQTT 发布 | 网络 I/O | **次要瓶颈** — 毫秒级 |

**结论**：管线的吞吐量主要受限于驱动读取（通信速度）和 CmdPeriod/MinPeriod 的配置。其他阶段的开销几乎可以忽略。

### 8.13 管线设计的思维提炼

**思维一：阶段化思维**
将复杂的数据处理拆分为多个独立阶段，每个阶段有明确的输入和输出。这样做的好处：
- 每个阶段可以独立测试
- 可以在任意阶段插入日志或断点
- 可以灵活组合或跳过阶段

**思维二：数据流思维**
跟踪一个数据点从产生到消费的完整路径。在每个阶段问自己：
- 输入是什么？
- 输出是什么？
- 如果输入异常怎么办？
- 这个阶段可以省略吗？

**思维三：关注管线边界**
阶段与阶段之间的"接口"是最容易出问题的地方。明确定义每个阶段的数据格式：
- 驱动 → DeviceThread：`DriverReturnValueModel`
- DeviceThread → MessageService：`Dictionary<string, List<PayLoad>>`
- MessageService → MQTT：JSON 字符串

**思维四：延迟与吞吐的权衡**
每个阶段都会增加处理延迟，但也提供了过滤和优化的机会。变化检测减少了网络吞吐，但增加了 CPU 开销。在设计管线时，明确你的优化目标是什么。

**思维五：可观测性**
管线中的每个阶段都应该可观测 — 能查看中间结果、能记录处理耗时、能统计错误率。IoTGateway 通过 `StatusType` 和 `Message` 字段实现了基本的可观测性，但在生产环境中，通常需要更详细的度量指标。

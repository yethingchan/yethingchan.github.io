## 字节序：上位机开发中最容易踩的坑

当你通过 Modbus 协议从 PLC 读取了两个 16 位寄存器 `[0x1234, 0x5678]`，它们代表一个 32 位浮点数。这个浮点数到底是多少？

答案取决于**字节序**（Endianness）：

| 字节序 | 字节排列 | IEEE 754 值 |
|--------|---------|------------|
| BigEndian (ABCD) | 0x12 0x34 0x56 0x78 | 5.6904e-28 |
| LittleEndian (DCBA) | 0x78 0x56 0x34 0x12 | 4.2598e-33 |
| BigEndianSwap (BADC) | 0x34 0x12 0x78 0x56 | 3.4927e-5 |
| LittleEndianSwap (CDAB) | 0x56 0x78 0x12 0x34 | 7.5398e+12 |

**同一个原始数据，四种完全不同的数值**。如果你搞错了字节序，读到的是一个完全无意义的数字 — 而且这个数字"看起来很正常"（不是 0 也不是无穷大），所以你可能很长时间都不会发现问题。

### 7.1 字节序的本质

字节序解决的是一个基本问题：**多字节数据在内存/通信中，哪个字节在前、哪个在后**。

```
32 位整数 0x12345678 存储在内存中：

BigEndian (大端序/网络序):
地址 0: 0x12 (MSB)
地址 1: 0x34
地址 2: 0x56
地址 3: 0x78 (LSB)

LittleEndian (小端序):
地址 0: 0x78 (LSB)
地址 1: 0x56
地址 2: 0x34
地址 3: 0x12 (MSB)
```

不同厂商的设备有不同的偏好：

| 设备/协议 | 字节序 |
|----------|--------|
| Modbus 标准 | BigEndian (ABCD) |
| 西门子 S7-300/400 | BigEndian |
| 西门子 S7-1200/1500 | 可配置 |
| 三菱 MC 协议 | LittleEndian |
| 欧姆龙 FINS | BigEndian |
| AB (Allen-Bradley) | LittleEndian |
| OPC UA | 取决于传输层 |

### 7.2 IoTGateway 的字节序枚举

```csharp
// EndianEnum.cs
public enum EndianEnum
{
    None = 0,           // 不转换（直接使用原始数据）
    BigEndian,          // ABCD — 大端序
    LittleEndian,       // DCBA — 小端序
    BigEndianSwap,      // BADC — 大端交换（字内交换）
    LittleEndianSwap    // CDAB — 小端交换（字间交换）
}
```

这四种模式对应了 Modbus 协议中常见的四种字节排列方式。以 32 位数据（2 个 Modbus 寄存器）为例：

```
Modbus 寄存器: Reg0 = 0xABCD, Reg1 = 0xEF12

每种 ushort 占 2 字节，在 x86 (LittleEndian) 系统上：
Reg0 内存: [0xCD, 0xAB]  (低字节在前)
Reg1 内存: [0x12, 0xEF]  (低字节在前)

四种字节序的结果：

BigEndian (ABCD):
  按原始顺序: Reg0=0xABCD, Reg1=0xEF12
  32位值: 0xABCDEF12

LittleEndian (DCBA):
  完全反转: Reg1字节反转 + Reg0字节反转
  32位值: 0x12EFCDAB

BigEndianSwap (BADC):
  字内交换: Reg0 字节交换 + Reg1 字节交换
  32位值: 0xCDAB12EF

LittleEndianSwap (CDAB):
  字间交换: Reg1在前, Reg0在后 (不交换字内)
  32位值: 0xEF12ABCD
```

### 7.3 ChangeBuffersOrder：核心转换实现

IoTGateway 的字节序转换函数处理了 16 位、32 位和 64 位三种数据宽度：

```csharp
// DeviceModBusMaster.cs — 字节序转换核心
private ushort[] ChangeBuffersOrder(ushort[] buffers, EndianEnum dataType)
{
    int datalen = buffers.Length;
    ushort[] newBuffers = new ushort[datalen];

    if (dataType == EndianEnum.None)
    {
        newBuffers = buffers;  // 不转换
    }
    else if (datalen == 1)  // 16 位
    {
        switch (dataType)
        {
            case EndianEnum.LittleEndian:  // BA
                var ab = BitConverter.GetBytes(buffers[0]);
                newBuffers[0] = BitConverter.ToUInt16(
                    new byte[] { ab[1], ab[0] });
                break;
            case EndianEnum.BigEndian:     // AB
            default:
                newBuffers[0] = buffers[0];
                break;
        }
    }
    else if (datalen == 2)  // 32 位
    {
        // ... 32 位转换 ...
    }
    else if (datalen == 4)  // 64 位
    {
        // ... 64 位转换 ...
    }
    return newBuffers;
}
```

以 32 位（datalen=2）为例，详细分析四种转换：

```csharp
var ab = BitConverter.GetBytes(buffers[0]); // Reg0 拆为字节 [A, B]
var cd = BitConverter.GetBytes(buffers[1]); // Reg1 拆为字节 [C, D]

switch (dataType)
{
    case EndianEnum.BigEndian:     // ABCD
        _ab = ab;                  // A B
        _cd = cd;                  // C D
        break;

    case EndianEnum.LittleEndian:  // DCBA
        _ab[0] = cd[1];           // D
        _ab[1] = cd[0];           // C
        _cd[0] = ab[1];           // B
        _cd[1] = ab[0];           // A
        break;

    case EndianEnum.BigEndianSwap: // BADC
        _ab[0] = ab[1];           // B
        _ab[1] = ab[0];           // A
        _cd[0] = cd[1];           // D
        _cd[1] = cd[0];           // C
        break;

    case EndianEnum.LittleEndianSwap: // CDAB
        _ab[0] = cd[0];           // C
        _ab[1] = cd[1];           // D
        _cd[0] = ab[0];           // A
        _cd[1] = ab[1];           // B
        break;
}
```

### 7.4 ASCII 字符串的特殊字节序处理

ASCII 字符串的字节序处理与数值类型不同 — 它需要**逐元素**处理，而不是整体反转：

```csharp
// DeviceModBusMaster.cs — ASCII 字符串的字节序处理
if (ioArg.ValueType == DataTypeEnum.AsciiString)
{
    if (ioArg.EndianType != EndianEnum.None)
    {
        // 逐个寄存器处理字节序（每个 ushort 独立交换字节）
        ushort[] processedBuffers = rawBuffers
            .Select(x => ChangeBuffersOrder(
                new ushort[] { x }, ioArg.EndianType)[0])
            .ToArray();
        retBuffers = processedBuffers;
    }
    else
    {
        retBuffers = rawBuffers;
    }
}
```

**为什么字符串需要逐元素处理？**

因为 ASCII 字符串在每个寄存器中存储 2 个字符。字节序决定了每个寄存器内的 2 个字符谁在前：

```
字符串 "Hello" 存储在 Modbus 寄存器中：

BigEndian:    Reg0='He'  Reg1='ll'  Reg2='o\0'
              字节: [H,e]  [l,l]    [o,\0]

LittleEndian: Reg0='eH'  Reg1='ll'  Reg2='\0o'
              字节: [e,H]  [l,l]    [\0,o]
```

如果对字符串做整体反转，字符顺序就全乱了。正确的做法是**在每个寄存器内部**交换字节。

### 7.5 数据类型与寄存器数量的关系

```csharp
// DeviceModBusMaster.cs — 根据数据类型确定读取的寄存器数量
private ushort GetModbusReadCount(uint functionCode, DataTypeEnum dataType)
{
    if (dataType.ToString().Contains("32")
        || dataType.ToString().Contains("Float"))
        return 2;   // 32 位 = 2 个寄存器

    if (dataType.ToString().Contains("64")
        || dataType.ToString().Contains("Double"))
        return 4;   // 64 位 = 4 个寄存器

    return 1;       // 16 位 = 1 个寄存器
}
```

### 7.6 从 ushort[] 到具体数值的转换

字节序处理完成后，还需要将 `ushort[]` 转换为具体的数据类型：

```csharp
// DeviceModBusMaster.cs — 数据类型转换
if (ioArg.ValueType == DataTypeEnum.Uint16)
    ret.Value = retBuffers[0];

else if (ioArg.ValueType == DataTypeEnum.Int16)
    ret.Value = (short)retBuffers[0];

else if (ioArg.ValueType == DataTypeEnum.Uint32)
    ret.Value = (uint)(retBuffers[0] << 16) + retBuffers[1];

else if (ioArg.ValueType == DataTypeEnum.Int32)
    ret.Value = (retBuffers[0] << 16) + retBuffers[1];

else if (ioArg.ValueType == DataTypeEnum.Float)
{
    var bytes = new[]
    {
        (byte)(retBuffers[1] & 0xff), (byte)((retBuffers[1] >> 8) & 0xff),
        (byte)(retBuffers[0] & 0xff), (byte)((retBuffers[0] >> 8) & 0xff)
    };
    ret.Value = BitConverter.ToSingle(bytes, 0);
}
```

**Float 类型的特殊处理**

注意 Float 的转换不是简单的位移操作。它需要：
1. 将两个 `ushort` 拆为 4 个 `byte`
2. 按照 LittleEndian 排列（x86 系统的 `BitConverter` 期望的格式）
3. 使用 `BitConverter.ToSingle` 将字节解释为 IEEE 754 浮点数

```
retBuffers = [0x4228, 0x0000]  (经过字节序转换后)

拆分字节:
retBuffers[1] = 0x0000 → [0x00, 0x00]
retBuffers[0] = 0x4228 → [0x28, 0x42]

组合为 float 字节: [0x00, 0x00, 0x28, 0x42]
BitConverter.ToSingle → 42.0
```

### 7.7 BCD 编码的处理

BCD（Binary Coded Decimal）在工业仪表中很常见 — 每个半字节（4 位）表示一个十进制数字：

```csharp
// ModBusDataConvert.cs — BCD 解码
public static int GetBCD(List<byte> b)
{
    int bcd = 0;
    int j = 1;
    for (int i = 0; i < b.Count; i++)
    {
        int tmp = b[i] & 0x0f;   // 低 4 位
        bcd += tmp * j;
        j *= 10;
        tmp = (b[i] >> 4) & 0x0f; // 高 4 位
        bcd += tmp * j;
        j *= 10;
    }
    return bcd;
}
```

例如 BCD 编码的 `0x1234`：
- 字节 `0x34`：低 4 位 = 4，高 4 位 = 3 → 34
- 字节 `0x12`：低 4 位 = 2，高 4 位 = 1 → 12
- 组合：1234

### 7.8 写入时的字节序处理

读取需要字节序转换，写入也需要 — 但方向相反：

```csharp
// DeviceModBusMaster.cs — 写入 Float 时的字节序处理
case DataTypeEnum.Float:
    var f = float.Parse(ioArg.Value.ToString());
    var fValue = BitConverter.SingleToUInt32Bits(f);
    shortArray[1] = (ushort)(fValue & 0xffff);
    shortArray[0] = (ushort)(fValue >> 16 & 0xffff);

    // 转换为设备期望的字节序
    toWriteArray = ChangeBuffersOrder(shortArray, ioArg.EndianType);

    await _master.WriteMultipleRegistersAsync(
        slaveAddress, address, toWriteArray);
    break;
```

**读写对称性**：读取时用 `ChangeBuffersOrder` 把设备字节序转为系统字节序；写入时用同一个函数把系统字节序转为设备字节序。这要求 `ChangeBuffersOrder` 是一个**自反函数** — 即 `f(f(x)) = x`。对于 BigEndian 和 LittleEndian 确实如此，但 BigEndianSwap 和 LittleEndianSwap 需要特别注意。

### 7.9 调试字节序问题的方法

字节序问题是最难调试的工业通信问题之一。以下是系统化的调试方法：

**方法一：已知值验证法**
在 PLC 中写入一个你知道的值（如 42.0），然后读取看是否正确。如果不正确，用所有四种字节序分别解析，看哪个能得到 42.0。

**方法二：十六进制打印法**
```csharp
// 在 ReadRegistersBuffers 中添加调试日志
_logger.LogDebug($"Raw buffers: [{string.Join(", ",
    rawBuffers.Select(b => $"0x{b:X4}"))}]");
_logger.LogDebug($"Converted buffers: [{string.Join(", ",
    retBuffers.Select(b => $"0x{b:X4}"))}]");
```

**方法三：逐字节分析法**
把读取到的字节按顺序写出来，手动用 IEEE 754 计算器验证。

**方法四：对比法**
用已知的工具（如 Modbus Poll）读取同一个地址，对比结果。

### 7.10 字节序处理的思维提炼

**思维一：协议文档是第一手资料**
在开始编写字节序处理代码之前，先读设备手册。手册中通常会说明数据格式和字节序。如果没有，联系设备厂商获取。

**思维二：小端陷阱**
x86/x64 系统都是 LittleEndian。当你用 `BitConverter.GetBytes()` 把一个 `ushort` 拆为字节时，得到的字节顺序是 LittleEndian。很多字节序 bug 都源于忘记考虑"系统本身的字节序"。

**思维三：读写对称**
读取和写入的字节序转换必须是互逆操作。如果你读取时用 BigEndian，写入时也必须用 BigEndian。

**思维四：先验证，后信任**
每次对接新设备时，先读取一个已知值来验证字节序设置是否正确。不要假设上次能用的设置这次也能用。

**思维五：可配置优于硬编码**
IoTGateway 把字节序作为每个变量的可配置参数（`EndianType`），而不是驱动级别的固定设置。这是正确的设计 — 同一台设备上的不同变量可能使用不同的字节序。

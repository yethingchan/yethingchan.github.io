## 为什么需要表达式引擎

从设备读到的原始值，往往不是我们最终需要的值。

一个温度传感器通过 Modbus 返回了一个 `ushort` 值 `2567`。这意味着什么？可能是 256.7°C（需要除以 10），可能是 25.67°C（需要除以 100），也可能需要根据传感器的校准曲线做更复杂的变换。

如果你为每个变量硬编码转换逻辑，当你有 500 个变量时，代码就不可维护了。你需要一种**运行时可配置的计算引擎** — 这就是表达式引擎的作用。

### 2.1 IoTGateway 的表达式引擎设计

IoTGateway 使用 [DynamicExpresso](https://github.com/davideicardi/DynamicExpresso) 库实现动态表达式求值。整个设计分为三层：

```
配置层: 用户在 Web UI 中填写表达式字符串
        例如: "$v / 10.0" 或 "$v * 1.8 + 32"
        ↓
解析层: Expression.cs 将占位符替换为实际值
        例如: "$v / 10.0" → "2567 / 10.0"
        ↓
求值层: DynamicExpresso.Interpreter 计算表达式
        例如: "2567 / 10.0" → 256.7
```

### 2.2 占位符体系：$v / $pv / $ppv

IoTGateway 的表达式引擎支持一套精心设计的占位符体系：

```csharp
// Expression.cs — 占位符替换逻辑
var current = values[0];      // 当前值
var previous = values[1];     // 前次值
var prePrevious = values[2];  // 前前次值

var result = expression.Trim()
    .ReplaceExpressionText("raw", current)   // "raw" 等价于 "$v"
    .ReplaceExpressionText("$v", current)    // 当前值
    .ReplaceExpressionText("$pv", previous)  // 前次值
    .ReplaceExpressionText("$ppv", prePrevious); // 前前次值
```

这三个占位符的设计不是随意的 — 它们对应了工业数据分析中最基本的三种时间视角：

**$v — 瞬时值视角**
最直接的用法：单位转换、线性校准。
```
$v / 10.0          // 原始值除以10，得到工程值
$v * 0.01 + 4.0    // 4-20mA信号转换为工程量
($v - 32) * 5 / 9  // 华氏度转摄氏度
```

**$v 与 $pv — 变化趋势视角**
通过比较当前值和前次值，可以判断变化方向：
```
$v - $pv           // 变化量（正值=上升，负值=下降）
($v - $pv) / $pv * 100  // 变化率百分比
Abs($v - $pv) > 50      // 突变检测
```

**$v, $pv, $ppv — 加速度视角**
三个连续值可以计算变化的"加速度"：
```
($v - $pv) - ($pv - $ppv)  // 变化率的导数
```
如果这个值为正，说明变化在加速；为负则在减速。这在预测性维护中非常有用 — 例如振动值的加速度突然增大，可能预示着轴承即将损坏。

### 2.3 跨变量引用：{otherVar} 模式

除了时间维度的引用，表达式引擎还支持跨变量引用：

```csharp
// Expression.cs — 跨变量引用
var parameterNames = ParameterRegex.Matches(result)
    .Select(m => m.Groups[1].Value)
    .Distinct();

var filteredDatas = datas.Where(kvp => parameterNames.Contains(kvp.Key));

foreach (var kvp in filteredDatas)
{
    result = result.ReplaceExpressionText($"{{{kvp.Key}}}", kvp.Value);
}
```

使用场景举例：

**温压补偿**
气体流量计的读数需要根据温度和压力进行补偿：
```
$v * Sqrt({Pressure} / 101.325) * Sqrt(293.15 / ({Temperature} + 273.15))
```
这里 `$v` 是原始流量值，`{Pressure}` 和 `{Temperature}` 是同一组中其他变量的当前值。

**差值计算**
两根热电偶的温差：
```
$v - {T_ref}
```

**比例控制**
阀门开度与设定值的偏差：
```
$v - {SetPoint}
```

这种跨变量引用的设计，让表达式引擎从"单变量计算器"升级为"多变量计算器"，大大增强了灵活性。

### 2.4 值替换的实现细节

```csharp
// Expression.cs — 替换方法
public static string ReplaceExpressionText(
    this string expression, string placeholder, object value)
{
    return expression.Replace(
        placeholder,
        value is bool
            ? $"Convert.ToBoolean(\"{value}\")"
            : value?.ToString())
        .Replace("&lt;", "<")     // HTML 实体还原
        .Replace("&gt;", ">")
        .Replace("&amp;", "&")
        .Replace("&quot;", "\"");
}
```

注意几个细节：

1. **bool 类型特殊处理**：布尔值不能直接替换为字符串 `"True"`，因为 DynamicExpresso 无法将其识别为布尔表达式。所以使用 `Convert.ToBoolean("True")` 包装。

2. **HTML 实体还原**：Web UI 中用户输入的 `<`、`>`、`&` 可能被自动转义为 HTML 实体（`&lt;`、`&gt;`、`&amp;`）。这里统一还原，确保表达式语法正确。

这些看似琐碎的细节，恰恰是工业软件开发的真实写照 — 你需要处理各种边界情况，而不仅仅是理想路径。

### 2.5 表达式求值在读取流程中的位置

```csharp
// DeviceThread.cs — 表达式求值的完整流程
ret = methodDelegate(ioarg);  // 1. 从驱动读取原始值

ret.Timestamp = DateTime.Now;
item.EnqueueVariable(ret.Value);  // 2. 存入环形缓冲区

// 3. 如果读取成功且配置了表达式，进行计算
if (ret.StatusType == VaribaleStatusTypeEnum.Good
    && !string.IsNullOrWhiteSpace(item.Expressions?.Trim()))
{
    var expressionText = string.Empty;
    try
    {
        expressionText = item.Expressions.GetExpressionText(
            item.Values,
            variables.DistinctBy(x => x.Name)
                .ToDictionary(x => x.Name, x => x.Value));
        ret.CookedValue = _interpreter!.Eval(expressionText);
    }
    catch (Exception)
    {
        ret.Message = $"表达式错误：{expressionText}";
        ret.StatusType = VaribaleStatusTypeEnum.ExpressionError;
    }
}
else
{
    // 4. 没有表达式，原始值直接作为最终值
    ret.CookedValue = ret.Value;
}

item.EnqueueCookedVariable(ret.CookedValue);  // 5. 计算后的值也存入缓冲区
```

注意几个关键设计点：

**表达式错误不中断采集**：如果表达式有语法错误，变量状态变为 `ExpressionError`，但采集循环继续。这是工业软件的容错思维 — 一个变量的表达式配错了，不应该影响其他变量。

**CookedValue 也有缓冲区**：不仅原始值有三环缓冲，计算后的值也有。这让你可以同时追踪原始值趋势和计算值趋势。

### 2.6 DynamicExpresso 的性能考量

DynamicExpresso 每次 `Eval` 都会解析表达式字符串。对于高频采集场景，这可能成为性能瓶颈。IoTGateway 使用一个共享的 `Interpreter` 实例：

```csharp
private Interpreter? _interpreter;
// 构造函数中
_interpreter = new Interpreter();
```

在实际项目中，如果表达式不变（大多数情况下不变），可以考虑缓存编译结果：

```csharp
// 优化思路：缓存编译后的表达式
private readonly Dictionary<string, Func<object>> _compiledCache = new();

// 首次使用时编译并缓存
if (!_compiledCache.TryGetValue(expressionText, out var func))
{
    var expression = _interpreter.Parse(expressionText);
    func = () => expression.Eval();
    _compiledCache[expressionText] = func;
}
ret.CookedValue = func();
```

这种"惰性编译 + 缓存"的模式在很多工业软件中都有应用。

### 2.7 工业场景中的典型表达式

以下是实际工业项目中常见的表达式模式：

**单位转换**
```
$v / 10.0                    // 整数→带一位小数
$v * 0.001                   // mm → m
$v / 1000.0 * 3600           // m/s → km/h
```

**模拟量标定（4-20mA）**
```
($v - 4.0) / 16.0 * ($pv_max - $pv_min) + $pv_min
```
将 4-20mA 信号转换为工程量程。

**温度补偿**
```
$v + {ambient_temp} * 0.003   // 温度漂移补偿
```

**报警阈值判断**
```
$v > 100 ? 1 : 0              // 超温报警标志
```

**滤波**
```
$v * 0.3 + $pv * 0.7          // 一阶低通滤波（指数加权平均）
```

**变化率计算**
```
($v - $pv) * 1000 / CmdPeriod_ms  // 每秒变化率
```

**死区处理**
```
Abs($v - $pv) < 0.5 ? $pv : $v  // 变化小于0.5时保持不变
```

### 2.8 表达式设计的思维提炼

**思维一：配置优于编码**
工业场景的变量数量庞大（动辄数百上千），每个变量单独写转换代码是不可行的。表达式引擎将"转换逻辑"变成了"可配置参数"，这是上位机开发中非常重要的抽象思维。

**思维二：时间维度是数据的灵魂**
`$v/$pv/$ppv` 的设计告诉我们：一个数据点的值不是孤立的，它的"历史"同样重要。在设计数据模型时，始终考虑"我需要过去的数据吗？"

**思维三：组合优于继承**
与其设计复杂的继承体系来处理不同类型的数据转换，不如提供一个通用的表达式引擎，让用户自由组合数学运算。简单的积木可以搭建出复杂的结构。

**思维四：容错不是可选项**
表达式配错了，系统不能崩。上报一个 `ExpressionError` 状态，继续处理其他变量。工业软件的第一原则是"不能因为一个点的故障影响整个系统"。

### 2.9 扩展思考：如何设计更好的表达式引擎

IoTGateway 的表达式引擎已经足够实用，但如果追求更强的能力，可以考虑：

1. **函数库扩展**：预注册 `Sin`、`Cos`、`Sqrt`、`Log`、`Map` 等工业常用函数
2. **条件表达式**：支持 `if/else` 或多段线性函数
3. **表达式验证**：在保存时进行语法检查，而不是运行时才发现错误
4. **性能优化**：对不变的表达式预编译缓存
5. **表达式调试**：提供"测试"功能，输入样例值，输出计算结果

这些扩展方向的共同点是：让用户更容易正确配置，让系统更容易提前发现问题。

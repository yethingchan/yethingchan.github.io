## 工业通信的残酷现实：一切都会断

在理想世界中，网络连接永远稳定，设备永远在线。但在工业现场：

- 交换机可能在凌晨自动重启
- 电磁干扰可能导致串口数据错乱
- 网线可能被叉车碾压
- PLC 可能因为看门狗超时而重启
- 工控机的网卡驱动可能在高负载下崩溃

上位机程序必须假设**通信随时可能中断**，并且在中断后能够**自动恢复**。这不是锦上添花，而是基本要求。

### 4.1 IoTGateway 的两层重连架构

IoTGateway 采用了精心设计的两层重连策略：

```
第一层：驱动级连接检测
        ↓ 每次轮询前检查 Driver.IsConnected
        ↓ 断开时调用 Driver.Connect()
        ↓
第二层：时间容错重连
        ↓ 所有变量连续 Bad 超过 60 秒
        ↓ 强制 Close() + Dispose()
        ↓ 下一轮循环触发重新 Connect()
```

### 4.2 第一层：即时连接检测

```csharp
// DeviceThread.cs — CreateThreadAsync 主循环
while (!token.IsCancellationRequested)
{
    _resetEvent.Wait(token);
    try
    {
        if (Driver.IsConnected)
        {
            // 正常读取变量...
        }
        else
        {
            // 连接已断开，上报离线状态
            foreach (var group in Device.DeviceVariables!.GroupBy(x => x.Alias))
            {
                var deviceName = string.IsNullOrWhiteSpace(group.Key)
                    ? Device.DeviceName : group.Key;
                _messageService?.DeviceDisconnected(deviceName, Device);
            }

            // 尝试重连
            if (Driver.Connect())
            {
                // 重连成功，上报在线状态
                foreach (var group in Device.DeviceVariables!.GroupBy(x => x.Alias))
                {
                    var deviceName = string.IsNullOrWhiteSpace(group.Key)
                        ? Device.DeviceName : group.Key;
                    _messageService?.DeviceConnected(deviceName, Device);
                }
            }
        }
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, $"线程循环异常,{Device.DeviceName}");
    }
    await Task.Delay(Device.DeviceVariables!.Any()
        ? (int)Driver.MinPeriod : 10000, token);
}
```

**设计分析**：

1. **先上报离线，再尝试重连**：这个顺序很重要。如果先重连，在重连的那几秒内，云平台不知道设备已经断线了。
2. **重连成功立即上报在线**：让云平台的设备状态与实际状态尽快同步。
3. **重连失败不报错**：连接失败只是 `Connect()` 返回 `false`，不会抛异常。下一轮循环会再次尝试。

### 4.3 第二层：时间容错机制

第一层检测的是"驱动认为连接已断开"的情况。但有些故障更隐蔽 — TCP 连接看似还活着（Socket 状态为 Connected），但实际上数据已经无法传输了。这就是所谓的"半开连接"（Half-Open Connection）或"僵死连接"。

IoTGateway 用时间容错机制来对付这种隐蔽故障：

```csharp
// DeviceThread.cs — 时间容错重连
private DateTime _lastGoodTime = DateTime.UtcNow;
private readonly TimeSpan _maxFailureDuration = TimeSpan.FromSeconds(60);

// 在主循环中
if (Driver.IsConnected)
{
    // ... 读取变量 ...

    // 检查是否所有变量都读取失败
    if (Device.DeviceVariables.All(
        x => x.StatusType != VaribaleStatusTypeEnum.Good))
    {
        // 所有变量都 Bad，检查是否超过容忍时间
        if (DateTime.UtcNow - _lastGoodTime > _maxFailureDuration
            && Driver.IsConnected)
        {
            _logger.LogWarning(
                $"{Device.DeviceName} 读取变量连续失败超过 " +
                $"{_maxFailureDuration.TotalSeconds} 秒，主动断开连接重连");
            Driver.Close();
            Driver.Dispose();
        }
    }
    else
    {
        // 至少有一个变量读取成功，刷新最后成功时间
        _lastGoodTime = DateTime.UtcNow;
    }
}
```

**为什么选择 60 秒？**

这个值是工程经验的产物：

- **太短（如 5 秒）**：一次网络抖动就会导致重连，过于敏感
- **太长（如 300 秒）**：故障恢复时间太长，云平台上的数据严重滞后
- **60 秒**：足够容忍短暂的网络波动，又不会让故障持续太久

在实际项目中，这个值应该根据具体场景调整：

| 场景 | 建议容忍时间 | 原因 |
|------|-------------|------|
| 关键安全设备 | 10-30 秒 | 安全要求快速响应 |
| 一般生产设备 | 60 秒 | 平衡稳定性和恢复速度 |
| 慢变化环境量 | 120-300 秒 | 偶尔的通信失败影响不大 |
| 无线通信设备 | 120 秒 | 无线链路天然不稳定 |

### 4.4 "全部 Bad" 的判断条件

```csharp
if (Device.DeviceVariables.All(
    x => x.StatusType != VaribaleStatusTypeEnum.Good))
```

为什么要求**所有变量**都 Bad 才触发重连，而不是**任一变量** Bad？

因为工业通信中，单个变量读取失败是常见现象：

- 某个寄存器地址配错了（AddressError）
- 某个驱动方法名写错了（MethodError）
- 某个表达式语法有问题（ExpressionError）
- PLC 某个区域暂时不可读

如果因为一个变量的地址配错就触发重连，会导致所有其他正常变量也跟着中断。**"全部 Bad"才意味着真正的通信故障**。

### 4.5 驱动级的重连实现

以 Modbus 驱动为例，看重连是如何具体执行的：

```csharp
// DeviceModBusMaster.cs — IsConnected 属性
public bool IsConnected
{
    get
    {
        switch (MasterType)
        {
            case MasterType.Tcp:
            case MasterType.RtuOnTcp:
            case MasterType.AsciiOnTcp:
                return _tcpClient != null
                    && _master != null
                    && _tcpClient.Connected;
            // ...
        }
    }
}

// Connect() — 建立新连接
public bool Connect()
{
    try
    {
        switch (MasterType)
        {
            case MasterType.Tcp:
                _tcpClient = new TcpClient(IpAddress, Port);
                _tcpClient.ReceiveTimeout = Timeout;
                _tcpClient.SendTimeout = Timeout;
                _master = ModbusIpMaster.CreateIp(_tcpClient);
                break;
            // ...
        }
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, $"Device:[{_device}],Connect(),Error");
        return false;
    }
    return IsConnected;
}

// Close() — 关闭连接
public bool Close()
{
    try
    {
        _tcpClient?.Close();
        _udpClient?.Close();
        _serialPort?.Close();
        return !IsConnected;
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, $"Device:[{_device}],Close(),Error");
        return false;
    }
}
```

注意 `Connect()` 方法会创建新的 `TcpClient` 实例。这意味着重连不是"修复"旧连接，而是**销毁旧连接 + 创建新连接**。这种"推倒重来"的策略在工业通信中是标准做法 — 因为旧连接的内部状态可能已经不可靠了。

### 4.6 强制断开 + Dispose 的完整流程

```csharp
// DeviceThread.cs — 强制重连
if (DateTime.UtcNow - _lastGoodTime > _maxFailureDuration
    && Driver.IsConnected)
{
    Driver.Close();    // 关闭 Socket/串口
    Driver.Dispose();  // 释放资源
}
```

当时间容错触发时，IoTGateway 同时调用了 `Close()` 和 `Dispose()`。这是因为：

- `Close()` 关闭通信通道（Socket、串口），但不释放驱动对象
- `Dispose()` 释放驱动持有的所有资源（包括内部缓冲区、事件对象等）

下一轮循环时，`Driver.IsConnected` 返回 `false`，触发第一层重连逻辑中的 `Driver.Connect()`，创建全新的连接。

### 4.7 变量级别的错误分类

IoTGateway 对变量状态做了精细的分类：

```csharp
// VaribaleStatusTypeEnum.cs
public enum VaribaleStatusTypeEnum
{
    Good = 0,           // 正常
    AddressError,       // 地址错误（地址格式不对或越界）
    MethodError,        // 方法错误（驱动方法不存在或调用异常）
    ExpressionError,    // 表达式错误（表达式语法或计算异常）
    Bad,                // 通信失败（读不到值）
    UnKnow,             // 未知（未初始化或类型不支持）
    Custome1,           // 自定义1（驱动可扩展）
    Custome2,           // 自定义2
    Custome3,           // 自定义3
    Custome4,           // 自定义4
    Custome5            // 自定义5
}
```

**为什么需要这么细的分类？**

因为不同类型的错误需要不同的处理方式：

| 状态 | 含义 | 处理方式 |
|------|------|---------|
| Good | 正常 | 正常上报 |
| AddressError | 配置错误 | 需要修改配置，不是通信问题 |
| MethodError | 驱动错误 | 需要检查驱动方法名 |
| ExpressionError | 表达式错误 | 需要修改表达式 |
| Bad | 通信故障 | 等待自动重连 |
| UnKnow | 初始化问题 | 检查数据类型配置 |

关键洞察：只有 `Bad` 状态才应该触发重连逻辑。`AddressError`、`MethodError`、`ExpressionError` 是配置或编程错误，重连不会解决它们。

### 4.8 读取级别的异常处理

```csharp
// DeviceThread.cs — ReadVariablesAsync 中的异常处理
if (!MethodDelegates.TryGetValue(item.Method, out var methodDelegate))
{
    ret.StatusType = VaribaleStatusTypeEnum.MethodError;
}
else
{
    try
    {
        ret = methodDelegate(ioarg);
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, $"调用方法 {item.Method} 异常");
        ret.StatusType = VaribaleStatusTypeEnum.MethodError;
    }
}
```

**核心原则**：单个变量的读取异常不能中断整个采集循环。

每个变量都被独立的 `try-catch` 包裹。如果变量 A 读取失败，变量 B、C、D 仍然会被正常读取。这是工业软件"故障隔离"思维的直接体现。

### 4.9 重连期间的数据上报策略

当设备处于断线状态时，IoTGateway 并不是什么都不做。它会持续向云平台上报道离线状态：

```csharp
// 连接断开时，每个 Alias 分组都上报离线
foreach (var group in Device.DeviceVariables!.GroupBy(x => x.Alias))
{
    var deviceName = string.IsNullOrWhiteSpace(group.Key)
        ? Device.DeviceName : group.Key;
    _messageService?.DeviceDisconnected(deviceName, Device);
}
```

这确保了云平台的设备状态始终是准确的。如果上位机"静默失败"（断线了但不上报），云平台会以为设备还在线，导致决策错误。

### 4.10 异常处理的反模式与最佳实践

**反模式一：忽略异常**
```csharp
// 错误示范：吞掉异常
try { ret = methodDelegate(ioarg); }
catch { }  // 不知道发生了什么
```

**反模式二：一次失败就崩溃**
```csharp
// 错误示范：一个变量失败就停止整个循环
try
{
    foreach (var item in variables)
        ret = methodDelegate(ioarg);  // 任一失败就抛出
}
catch { throw; }  // 整个循环终止
```

**反模式三：无限快速重连**
```csharp
// 错误示范：没有退避策略
while (true)
{
    if (!Driver.Connect())
        continue;  // 疯狂重试，可能加剧问题
}
```

**IoTGateway 的最佳实践**：
- 每个变量独立 try-catch
- 错误分类并记录
- 容忍短暂故障（60 秒窗口）
- 有退避间隔（MinPeriod 控制重试间隔）
- 断线状态持续上报

### 4.11 异常处理的思维提炼

**思维一：悲观假设，乐观执行**
假设一切都会失败，但不要因为一次失败就放弃。60 秒的容错窗口完美体现了这种思维。

**思维二：故障隔离**
一个变量的问题不应该影响其他变量；一台设备的问题不应该影响其他设备。线程隔离 + 变量级 try-catch 实现了双重隔离。

**思维三：状态可见**
即使设备断线了，也要让云平台知道它断线了。"不知道设备状态"比"知道设备断线"更危险。

**思维四：区分可恢复与不可恢复错误**
通信故障是可恢复的（重连就好），配置错误是不可恢复的（需要人工修改）。正确区分这两种错误，才能采取正确的应对策略。

**思维五：时间是最好的裁判**
单次失败可能是偶然的，连续失败才是真的故障。用时间窗口来判断故障的严重程度，比用"失败次数"更稳健。

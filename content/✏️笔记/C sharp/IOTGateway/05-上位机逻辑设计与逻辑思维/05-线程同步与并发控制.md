## 上位机的并发困境

上位机程序天然是多线程的。即使你只连接一台设备，也至少有以下线程在同时运行：

- **轮询线程**：持续读取设备数据
- **MQTT 客户端线程**：接收云端下发的 RPC 写入指令
- **UI 线程**（如果有）：刷新界面显示
- **后台服务线程**：日志、健康检查等

当这些线程同时操作同一个设备时，就可能产生竞态条件（Race Condition）。最典型的冲突是：**轮询线程正在读取寄存器，RPC 写入线程同时向同一寄存器写入新值** — 结果不可预测。

### 5.1 IoTGateway 的核心同步机制：ManualResetEventSlim

IoTGateway 使用 `ManualResetEventSlim` 实现了轮询与写入之间的互斥控制：

```csharp
// DeviceThread.cs — 同步原语声明
private readonly ManualResetEventSlim _resetEvent =
    new ManualResetEventSlim(true);  // 初始状态：有信号（允许通过）
```

**ManualResetEventSlim 的工作原理**：

```
初始状态：Set（有信号）→ 所有 Wait() 调用立即通过
    ↓
调用 Reset()：变为无信号 → 后续的 Wait() 调用被阻塞
    ↓
调用 Set()：恢复有信号 → 所有被阻塞的 Wait() 调用恢复
```

在 IoTGateway 中，它的使用方式非常清晰：

```
正常状态：_resetEvent = Set → 轮询线程自由运行
    ↓
RPC写入到达：_resetEvent.Reset() → 轮询线程在下一个 Wait() 处暂停
    ↓
执行写入操作...
    ↓
写入完成：_resetEvent.Set() → 轮询线程恢复运行
```

### 5.2 轮询侧：等待与检查

```csharp
// DeviceThread.cs — 轮询循环中的等待点
while (!token.IsCancellationRequested)
{
    // ★ 关键同步点：如果 RPC 写入正在进行，这里会阻塞
    _resetEvent.Wait(token);

    try
    {
        if (Driver.IsConnected)
        {
            // 正常读取变量...
        }
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, $"线程循环异常,{Device.DeviceName}");
    }
    await Task.Delay(..., token);
}
```

`_resetEvent.Wait(token)` 这行代码做两件事：

1. **检查信号状态**：如果 `_resetEvent` 处于 Set 状态，立即通过
2. **支持取消**：传入 `token` 参数，如果收到取消信号（程序关闭），即使 `_resetEvent` 未 Set 也能退出

这个设计保证了：
- 轮询线程在写入进行时不会同时读取
- 程序关闭时，即使写入还没完成，轮询线程也能及时退出

### 5.3 写入侧：暂停-执行-恢复

```csharp
// DeviceThread.cs — RPC 写入方法
public async void MyMqttClient_OnExcRpc(object? sender, RpcRequest e)
{
    if (e.Method.ToLower() == "write")
    {
        // ★ 步骤1：暂停轮询
        _resetEvent.Reset();

        bool rpcConnected = false;
        if (!Driver.IsConnected)
        {
            if (Driver.Connect())
                rpcConnected = true;
        }

        if (Driver.IsConnected)
        {
            // ★ 步骤2：执行写入（此时轮询已暂停）
            foreach (var para in e.Params)
            {
                // ... 查找变量、调用驱动写入 ...
                var writeResponse = await Driver.WriteAsync(
                    e.RequestId, deviceVariable.Method, ioArgModel);
            }

            // 如果是 RPC 临时建立的连接，写入后关闭
            if (rpcConnected)
                Driver.Close();
        }

        // ★ 步骤3：恢复轮询
        _resetEvent.Set();
    }
}
```

注意"暂停-执行-恢复"这个三步模式的严谨性：

1. **Reset 在最前面**：确保在任何实际工作之前就暂停轮询
2. **Set 在最后面**：确保所有写入操作都完成后才恢复轮询
3. **即使写入失败也会 Set**：因为 `Set()` 在 `if (Driver.IsConnected)` 块之外

### 5.4 为什么不用 lock？

一个自然的疑问：为什么不用更常见的 `lock` 语句？

```csharp
// 假设用 lock 实现
private readonly object _syncLock = new object();

// 轮询线程
lock (_syncLock) { /* 读取变量 */ }

// 写入线程
lock (_syncLock) { /* 写入变量 */ }
```

`lock` 的问题在于：

**问题一：轮询是长时间操作**
一个轮询周期可能持续数秒（几十个变量 × CmdPeriod）。如果用 `lock`，写入线程要等整个轮询周期结束才能获得锁。对于控制指令来说，几秒钟的延迟可能是不可接受的。

**问题二：不支持中断**
`lock` 不支持"暂停当前操作"。一旦轮询线程持有锁，你无法让它"暂时让出"。而 `ManualResetEventSlim` 的 `Wait()` 可以在每轮循环的固定检查点暂停，给写入操作一个"干净的窗口"。

**问题三：与 CancellationToken 的协作**
`lock` 无法响应取消请求。如果程序需要关闭，持有锁的线程必须等到操作完成。而 `_resetEvent.Wait(token)` 可以在收到取消信号时立即退出。

### 5.5 CancellationToken：优雅退出的关键

```csharp
// DeviceThread.cs — CancellationToken 的传递链
private readonly CancellationTokenSource _tokenSource =
    new CancellationTokenSource();

// 构造函数中启动线程
_task = CreateThreadAsync(_tokenSource.Token);

// 主循环中多处检查取消
while (!token.IsCancellationRequested)       // 检查点1：循环条件
{
    _resetEvent.Wait(token);                  // 检查点2：等待同步
    // ...
    await Task.Delay(..., token);             // 检查点3：延迟等待
}

// 停止方法
public void StopThread()
{
    _tokenSource.Cancel();    // 发送取消信号
    Driver.Close();           // 关闭设备连接
}
```

**为什么有多个检查点？**

因为轮询循环中有多个可能阻塞的操作。如果只在循环条件处检查取消，那么线程可能卡在 `Task.Delay` 中等待数秒才能退出。通过在**每个阻塞操作**中都传入 `token`，确保取消信号能在毫秒级内被响应。

```
检查点1: while 条件 → 每次循环迭代开始时检查
检查点2: _resetEvent.Wait(token) → RPC 写入等待时检查
检查点3: Task.Delay(..., token) → 轮询间隔等待时检查
```

### 5.6 Dispose 模式：资源的安全释放

```csharp
// DeviceThread.cs — Dispose 实现
public void Dispose()
{
    Driver.Dispose();           // 释放驱动资源
    _interpreter = null;        // 释放表达式引擎
    MethodDelegates.Clear();    // 清空调用委托缓存
    _tokenSource.Dispose();     // 释放取消令牌源
    _resetEvent.Dispose();      // 释放同步事件
    _logger.LogInformation($"线程释放,{Device.DeviceName}");
}
```

`StopThread()` 和 `Dispose()` 的分工：

| 方法 | 作用 | 调用时机 |
|------|------|---------|
| StopThread() | 发取消信号 + 关闭连接 | 设备更新/删除时 |
| Dispose() | 释放所有非托管资源 | StopThread 之后 |

这种两步释放模式确保了：先让线程安全退出（StopThread），再释放资源（Dispose）。如果顺序反过来，线程可能在资源被释放后仍然尝试访问，导致 `ObjectDisposedException`。

### 5.7 DeviceService 的线程管理

```csharp
// DeviceService.cs — 设备更新时的线程管理
public void UpdateDevice(Device device)
{
    try
    {
        _logger.LogInformation($"UpdateDevice Start: {device.DeviceName}");
        RemoveDeviceThread(device);    // 停止并释放旧线程
        CreateDeviceThread(device);    // 创建并启动新线程
        _logger.LogInformation($"UpdateDevice End: {device.DeviceName}");
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, $"UpdateDevice Error: {device.DeviceName}");
    }
}

public void RemoveDeviceThread(Device device)
{
    var deviceThread = DeviceThreads
        .FirstOrDefault(x => x.Device.ID == device.ID);
    if (deviceThread != null)
    {
        deviceThread.StopThread();   // 取消 + 关闭连接
        deviceThread.Dispose();      // 释放资源
        DeviceThreads.Remove(deviceThread);
    }
}
```

这个"先销毁后创建"的模式实现了**热重载** — 用户在 Web UI 中修改设备配置后，系统不需要重启就能应用新配置。

### 5.8 线程安全的集合选择

IoTGateway 在不同场景使用了不同的线程安全策略：

```csharp
// MQTTService.cs — ConcurrentDictionary 用于客户端主题管理
public ConcurrentDictionary<string, ConcurrentDictionary<string, byte>>
    ClientTopics = new();

// MessageService.cs — ConcurrentDictionary 用于缓存上次遥测值
private readonly ConcurrentDictionary<string, List<PayLoad>>
    _lastTelemetrys = new();

// DeviceService.cs — 普通 List 用于设备线程管理
public List<DeviceThread> DeviceThreads { get; } = new List<DeviceThread>();
```

为什么 `DeviceThreads` 用的是普通 `List` 而不是 `ConcurrentBag`？因为 `DeviceThreads` 只在 `DeviceService` 的方法中被修改（`UpdateDevice`、`RemoveDeviceThread`），而这些方法只在管理线程中被调用，不存在并发修改的场景。过度使用线程安全集合会降低性能。

### 5.9 MQTT 事件与轮询线程的交互

```csharp
// DeviceThread.cs — MQTT 消息接收事件的订阅
public DeviceThread(...)
{
    _messageService.OnExcRpc += MyMqttClient_OnExcRpc;
}

public void StopThread()
{
    _messageService.OnExcRpc -= MyMqttClient_OnExcRpc;
    // ...
}
```

`MyMqttClient_OnExcRpc` 方法是在 MQTT 客户端的消息接收线程中被调用的，而轮询逻辑在 DeviceThread 自己的线程中运行。`ManualResetEventSlim` 就是这两个线程之间的协调桥梁。

**线程交互时序图**：

```
轮询线程                    MQTT线程
   │                           │
   │── 读取变量1 ──→           │
   │                           │── 收到RPC写入请求 ──→
   │                           │   Reset() → 暂停信号
   │── 读取变量2 ──→           │
   │                           │   写入变量...
   │── 读取变量3 ──→           │
   │                           │   Set() → 恢复信号
   │── Wait() → 检查点         │
   │   (通过，继续读取)         │
   │── 读取变量4 ──→           │
```

### 5.10 潜在的并发风险与改进

IoTGateway 的当前设计在大多数场景下是安全的，但有一个潜在风险值得关注：

**风险：Reset 和 Set 之间的异常**

```csharp
_resetEvent.Reset();
try
{
    // ... 写入操作 ...
    // 如果这里抛出未捕获的异常
}
finally
{
    _resetEvent.Set();  // 用 finally 确保一定恢复
}
```

当前代码中 `Set()` 不在 `finally` 块中。如果写入过程中发生了未被 try-catch 捕获的异常（如 `StackOverflowException`），`Set()` 就不会执行，轮询线程会永久阻塞。

**改进建议**：将 `Set()` 放在 `finally` 块中，确保无论发生什么异常，轮询都能恢复。

### 5.11 并发控制的思维提炼

**思维一：同步点设计**
不要试图锁住整个操作，而是在关键检查点设置"关卡"。这样既保护了共享资源，又不会长时间阻塞任何一方。

**思维二：优雅退出**
程序关闭时，所有线程都应该及时退出。通过在每一个阻塞操作中传入 `CancellationToken`，确保没有线程会被"遗忘"。

**思维三：最小临界区**
`_resetEvent` 只在轮询循环的开头等待，不在每个变量的读取中都等待。这意味着临界区非常小 — 只在"开始新一轮轮询"时检查，而不是在"读取每个变量"时检查。

**思维四：对称操作**
有 `Reset()` 就必须有 `Set()`，有 `StopThread()` 就必须有 `Dispose()`。每一对操作都是对称的。在设计并发控制时，始终问自己："如果我暂停了某个操作，什么条件下会恢复它？"

**思维五：选择正确的工具**
`ManualResetEventSlim` vs `lock` vs `Semaphore` vs `Monitor` — 每种同步工具都有适用场景。选择的标准不是"哪个更强大"，而是"哪个最适合当前的协调模式"。

## 上位机性能优化的特殊性

上位机程序的性能优化与普通应用有本质区别：

1. **7x24 小时运行**：内存泄漏和性能衰退会随时间累积
2. **高频轮询**：设备数据采集可能每 10-100ms 执行一次
3. **多设备并发**：同时管理数十到数百台设备
4. **实时性要求**：告警和控制指令需要毫秒级响应
5. **资源受限**：工控机通常 CPU 和内存有限

VS 2022 提供了强大的性能分析工具，本章将系统讲解在上位机开发中的应用。

```csharp
{

    {

                        $"时间: {DateTime.Now:yyyy-MM-dd HH:mm:ss.fff}";

        var activeVariables = device.Variables
            .Where(v => v.IsActive)
            .OrderBy(v => v.Address)
            .ToList();
```

```csharp
private Dictionary<string, List<DeviceVariable>> _cachedActiveVariables;

public void RefreshActiveVariablesCache()
{
    _cachedActiveVariables = _devices.ToDictionary(
        d => d.Name,
        d => d.Variables
            .Where(v => v.IsActive)
            .OrderBy(v => v.Address)
            .ToList()

public async Task PollAllDevices()
{
    foreach (var device in _devices)
    {
        // 优化 1：使用结构化日志（延迟格式化）
        _logger.LogDebug("轮询设备: {DeviceName}, 地址: {Address}",
            device.Name, device.Address);

        var data = await _serialClient.ReadHoldingRegistersAsync(
            device.StartAddress, device.RegisterCount);

        // 优化 3：使用缓存的变量列表
        if (_cachedActiveVariables.TryGetValue(device.Name, out var variables))
        {
            for (int i = 0; i < variables.Count; i++)
            {
                variables[i].UpdateValue(data[variables[i].Offset]);
            }
        }
    }
}
```

### 2.2 编写基准测试

```csharp
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

[MemoryDiagnoser]  // 追踪内存分配
[RankColumn]       // 显示排名
public class ModbusParserBenchmarks
{
    private byte[] _responseData;

    [GlobalSetup]
    public void Setup()
    {
        // 模拟 Modbus 响应：设备地址 01, 功能码 03, 10 个寄存器
        _responseData = new byte[] {
            0x01, 0x03, 0x14,
            0x00, 0x1A, 0x00, 0x3F, 0x01, 0x02, 0x03, 0x04,
            0x05, 0x06, 0x07, 0x08, 0x09, 0x0A, 0x0B, 0x0C,
            0x0D, 0x0E, 0x56, 0x78
        };
    }

    [Benchmark(Baseline = true)]
    public ushort[] ParseWithLINQ()
    {
        return _responseData
            .Skip(3)
            .Take(_responseData[2])
            .Chunk(2)
            .Select(pair => (ushort)(pair[0] << 8 | pair[1]))
            .ToArray();
    }

    [Benchmark]
    public ushort[] ParseWithLoop()
    {
        var byteCount = _responseData[2];
        var registerCount = byteCount / 2;
        var result = new ushort[registerCount];

        for (int i = 0; i < registerCount; i++)
        {
            result[i] = (ushort)((_responseData[3 + i * 2] << 8)
                        | _responseData[3 + i * 2 + 1]);
        }

        return result;
    }

    [Benchmark]
    public Span<ushort> ParseWithSpan()
    {
        var byteCount = _responseData[2];
        var registerCount = byteCount / 2;
        var result = new ushort[registerCount];

        var source = _responseData.AsSpan(3, byteCount);
        for (int i = 0; i < registerCount; i++)
        {
            result[i] = (ushort)((source[i * 2] << 8) | source[i * 2 + 1]);
        }

        return result;
    }
}

// 运行基准测试
// BenchmarkRunner.Run<ModbusParserBenchmarks>();
```

### 2.3 解读基准测试结果

```
BenchmarkDotNet 输出示例：

| Method          | Mean      | Error    | StdDev   | Rank | Allocated |
|---------------- |----------:|---------:|---------:|-----:|----------:|
| ParseWithLINQ   | 342.5 ns  | 6.82 ns  | 7.30 ns  | 3    | 480 B     |
| ParseWithLoop   | 42.3 ns   | 0.87 ns  | 0.93 ns  | 2    | 128 B     |
| ParseWithSpan   | 18.7 ns   | 0.41 ns  | 0.38 ns  | 1    | 128 B     |

分析：
- Span 版本比 LINQ 版本快 18 倍
- LINQ 版本分配了 480 字节（迭代器、中间数组等）
- 在每秒 100 次轮询的场景下：
  - LINQ：每秒分配 48 KB → 每小时 172 MB
  - Span：每秒分配 12.8 KB → 每小时 46 MB
```

> [!important] 基准测试的黄金法则
> 不要凭直觉优化！总是先写基准测试验证假设。有时候"优化"后的代码反而更慢（例如 JIT 编译开销、缓存失效等）。

## 三、上位机常见性能陷阱

### 3.1 字符串拼接问题

```csharp
// ❌ 错误：在轮询循环中拼接字符串
public void ProcessPollingData(Device device, byte[] data)
{
    string logLine = "";
    for (int i = 0; i < data.Length; i++)
    {
        logLine += $"[{i}]={data[i]:X2} ";  // 每次循环创建新字符串
    }
    _logger.LogTrace(logLine);
}

// ✅ 正确：使用 StringBuilder
public void ProcessPollingData(Device device, byte[] data)
{
    var sb = new StringBuilder(data.Length * 6);
    for (int i = 0; i < data.Length; i++)
    {
        sb.Append('[').Append(i).Append("]=")
          .Append(data[i], 'X', 2).Append(' ');
    }
    _logger.LogTrace("{Data}", sb.ToString());
}

// ✅ 更好：使用 string.Create 或仅在需要时格式化
public void ProcessPollingData(Device device, ReadOnlySpan<byte> data)
{
    if (_logger.IsEnabled(LogLevel.Trace))
    {
        _logger.LogTrace("设备 {Name} 数据: {Hex}",
            device.Name, Convert.ToHexString(data));
    }
}
```

## 四、内存泄漏检测

### 4.1 上位机常见的内存泄漏原因

| 原因 | 说明 | 检测方法 |
|------|------|---------|
| 事件订阅未取消 | `DataReceived += handler` 但从未 `-=` | 内存快照对比 |
| Timer 未释放 | `System.Timers.Timer` 没有 `Dispose` | 终结器队列检查 |
| 集合无限增长 | 历史数据列表没有上限 | 内存分析器 |
| 静态集合 | `static List<>` 只增不减 | 代码审查 |
| Socket/Stream 未关闭 | 连接断开但未释放资源 | 句柄监控 |

### 4.2 事件订阅泄漏示例

```csharp
// ❌ 泄漏：事件订阅导致对象无法被 GC
public class DeviceMonitor
{
    public DeviceMonitor(SerialPort port)
    {
        port.DataReceived += OnDataReceived;  // 订阅事件
        // 当 DeviceMonitor 被丢弃时，port 仍然持有它的引用
        // → DeviceMonitor 无法被 GC 回收
    }

    private void OnDataReceived(object sender, SerialDataReceivedEventArgs e)
    {
        // 处理数据...
    }
}

// ✅ 正确：实现 IDisposable 并取消订阅
public class DeviceMonitor : IDisposable
{
    private readonly SerialPort _port;
    private bool _disposed;

    public DeviceMonitor(SerialPort port)
    {
        _port = port;
        _port.DataReceived += OnDataReceived;
    }

    private void OnDataReceived(object sender, SerialDataReceivedEventArgs e)
    {
        if (_disposed) return;
        // 处理数据...
    }

    public void Dispose()
    {
        if (_disposed) return;
        _port.DataReceived -= OnDataReceived;  // 取消订阅
        _disposed = true;
    }
}
```

### 4.4 WeakReference 模式

```csharp
// 使用 WeakReference 避免强引用导致的泄漏
public class WeakEventManager<TEventArgs>
{
    private readonly List<WeakReference<EventHandler<TEventArgs>>> _handlers = new();

    public void AddHandler(EventHandler<TEventArgs> handler)
    {
        _handlers.Add(new WeakReference<EventHandler<TEventArgs>>(handler));
    }

    public void RaiseEvent(object sender, TEventArgs args)
    {
        _handlers.RemoveAll(wr =>
        {
            if (wr.TryGetTarget(out var handler))
            {
                handler(sender, args);
                return false;
            }
            return true;  // 目标已被 GC，移除弱引用
        });
    }
}
```

## 五、Async/Await 性能优化

### 5.1 ConfigureAwait(false)

```csharp
// 在类库和后台服务中使用 ConfigureAwait(false)
// 避免捕获同步上下文（上位机类库不需要回到 UI 线程）

public class ModbusDriver
{
    public async Task<byte[]> ReadRegistersAsync(int address, int count)
    {
        var request = BuildRequest(address, count);
        await _stream.WriteAsync(request).ConfigureAwait(false);  // 不回到原上下文
        await _stream.FlushAsync().ConfigureAwait(false);

        var response = new byte[256];
        var bytesRead = await _stream.ReadAsync(response)
            .ConfigureAwait(false);

        return response.AsSpan(0, bytesRead).ToArray();
    }
}

// ⚠ 注意：ASP.NET Core 控制器和 UI 代码中不要使用 ConfigureAwait(false)
// 因为可能需要回到请求上下文或 UI 线程
```

### 5.2 ValueTask 优化

```csharp
// 当方法经常同步完成时，使用 ValueTask 替代 Task

// ❌ Task：即使缓存命中也会分配 Task 对象
public async Task<DeviceStatus> GetStatusAsync(string deviceId)
{
    if (_cache.TryGetValue(deviceId, out var status))
        return status;  // 仍然创建了 Task<DeviceStatus>

    return await ReadFromDeviceAsync(deviceId);
}

// ✅ ValueTask：缓存命中时零分配
public async ValueTask<DeviceStatus> GetStatusAsync(string deviceId)
{
    if (_cache.TryGetValue(deviceId, out var status))
        return status;  // 同步返回，不分配 ValueTask

    return await ReadFromDeviceAsync(deviceId);
}

// ValueTask 使用限制：
// 1. 只能 await 一次
// 2. 不能并发 await（不能同时 await 两次）
// 3. 适合"经常同步完成"的场景（如缓存）
```

### 5.3 异步并行执行

```csharp
// ❌ 顺序执行：逐个轮询设备
public async Task PollAllDevices()
{
    foreach (var device in _devices)
    {
        await PollDeviceAsync(device);  // 等一个完成才开始下一个
    }
}

// ✅ 并行执行：同时轮询所有设备
public async Task PollAllDevices()
{
    var tasks = _devices.Select(d => PollDeviceAsync(d));
    await Task.WhenAll(tasks);
}

// ✅ 更好的方式：控制并发度（避免同时打开太多连接）
public async Task PollAllDevices()
{
    var semaphore = new SemaphoreSlim(10);  // 最多 10 个并发
    var tasks = _devices.Select(async device =>
    {
        await semaphore.WaitAsync();
        try
        {
            await PollDeviceAsync(device);
        }
        finally
        {
            semaphore.Release();
        }
    });
    await Task.WhenAll(tasks);
}
```

### 6.2 何时使用专用线程

```csharp
// ✅ 专用线程适合：
// - 长时间运行的轮询循环
// - 需要精确时间控制的操作
// - 需要设置线程优先级

public class DevicePollingThread
{
    private Thread _pollingThread;
    private volatile bool _running = true;

    public void Start()
    {
        _pollingThread = new Thread(PollingLoop)
        {
            Name = $"Polling-{_device.Name}",
            IsBackground = true,
            Priority = ThreadPriority.AboveNormal  // 通信线程优先级更高
        };
        _pollingThread.Start();
    }

    private void PollingLoop()
    {
        var stopwatch = new Stopwatch();

        while (_running)
        {
            stopwatch.Restart();

            // 执行轮询
            var data = _driver.ReadRegisters();
            _dataStore.Update(data);

            stopwatch.Stop();

            // 精确控制轮询间隔
            var sleepTime = _pollIntervalMs - (int)stopwatch.ElapsedMilliseconds;
            if (sleepTime > 0)
                Thread.Sleep(sleepTime);
        }
    }

    public void Stop()
    {
        _running = false;
        _pollingThread?.Join(5000);  // 等待线程结束，最多 5 秒
    }
}
```

```csharp
public class DeviceDataPipeline

    public async Task ProcessDataAsync(CancellationToken ct)
```

### 7.1 减少 GC 压力

```csharp
// GC 压力大的代码：频繁分配和释放小对象
public void ProcessSensorData(Span<byte> rawData)

// GC 友好的代码：使用 Span 和栈分配
public void ProcessSensorData(ReadOnlySpan<byte> rawData)
{
    var header = rawData.Slice(0, 4);
    var payload = rawData.Slice(4);

    // 使用栈分配避免堆分配（适用于小数据量）
    Span<float> values = stackalloc float[payload.Length];
    for (int i = 0; i < payload.Length; i++)
        values[i] = payload[i];

    // 直接处理数据，无需序列化
    ProcessValues(values);
}
```

## 八、性能优化检查清单

```
上位机性能优化检查清单：

1. 高频循环（轮询、数据处理）
   [ ] 没有字符串拼接
   [ ] 没有 LINQ（改用 for 循环）
   [ ] 没有装箱操作
   [ ] 使用预分配缓冲区或 ArrayPool
   [ ] 使用 Span/Memory 避免数组复制

2. 异步代码
   [ ] 类库中使用 ConfigureAwait(false)
   [ ] 高频方法考虑 ValueTask
   [ ] CancellationToken 被正确传递
   [ ] 避免 async void（除了事件处理器）

3. 内存管理
   [ ] 所有 IDisposable 对象使用 using 语句
   [ ] 事件订阅有对应的取消订阅
   [ ] 静态集合有大小限制或清理策略
   [ ] 大对象使用 ArrayPool

4. 多线程
   [ ] 长时间运行的循环使用专用线程
   [ ] 短时操作使用 Task/ThreadPool
   [ ] 使用 Channel 实现高效的生产者-消费者
   [ ] 避免使用 lock 包裹异步操作

5. 构建和部署
   [ ] 生产环境使用 Release 模式构建
   [ ] 启用 ReadyToRun 编译
   [ ] 服务器环境使用 Server GC
   [ ] 配置合理的 GC 参数
```

## 小结

性能优化是上位机程序长期稳定运行的保障。本章涵盖了：

- **VS Profiler**：CPU 使用率和内存分配分析
- **BenchmarkDotNet**：微基准测试的正确方法
- **常见陷阱**：字符串拼接、装箱、过度 async
- **内存泄漏**：检测方法和常见原因
- **Async 优化**：ConfigureAwait、ValueTask、并行执行
- **线程策略**：ThreadPool vs 专用线程 vs Channel
- **GC 优化**：减少分配和 GC 配置

**性能优化的核心原则：**
1. 先测量，后优化（不要凭直觉）
2. 关注热路径（高频执行的代码）
3. 减少内存分配是减少 GC 压力的关键
4. 在正确的设计上优化，而不是优化糟糕的设计

## 部署方案总览

IoTGateway作为一个基于.NET 8.0的跨平台Web应用，支持多种部署方式以适应不同的工业现场环境。从简单的单机直接运行到容器化集群部署，本章概述各种部署方案的适用场景、优劣势和选型建议，帮助工控工程师根据实际条件选择最合适的部署方式。

## 部署架构全景

```
                        ┌─────────────────────────────────┐
                        │          工业现场网络             │
                        │                                 │
  PLC/仪表 ──Modbus──→  │  ┌─────────────────────────┐    │
  PLC/仪表 ──OPC UA──→  │  │     IoTGateway          │    │ ──→ 浏览器
  传感器 ──MQTT────→    │  │  (518:HTTP, 1888:MQTT)  │    │
                        │  └─────────────────────────┘    │
                        │                                 │
                        └─────────────────────────────────┘
```

## 部署方案对比

### 方案一：单机直接部署

最简单的部署方式，直接在目标机器上安装.NET运行时并运行程序。

**部署步骤：**
1. 安装.NET 8.0 Runtime
2. 将发布文件拷贝到目标目录
3. 运行`dotnet IoTGateway.dll`

**适用场景：**
- 小型工厂的单机网关
- 开发和测试环境
- 演示和评估

**优势：**
- 部署最简单，几分钟即可完成
- 不需要额外软件
- 适合资源受限的工控机

**劣势：**
- 没有进程守护，重启后需手动启动
- 环境一致性难以保证
- 升级需要停机操作

### 方案二：系统服务部署（推荐）

将IoTGateway注册为操作系统服务，实现开机自启和崩溃自动重启。

**Windows - 使用Windows Service：**
```powershell
# 使用sc.exe注册为Windows服务
sc.exe create IoTGateway binPath= "C:\IoTGateway\IoTGateway.exe" start= auto
sc.exe start IoTGateway
```

**Linux - 使用systemd：**
```ini
[Unit]
Description=IoTGateway Service
After=network.target

[Service]
WorkingDirectory=/opt/iotgateway
ExecStart=/usr/bin/dotnet /opt/iotgateway/IoTGateway.dll
Restart=always
RestartSec=10
User=iotgateway

[Install]
WantedBy=multi-user.target
```

**适用场景：**
- 生产环境的长期运行
- 需要开机自启的工控机
- 无人值守的边缘网关

**优势：**
- 开机自动启动
- 崩溃自动重启
- 可通过系统命令管理（start/stop/restart/status）
- 日志集成到系统日志

### 方案三：Docker容器化部署

将IoTGateway打包为Docker镜像，通过容器方式运行。

**快速启动：**
```bash
docker run -d \
  --name iotgateway \
  -p 518:518 \
  -p 1888:1888 \
  -v /data/iotgateway:/app/data \
  iotgateway:latest
```

**适用场景：**
- 需要快速部署和迁移的场景
- 多实例部署（不同工厂、不同产线）
- 边缘计算网关集群
- CI/CD自动化部署流水线

**优势：**
- 环境一致性好，消除"在我机器上能跑"问题
- 快速部署和回滚
- 资源隔离，不影响宿主机其他服务
- 易于横向扩展

**劣势：**
- 需要安装Docker运行时
- 部分工控机不支持Docker
- 存储卷挂载需要注意数据持久化
- 学习成本略高

### 方案四：反向代理部署

在前面放置Nginx或IIS作为反向代理，后面运行IoTGateway。

```
浏览器 → Nginx(:80/:443) → IoTGateway(:518)
```

**Nginx配置示例：**
```nginx
server {
    listen 80;
    server_name iot.example.com;

    location / {
        proxy_pass http://localhost:518;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";  # WebSocket支持
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    location /mqtt {
        proxy_pass http://localhost:518;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
```

**适用场景：**
- 需要HTTPS证书的场景
- 需要域名访问的场景
- 与现有Web系统集成的场景
- 需要负载均衡的场景

**优势：**
- 支持HTTPS/TLS加密
- 支持域名和虚拟主机
- 静态文件缓存
- 请求限流和安全防护

### 方案五：云端部署

将IoTGateway部署在云服务器上，设备通过公网MQTT连接。

```
现场设备 ──MQTT(TLS)──→ 云服务器 ──→ IoTGateway ──→ 浏览器
                         (阿里云/腾讯云/AWS)
```

**适用场景：**
- 多工厂统一管理
- 需要外网远程监控
- 数据需要云端存储和分析

**优势：**
- 随时随地访问
- 弹性扩展
- 高可用性保障

**劣势：**
- 需要稳定的公网连接
- 数据传输延迟增加
- 数据安全风险需要额外处理
- 持续的云服务费用

## 端口规划

IoTGateway使用的端口一览：

| 端口 | 协议 | 用途 | 是否必须 |
|------|------|------|---------|
| 518 | HTTP | Web管理界面、API接口 | 是 |
| 1888 | TCP | MQTT Broker（设备连接） | 是 |
| 503 | TCP | 预留端口（Modbus Slave等） | 否 |

**防火墙配置建议：**

```bash
# Linux防火墙（firewalld）
firewall-cmd --permanent --add-port=518/tcp
firewall-cmd --permanent --add-port=1888/tcp
firewall-cmd --reload

# Windows防火墙
netsh advfirewall firewall add rule name="IoTGateway Web" dir=in action=allow protocol=tcp localport=518
netsh advfirewall firewall add rule name="IoTGateway MQTT" dir=in action=allow protocol=tcp localport=1888
```

## 存储规划

IoTGateway涉及的主要存储路径：

| 路径 | 内容 | 备份建议 |
|------|------|---------|
| `./data/iotgateway.db` | SQLite数据库 | 定期备份 |
| `./logs/` | 日志文件 | 定期清理 |
| `./files/` | 上传的文件 | 按需备份 |
| `./Plugins/` | 驱动插件DLL | 版本管理 |

## 部署方式选型决策树

```
你的部署环境是什么？
│
├── 工控机/边缘设备（无Docker）
│   ├── 需要开机自启？ ──→ 系统服务部署
│   └── 临时使用？ ──→ 单机直接部署
│
├── Linux服务器（有Docker）
│   ├── 单实例？ ──→ Docker容器部署
│   └── 多实例？ ──→ docker-compose部署
│
├── 需要HTTPS/域名？
│   └── 反向代理部署（Nginx/IIS）
│
└── 需要远程访问/多工厂？
    └── 云端部署 + 反向代理
```

## 发布构建

无论选择哪种部署方式，都需要先将项目发布为可部署的包：

```bash
# Windows发布
dotnet publish -c Release -r win-x64 --self-contained true -o ./publish/win

# Linux发布
dotnet publish -c Release -r linux-x64 --self-contained true -o ./publish/linux

# ARM发布（树莓派等）
dotnet publish -c Release -r linux-arm64 --self-contained true -o ./publish/arm64

# 跨平台发布（依赖已安装的运行时）
dotnet publish -c Release -o ./publish/portable
```

**发布选项说明：**

| 选项 | 说明 |
|------|------|
| `-c Release` | 发布配置（优化编译） |
| `-r <rid>` | 目标运行时标识 |
| `--self-contained true` | 自包含（自带运行时，体积大约150MB） |
| `--self-contained false` | 依赖框架（需要目标机器安装.NET运行时） |
| `-o` | 输出目录 |

## 小结

IoTGateway提供了从单机直接运行到云端容器化部署的完整方案。对于大多数工业现场，推荐使用系统服务部署（Linux systemd或Windows Service），兼顾简单性和可靠性。对于需要快速迁移和批量部署的场景，Docker容器化是更好的选择。下一章将详细讲解Docker容器化部署的具体步骤。

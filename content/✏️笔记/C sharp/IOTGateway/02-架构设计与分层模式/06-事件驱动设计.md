## 事件驱动设计

### 工业上位机中的事件场景

在工业现场，上位机不仅要主动采集数据，还需要被动地响应各种异步事件：

- 云平台下发远程控制指令（RPC写入）
- 设备连接状态变化（上线/断线）
- 传感器数值超过报警阈值
- 操作员在Web界面修改了设备配置

这些事件的发生时间和顺序都是不确定的。如果用轮询方式检查事件，不仅浪费资源，还可能错过时间敏感的指令。IoTGateway 采用了经典的**观察者模式**来构建事件驱动架构。

### 观察者模式回顾

观察者模式定义了一对多的依赖关系：当一个对象（被观察者/发布者）状态改变时，所有依赖它的对象（观察者/订阅者）都会自动收到通知。

```
发布者 (Publisher)
    │
    ├── event EventHandler<T> SomeEvent
    │
    ├── 订阅者A.Subscribe(SomeEvent)
    ├── 订阅者B.Subscribe(SomeEvent)
    └── 订阅者C.Subscribe(SomeEvent)
    
当发布者触发 SomeEvent 时：
    → 订阅者A.Handler() 被调用
    → 订阅者B.Handler() 被调用
    → 订阅者C.Handler() 被调用
```

### OnExcRpc：核心事件链

IoTGateway 中最关键的事件是 `OnExcRpc`（RPC指令执行事件），它负责将云平台的远程控制指令分发到正确的设备采集线程。

#### 事件传播链路

```
IoT云平台 (MQTT Broker)
    │
    │ MQTT 消息到达
    ▼
IPlatformHandler.ReceiveRpc()
    │
    │ 解析平台特定格式 → 统一的 RpcRequest
    ▼
IPlatformHandler.OnExcRpc 事件触发
    │
    │ 事件转发
    ▼
MessageService.OnExcRpc 事件触发
    │
    │ 多播委托（所有订阅者同时收到）
    ├── DeviceThread_1.MyMqttClient_OnExcRpc()  ← 检查是否是自己的指令
    ├── DeviceThread_2.MyMqttClient_OnExcRpc()  ← 检查是否是自己的指令
    ├── DeviceThread_3.MyMqttClient_OnExcRpc()  ← 检查是否是自己的指令
    └── ...
```

### MessageService：事件的中心枢纽

`MessageService` 是整个事件体系的中心枢纽，它既是事件的发布者，也是事件的转发者：

```csharp
public class MessageService
{
    // 对外暴露的事件
    public event EventHandler<RpcRequest>? OnExcRpc;
    public event EventHandler<ISAttributeResponse>? OnReceiveAttributes;

    private IPlatformHandler _platformHandler;

    public async Task StartClientAsync()
    {
        // 创建平台处理器
        _platformHandler = PlatformHandlerFactory.CreateHandler(
            _systemConfig.IoTPlatformType, Client, _logger, OnExcRpc);

        // 将平台处理器的事件转发给自己的事件
        _platformHandler.OnExcRpc += (sender, request) =>
            OnExcRpc?.Invoke(sender, request);
    }

    // MQTT消息到达时的处理
    public async Task Client_ApplicationMessageReceivedAsync(
        MqttApplicationMessageReceivedEventArgs e)
    {
        // 委托给平台处理器解析
        _platformHandler.ReceiveRpc(e);
    }
}
```

#### 事件转发机制

这里有一个精妙的设计：`MessageService` 并没有直接处理 MQTT 消息，而是将解析工作委托给 `IPlatformHandler`。平台处理器解析出统一的 `RpcRequest` 后，通过事件通知 `MessageService`，`MessageService` 再通过自己的事件广播给所有 `DeviceThread`。

```
MQTT原始消息（平台特定格式）
    │
    ▼ IPlatformHandler.ReceiveRpc() 解析
    │
RpcRequest（统一格式）
    │
    ▼ IPlatformHandler.OnExcRpc 事件
    │
    ▼ MessageService.OnExcRpc 事件（转发）
    │
    ▼ 所有 DeviceThread 的事件处理器
```

### DeviceThread：事件订阅与处理

每个 `DeviceThread` 在创建时都会订阅 `MessageService.OnExcRpc` 事件：

```csharp
public class DeviceThread : IDisposable
{
    private readonly ManualResetEventSlim _resetEvent = new(true);

    public DeviceThread(Device device, IDriver driver, ...)
    {
        // 订阅RPC事件
        _messageService.OnExcRpc += MyMqttClient_OnExcRpc;
    }

    // RPC事件处理器
    public async void MyMqttClient_OnExcRpc(object sender, RpcRequest e)
    {
        // 第一步：检查RPC请求是否属于当前设备
        if (e.DeviceName == Device.DeviceName ||
            Device.DeviceVariables.Select(x => x.Alias).Contains(e.DeviceName))
        {
            // 第二步：暂停采集循环，避免读写冲突
            _resetEvent.Reset();

            // 第三步：执行RPC写入
            if (e.Method.ToLower() == "write")
            {
                if (!Driver.IsConnected)
                    Driver.Connect();

                foreach (var para in e.Params)
                {
                    var variable = Device.DeviceVariables
                        .FirstOrDefault(x => x.Name == para.Key);
                    if (variable?.ProtectType != ProtectTypeEnum.ReadOnly)
                    {
                        var writeResponse = await Driver.WriteAsync(
                            e.RequestId, variable.Method, ioArgModel);
                        rpcResponse.IsSuccess = writeResponse.IsSuccess;
                    }
                }
            }

            // 第四步：恢复采集循环
            _resetEvent.Set();

            // 第五步：回复RPC结果
            await _messageService.ResponseRpcAsync(rpcResponse);

            // 第六步：记录RPC日志
            await using var dc = new DataContext(...);
            dc.Set<RpcLog>().Add(rpcLog);
            await dc.SaveChangesAsync();
        }
    }
}
```

### ManualResetEventSlim：采集与控制的协调

`ManualResetEventSlim` 是一个轻量级的线程同步原语，在 IoTGateway 中用于协调**采集循环**和**RPC写入**之间的并发访问。

#### 工作原理

```
ManualResetEventSlim 状态：
  - Set (true)   → Wait() 立即返回，采集循环正常运行
  - Reset (false) → Wait() 阻塞，采集循环暂停
```

#### 在 DeviceThread 中的使用

```csharp
private readonly ManualResetEventSlim _resetEvent = new(true); // 初始状态：Set

// 采集循环中的使用
private async Task CreateThreadAsync(CancellationToken token)
{
    while (!token.IsCancellationRequested)
    {
        _resetEvent.Wait(token); // 如果Reset状态，则在此阻塞

        // ... 正常的数据采集逻辑 ...

        await Task.Delay(Driver.MinPeriod, token);
    }
}

// RPC处理中的使用
public async void MyMqttClient_OnExcRpc(object sender, RpcRequest e)
{
    _resetEvent.Reset();  // 暂停采集循环
    // ... 执行RPC写入 ...
    _resetEvent.Set();    // 恢复采集循环
}
```

#### 时序图

```
采集线程                      RPC线程
   │                            │
   │ _resetEvent.Wait() → 通过  │
   │ 读取变量...                │
   │                            │ MQTT RPC消息到达
   │                            │ _resetEvent.Reset() → 设为阻塞
   │ _resetEvent.Wait() → 阻塞  │
   │    (等待中...)             │ 执行 WriteAsync()
   │    (等待中...)             │ 回复 ResponseRpcAsync()
   │                            │ _resetEvent.Set() → 设为通过
   │ _resetEvent.Wait() → 通过  │
   │ 继续读取变量...            │
```

> **为什么需要暂停采集？** 因为大多数工业协议（如 Modbus、S7）不支持同时读写。如果在读取过程中发送写入指令，可能导致通信冲突或数据损坏。

### 事件取消订阅

在 `DeviceThread` 停止时，必须取消事件订阅，否则已销毁的对象仍会收到事件通知，导致 `ObjectDisposedException`：

```csharp
public void StopThread()
{
    // 通知云平台设备下线
    foreach (var group in Device.DeviceVariables.GroupBy(x => x.Alias))
    {
        var deviceName = string.IsNullOrWhiteSpace(group.Key)
            ? Device.DeviceName : group.Key;
        _messageService?.DeviceDisconnected(deviceName, Device);
    }

    // 取消事件订阅（关键！）
    _messageService.OnExcRpc -= MyMqttClient_OnExcRpc;

    // 取消采集循环
    _tokenSource.Cancel();

    // 关闭驱动连接
    Driver.Close();
}
```

### 内置 MQTT 消息推送

除了 RPC 事件链，`DeviceThread` 还通过内置 MQTT Server 实现了变量变化时的前端推送：

```csharp
// 当变量值发生变化时，通过内部 MQTT 推送
if (JsonConvert.SerializeObject(item.Values[1]) !=
    JsonConvert.SerializeObject(item.Values[0]))
{
    var msg = new InjectedMqttApplicationMessage(
        new MqttApplicationMessage()
        {
            Topic = $"internal/v1/gateway/telemetry/{Device.DeviceName}/{item.Name}",
            PayloadSegment = Encoding.UTF8.GetBytes(JsonConvert.SerializeObject(ret))
        });
    mqttServer.InjectApplicationMessage(msg);
}
```

> 这里使用了 MQTTnet 的 `InjectApplicationMessage` 方法，直接向内置 MQTT Broker 注入消息，无需经过网络传输。前端 WebSocket 客户端订阅该 Topic 即可实时显示数据变化。

### 事件驱动 vs 轮询对比

| 对比维度 | 轮询方案 | 事件驱动方案 |
|---------|---------|-------------|
| 响应延迟 | 取决于轮询间隔 | 事件到达立即处理 |
| 资源消耗 | 持续检查，浪费CPU | 无事件时阻塞等待 |
| 代码复杂度 | 需要状态标志管理 | 事件订阅/发布清晰 |
| 扩展性 | 新增检查项需修改循环 | 新增订阅者不影响发布者 |

### 事件驱动设计在工业场景的最佳实践

1. **事件处理器要快速返回**：`async void` 的 RPC 处理器中，耗时操作应使用 `await`，不要阻塞事件线程
2. **务必取消订阅**：对象销毁前必须取消事件订阅，避免内存泄漏和空引用异常
3. **同步原语不可少**：共享资源（如驱动连接）的并发访问必须通过 `ManualResetEventSlim` 等同步机制保护
4. **异常要隔离**：每个事件处理器内部要 try-catch，一个处理器的异常不应影响其他处理器

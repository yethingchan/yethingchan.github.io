## 分层架构设计

### 为什么需要分层

在工业上位机开发中，最常见的痛点就是"改一处，处处出错"。数据采集逻辑、数据库操作、界面展示混在一起，一旦需要更换协议或调整界面，就像拆炸弹一样危险。

分层架构的核心思想是**关注点分离**（Separation of Concerns）：每一层只负责一类事情，层与层之间通过约定好的接口通信。

### IoTGateway 的四层架构

```
┌─────────────────────────────────────────────────┐
│            表现层 (IoTGateway Web App)            │
│   Program.cs / Startup.cs / Controllers / Views  │
├─────────────────────────────────────────────────┤
│           视图模型层 (IoTGateway.ViewModel)       │
│   DeviceVM / DeviceListVM / DeviceSearcher       │
├─────────────────────────────────────────────────┤
│           数据访问层 (IoTGateway.DataAccess)      │
│   DataContext / Migrations                       │
├─────────────────────────────────────────────────┤
│            实体模型层 (IoTGateway.Model)          │
│   Device / Driver / DeviceVariable / SystemConfig│
└─────────────────────────────────────────────────┘
```

### 第一层：实体模型层 (IoTGateway.Model)

实体模型层是整个系统的数据基石。它定义了系统中所有持久化对象的结构，**不包含任何业务逻辑和数据库操作代码**。

#### 核心实体

```csharp
// Device.cs - 设备实体，支持树形结构
[Comment("设备维护")]
[Index(nameof(DeviceName))]
public class Device : TreePoco<Device>, IBasePoco
{
    [Comment("名称")]
    [Display(Name = "DeviceName")]
    public string DeviceName { get; set; }

    [Comment("驱动")]
    public Guid? DriverId { get; set; }
    public Driver Driver { get; set; }

    [Comment("启动")]
    public bool AutoStart { get; set; }

    [Comment("变化上传")]
    public bool CgUpload { get; set; }

    [Comment("类型(组或设备)")]
    public DeviceTypeEnum DeviceTypeEnum { get; set; }

    // 导航属性
    public List<DeviceConfig> DeviceConfigs { get; set; }
    public List<DeviceVariable> DeviceVariables { get; set; }
}
```

#### 模型层设计原则

| 原则 | 说明 |
|------|------|
| 纯POCO | 实体类不依赖任何ORM框架特定基类 |
| 数据注解 | 使用 `[Comment]`、`[Display]` 等注解描述元数据 |
| 导航属性 | 通过 `List<T>` 和引用属性表达实体关系 |
| 枚举集中 | 所有枚举类型定义在 `Common.cs` 中统一管理 |

#### 运行时字段标记

`DeviceVariable` 是一个典型例子，展示了持久化字段和运行时字段的分离设计：

```csharp
public class DeviceVariable : TopBasePoco, IVariable
{
    // === 持久化字段（存入数据库）===
    public string Name { get; set; }          // 变量名
    public string DeviceAddress { get; set; } // 设备地址
    public DataTypeEnum DataType { get; set; } // 数据类型
    public bool IsTrigger { get; set; }       // 触发标志

    // === 运行时字段（不存入数据库）===
    [NotMapped]
    public object Value { get; set; }         // 当前原值
    [NotMapped]
    public object CookedValue { get; set; }   // 计算后的值
    [NotMapped]
    public VaribaleStatusTypeEnum StatusType { get; set; } // 状态

    // === 环形缓冲区（最近三次值）===
    [NotMapped]
    public object[] Values { get; set; } = new object[3];

    public void EnqueueVariable(object value)
    {
        Values[2] = Values[1];
        Values[1] = Values[0];
        Values[0] = value;
    }
}
```

> **设计亮点**：`[NotMapped]` 标注的字段不会被EF Core持久化，它们在运行时由 `DeviceThread` 动态填充。环形缓冲区用于变化检测和趋势分析。

### 第二层：数据访问层 (IoTGateway.DataAccess)

数据访问层只包含一个核心类 `DataContext`，它继承自 WTM 框架的 `FrameworkContext`。

```csharp
public class DataContext : FrameworkContext
{
    public DbSet<FrameworkUser> FrameworkUsers { get; set; }
    public DbSet<Device> Devices { get; set; }
    public DbSet<DeviceConfig> DeviceConfigs { get; set; }
    public DbSet<DeviceVariable> DeviceVariables { get; set; }
    public DbSet<Driver> Drivers { get; set; }
    public DbSet<SystemConfig> SystemConfig { get; set; }
    public DbSet<RpcLog> RpcLogs { get; set; }

    // 多数据库构造函数
    public DataContext(string cs, DBTypeEnum dbtype) : base(cs, dbtype) { }
    public DataContext(DbContextOptions<DataContext> options) : base(options) { }
}
```

#### 数据访问层的设计考量

1. **薄层设计**：DataAccess 层非常薄，几乎没有自定义的业务逻辑。EF Core 的 `DbContext` 已经提供了完整的 CRUD 能力，不需要再封装 Repository
2. **FrameworkContext 继承**：WTM 框架的 `FrameworkContext` 提供了用户管理、角色管理、菜单管理等基础表结构
3. **DataInit 方法**：用于首次运行时创建默认数据（管理员账户等）
4. **DesignTimeFactory**：支持 EF Core 迁移工具在设计时创建 DbContext 实例

### 第三层：视图模型层 (IoTGateway.ViewModel)

视图模型层是连接数据层和表现层的桥梁。在 WTM 框架中，ViewModel 遵循严格的命名和继承约定：

#### ViewModel 类族

```
BaseVM                    ← 基础ViewModel
├── BaseCRUDVM<T>         ← 增删改查ViewModel
│   ├── DeviceVM          ← 设备的增删改
│   ├── DriverVM          ← 驱动的增删改
│   └── DeviceVariableVM  ← 变量的增删改
├── BasePagedListVM<T,S>  ← 列表ViewModel
│   ├── DeviceListVM      ← 设备列表查询
│   ├── DriverListVM      ← 驱动列表查询
│   └── DeviceVariableListVM ← 变量列表查询
└── BaseSearcher          ← 搜索条件ViewModel
    ├── DeviceSearcher    ← 设备搜索条件
    ├── DriverSearcher    ← 驱动搜索条件
    └── DeviceVariableSearcher ← 变量搜索条件
```

#### CRUD ViewModel 示例

```csharp
public class DeviceVM : BaseCRUDVM<Device>
{
    public List<ComboSelectListItem> AllDrivers { get; set; }

    public DeviceVM()
    {
        // 声明加载时需要Include的关联实体
        SetInclude(x => x.Driver);
        SetInclude(x => x.Parent);
    }

    protected override void InitVM()
    {
        // 初始化下拉选项数据
        AllDrivers = DC.Set<Driver>().GetSelectListItems(Wtm, y => y.FileName);
    }

    public override void DoAdd()
    {
        base.DoAdd();
        // 添加设备后，创建驱动配置和采集线程
        if (Entity.DeviceTypeEnum == DeviceTypeEnum.Device)
        {
            var deviceService = Wtm.ServiceProvider.GetService(typeof(DeviceService)) as DeviceService;
            deviceService.DriverManager.AddConfigs(Entity.ID, Entity.DriverId);
            deviceService.CreateDeviceThread(device);
        }
    }
}
```

> **关键点**：`DoAdd` 方法在 `base.DoAdd()` 完成数据库插入后，立即调用 `DeviceService` 创建采集线程。这体现了 ViewModel 层不仅处理数据，还协调运行时状态。

### 第四层：表现层 (IoTGateway Web App)

表现层是应用的入口，包含：

| 组件 | 职责 |
|------|------|
| `Program.cs` | 应用入口，配置WebHost、Kestrel端口 |
| `Startup.cs` | 服务注册、中间件管道配置 |
| Controllers | 路由映射，委托给ViewModel处理 |
| Views | Razor视图，使用LayUI组件渲染 |
| `appsettings.json` | 应用配置 |

#### 应用入口配置

```csharp
public static IHostBuilder CreateWebHostBuilder(string[] args)
{
    return Host.CreateDefaultBuilder(args)
        .ConfigureAppConfiguration((hostingContext, config) =>
        {
            config.AddInMemoryCollection(new Dictionary<string, string>
            {
                { "HostRoot", hostingContext.HostingEnvironment.ContentRootPath }
            });
        })
        .ConfigureWebHostDefaults(webBuilder =>
        {
            webBuilder.UseStartup<Startup>();
            webBuilder.UseKestrel(option =>
            {
                option.ListenAnyIP(1888, l => l.UseMqtt()); // MQTT端口
                option.ListenAnyIP(518);                     // HTTP端口
            });
        })
        .UseNLog();
}
```

### 层间数据流

以"添加新设备"为例，展示完整的层间数据流：

```
1. 用户在Web界面填写设备信息，点击"保存"
   │
   ▼
2. Controller 接收请求，创建 DeviceVM 实例
   │  DeviceVM vm = new DeviceVM();
   │  vm.Entity = 请求数据绑定;
   │
   ▼
3. DeviceVM.DoAdd() 调用基类方法写入数据库
   │  base.DoAdd() → DataContext.Set<Device>().Add()
   │                → DataContext.SaveChanges()
   │
   ▼
4. DeviceVM.DoAdd() 调用 DeviceService 创建采集线程
   │  DeviceService.CreateDeviceThread(device)
   │  → 反射加载驱动DLL → 实例化IDriver
   │  → 创建DeviceThread → 启动采集循环
   │
   ▼
5. Controller 返回成功响应给前端
   │
   ▼
6. DeviceThread 开始轮询读取设备数据
```

### 层间引用规则

严格的层间引用规则是保证架构不腐化的关键：

```
IoTGateway ──────→ IoTGateway.ViewModel ──────→ IoTGateway.DataAccess ──────→ IoTGateway.Model
 (表现层)           (视图模型层)                  (数据访问层)                  (实体模型层)
    │                    │                           │
    │                    │                           │
    └────────────────────┴───────────────────────────┘
              都引用 Model 层（共享实体定义）
```

**禁止的引用方向**：
- Model 层不能引用任何其他层
- DataAccess 层不能引用 ViewModel 或 Web App
- ViewModel 层不能引用 Web App 的 Controller

### 与插件系统的交互

四层架构与插件系统之间有一条清晰的分界线：

```
┌───────────────────────────────┐
│    四层架构（Web管理部分）      │
│  Model → DataAccess →         │
│  ViewModel → Web App          │
│  职责：配置管理、数据查询       │
├───────────────────────────────┤
│    插件系统（运行时部分）       │
│  PluginInterface → Plugin →   │
│  Drivers                        │
│  职责：数据采集、通信调度       │
└───────────────────────────────┘
        │                │
        └──── 共享 Model ────┘
```

两个子系统通过 `IoTGateway.Model` 共享实体定义，通过 `DeviceService`/`MessageService` 等 Singleton 服务实现运行时协调。

### 上位机架构的最佳实践

1. **模型层保持纯净**：实体类不要包含任何业务逻辑，使用 `[NotMapped]` 分离持久化和运行时数据
2. **数据访问层要薄**：EF Core 已经足够强大，不需要再写一层 Repository
3. **ViewModel 承载业务逻辑**：CRUD 操作后的联动逻辑（如创建线程）放在 ViewModel 中
4. **表现层只做路由**：Controller 尽可能薄，把逻辑委托给 ViewModel

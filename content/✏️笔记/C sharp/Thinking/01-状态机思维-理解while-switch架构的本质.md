## 状态机思维——理解 while+switch 架构的本质

### 你遇到的到底是什么

你们项目里的仓储机程序，用的是工业控制领域最经典的架构模式：**轮询式状态机**。它的骨架长这样：

```csharp
while (true)
{
    switch (step)
    {
        case 1000: /* 检查抽屉是否为空 */ break;
        case 1100: /* 扫码 */ break;
        case 1200: /* 吸盘吸取物料 */ break;
        case 1500: /* NG处理 */ break;
        // ...
    }
    Thread.Sleep(50);
}
```

如果你之前学的是Java，习惯的是面向对象那一套——事件驱动、回调、消息队列——看到这种"一个大循环包一个switch"的写法，第一反应会觉得原始、笨重、不好维护。**这个感觉是对的**，它确实不是最优雅的方案，但它在工控领域存活了几十年是有原因的：简单、可控、调试方便。PLC本身就是这么跑的（扫描周期），上位机用同样的模式，两边的思维模型一致，出了问题容易排查。

所以第一步不是否定它，而是**理解它到底在做什么**。

---

### 状态机的本质：一张"流程图"变成了代码

你可以把整个 while+switch 结构理解为：**把一张流程图"铺平"成了代码**。

想象你画了一张入库流程图：

```
开始 → 检查抽屉空？ → 不空则等待 → 空了 → 检查推盒有料？ → 没料则等待 → 有料 → 扫码
  → 扫码成功？ → 是 → 吸盘吸取 → 放入抽屉 → 完成
  → 扫码失败？ → 放入6号推盒 → 完成
```

每个箭头就是一个"步骤跳转"，每个节点就是一个 case。当你在脑子里追踪流程时，你其实是在**沿着这张图走路**。问题是：当流程变复杂（同时有入库和出库、有NG分支、有错误恢复），这张图会变得像一团意大利面，光靠脑子根本记不住。

**这就是你觉得"无法在脑子里形成思维链"的根本原因**——不是你脑子不行，而是这张图的信息量超过了人脑的工作记忆容量（一般人同时追踪 5~7 个节点就已经很吃力了）。

---

### 怎么让状态机在脑子里变清晰

#### 方法一：给步骤编号赋予"语义层级"

你们的步骤编号（1000、1100、1200……）其实已经有这个意图了，但可以更系统化。建议用这样的编号规则：

| 千位 | 百位 | 十位 | 含义 |
|------|------|------|------|
| 1 | - | - | 入库主流程 |
| 2 | - | - | 出库主流程 |
| - | 0 | - | 正常路径 |
| - | 5 | - | NG/异常路径 |
| - | - | 0~9 | 子步骤顺序 |

比如 `case 1050` 一看就是"入库流程的NG分支第5步"。这样你不用记住每个数字代表什么，编号本身就是语义。

#### 方法二：分层思维——不要一次想完所有 case

这是最关键的一点。你的 while+switch 看起来是"扁平"的，但你的思维应该是**分层**的：

**第一层：主流程骨架。** 只关心"入库走哪些大步骤""出库走哪些大步骤"，大概 5~8 个关键节点就够了。

**第二层：每个大步骤内部的细节。** 比如"扫码"这个大步骤里面包含：发指令给扫码枪、等返回、解析结果、判断成功/失败。这些细节你在第一层不需要关心。

**第三层：异常处理和边界情况。** NG抽屉满了怎么办、通信超时怎么办、断电重启怎么办。

当你在脑子里追踪流程时，永远只在当前层思考。就像看一本书，先看目录，再看章节，最后看段落。

#### 方法三：画出"状态转换图"并贴在屏幕旁边

这不是形式主义。准备一张A3纸或者用一个白板软件，把当前项目的状态机画出来：

- 每个 case 是一个方框
- 方框里用一句话写清楚"这一步做什么"
- 箭头标注跳转条件（step = 1200）
- 异常路径用红色箭头

画完之后，你写代码的时候眼睛一扫就知道"当前在图的哪个位置"，不用全靠脑子记。很多资深工控工程师桌上都有这么一张图，这不是水平低，这是专业的表现。

### 从Java思维到状态机思维的转换

你提到你之前学Java，这里帮你做一个对照，可能有助于理解：

| Java世界 | 状态机世界 | 核心区别 |
|----------|-----------|---------|
| 事件驱动（onClick、onMessage） | 轮询驱动（每50ms检查一次） | 触发方式不同 |
| 对象持有状态（成员变量） | 全局变量持有状态（step、标志位） | 状态存放位置不同 |
| 方法调用链（A调B调C） | case跳转（step=1000→1100→1200） | 流程推进方式不同 |
| 异常try-catch | 检查标志位，跳到异常case | 错误处理方式不同 |
| 异步回调 | 在一个case里等待条件满足，不满足就break等下次循环 | 等待方式不同 |

最大的思维转变是：**在状态机里，"等待"不是阻塞，而是"退出本次循环，下次再来检查"。** 每个case执行时间极短，不等待任何IO完成——如果IO没完成，就设置一个中间状态，break出去，下次循环再进来检查。这是和Java里写 `future.get()` 阻塞等待完全不同的思维方式。

理解了这一点，你会发现很多困惑迎刃而解：为什么要有步骤变量、为什么每个case都很短、为什么要反复判断同一个条件——因为整个程序在不断地"快照→检查→推进→快照→检查→推进"。

### 一个实用的心智模型：把自己当成PLC

最后给你一个思维练习。闭上眼睛，想象你自己就是那个PLC。你的世界非常简单：

1. 每过50毫秒，你"醒来"一次
2. 你看一眼"当前步骤号"（step变量）
3. 你根据步骤号，执行对应的一小段动作
4. 你检查一下：这步完了没？完了就改步骤号，跳到下一步；没完就保持不变
5. 你"睡过去"，等50毫秒后再醒来

你没有记忆——每次醒来你唯一知道的就是"现在在第几步"以及"几个关键标志位的值"。所以你写的每一步代码，都必须能从"步骤号+标志位"完全还原当前该做什么。

这个模型也解释了为什么"断步"问题会发生：上微机重启后，步骤号丢了，就像PLC失忆了。解决方案就是把步骤号持久化（写入PLC或者本地文件），下次醒来时恢复。

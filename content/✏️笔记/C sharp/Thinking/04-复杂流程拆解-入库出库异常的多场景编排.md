## 复杂流程拆解——入库/出库/异常的多场景编排

### 你的仓储机到底在做几件事

先把你描述的场景结构化。整个机器从功能角度，其实只做三件事：

**入库（存物料）：** 推盒里的物料 → 扫码 → 扫码成功则吸盘吸取放入抽屉 → 扫码失败则放入6号推盒

**出库（取物料）：** 抽屉里的物料 → 取出 → 放到外部推盒

**异常处理：** NG物料的处理、NG抽屉满了的处理、各种中间态的恢复

之所以你觉得复杂，不是因为单独看哪一条路径难，而是因为这三件事**不是串行发生的**——它们可能同时处于不同的状态，而且会互相影响（比如正在入库的时候，出库请求来了；或者入库扫码失败，需要临时插入一个"放入6号推盒"的子流程）。

### 用"有限状态机"把流程画清楚

下面我用你的实际场景，画一个入库流程的完整状态转换图。你可以把这个当作模板，对照你们项目的代码，看看哪些步骤你实现了，哪些漏了。

#### 入库主流程（正常路径）

```

     │

[检查目标抽屉是否为空]
     │

     │

     │
     ├─ 无物料 → [等待上料] → 循环检查
     │
     ▼ 推盒有料

     │
     ▼
[等待扫码结果]
     │
     ├─ 扫码成功 → [吸盘吸取物料] → [放入抽屉] → [更新抽屉状态] → [完成，回到等待]
     │
     ├─ 扫码失败 → [进入NG流程]
     │
     └─ 扫码超时 → [进入NG流程]
```

#### NG 处理流程（异常路径）

```
[进入NG流程]
     │
     ▼
[检查6号推盒是否已满]
     │
     ├─ 已满 → [报警/等待人工处理] → 循环检查
     │
     ▼ 6号推盒有空间
[将NG物料放入6号推盒]
     │
     ▼
[NG计数+1]
     │
     ▼
[更新6号推盒状态]
     │
     ▼

```

#### 出库主流程（正常路径）

```
[等待出库指令]
     │
     ▼ 收到出库指令（指定抽屉号）
[检查目标抽屉是否有物料]
     │
     ├─ 无物料 → [报警/跳过] → [完成]
     │
     ▼ 抽屉有物料
[吸盘/机构取出物料]
     │
     ▼
[放到指定推盒]
     │
     ▼
[更新抽屉状态为空]
     │
     ▼

```

### 当入库和出库"同时"发生时

你提到"又入库又出库"，这是最让人头疼的场景。在状态机架构下，有几种处理方式：

#### 方案一：串行化——一次只做一件事（推荐新手）

最简单的方式：**排队**。设一个任务队列，入库和出库请求都丢进去，当前任务做完了才取下一个。

```csharp
Queue<TaskRequest> taskQueue = new Queue<TaskRequest>();

// 主循环
while (true)
{
    if (step == 0) // 空闲状态
    {
        if (taskQueue.Count > 0)
        {
            var task = taskQueue.Dequeue();
            if (task.Type == TaskType.Store)
                SetStep(1000); // 进入入库流程
            else if (task.Type == TaskType.Retrieve)
                SetStep(2000); // 进入出库流程
        }
    }
    // ... switch(step) 处理
}
```

好处：逻辑简单，不用考虑入库出库互相干扰。坏处：效率低，入库出库不能并行。

#### 方案二：交错执行——用两组独立的步骤变量

如果你的硬件支持入库和出库同时物理执行（比如不同轴、不同工位），可以用两套独立的步骤变量：

```csharp
int storeStep = 0;    // 入库流程的步骤
int retrieveStep = 0; // 出库流程的步骤

while (true)
{
    // 入库流程推进
    switch (storeStep) { case 1000: ... case 1100: ... }
    
    // 出库流程推进
    switch (retrieveStep) { case 2000: ... case 2100: ... }
    
    Thread.Sleep(50);
}
```

但要注意：**如果两个流程会争抢同一个资源（比如同一个吸盘、同一个抽屉），必须加互斥锁或者调度逻辑。**

#### 方案三：统一编排——把所有任务抽象成"搬运指令"

更高级的做法是：不区分"入库"和"出库"，而是把所有操作抽象成一组"搬运指令"：

```
搬运指令 {
    源位置: "推盒3",
    目标位置: "抽屉2",
    需要扫码: true,
    扫码失败处理: "放入6号推盒"
}
```

这样无论入库还是出库，都是"从A搬到B"，只是A和B不同。状态机只需要一套通用的"搬运流程"，根据指令里的源和目标参数执行不同动作。这是最灵活也最不容易出错的架构，但设计起来需要一定的抽象能力。

### 处理"NG抽屉满"这类边界情况

你提到之前缺了 case 1500（NG抽屉满的处理），这类问题的根源是：**在写代码的时候只想着"正常流程"，忘记了"异常也是有流程的"。**

#### 思维工具：每个动作都要问三个问题

1. **如果这个动作失败了怎么办？**（吸盘吸取失败、扫码失败、通信超时）
2. **如果这个动作的前置条件不满足怎么办？**（抽屉满了、推盒空了、6号推盒满了）
3. **如果这个动作执行到一半突然断电了怎么办？**（吸盘吸到一半、物料在移动途中）

对每个case都做这个"三问"检查，基本上不会漏掉边界情况。

#### 你的 case 1500 问题复盘

原代码从某个步骤跳到了NG处理，但没有处理"NG抽屉已满"的情况，导致流程落入 default 被重置为 0（重新开始）。这就是典型的"异常路径没有闭环"。

正确的做法是给每个异常路径也画上完整的流程图：

```
NG物料产生 → 检查6号推盒 → 未满则放入 → 计数+1 → 继续主流程
                        └→ 已满 → 报警/等待 → 人工清空后 → 放入 → 继续主流程
```

### 你之前重构中几个改进的解读

帮你回顾一下上次重构做了什么，以及为什么这些改进是正确的方向：

**1. 封装 ReadPlcFloat / WritePlcOrder / WritePlcOrderDirect**

把"读写D寄存器+加锁"的细节封装起来，让你在写业务流程时不需要操心互斥锁和地址转换。这就是"分层"思想的体现——底层通信对业务层透明。

**2. WritePlcOrder 写入前校验 D900==2 且 D940==1**

这是一个非常好的防御性编程。在发送指令之前先确认PLC处于可接收状态，避免了"往一个还没准备好的PLC发指令"导致的混乱。而 WritePlcOrderDirect 用于跳过校验的特殊场景（初始指令、错误恢复），这种"正常走校验通道，特殊情况走直连通道"的设计很合理。

**3. ReadPlcFloat 读取前自动备份 D940 到 D950**

这就是前面提到的"断步恢复"基础设施。备份当前PLC状态，这样即使上位机重启，也能通过 TryRecoverStepFromPlcStatus 方法读D950来推断之前执行到哪了。

**4. 修复 NgProductQty 重复计数 bug**

步骤2400和2410各做了一次 `NgProductQty++`，导致一个NG物料被计数两次。这种bug在状态机里非常典型——两个相邻的case之间，有一个"共享的副作用"被重复执行了。解决方法就是确保副作用只在流程中的一个点发生。

### 一个实用的编码规范：每个 case 的"标准模板"

为了减少出错，建议每个case都遵循统一的结构：

```csharp
case 1100: // 扫码
{
    // 1. 入口条件检查（这步能执行吗？）
    if (!IsPlcReady()) break;  // 不满足就等下次循环
    
    // 2. 核心动作（这步做什么？）
    bool scanOk = SendScanCommand();
    
    // 3. 出口分支（做完后去哪？）
    if (scanOk)
        SetStep(1200); // 扫码成功，进入吸取
    else
        SetStep(1500); // 扫码失败，进入NG处理
    
    // 4. 日志
    Log($"case 1100: 扫码结果={scanOk}, 下一步={step}");
    break;
}
```

每个case都有这四个部分，代码的可读性和可维护性会大幅提升，而且你不容易漏掉"做完之后去哪"这个关键问题。

### 最后的建议：不要试图一次写完

面对一个复杂的仓储机程序，最有效的工作方式是**增量开发**：

1. 先把最简单的"正常入库"路径跑通（扫码成功 → 放入抽屉），不做任何异常处理
2. 然后加入"扫码失败 → 放6号推盒"
3. 然后加入"6号推盒满 → 报警等待"
4. 然后加入出库流程
5. 然后加入入库出库并行
6. 然后加入断步恢复
7. 最后加入各种边界情况的处理

每加一层，先测试确认没问题，再加下一层。不要试图在脑子里把整个系统想清楚再动手——没有人能做到这一点，包括写了几十年工控代码的老工程师。

# 01 - 代码坑点与安全隐患

> 本文档系统梳理 RuoYi-Vue 项目中存在的代码坑点与安全隐患，包含具体源码位置、风险分析和修复建议。

---

## 一、空指针风险

### 1.1 SecurityUtils.getLoginUser() 可能返回 null

**查看&剖析点**

`SecurityUtils` 是全局高频使用的工具类，几乎所有需要获取当前登录用户的场景都依赖它。但 `getLoginUser()` 在未登录或 Token 失效时可能抛出异常或返回 null。

**源码关键片段**

文件：`ruoyi-common/src/main/java/com/ruoyi/common/utils/SecurityUtils.java`

```java
public static LoginUser getLoginUser()
{
    try
    {
        return (LoginUser) getAuthentication().getPrincipal();
    }
    catch (Exception e)
    {
        throw new ServiceException("获取用户信息异常", HttpStatus.UNAUTHORIZED);
    }
}

public static Authentication getAuthentication()
{
    return SecurityContextHolder.getContext().getAuthentication();
}
```

**风险分析**

- `getAuthentication()` 返回值可能为 `null`（未经过任何过滤器时），此时调用 `.getPrincipal()` 会抛出 NPE
- 虽然外层有 `try-catch`，但捕获的是 `Exception`，NPE 会被转为 `ServiceException`，这在业务代码中可能被忽略
- `getUserId()`、`getDeptId()`、`getUsername()` 等方法都依赖 `getLoginUser()`，链式调用中任何一环都可能出问题

**修复建议**

```java
public static LoginUser getLoginUser()
{
    Authentication authentication = getAuthentication();
    if (authentication == null || authentication.getPrincipal() == null)
    {
        return null;
    }
    Object principal = authentication.getPrincipal();
    if (principal instanceof LoginUser)
    {
        return (LoginUser) principal;
    }
    return null;
}
```

### 1.2 BaseEntity.getParams() 的 NPE 风险

**查看&剖析点**

`BaseEntity` 是所有实体类的基类，`getParams()` 返回的 `Map` 被广泛用于数据权限拼接、自定义查询参数传递等场景。

**源码关键片段**

文件：`ruoyi-common/src/main/java/com/ruoyi/common/core/domain/BaseEntity.java`

```java
@JsonInclude(JsonInclude.Include.NON_EMPTY)
private Map<String, Object> params;

public Map<String, Object> getParams()
{
    if (params == null)
    {
        params = new HashMap<>();
    }
    return params;
}
```

**风险分析**

- `getParams()` 本身做了懒初始化，不会返回 null，这一点设计是安全的
- 但在 `DataScopeAspect` 中直接调用 `baseEntity.getParams().put(DATA_SCOPE, ...)` 时，如果 `params` 字段被 JSON 反序列化时被忽略（因为 `@JsonInclude(NON_EMPTY)`），前端传来的空 Map 可能导致 `params` 为 null
- 更关键的是，如果子类覆盖了 `getParams()` 方法且未做空判断，就会产生 NPE

### 1.3 DataScopeAspect 中的链式调用风险

**源码关键片段**

文件：`ruoyi-framework/src/main/java/com/ruoyi/framework/aspectj/DataScopeAspect.java`

```java
LoginUser loginUser = SecurityUtils.getLoginUser();
if (StringUtils.isNotNull(loginUser))
{
    SysUser currentUser = loginUser.getUser();
    if (StringUtils.isNotNull(currentUser) && !currentUser.isAdmin())
    {
        // ...
        user.getRoles().forEach(role -> {
            // role.getDataScope() 可能为 null
        });
    }
}
```

**风险分析**

- `loginUser.getUser()` 可能返回 null
- `user.getRoles()` 可能返回 null 或空集合
- `role.getDataScope()` 可能为 null，后续的 `Constants.Dept.DATA_SCOPE_ALL.equals(dataScope)` 虽然是常量在前不会 NPE，但逻辑上可能遗漏

## 二、循环依赖风险

### 2.1 framework 与 system 的模块依赖

**查看&剖析点**

RuoYi 的模块依赖关系为：`ruoyi-admin -> ruoyi-framework -> ruoyi-system -> ruoyi-common`。但 `ruoyi-framework` 中的切面、过滤器等组件需要调用 `ruoyi-system` 中的 Service，这就形成了潜在的循环依赖。

**源码关键片段**

文件：`ruoyi-framework/src/main/java/com/ruoyi/framework/manager/factory/AsyncFactory.java`

```java
public class AsyncFactory
{
    public static TimerTask recordLogininfor(final String username, final String status, final String message,
            final Object... args)
    {
        return new TimerTask()
        {
            @Override
            public void run()
            {
                // 通过 SpringUtils 延迟获取 Bean，避免循环依赖
                SpringUtils.getBean(ISysLogininforService.class).insertLogininfor(logininfor);
            }
        };
    }

    public static TimerTask recordOper(final SysOperLog operLog)
    {
        return new TimerTask()
        {
            @Override
            public void run()
            {
                operLog.setOperLocation(AddressUtils.getRealAddressByIP(operLog.getOperIp()));
                SpringUtils.getBean(ISysOperLogService.class).insertOperlog(operLog);
            }
        };
    }
}
```

**风险分析**

- `AsyncFactory` 位于 `ruoyi-framework` 模块，但它需要使用 `ISysLogininforService` 和 `ISysOperLogService`（属于 `ruoyi-system` 模块）
- 如果直接用 `@Autowired` 注入，会因为 `framework -> system -> framework` 的依赖链导致循环依赖
- 项目通过 `SpringUtils.getBean()` 在运行时延迟获取 Bean 来规避这个问题，这是一种"运行时解决编译时矛盾"的做法

**细节留神**

- `SpringUtils.getBean()` 每次调用都会从 BeanFactory 获取，虽然 Spring 默认是单例所以不会创建新对象，但频繁调用仍有微小开销
- 如果 `SpringUtils` 的 `postProcessBeanFactory` 尚未被调用（上下文未完全初始化），`getBean` 会抛出异常

### 2.2 SpringUtils.getAopProxy 的使用

**源码关键片段**

文件：`ruoyi-system/src/main/java/com/ruoyi/system/service/impl/SysRoleServiceImpl.java`

```java
public List<SysRole> selectRoleAll()
{
    return SpringUtils.getAopProxy(this).selectRoleList(new SysRole());
}
```

文件：`ruoyi-system/src/main/java/com/ruoyi/system/service/impl/SysUserServiceImpl.java`

```java
public void checkUserDataScope(Long userId)
{
    if (!SecurityUtils.isAdmin())
    {
        SysUser user = new SysUser();
        user.setUserId(userId);
        List<SysUser> users = SpringUtils.getAopProxy(this).selectUserList(user);
        if (StringUtils.isEmpty(users))
        {
            throw new ServiceException("没有权限访问用户数据！");
        }
    }
}
```

**风险分析**

- `getAopProxy(this)` 依赖 `AopContext.currentProxy()`，这要求 Spring 配置中开启 `@EnableAspectJAutoProxy(exposeProxy = true)`
- 如果未开启 `exposeProxy`，调用 `getAopProxy()` 会抛出 `IllegalStateException`
- 在 RuoYi 中，`selectRoleAll()` 和 `checkUserDataScope()` 需要通过 AOP 代理调用自身方法，以触发 `@DataScope` 切面

## 三、事务问题

### 3.1 先删后插的事务风险

**查看&剖析点**

用户管理中的新增和修改操作涉及多张关联表的操作，需要事务保证原子性。

**源码关键片段**

文件：`ruoyi-system/src/main/java/com/ruoyi/system/service/impl/SysUserServiceImpl.java`

```java
@Override
@Transactional
public int insertUser(SysUser user)
{
    // 新增用户信息
    int rows = userMapper.insertUser(user);
    // 新增用户岗位关联
    insertUserPost(user);
    // 新增用户与角色管理
    insertUserRole(user);
    return rows;
}

@Override
@Transactional
public int updateUser(SysUser user)
{
    Long userId = user.getUserId();
    // 删除用户与角色关联
    userRoleMapper.deleteUserRoleByUserId(userId);
    // 新增用户与角色管理
    insertUserRole(user);
    // 删除用户与岗位关联
    userPostMapper.deleteUserPostByUserId(userId);
    // 新增用户与岗位管理
    insertUserPost(user);
    return userMapper.updateUser(user);
}
```

**风险分析**

- `insertUser()` 方法标注了 `@Transactional`，如果 `insertUserPost()` 或 `insertUserRole()` 抛出异常，用户主表数据会回滚 -- 这是正确的
- `updateUser()` 采用先删后插策略，如果中间步骤失败，已删除的关联数据会回滚 -- 这也是正确的
- 但 `updateUser()` 中 `userMapper.updateUser(user)` 放在最后，如果前面删除成功但更新失败，虽然事务会回滚，但在大并发下事务持锁时间较长

### 3.2 importUser 缺少事务注解

**源码关键片段**

```java
@Override
public String importUser(List<SysUser> userList, Boolean isUpdateSupport, String operName)
{
    // 注意：此方法没有 @Transactional 注解
    for (SysUser user : userList)
    {
        try
        {
            // ... 逐条插入或更新
            userMapper.insertUser(user);
        }
        catch (Exception e)
        {
            failureNum++;
            // ...
        }
    }
    // ...
}
```

**风险分析**

- `importUser()` 方法没有 `@Transactional` 注解，每个用户的插入/更新是独立事务
- 如果导入 100 条数据，前 50 条成功后系统崩溃，后 50 条不会回滚，导致数据部分导入
- 这是设计选择还是遗漏？从代码中的 `try-catch` 来看，似乎是故意让部分失败不影响其他数据

### 3.3 异步操作不在事务范围内

**源码关键片段**

文件：`ruoyi-framework/src/main/java/com/ruoyi/framework/manager/AsyncManager.java`

```java
public class AsyncManager
{
    private final int OPERATE_DELAY_TIME = 10;
    private ScheduledExecutorService executor = SpringUtils.getBean("scheduledExecutorService");

    public void execute(TimerTask task)
    {
        executor.schedule(task, OPERATE_DELAY_TIME, TimeUnit.MILLISECONDS);
    }
}
```

**风险分析**

- `AsyncManager` 使用独立线程池执行异步任务，不在主事务范围内
- 日志记录失败（如数据库异常）不会影响业务操作的提交
- 但如果异步任务中使用了主事务尚未提交的数据（如新创建的用户ID），可能出现数据不一致

## 四、并发问题

### 4.1 密码错误计数的竞态条件

**查看&剖析点**

密码错误计数使用 Redis 存储，在集群环境下多个实例同时读取和更新计数可能产生竞态条件。

**源码关键片段**

文件：`ruoyi-framework/src/main/java/com/ruoyi/framework/web/service/SysLoginService.java`

```java
public String login(String username, String password, String code, String uuid)
{
    // ...
    try
    {
        authentication = authenticationManager.authenticate(authenticationToken);
    }
    catch (Exception e)
    {
        if (e instanceof BadCredentialsException)
        {
            AsyncManager.me().execute(AsyncFactory.recordLogininfor(username, Constants.LOGIN_FAIL, ...));
            throw new UserPasswordNotMatchException();
        }
    }
    // ...
}
```

**风险分析**

- 密码错误计数在 `SysPasswordService` 中通过 Redis 的 `increment` 操作实现
- 如果使用 `get -> 判断 -> set` 模式而非 Redis 原子操作，在集群环境下可能出现计数不准确
- 限流脚本使用了 Lua 脚本保证原子性（见 `RedisConfig.limitScriptText()`），但密码计数是否也用了原子操作需要确认

### 4.2 防重复提交的并发安全

**源码关键片段**

文件：`ruoyi-framework/src/main/java/com/ruoyi/framework/interceptor/RepeatSubmitInterceptor.java`

```java
@Override
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) throws Exception
{
    if (handler instanceof HandlerMethod)
    {
        HandlerMethod handlerMethod = (HandlerMethod) handler;
        Method method = handlerMethod.getMethod();
        RepeatSubmit annotation = method.getAnnotation(RepeatSubmit.class);
        if (annotation != null)
        {
            if (this.isRepeatSubmit(request, annotation))
            {
                AjaxResult ajaxResult = AjaxResult.error(annotation.message());
                ServletUtils.renderString(response, JSON.toJSONString(ajaxResult));
                return false;
            }
        }
    }
    return true;
}
```

**风险分析**

- 防重复提交基于 Redis 实现，使用 `setIfAbsent`（Redis SETNX）保证原子性
- 在分布式环境下是安全的，但如果 Redis 不可用，防重复提交功能将失效
- 需要确认 `isRepeatSubmit` 的具体实现是否使用了 Redis 原子命令

### 4.3 DataScopeAspect 的 StringBuilder 线程安全

**源码关键片段**

文件：`ruoyi-framework/src/main/java/com/ruoyi/framework/aspectj/DataScopeAspect.java`

```java
public static void dataScopeFilter(JoinPoint joinPoint, SysUser user, ...)
{
    StringBuilder sqlString = new StringBuilder();
    // ...
    for (SysRole role : user.getRoles())
    {
        String dataScope = role.getDataScope();
        // ...
        sqlString.append(StringUtils.format(" OR {}.{} IN (...) ", deptAlias, deptField, ...));
    }
    // ...
    baseEntity.getParams().put(DATA_SCOPE, " AND (" + sqlString.substring(4) + ")");
}
```

**风险分析**

- `StringBuilder` 不是线程安全的，但此处是方法局部变量，每次调用创建新实例，所以没有并发问题
- 但 `baseEntity.getParams()` 返回的是共享的 Map 对象，如果同一个 `BaseEntity` 实例被多个线程同时使用，`put` 操作可能产生并发问题

## 五、安全隐患

### 5.1 JWT 密钥过于简单

**查看&剖析点**

JWT Token 的签名密钥直接硬编码在配置文件中，且使用了极其简单的字符串。

**源码关键片段**

文件：`ruoyi-admin/src/main/resources/application.yml`

```yaml
token:
  header: Authorization
  secret: abcdefghijklmnopqrstuvwxyz
  expireTime: 30
```

**风险分析**

- 密钥 `abcdefghijklmnopqrstuvwxyz` 是连续的英文字母，极易被猜测或暴力破解
- 攻击者一旦获取密钥，可以伪造任意用户的 JWT Token
- 密钥硬编码在配置文件中，如果配置文件泄露（如误提交到 Git），密钥也随之泄露

**修复建议**

```yaml
token:
  secret: ${TOKEN_SECRET:请使用环境变量注入至少32位的随机密钥}
```

### 5.2 数据库密码硬编码

**源码关键片段**

文件：`ruoyi-admin/src/main/resources/application-druid.yml`

```yaml
spring:
    datasource:
        druid:
            master:
                url: jdbc:mysql://localhost:3306/ry-vue?useUnicode=true&characterEncoding=utf8&zeroDateTimeBehavior=convertToNull&useSSL=true&serverTimezone=GMT%2B8
                username: root
                password: 123456
```

**风险分析**

- 数据库密码 `123456` 是最常见弱密码之一
- 使用 `root` 账户连接数据库，权限过大
- 配置文件明文存储，无加密处理

### 5.3 Druid 监控密码硬编码

**源码关键片段**

```yaml
statViewServlet:
    enabled: true
    allow:
    url-pattern: /druid/*
    login-username: ruoyi
    login-password: 123456
```

**风险分析**

- Druid 监控页面使用弱密码 `123456`
- `allow` 白名单为空，意味着所有 IP 都可以访问 Druid 监控页面
- Druid 监控页面暴露了数据库连接信息、SQL 执行记录等敏感信息

### 5.4 Redis 无密码配置

**源码关键片段**

```yaml
spring:
  data:
    redis:
      host: localhost
      port: 6379
      database: 0
      password:
      timeout: 10s
```

**风险分析**

- Redis 未设置密码，任何能访问 Redis 端口的人都可以操作数据
- Redis 中存储了用户登录信息（Token）、验证码、密码错误计数等敏感数据
- 攻击者可以通过 Redis 直接获取或伪造用户 Token

### 5.5 XSS 过滤可通过 excludes 绕过

**源码关键片段**

文件：`ruoyi-common/src/main/java/com/ruoyi/common/filter/XssFilter.java`

```java
public class XssFilter implements Filter
{
    public List<String> excludes = new ArrayList<>();

    private boolean handleExcludeURL(HttpServletRequest request, HttpServletResponse response)
    {
        String url = request.getServletPath();
        String method = request.getMethod();
        // GET DELETE 不过滤
        if (method == null || HttpMethod.GET.matches(method) || HttpMethod.DELETE.matches(method))
        {
            return true;
        }
        return StringUtils.matches(url, excludes);
    }
}
```

配置：

```yaml
xss:
  enabled: true
  excludes: /system/notice
  urlPatterns: /system/*,/monitor/*,/tool/*
```

**风险分析**

- `/system/notice` 路径被排除在 XSS 过滤之外
- GET 和 DELETE 请求完全不过滤 XSS
- `urlPatterns` 只匹配了部分路径，其他路径（如自定义 Controller）不受 XSS 保护
- XSS 过滤仅对参数值进行处理，不处理 Header 中的恶意内容

### 5.6 Druid 监控页面路径暴露

**源码关键片段**

文件：`ruoyi-framework/src/main/java/com/ruoyi/framework/config/SecurityConfig.java`

```java
.authorizeHttpRequests((requests) -> {
    // ...
    .requestMatchers("/swagger-ui.html", "/v3/api-docs/**", "/swagger-ui/**", "/druid/**").permitAll()
    // ...
})
```

**风险分析**

- `/druid/**` 路径被设置为 `permitAll()`，任何人都可以访问
- 虽然 Druid 自身有登录认证，但弱密码等于没有保护
- 生产环境中 Druid 监控页面不应暴露给公网

## 六、大事务风险

### 6.1 用户插入的大事务

**源码关键片段**

文件：`ruoyi-system/src/main/java/com/ruoyi/system/service/impl/SysUserServiceImpl.java`

```java
@Override
@Transactional
public int insertUser(SysUser user)
{
    int rows = userMapper.insertUser(user);      // 用户主表
    insertUserPost(user);                         // 用户-岗位关联表
    insertUserRole(user);                         // 用户-角色关联表
    return rows;
}
```

**风险分析**

- 一个事务中涉及 3 张表的操作（用户表 + 用户岗位关联 + 用户角色关联）
- 如果关联数据量大（如一个用户关联多个角色和岗位），事务持锁时间会更长
- 在高并发场景下，长事务会导致数据库连接被长时间占用

### 6.2 角色批量授权无事务

**源码关键片段**

文件：`ruoyi-system/src/main/java/com/ruoyi/system/service/impl/SysRoleServiceImpl.java`

```java
@Override
public int insertAuthUsers(Long roleId, Long[] userIds)
{
    List<SysUserRole> list = new ArrayList<SysUserRole>();
    for (Long userId : userIds)
    {
        SysUserRole ur = new SysUserRole();
        ur.setUserId(userId);
        ur.setRoleId(roleId);
        list.add(ur);
    }
    return userRoleMapper.batchUserRole(list);
}
```

**风险分析**

- `insertAuthUsers()` 方法没有 `@Transactional` 注解
- 如果批量插入过程中部分失败，可能导致数据不一致
- 虽然使用了 `batchUserRole` 批量操作，但 MyBatis 的批量插入在一条 SQL 中执行，要么全成功要么全失败

## 七、细节留神

1. **SecurityUtils 的异常处理**：所有方法都 catch 了 `Exception`，但将 NPE、ClassCastException 等都统一包装为 `ServiceException("获取用户信息异常")`，丢失了原始异常信息，不利于排查问题。

2. **AsyncFactory 中 ServletUtils.getRequest()**：在异步线程中调用 `ServletUtils.getRequest()` 获取 Request 对象，但此时可能已经脱离了 Servlet 线程的上下文，获取到的可能是 null 或过期的 Request。

3. **DataScopeAspect 的 SQL 拼接**：使用 `StringUtils.format()` 直接拼接 SQL 片段，虽然参数值来自系统内部（角色ID、部门ID等），但拼接方式不够安全，应考虑使用参数化查询。

4. **SysRoleServiceImpl.insertRoleMenu() 中的 NPE**：`role.getMenuIds()` 如果返回 null，`for (Long menuId : role.getMenuIds())` 会抛出 NPE。

5. **TokenService.refreshPermissionByRoleId() 使用 keys 命令**：`redisCache.keys(pattern)` 在生产环境中使用 `KEYS` 命令会阻塞 Redis，应改用 `SCAN`。

## 八、提问方向

1. **SecurityUtils 的 getLoginUser() 在匿名接口（如 @Anonymous 注解标记的接口）中调用会怎样？RuoYi 是如何保证匿名接口不会误调用 SecurityUtils 的？**

2. **AsyncFactory 通过 SpringUtils.getBean() 延迟获取 Bean 来解决循环依赖，这种做法有什么潜在问题？如果 Spring 上下文尚未完全初始化时调用会怎样？**

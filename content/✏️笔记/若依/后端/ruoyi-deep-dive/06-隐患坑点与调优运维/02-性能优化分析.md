# 02 - 性能优化分析

> 本文档深入分析 RuoYi-Vue 项目的性能优化现状，涵盖接口限流、缓存策略、数据库优化、JVM 优化和线程池优化，并提出改进建议。

## 一、接口限流

### 1.1 @RateLimiter 注解实现

**查看&剖析点**

RuoYi 通过自定义 `@RateLimiter` 注解 + AOP 切面实现了基于 Redis 的分布式接口限流。

**源码关键片段**

文件：`ruoyi-common/src/main/java/com/ruoyi/common/annotation/RateLimiter.java`

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RateLimiter
{
    /**
     * 限流key
     */
    public String key() default Constants.RATE_LIMIT_KEY;

    /**
     * 限流时间窗口（单位秒）
     */
    public int time() default 60;

    /**
     * 限流次数
     */
    public int count() default 100;

    /**
     * 限流类型
     */
    public LimitType limitType() default LimitType.GLOBAL;
}
```

文件：`ruoyi-framework/src/main/java/com/ruoyi/framework/aspectj/RateLimiterAspect.java`

```java
@Before("@annotation(rateLimiter)")
public void doBefore(JoinPoint point, RateLimiter rateLimiter) throws Throwable
{
    int time = rateLimiter.time();
    int count = rateLimiter.count();
    String combineKey = getCombineKey(rateLimiter, point);
    List<Object> keys = Collections.singletonList(combineKey);
    try
    {
        Long number = redisTemplate.execute(limitScript, keys, count, time);
        if (StringUtils.isNull(number) || number.intValue() > count)
        {
            throw new ServiceException("访问过于频繁，请稍候再试");
        }
    }
    catch (ServiceException e)
    {
        throw e;
    }
    catch (Exception e)
    {
        throw new RuntimeException("服务器限流异常，请稍候再试");
    }
}
```

**限流 Lua 脚本**

文件：`ruoyi-framework/src/main/java/com/ruoyi/framework/config/RedisConfig.java`

```java
private String limitScriptText()
{
    return "local key = KEYS[1]\n" +
            "local count = tonumber(ARGV[1])\n" +
            "local time = tonumber(ARGV[2])\n" +
            "local current = redis.call('get', key);\n" +
            "if current and tonumber(current) > count then\n" +
            "    return tonumber(current);\n" +
            "end\n" +
            "current = redis.call('incr', key);\n" +
            "if tonumber(current) == 1 then\n" +
            "    redis.call('expire', key, time);\n" +
            "end\n" +
            "return tonumber(current);";
}
```

**现状分析**

- 使用 Redis + Lua 脚本实现，保证了原子性，分布式环境下安全
- 支持两种限流维度：`GLOBAL`（全局限流）和 `IP`（按 IP 限流）
- 默认 60 秒内允许 100 次请求

**改进建议**

1. **令牌桶/漏桶算法**：当前实现是固定窗口计数器，存在窗口边界突刺问题。建议改为滑动窗口或令牌桶算法
2. **限流降级策略**：当前限流直接抛异常，建议增加降级策略（如返回默认值、排队等待）
3. **动态限流配置**：限流阈值硬编码在注解中，建议支持从配置中心动态读取

## 二、缓存策略

### 2.1 Redis 缓存热点数据

**查看&剖析点**

RuoYi 使用 Redis 缓存了以下几类热点数据：

| 缓存 Key | 用途 | 过期策略 |
|---------|------|---------|
| `login_tokens:*` | 用户登录信息 | 30 分钟（自动续期） |
| `sys_config:*` | 系统配置参数 | 永久（手动清除） |
| `sys_dict:*` | 数据字典 | 永久（手动清除） |
| `captcha_codes:*` | 验证码 | 2 分钟 |
| `repeat_submit:*` | 防重复提交 | 10 秒 |
| `rate_limit:*` | 限流计数 | 60 秒 |
| `pwd_err_cnt:*` | 密码错误次数 | 10 分钟 |

**源码关键片段**

**Token 自动续期机制**

文件：`ruoyi-framework/src/main/java/com/ruoyi/framework/web/service/TokenService.java`

```java
public void verifyToken(LoginUser loginUser)
{
    long expireTime = loginUser.getExpireTime();
    long currentTime = System.currentTimeMillis();
    // 距过期不足 20 分钟时自动续期
    if (expireTime - currentTime <= MILLIS_MINUTE_TWENTY)
    {
        refreshToken(loginUser);
    }
}

public void refreshToken(LoginUser loginUser)
{
    loginUser.setLoginTime(System.currentTimeMillis());
    loginUser.setExpireTime(loginUser.getLoginTime() + expireTime * MILLIS_MINUTE);
    String userKey = getTokenKey(loginUser.getToken());
    redisCache.setCacheObject(userKey, loginUser, expireTime, TimeUnit.MINUTES);
}
```

**现状分析**

- 字典和配置数据使用永久缓存，只有通过管理后台手动清除才会刷新
- Token 使用了自动续期机制，用户活跃期间不会过期
- Redis 序列化使用 FastJson2，序列化/反序列化效率较高

**改进建议**

1. **多级缓存**：对字典、配置等极少变化的数据，可增加本地缓存（如 Caffeine）作为一级缓存，Redis 作为二级缓存
2. **缓存预热**：系统启动时主动加载字典和配置数据到 Redis，避免首次查询的延迟
3. **缓存穿透保护**：对查询结果为 null 的数据也进行缓存（设置短过期时间），防止恶意请求穿透到数据库

## 三、数据库优化

### 3.1 Druid 连接池配置

**查看&剖析点**

**源码关键片段**

文件：`ruoyi-admin/src/main/resources/application-druid.yml`

```yaml
spring:
    datasource:
        type: com.alibaba.druid.pool.DruidDataSource
        driverClassName: com.mysql.cj.jdbc.Driver
        druid:
            initialSize: 5
            minIdle: 10
            maxActive: 20
            maxWait: 60000
            connectTimeout: 30000
            socketTimeout: 60000
            timeBetweenEvictionRunsMillis: 60000
            minEvictableIdleTimeMillis: 300000
            maxEvictableIdleTimeMillis: 900000
            validationQuery: SELECT 1 FROM DUAL
            testWhileIdle: true
            testOnBorrow: false
            testOnReturn: false
            filter:
                stat:
                    enabled: true
                    log-slow-sql: true
                    slow-sql-millis: 1000
                    merge-sql: true
```

**现状分析**

- 最大连接数 `maxActive: 20`，对于生产环境可能偏小
- 慢 SQL 阈值设为 1000ms，超过 1 秒的 SQL 会被记录
- 开启了 SQL 合并统计（`merge-sql: true`），相同模板的 SQL 会被合并统计
- 使用 `testWhileIdle` 空闲检测，避免连接失效

**改进建议**

| 参数 | 当前值 | 建议值（生产） | 说明 |
|------|--------|---------------|------|
| initialSize | 5 | 10 | 减少启动时的连接创建开销 |
| minIdle | 10 | 20 | 保持更多空闲连接 |
| maxActive | 20 | 50-100 | 根据并发量调整 |
| maxWait | 60000 | 5000 | 缩短等待超时，快速失败 |
| slow-sql-millis | 1000 | 500 | 更早发现慢 SQL |

### 3.2 PageHelper 分页

**源码关键片段**

文件：`ruoyi-admin/src/main/resources/application.yml`

```yaml
pagehelper:
    helperDialect: mysql
    supportMethodsArguments: true
    params: count=countSql
```

**现状分析**

- 使用 PageHelper 插件实现物理分页，避免全表查询
- `supportMethodsArguments: true` 支持通过方法参数自动分页
- `params: count=countSql` 优化了 count 查询

**改进建议**

1. **大数据量分页优化**：深度分页（如 offset 超过 10 万）时，`LIMIT offset, size` 性能急剧下降。建议使用游标分页或基于索引的子查询优化
2. **count 优化**：对于不需要总数的场景（如无限滚动加载），可配置 `pagehelper.count=false` 跳过 count 查询

### 3.3 SQL 注入防护

**源码关键片段**

文件：`ruoyi-common/src/main/java/com/ruoyi/common/utils/sql/SqlUtil.java`

```java
public static String SQL_REGEX = "...|and |extractvalue|updatexml|sleep|information_schema|exec |insert |select |delete |update |drop |count |chr |mid |master |truncate |char |declare |or |union |like |+|/*|user()";

public static String SQL_PATTERN = "[a-zA-Z0-9_\\ \\,\\.]+";

public static String escapeOrderBySql(String value)
{
    if (StringUtils.isNotEmpty(value) && !isValidOrderBySql(value))
    {
        throw new UtilException("参数不符合规范，不能进行查询");
    }
    if (StringUtils.length(value) > ORDER_BY_MAX_LENGTH)
    {
        throw new UtilException("参数已超过最大限制，不能进行查询");
    }
    return value;
}
```

**现状分析**

- `orderBy` 参数通过正则白名单验证，只允许字母、数字、下划线、空格、逗号、小数点
- SQL 关键字黑名单过滤，防止 SQL 注入
- 限制 `orderBy` 参数最大长度为 500 字符

**改进建议**

1. **SQL_PATTERN 过于宽松**：允许任意字母数字组合，攻击者可能通过字段名注入。建议维护一个允许排序的字段白名单
2. **filterKeyword 误报**：正常数据中包含 "select"、"user" 等词会被误拦截，建议结合上下文判断

## 四、JVM 优化

### 4.1 当前 JVM 配置

**查看&剖析点**

RuoYi 项目没有自定义 JVM 启动参数，使用 Spring Boot 默认配置。

**现状分析**

Spring Boot 默认 JVM 参数：
- 堆内存：根据机器内存自动分配（通常为物理内存的 1/4）
- GC 算法：JDK 8 默认 Parallel GC，JDK 11+ 默认 G1 GC
- Metaspace：默认无上限（仅受物理内存限制）
- 线程栈大小：默认 1MB

**改进建议**

```bash
# 生产环境推荐 JVM 参数（4C8G 服务器）
java -Xms2g -Xmx2g \
     -XX:MetaspaceSize=256m -XX:MaxMetaspaceSize=512m \
     -XX:+UseG1GC \
     -XX:MaxGCPauseMillis=200 \
     -XX:+HeapDumpOnOutOfMemoryError \
     -XX:HeapDumpPath=/home/ruoyi/logs/heapdump.hprof \
     -Xlog:gc*:file=/home/ruoyi/logs/gc.log:time,tags:filecount=5,filesize=50m \
     -jar ruoyi-admin.jar
```

### 4.2 OOM 排查要点

**常见 OOM 场景**

| 场景 | 原因 | 排查方式 |
|------|------|---------|
| Java Heap Space | 内存泄漏或堆内存不足 | HeapDump + MAT 分析 |
| Metaspace | 动态类加载过多 | 检查 ClassLoader 泄漏 |
| Direct Buffer Memory | NIO DirectByteBuffer 泄漏 | 检查 Netty/Druid 配置 |
| unable to create new native thread | 线程数超限 | 检查线程池配置 |

**RuoYi 特有的 OOM 风险**

1. **Druid 连接泄漏**：如果代码中获取了连接但未正确关闭，连接池会被耗尽
2. **Redis 大对象**：`LoginUser` 对象包含完整的用户信息和权限列表，在线用户量大时 Redis 内存占用高
3. **Excel 导入导出**：大量数据的 Excel 操作可能占用大量内存

## 五、线程池优化

### 5.1 线程池配置

**查看&剖析点**

**源码关键片段**

文件：`ruoyi-framework/src/main/java/com/ruoyi/framework/config/ThreadPoolConfig.java`

```java
@Configuration
public class ThreadPoolConfig
{
    private int corePoolSize = 50;
    private int maxPoolSize = 200;
    private int queueCapacity = 1000;
    private int keepAliveSeconds = 300;

    @Bean(name = "threadPoolTaskExecutor")
    public ThreadPoolTaskExecutor threadPoolTaskExecutor()
    {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setMaxPoolSize(maxPoolSize);
        executor.setCorePoolSize(corePoolSize);
        executor.setQueueCapacity(queueCapacity);
        executor.setKeepAliveSeconds(keepAliveSeconds);
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        return executor;
    }

    @Bean(name = "scheduledExecutorService")
    protected ScheduledExecutorService scheduledExecutorService()
    {
        return new ScheduledThreadPoolExecutor(corePoolSize,
            BasicThreadFactory.builder().namingPattern("schedule-pool-%d").daemon(true).build(),
            new ThreadPoolExecutor.CallerRunsPolicy())
        {
            @Override
            protected void afterExecute(Runnable r, Throwable t)
            {
                super.afterExecute(r, t);
                Threads.printException(r, t);
            }
        };
    }
}
```

**现状分析**

- **threadPoolTaskExecutor**：核心 50 / 最大 200 / 队列 1000
  - 理论最大并发：200 个线程 + 1000 个排队 = 1200 个任务
  - 拒绝策略：`CallerRunsPolicy`（由调用线程执行，不丢弃任务）
- **scheduledExecutorService**：核心 50 的定时任务线程池
  - 使用守护线程（daemon=true），不会阻止 JVM 关闭
  - 重写了 `afterExecute` 方法，打印任务异常信息

**改进建议**

1. **线程命名**：`threadPoolTaskExecutor` 未设置线程命名前缀，排查问题时难以区分线程来源。建议添加：
   ```java
   executor.setThreadNamePrefix("async-pool-");
   ```

2. **核心线程数过大**：50 个核心线程对于一般业务系统偏多。建议根据 CPU 核数调整：
   ```java
   // CPU 密集型：核心线程数 = CPU 核数 + 1
   // IO 密集型：核心线程数 = CPU 核数 * 2
   private int corePoolSize = Runtime.getRuntime().availableProcessors() * 2;
   ```

3. **队列容量过大**：1000 的队列容量意味着任务可能在队列中等待很长时间。建议配合监控告警。

4. **线程池监控**：建议暴露线程池指标（活跃线程数、队列大小、已完成任务数等）到监控系统。

### 5.2 异步任务管理器

**源码关键片段**

文件：`ruoyi-framework/src/main/java/com/ruoyi/framework/manager/AsyncManager.java`

```java
public class AsyncManager
{
    private final int OPERATE_DELAY_TIME = 10;
    private ScheduledExecutorService executor = SpringUtils.getBean("scheduledExecutorService");

    private AsyncManager(){}

    private static AsyncManager me = new AsyncManager();

    public static AsyncManager me()
    {
        return me;
    }

    public void execute(TimerTask task)
    {
        executor.schedule(task, OPERATE_DELAY_TIME, TimeUnit.MILLISECONDS);
    }
}
```

**现状分析**

- 使用单例模式，全局共享一个 `AsyncManager` 实例
- 延迟 10ms 执行任务，主要是为了快速返回响应
- 使用 `ScheduledExecutorService` 而非 `ThreadPoolTaskExecutor`，任务以定时调度方式执行

**风险分析**

- `AsyncManager` 的构造方式是饿汉式单例（静态字段直接 new），但 `executor` 字段通过 `SpringUtils.getBean()` 获取，如果 Spring 上下文未就绪就调用会抛异常
- 所有异步任务（日志记录、登录信息记录）共用一个线程池，日志积压可能影响其他异步任务

- IP 归属地查询是外部调用（可能访问在线 API），如果 API 响应慢，会占用线程池线程

3. **失败重试/降级**：IP 查询失败时不应影响日志记录

## 七、细节留神

1. **RateLimiterAspect 的异常处理**：Redis 不可用时抛出 `RuntimeException("服务器限流异常")`，这会导致所有接口不可用。建议降级为不限流而非直接报错。

2. **Redis 序列化方式**：使用 FastJson2 序列化 `LoginUser` 对象，如果 `LoginUser` 类结构变更（如新增/删除字段），可能导致反序列化失败。

3. **PageHelper 的 count 优化**：当前配置 `params: count=countSql`，PageHelper 会生成优化的 count SQL，但对于复杂查询（多表 join + 子查询），count 查询可能比数据查询更慢。

4. **Druid 的 wall filter**：配置了 `multi-statement-allow: true`，允许多条 SQL 语句执行，这增加了 SQL 注入的风险。

5. **ScheduledExecutorService 使用 daemon 线程**：守护线程在所有非守护线程结束后会被强制终止，如果 JVM 退出时有正在执行的日志记录任务，这些任务可能丢失。

## 八、提问方向

1. **RateLimiter 使用固定窗口计数器算法，在窗口边界时刻可能出现什么问题？如何用 Redis 实现滑动窗口限流？**

2. **RuoYi 的字典和配置数据使用永久缓存策略，如果管理员修改了配置但忘记清除缓存，会导致什么问题？如何实现自动刷新机制？**

3. **Druid 连接池的 maxActive 设为 20，在高并发场景下（如 100 个并发请求），连接等待超时后会发生什么？如何根据业务量合理设置连接池参数？**

4. **AsyncManager 中 IP 归属地查询（AddressUtils.getRealAddressByIP）是在异步线程中执行的，如果这个外部 API 响应需要 2 秒，对线程池的影响是什么？**

5. **TokenService.verifyToken() 在每次请求中都会检查 Token 是否需要续期，当并发请求量很大时（如 QPS 1000），Redis 的续期操作会成为瓶颈吗？**

6. **ThreadPoolConfig 中 scheduledExecutorService 的核心线程数为 50，但实际使用场景主要是日志记录和定时任务，50 个线程是否过多？如何评估合理的线程数？**

7. **PageHelper 在深度分页场景下（如查询第 100 万条数据），MySQL 的 LIMIT offset, size 为什么会变慢？如何优化？**

8. **RuoYi 使用 FastJson2 作为 Redis 的序列化方案，相比 JDK 序列化和 Jackson，FastJson2 在序列化效率和安全性方面有什么优劣？**

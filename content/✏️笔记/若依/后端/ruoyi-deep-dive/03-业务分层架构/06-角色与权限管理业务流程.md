# 06 - 角色与权限管理业务流程

> 本文档深入剖析 RuoYi-Vue 角色与权限管理模块的完整业务流程，涵盖角色 CRUD、菜单权限分配、数据权限设置、用户授权/取消授权的全链路分析。

---

## 一、模块概览

角色与权限管理是 RuoYi-Vue 权限体系的核心，实现了 **RBAC（Role-Based Access Control，基于角色的访问控制）** 模型。

### 1.1 核心表结构

```
sys_role          - 角色表（角色基本信息 + 数据权限配置）
sys_role_menu     - 角色-菜单关联表（菜单权限分配）
sys_role_dept     - 角色-部门关联表（数据权限-自定义部门）
sys_user_role     - 用户-角色关联表（用户角色授权）
sys_menu          - 菜单表（权限标识定义）
sys_dept          - 部门表（组织架构）
```

### 1.2 权限模型关系

```
用户(User) ──N:N── 角色(Role) ──N:N── 菜单(Menu)    ← 功能权限（能访问什么）
                      │
                      └──N:N── 部门(Dept)              ← 数据权限（能看什么数据）
```

### 1.3 三层调用链

```
SysRoleController (ruoyi-admin)
    │
    ├─ ISysRoleService (ruoyi-system/service)
    │      └─ SysRoleServiceImpl (ruoyi-system/service/impl)
    │            ├─ SysRoleMapper
    │            ├─ SysRoleMenuMapper
    │            ├─ SysRoleDeptMapper
    │            └─ SysUserRoleMapper
    │
    ├─ ISysUserService (用户授权相关)
    ├─ ISysDeptService (部门树相关)
    ├─ TokenService (权限刷新)
    └─ SysPermissionService (权限计算)
```

### 2.2 新增角色

```
前端 POST /system/role  Body: { roleName, roleKey, roleSort, status, menuIds }
    │
    ▼
SysRoleController.add(@Validated @RequestBody SysRole role)
    │
    ├─ 1. @PreAuthorize("@ss.hasPermi('system:role:add')")
    ├─ 2. @Validated JSR-303 校验
    ├─ 3. roleService.checkRoleNameUnique(role)        [角色名唯一性]
    ├─ 4. roleService.checkRoleKeyUnique(role)          [角色标识唯一性]
    ├─ 5. role.setCreateBy(getUsername())
    └─ 6. roleService.insertRole(role)
         │
         ▼
    SysRoleServiceImpl.insertRole(SysRole role)
         → @Transactional
         → roleMapper.insertRole(role)                   [插入角色主表]
         → insertRoleMenu(role)                           [插入角色-菜单关联]
              → roleMenuMapper.batchRoleMenu(list)
```

**源码引用：**

```java
// Controller 层
@PreAuthorize("@ss.hasPermi('system:role:add')")
@Log(title = "角色管理", businessType = BusinessType.INSERT)
@PostMapping
public AjaxResult add(@Validated @RequestBody SysRole role) {
    if (!roleService.checkRoleNameUnique(role)) {
        return error("新增角色'" + role.getRoleName() + "'失败，角色名称已存在");
    }
    else if (!roleService.checkRoleKeyUnique(role)) {
        return error("新增角色'" + role.getRoleName() + "'失败，角色权限已存在");
    }
    role.setCreateBy(getUsername());
    return toAjax(roleService.insertRole(role));
}

// Service 层
@Override
@Transactional
public int insertRole(SysRole role) {
    roleMapper.insertRole(role);
    return insertRoleMenu(role);
}

// Service 层 - 插入角色菜单关联
public int insertRoleMenu(SysRole role) {
    int rows = 1;
    List<SysRoleMenu> list = new ArrayList<SysRoleMenu>();
    for (Long menuId : role.getMenuIds()) {
        SysRoleMenu rm = new SysRoleMenu();
        rm.setRoleId(role.getRoleId());
        rm.setMenuId(menuId);
        list.add(rm);
    }
    if (list.size() > 0) {
        rows = roleMenuMapper.batchRoleMenu(list);
    }
    return rows;
}
```

### 2.3 修改角色

```
前端 PUT /system/role  Body: { roleId, roleName, roleKey, ..., menuIds }
    │
    ▼
SysRoleController.edit(@Validated @RequestBody SysRole role)
    │
    ├─ 1. @PreAuthorize("@ss.hasPermi('system:role:edit')")
    ├─ 2. roleService.checkRoleAllowed(role)              [不允许修改管理员角色]
    ├─ 3. roleService.checkRoleDataScope(role.getRoleId()) [数据权限]
    ├─ 4. 唯一性校验
    ├─ 5. role.setUpdateBy(getUsername())
    └─ 6. roleService.updateRole(role)
         │
         ▼
    SysRoleServiceImpl.updateRole(SysRole role)
         → @Transactional
         → roleMapper.updateRole(role)                    [更新角色主表]
         → roleMenuMapper.deleteRoleMenuByRoleId(roleId)  [删除旧菜单关联]
         → insertRoleMenu(role)                             [插入新菜单关联]
    │
    ▼
    ★ 关键步骤：刷新在线用户权限
    → tokenService.refreshPermissionByRoleId(role.getRoleId(), permissionService)
    → 扫描 Redis 中所有在线 Token
    → 找到持有该角色的用户
    → 重新计算权限并更新 Redis 缓存
```

**源码引用（权限刷新）：**

```java
// Controller 层 - 修改角色后刷新权限
if (roleService.updateRole(role) > 0) {
    tokenService.refreshPermissionByRoleId(role.getRoleId(), permissionService);
    return success();
}

// TokenService - 刷新持有该角色的在线用户权限
public void refreshPermissionByRoleId(Long roleId, SysPermissionService permissionService) {
    String pattern = CacheConstants.LOGIN_TOKEN_KEY + "*";
    Collection<String> keys = redisCache.keys(pattern);
    for (String key : keys) {
        LoginUser loginUser = redisCache.getCacheObject(key);
        if (loginUser == null || loginUser.getUser().isAdmin()) continue;
        boolean hasRole = loginUser.getUser().getRoles() != null
            && loginUser.getUser().getRoles().stream()
                .anyMatch(r -> roleId.equals(r.getRoleId()));
        if (!hasRole) continue;
        loginUser.setPermissions(permissionService.getMenuPermission(loginUser.getUser()));
        refreshToken(loginUser);
    }
}
```

### 2.4 删除角色

```
前端 DELETE /system/role/1,2,3
    │
    ▼
SysRoleController.remove(@PathVariable Long[] roleIds)
    → roleService.deleteRoleByIds(roleIds)
    │
    ▼
SysRoleServiceImpl.deleteRoleByIds(Long[] roleIds)
    → @Transactional
```

## 三、菜单权限分配流程

### 3.1 权限分配原理

RuoYi-Vue 的菜单权限通过 `sys_role_menu` 关联表实现。每个菜单项对应一个权限标识（permission 字段），如 `system:user:list`、`system:user:add`。

```
角色(roleId=2) ──→ 菜单权限分配
    ├─ menuId=1 (系统管理)        permission=null (目录)
    ├─ menuId=100 (用户管理)     permission=null (菜单)
    ├─ menuId=1001 (用户查询)    permission=system:user:list
    ├─ menuId=1002 (用户新增)    permission=system:user:add
    ├─ menuId=1003 (用户修改)    permission=system:user:edit
    └─ menuId=1004 (用户删除)    permission=system:user:remove
```

### 3.2 分配流程

菜单权限分配在新增/修改角色时一并完成：

```
1. 前端传递 menuIds 数组（选中的菜单ID列表，包含目录、菜单、按钮）
2. Service 层遍历 menuIds，构建 SysRoleMenu 列表
3. 先删除旧的角色-菜单关联
4. 批量插入新的角色-菜单关联
```

### 3.3 权限验证流程

```
1. 用户登录后，SysPermissionService.getMenuPermission(user) 计算用户权限集合
2. 遍历用户的所有角色 → 获取每个角色的菜单 → 提取 permission 字段
3. 权限集合存入 LoginUser.permissions
4. 缓存到 Redis
5. 每次请求时，@PreAuthorize("@ss.hasPermi('xxx')") 从 LoginUser 中校验权限
```

## 四、数据权限设置流程

### 4.1 数据权限级别

| dataScope | 值 | 含义 | SQL 效果 |
|-----------|---|------|---------|
| DATA_SCOPE_ALL | 1 | 全部数据权限 | 无额外条件 |
| DATA_SCOPE_CUSTOM | 2 | 自定义数据权限 | 通过 sys_role_dept 指定部门 |
| DATA_SCOPE_DEPT | 3 | 本部门数据权限 | 只看本部门 |
| DATA_SCOPE_DEPT_AND_CHILD | 4 | 本部门及以下 | 看本部门+子部门 |
| DATA_SCOPE_SELF | 5 | 仅本人数据权限 | 只看自己的数据 |

### 4.2 设置数据权限流程

```
前端 PUT /system/role/dataScope  Body: { roleId, dataScope, deptIds }
    │
    ▼
SysRoleController.dataScope(@RequestBody SysRole role)
    → @PreAuthorize("@ss.hasPermi('system:role:edit')")
    → @Log(title = "角色管理", businessType = BusinessType.UPDATE)
    → roleService.checkRoleAllowed(role)                    [不允许操作管理员]
    → roleService.checkRoleDataScope(role.getRoleId())
    → roleService.authDataScope(role)
    │
    ▼
SysRoleServiceImpl.authDataScope(SysRole role)
    → @Transactional
    → roleMapper.updateRole(role)                           [更新角色主表的dataScope字段]
    → roleDeptMapper.deleteRoleDeptByRoleId(roleId)         [删除旧部门关联]
    → insertRoleDept(role)                                   [插入新部门关联]
         → 遍历 deptIds，构建 SysRoleDept 列表
         → roleDeptMapper.batchRoleDept(list)
```

**源码引用：**

```java
// Controller 层
@PreAuthorize("@ss.hasPermi('system:role:edit')")
@Log(title = "角色管理", businessType = BusinessType.UPDATE)
@PutMapping("/dataScope")
public AjaxResult dataScope(@RequestBody SysRole role) {
    roleService.checkRoleAllowed(role);
    roleService.checkRoleDataScope(role.getRoleId());
    return toAjax(roleService.authDataScope(role));
}

// Service 层
@Override
@Transactional
public int authDataScope(SysRole role) {
    roleMapper.updateRole(role);
    roleDeptMapper.deleteRoleDeptByRoleId(role.getRoleId());
    return insertRoleDept(role);
}

// Service 层 - 插入角色部门关联
public int insertRoleDept(SysRole role) {
    int rows = 1;
    List<SysRoleDept> list = new ArrayList<SysRoleDept>();
    for (Long deptId : role.getDeptIds()) {
        SysRoleDept rd = new SysRoleDept();
        rd.setRoleId(role.getRoleId());
        rd.setDeptId(deptId);
        list.add(rd);
    }
    if (list.size() > 0) {
        rows = roleDeptMapper.batchRoleDept(list);
    }
    return rows;
}
```

### 4.3 数据权限生效机制

```
1. 角色的 dataScope 字段存储在 sys_role 表中
2. 用户查询数据时，Service 层方法标注 @DataScope
3. DataScopeAspect 切面读取用户角色的 dataScope
4. 根据 dataScope 值动态拼接 SQL 条件
5. SQL 条件通过 ${params.dataScope} 注入到 Mapper XML
6. MyBatis 执行带数据权限条件的 SQL
```

## 六、角色修改后权限刷新机制

这是 RuoYi-Vue 权限系统的一个重要设计亮点。

### 6.1 刷新流程图

```
角色修改完成
    │
    ▼
tokenService.refreshPermissionByRoleId(roleId, permissionService)
    │
    ├─ 1. 扫描 Redis 中所有登录 Token (LOGIN_TOKEN_KEY + "*")
    │
    ├─ 2. 遍历每个 Token 对应的 LoginUser
    │     ├─ 跳过管理员（管理员拥有所有权限）
    │     └─ 判断该用户是否持有被修改的角色
    │
    ├─ 3. 如果持有该角色
    │     ├─ permissionService.getMenuPermission(user)  [重新计算权限集合]
    │     ├─ loginUser.setPermissions(permissions)       [更新权限]
    │     └─ refreshToken(loginUser)                      [刷新Redis缓存]
    │
    └─ 4. 记录日志：角色[xxx]权限变更，已刷新在线用户[xxx]的权限缓存
```

### 6.2 源码引用

```java
// 文件：ruoyi-framework/.../TokenService.java
public void refreshPermissionByRoleId(Long roleId, SysPermissionService permissionService) {
    String pattern = CacheConstants.LOGIN_TOKEN_KEY + "*";
    Collection<String> keys = redisCache.keys(pattern);
    if (keys == null || keys.isEmpty()) {
        return;
    }
    for (String key : keys) {
        LoginUser loginUser = redisCache.getCacheObject(key);
        if (loginUser == null || loginUser.getUser() == null || loginUser.getUser().isAdmin()) {
            continue;  // 管理员跳过
        }
        boolean hasRole = loginUser.getUser().getRoles() != null
            && loginUser.getUser().getRoles().stream()
                .anyMatch(r -> roleId.equals(r.getRoleId()));
        if (!hasRole) {
            continue;  // 不持有该角色则跳过
        }
        loginUser.setPermissions(permissionService.getMenuPermission(loginUser.getUser()));
        refreshToken(loginUser);
        log.info("角色[{}]权限变更，已刷新在线用户[{}]的权限缓存", roleId, loginUser.getUsername());
    }
}
```

## 八、细节留神

1. **修改角色后会刷新所有在线用户的权限**：`tokenService.refreshPermissionByRoleId()` 会扫描 Redis 中所有 Token，这在用户量很大时可能有性能影响
2. **数据权限和菜单权限是两个独立的概念**：菜单权限控制"能做什么"（通过 sys_role_menu），数据权限控制"能看到什么数据"（通过 sys_role.dataScope + sys_role_dept）
3. **删除角色前检查是否已分配用户**：`countUserRoleByRoleId(roleId) > 0` 时抛出异常，防止误删已使用的角色
4. **超级管理员角色不可操作**：`checkRoleAllowed` 方法检查 `role.isAdmin()`，admin 角色的修改和删除被禁止
5. **角色数据权限校验使用 AOP 代理**：`checkRoleDataScope` 中 `SpringUtils.getAopProxy(this).selectRoleList(role)` 确保数据权限切面生效

## 九、提问方向

1. **RuoYi-Vue 的角色修改后会通过 `refreshPermissionByRoleId` 刷新所有在线用户的权限缓存。如果系统有 10000 个在线用户，这个操作会很慢。有什么优化方案？是否可以改为"懒刷新"（用户下次请求时再刷新）？**

2. **数据权限的 5 种级别中，如果一个用户有多个角色，每个角色的 dataScope 不同（如角色A是"本部门"，角色B是"全部数据"），DataScopeAspect 是如何处理这种冲突的？最终用户能看到哪些数据？**

3. **菜单权限分配时，前端传递的 menuIds 包含目录、菜单和按钮三种类型的 ID。为什么需要把目录和菜单的 ID 也存入 sys_role_menu？如果只存按钮级别的权限标识，会有什么问题？**

4. **取消用户授权时，直接从 sys_user_role 中删除记录。如果该用户只有一个角色，取消后用户将没有任何角色和权限。这种设计是否合理？是否应该有"至少保留一个角色"的保护机制？**

5. **角色删除时检查 `countUserRoleByRoleId` 防止删除已分配的角色，但这个检查在 Service 层。如果前端绕过这个检查直接调用 Mapper 的 deleteRoleById，是否还能保护？**

6. **`checkRoleDataScope` 方法中遍历每个 roleId 并通过 AOP 代理查询角色列表来校验数据权限。如果传入的 roleIds 数量很大（如 100 个），会产生多少次数据库查询？如何优化？**

7. **新增角色时，角色主表插入和角色-菜单关联插入在同一个事务中。如果角色主表插入成功但菜单关联插入失败，事务回滚后角色ID还会被占用吗？为什么？**

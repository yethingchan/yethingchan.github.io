# 04 - 数据权限实现原理

## 一、概述

若依框架的数据权限（Data Scope）是基于AOP切面 + SQL拼接实现的行级数据访问控制。通过`@DataScope`注解标记需要数据权限过滤的Service方法，切面在方法执行前根据当前用户的角色数据范围动态拼接SQL条件，注入到MyBatis的查询条件中，实现对不同用户展示不同数据范围的效果。

---

## 二、查看与剖析点

### 2.1 核心文件清单

| 文件路径 | 作用 |
|---------|------|
| `ruoyi-framework/.../aspectj/DataScopeAspect.java` | 数据权限切面，核心SQL拼接逻辑 |
| `ruoyi-common/.../annotation/DataScope.java` | 数据权限注解定义 |
| `ruoyi-common/.../constant/Constants.java` | 数据范围常量（Dept内部类） |
| `ruoyi-common/.../core/domain/BaseEntity.java` | 基础实体类，包含params Map |
| `ruoyi-system/.../mapper/xml/SysUserMapper.xml` | 用户查询SQL，引用dataScope参数 |
| `ruoyi-system/.../mapper/xml/SysRoleMapper.xml` | 角色查询SQL，引用dataScope参数 |

### 2.2 数据权限五种范围

| 编码 | 名称 | 说明 | SQL效果 |
|------|------|------|---------|
| 1 | 全部数据权限 | 查看所有数据 | 无额外条件 |
| 2 | 自定义数据权限 | 查看指定部门数据 | `dept_id IN (SELECT dept_id FROM sys_role_dept WHERE role_id = ?)` |
| 3 | 本部门数据权限 | 仅查看本部门 | `dept_id = {当前用户部门ID}` |
| 4 | 本部门及以下数据权限 | 查看本部门及子部门 | `dept_id IN (SELECT dept_id FROM sys_dept WHERE dept_id = ? or find_in_set(?, ancestors))` |
| 5 | 仅本人数据权限 | 仅查看自己的数据 | `user_id = {当前用户ID}` |

## 三、源码关键片段引用

### 3.1 @DataScope 注解定义

> 源码位置：`ruoyi-common/src/main/java/com/ruoyi/common/annotation/DataScope.java`

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
@Documented
public @interface DataScope
{
    /** 用户表的别名 */
    public String userAlias() default "";
    /** 部门表的别名 */
    public String deptAlias() default "";
    /** 用户字段名 */
    public String userField() default "user_id";
    /** 部门字段名 */
    public String deptField() default "dept_id";
    /** 权限字符（用于多个角色匹配符合要求的权限） */
    public String permission() default "";
}
```

**剖析要点：**
- `userAlias`/`deptAlias`：SQL中用户表和部门表的别名，用于拼接条件
- `userField`/`deptField`：指定过滤使用的字段名，默认为`user_id`和`dept_id`
- `permission`：权限字符，用于多角色场景下匹配符合要求的权限

**使用示例：**

```java
@DataScope(deptAlias = "d", userAlias = "u")
public List<SysUser> selectUserList(SysUser user);

@DataScope(deptAlias = "d")
public List<SysRole> selectRoleList(SysRole role);
```

### 3.2 DataScopeAspect - 核心切面

> 源码位置：`ruoyi-framework/src/main/java/com/ruoyi/framework/aspectj/DataScopeAspect.java`

```java
@Aspect
@Component
public class DataScopeAspect
{
    public static final String DATA_SCOPE = "dataScope";

    @Before("@annotation(controllerDataScope)")
    public void doBefore(JoinPoint point, DataScope controllerDataScope) throws Throwable
    {
        clearDataScope(point);
        handleDataScope(point, controllerDataScope);
    }

    protected void handleDataScope(final JoinPoint joinPoint, DataScope controllerDataScope)
    {
        LoginUser loginUser = SecurityUtils.getLoginUser();
        if (StringUtils.isNotNull(loginUser))
        {
            SysUser currentUser = loginUser.getUser();
            // 如果是超级管理员，则不过滤数据
            if (StringUtils.isNotNull(currentUser) && !currentUser.isAdmin())
            {
                String permission = StringUtils.defaultIfEmpty(controllerDataScope.permission(), PermissionContextHolder.getContext());
                dataScopeFilter(joinPoint, currentUser, controllerDataScope.userAlias(), controllerDataScope.deptAlias(), controllerDataScope.userField(), controllerDataScope.deptField(), permission);
            }
        }
    }
}
```

**剖析要点：**
- 使用`@Before`前置通知，在方法执行前拼接SQL条件
- 超级管理员（admin）跳过数据权限过滤
- `clearDataScope`先清空params中的dataScope，防止SQL注入
- `permission`优先使用注解配置，其次使用`PermissionContextHolder`上下文

### 3.3 dataScopeFilter - SQL拼接核心逻辑

```java
public static void dataScopeFilter(JoinPoint joinPoint, SysUser user, String userAlias, String deptAlias, String userField, String deptField, String permission)
{
    StringBuilder sqlString = new StringBuilder();
    List<String> conditions = new ArrayList<String>();
    List<String> scopeCustomIds = new ArrayList<String>();

    // 先收集所有自定义数据权限的角色ID
    user.getRoles().forEach(role -> {
        if (Constants.Dept.DATA_SCOPE_CUSTOM.equals(role.getDataScope()) && StringUtils.equals(role.getStatus(), UserConstants.ROLE_NORMAL)
            && (StringUtils.isEmpty(permission) || StringUtils.containsAny(role.getPermissions(), Convert.toStrArray(permission))))
        {
            scopeCustomIds.add(Convert.toStr(role.getRoleId()));
        }
    });

    for (SysRole role : user.getRoles())
    {
        String dataScope = role.getDataScope();
        if (conditions.contains(dataScope) || StringUtils.equals(role.getStatus(), UserConstants.ROLE_DISABLE))
        {
            continue;
        }
        if (StringUtils.isNotEmpty(permission) && !StringUtils.containsAny(role.getPermissions(), Convert.toStrArray(permission)))
        {
            continue;
        }

        if (Constants.Dept.DATA_SCOPE_ALL.equals(dataScope))
        {
            sqlString = new StringBuilder();
            conditions.add(dataScope);
            break; // 全部权限，直接跳出
        }
        else if (Constants.Dept.DATA_SCOPE_CUSTOM.equals(dataScope))
        {
            if (scopeCustomIds.size() > 1)
            {
                sqlString.append(StringUtils.format(" OR {}.{} IN ( SELECT dept_id FROM sys_role_dept WHERE role_id in ({}) ) ", deptAlias, deptField, String.join(",", scopeCustomIds)));
            }
            else
            {
                sqlString.append(StringUtils.format(" OR {}.{} IN ( SELECT dept_id FROM sys_role_dept WHERE role_id = {} ) ", deptAlias, deptField, role.getRoleId()));
            }
        }
        else if (Constants.Dept.DATA_SCOPE_DEPT.equals(dataScope))
        {
            sqlString.append(StringUtils.format(" OR {}.{} = {} ", deptAlias, deptField, user.getDeptId()));
        }
        else if (Constants.Dept.DATA_SCOPE_DEPT_AND_CHILD.equals(dataScope))
        {
            sqlString.append(StringUtils.format(" OR {}.{} IN ( SELECT dept_id FROM sys_dept WHERE dept_id = {} or find_in_set( {} , ancestors ) )", deptAlias, deptField, user.getDeptId(), user.getDeptId()));
        }
        else if (Constants.Dept.DATA_SCOPE_SELF.equals(dataScope))
        {
            if (StringUtils.isNotBlank(userAlias))
            {
                sqlString.append(StringUtils.format(" OR {}.{} = {} ", userAlias, userField, user.getUserId()));
            }
            else
            {
                sqlString.append(StringUtils.format(" OR {}.{} = 0 ", deptAlias, deptField));
            }
        }
        conditions.add(dataScope);
    }

    // 角色都不包含传递过来的权限字符，不查询任何数据
    if (StringUtils.isEmpty(conditions))
    {
        sqlString.append(StringUtils.format(" OR {}.{} = 0 ", deptAlias, deptField));
    }

    if (StringUtils.isNotBlank(sqlString.toString()))
    {
        Object params = joinPoint.getArgs()[0];
        if (StringUtils.isNotNull(params) && params instanceof BaseEntity)
        {
            BaseEntity baseEntity = (BaseEntity) params;
            baseEntity.getParams().put(DATA_SCOPE, " AND (" + sqlString.substring(4) + ")");
        }
    }
}
```

**剖析要点：**
- 多角色取并集：用户有多个角色时，每个角色的数据范围条件用`OR`连接
- "全部数据权限"优先级最高，一旦匹配直接跳出循环
- "自定义数据权限"多个角色合并为`IN`查询，减少SQL子查询次数
- "本部门及以下"使用`find_in_set`函数匹配部门树中的ancestors字段
- "仅本人"且无userAlias时，设置`dept_id = 0`（永远不匹配），不返回任何数据
- 最终SQL通过`baseEntity.getParams().put("dataScope", ...)`注入到MyBatis XML中

### 3.4 MyBatis XML中的引用

在Mapper XML中，通过`${params.dataScope}`引用切面拼接的SQL：

```xml
<select id="selectUserList" resultMap="SysUserResult">
    select u.user_id, u.dept_id, u.user_name, ...
    from sys_user u
    left join sys_dept d on u.dept_id = d.dept_id
    where u.del_flag = '0'
    ${params.dataScope}
</select>
```

**剖析要点：**
- 使用`${}`而非`#{}`，因为dataScope已经是完整的SQL片段，不需要再参数化
- `clearDataScope`在切面前先清空params.dataScope，防止客户端伪造SQL注入

### 3.5 防注入清理

```java
private void clearDataScope(final JoinPoint joinPoint)
{
    Object params = joinPoint.getArgs()[0];
    if (StringUtils.isNotNull(params) && params instanceof BaseEntity)
    {
        BaseEntity baseEntity = (BaseEntity) params;
        baseEntity.getParams().put(DATA_SCOPE, "");
    }
}
```

**剖析要点：**
- 在拼接SQL之前，先将`params.dataScope`清空为空字符串
- 防止客户端通过请求参数传入恶意的SQL片段
- 这是防御SQL注入的重要安全措施

## 四、数据权限执行流程图

```
Controller调用Service方法
    |
@DataScope注解触发AOP切面
    |
clearDataScope() -- 清空params.dataScope防注入
    |
handleDataScope() -- 获取当前用户和角色
    |
dataScopeFilter() -- 遍历角色，拼接SQL
    |-- 全部权限: 不拼接
    |-- 自定义: dept_id IN (SELECT dept_id FROM sys_role_dept WHERE role_id = ?)
    |-- 本部门: dept_id = {当前部门}
    |-- 本部门及以下: dept_id IN (SELECT ... WHERE find_in_set(...))
    |-- 仅本人: user_id = {当前用户}
    |
baseEntity.getParams().put("dataScope", sqlString)
    |
MyBatis执行SQL时通过${params.dataScope}注入条件
    |
返回过滤后的数据
```

## 五、细节留神

1. **SQL注入风险**：虽然使用了`${}`拼接SQL，但`clearDataScope`在切面前清空了params.dataScope，且SQL内容由服务端控制，不接受外部输入，因此是安全的。
2. **多角色并集**：用户有多个角色时，数据权限取并集（OR连接），这意味着用户只要有一个角色拥有"全部数据权限"，就能看到所有数据。
3. **find_in_set性能**：本部门及以下使用`find_in_set`函数，依赖sys_dept表的ancestors字段（存储祖先部门ID链），需要确保ancestors字段正确维护。
4. **仅本人无userAlias**：如果数据权限为"仅本人"但未指定userAlias，SQL条件设为`dept_id = 0`，永远不匹配任何数据，相当于"无权限"。
5. **仅限第一个参数**：切面默认取`joinPoint.getArgs()[0]`作为参数对象，如果方法的第一个参数不是BaseEntity子类，数据权限不会生效。

## 六、提问方向

1. **数据权限使用`${params.dataScope}`拼接SQL，虽然`clearDataScope`做了清理，但如果攻击者通过其他方式（如自定义参数绑定）注入SQL，应该如何进一步防护？**

2. **用户有多个角色时，数据权限取并集。如果业务需求是取交集（最严格的角色权限），应该如何改造`dataScopeFilter`方法？**

3. **`find_in_set`函数在大数据量下性能如何？如果部门层级很深（如10级），ancestors字段会很长，是否会影响查询性能？**

4. **数据权限切面默认取第一个参数作为BaseEntity，如果Service方法的第一个参数不是BaseEntity（如分页参数在前），数据权限会如何处理？如何设计更灵活的参数匹配机制？**

5. **如果需要在数据权限基础上增加"数据权限+时间范围"的组合过滤（如只能查看最近30天的数据），应该如何扩展？**

6. **当前数据权限仅支持单表过滤，如果查询涉及多表JOIN且需要分别对不同的表设置数据权限，应该如何处理？**

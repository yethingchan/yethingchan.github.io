# 02 - 多模块结构与依赖关系

## 一、模块总览

RuoYi-Vue 项目采用 Maven 多模块架构，共包含 **6 个子模块**。根 `pom.xml` 中的模块声明：

```xml
<!-- 根 pom.xml -->
<modules>
    <module>ruoyi-admin</module>
    <module>ruoyi-framework</module>
    <module>ruoyi-system</module>
    <module>ruoyi-quartz</module>
    <module>ruoyi-generator</module>
    <module>ruoyi-common</module>
</modules>
<packaging>pom</packaging>
```

根 POM 的打包方式为 `pom`，表示它本身不产出构建产物，仅作为聚合与依赖管理的父工程。

---

## 二、6 个模块详细职责

### 2.1 ruoyi-admin（入口模块）

**定位**：Web 服务入口，是整个应用的启动模块。

**职责**：
- 包含 `RuoYiApplication` 启动类
- 包含所有 Controller 层代码（系统管理、监控、工具等）
- 包含配置文件（`application.yml`、`application-druid.yml`）
- 包含 MyBatis 全局配置（`mybatis-config.xml`）
- 包含国际化资源文件（`i18n/messages.properties`）
- 包含日志配置（`logback.xml`）
- 包含 Springdoc 接口文档配置

**pom.xml 关键依赖**：

```xml
<!-- ruoyi-admin/pom.xml -->
<packaging>jar</packaging>
<artifactId>ruoyi-admin</artifactId>
<description>web服务入口</description>

<dependencies>
    <!-- 热部署 -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-devtools</artifactId>
        <optional>true</optional>
    </dependency>
    <!-- 接口文档 -->
    <dependency>
        <groupId>org.springdoc</groupId>
        <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    </dependency>
    <!-- MySQL 驱动 -->
    <dependency>
        <groupId>com.mysql</groupId>
        <artifactId>mysql-connector-j</artifactId>
    </dependency>
    <!-- 核心模块 -->
    <dependency>
        <groupId>com.ruoyi</groupId>
        <artifactId>ruoyi-framework</artifactId>
    </dependency>
    <!-- 定时任务 -->
    <dependency>
        <groupId>com.ruoyi</groupId>
        <artifactId>ruoyi-quartz</artifactId>
    </dependency>
    <!-- 代码生成 -->
    <dependency>
        <groupId>com.ruoyi</groupId>
        <artifactId>ruoyi-generator</artifactId>
    </dependency>
</dependencies>
```

**关键点**：
- `spring-boot-devtools` 设置了 `<optional>true</optional>`，表示此依赖不会传递到其他模块
- MySQL 驱动放在 admin 模块而非 common 模块，体现了"按需引入"的原则
- 同时依赖了 `ruoyi-framework`、`ruoyi-quartz`、`ruoyi-generator` 三个业务模块

### 2.2 ruoyi-framework（框架核心模块）

**定位**：框架核心，封装了所有基础设施配置。

**职责**：
- Spring Security 安全配置（`SecurityConfig`）
- Druid 数据源配置（`DruidConfig`）
- Redis 缓存配置（`RedisConfig`）
- MyBatis 配置（`MyBatisConfig`）
- 验证码配置（`CaptchaConfig`、`KaptchaTextCreator`）
- 线程池配置（`ThreadPoolConfig`）
- 资源跨域配置（`ResourcesConfig`）
- AOP 切面：数据权限（`DataScopeAspect`）、数据源切换（`DataSourceAspect`）、操作日志（`LogAspect`）、限流（`RateLimiterAspect`）
- 动态数据源（`DynamicDataSource`、`DynamicDataSourceContextHolder`）
- 过滤器配置（`FilterConfig`）
- 异步任务管理（`AsyncManager`、`ShutdownManager`）
- 重复提交拦截（`RepeatSubmitInterceptor`）
- 国际化配置（`I18nConfig`）
- 服务器信息配置（`ServerConfig`）

**pom.xml 关键依赖**：

```xml
<!-- ruoyi-framework/pom.xml -->
<artifactId>ruoyi-framework</artifactId>
<description>framework框架核心</description>

<dependencies>
    <!-- SpringBoot Web容器 -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-webmvc</artifactId>
    </dependency>
    <!-- SpringBoot 拦截器 -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-aspectj</artifactId>
    </dependency>
    <!-- 阿里数据库连接池 -->
    <dependency>
        <groupId>com.alibaba</groupId>
        <artifactId>druid-spring-boot-4-starter</artifactId>
    </dependency>
    <!-- 验证码 -->
    <dependency>
        <groupId>pro.fessional</groupId>
        <artifactId>kaptcha</artifactId>
        <exclusions>
            <exclusion>
                <artifactId>servlet-api</artifactId>
                <groupId>javax.servlet</groupId>
            </exclusion>
        </exclusions>
    </dependency>
    <!-- 获取系统信息 -->
    <dependency>
        <groupId>com.github.oshi</groupId>
        <artifactId>oshi-core</artifactId>
    </dependency>
    <!-- 系统模块 -->
    <dependency>
        <groupId>com.ruoyi</groupId>
        <artifactId>ruoyi-system</artifactId>
    </dependency>
</dependencies>
```

**关键点**：
- Kaptcha 依赖排除了旧的 `javax.servlet` 的 `servlet-api`，因为 Spring Boot 4.x 使用的是 `jakarta.servlet`
- 依赖了 `ruoyi-system`，说明框架层需要访问系统模块中的 Service 和 Mapper

### 2.3 ruoyi-system（系统模块）

**定位**：系统业务模块，封装核心业务逻辑。

**职责**：
- 系统管理的 Service 层和 Mapper 层
- 涵盖：用户、角色、菜单、部门、岗位、字典、配置、通知、日志等
- MyBatis XML 映射文件（`mapper/system/` 目录下共 17 个 Mapper XML）
- 领域模型（Domain 实体类）

**Mapper XML 文件清单**：

```
mapper/system/
  ├── SysConfigMapper.xml       # 系统配置
  ├── SysDeptMapper.xml         # 部门
  ├── SysDictDataMapper.xml     # 字典数据
  ├── SysDictTypeMapper.xml     # 字典类型
  ├── SysLogininforMapper.xml   # 登录日志
  ├── SysMenuMapper.xml         # 菜单
  ├── SysNoticeMapper.xml       # 通知公告
  ├── SysNoticeReadMapper.xml   # 通知阅读记录
  ├── SysOperLogMapper.xml      # 操作日志
  ├── SysPostMapper.xml         # 岗位
  ├── SysRoleDeptMapper.xml     # 角色-部门关联
  ├── SysRoleMapper.xml         # 角色
  ├── SysRoleMenuMapper.xml     # 角色-菜单关联
  ├── SysUserMapper.xml         # 用户
  ├── SysUserPostMapper.xml     # 用户-岗位关联
  └── SysUserRoleMapper.xml     # 用户-角色关联
```

**pom.xml 关键依赖**：

```xml
<!-- ruoyi-system/pom.xml -->
<artifactId>ruoyi-system</artifactId>
<description>system系统模块</description>

<dependencies>
    <!-- 通用工具 -->
    <dependency>
        <groupId>com.ruoyi</groupId>
        <artifactId>ruoyi-common</artifactId>
    </dependency>
</dependencies>
```

**关键点**：
- 仅依赖 `ruoyi-common`，依赖关系非常干净
- 不直接依赖任何 Web 框架组件，保持了业务模块的纯粹性

- **常量定义**：`CacheConstants`、`Constants`、`UserConstants`、`HttpStatus`、`GenConstants`、`ScheduleConstants`
- **枚举类**：`BusinessType`、`BusinessStatus`、`DataSourceType`、`UserStatus`、`LimitType` 等
- **异常体系**：`ServiceException`、`GlobalException`、`DemoModeException`、`UtilException`

### 2.6 ruoyi-generator（代码生成模块）

**定位**：基于 Velocity 模板引擎的代码生成器。

**职责**：
- 从数据库表结构自动生成代码
- 生成内容：Controller、Service、ServiceImpl、Mapper、Domain、Vue 页面、API 接口、SQL 脚本
- 支持多种前端模板：Vue2、Vue3、Vue3+TS
- Velocity 模板文件（`vm/` 目录）

**pom.xml 关键依赖**：

```xml
<!-- ruoyi-generator/pom.xml -->
<artifactId>ruoyi-generator</artifactId>
<description>generator代码生成</description>

<dependencies>
    <!-- velocity代码生成使用模板 -->
    <dependency>
        <groupId>org.apache.velocity</groupId>
        <artifactId>velocity-engine-core</artifactId>
    </dependency>
    <!-- 通用工具 -->
    <dependency>
        <groupId>com.ruoyi</groupId>
        <artifactId>ruoyi-common</artifactId>
    </dependency>
    <!-- 阿里数据库连接池 -->
    <dependency>
        <groupId>com.alibaba</groupId>
        <artifactId>druid-spring-boot-4-starter</artifactId>
    </dependency>
</dependencies>
```

**关键点**：
- generator 模块额外引入了 `druid-spring-boot-4-starter`，因为代码生成器需要直接读取数据库元数据（表结构、字段信息）

## 三、模块依赖关系图

### 3.1 依赖链

```
ruoyi-admin (入口)
  ├── ruoyi-framework (框架核心)
  │     └── ruoyi-system (系统模块)
  │           └── ruoyi-common (公共模块)
  ├── ruoyi-quartz (定时任务)
  │     └── ruoyi-common (公共模块)
  └── ruoyi-generator (代码生成)
        └── ruoyi-common (公共模块)
```

### 3.2 依赖关系分析

| 依赖关系 | 类型 | 说明 |
|---------|------|------|
| admin -> framework | 强依赖 | admin 启动必须加载 framework 的所有配置 |
| admin -> quartz | 强依赖 | 定时任务是系统的核心功能之一 |
| admin -> generator | 强依赖 | 代码生成是开发辅助功能 |
| framework -> system | 强依赖 | 框架层的 AOP 切面需要调用系统模块的 Service |
| quartz -> common | 强依赖 | 定时任务使用 common 中的工具类和注解 |
| generator -> common | 强依赖 | 代码生成使用 common 中的工具类和常量 |
| system -> common | 强依赖 | 系统模块使用 common 中的基础类 |

### 3.3 传递依赖链

```
admin -> framework -> system -> common
admin -> quartz -> common
admin -> generator -> common
```

这意味着 `ruoyi-admin` 最终会传递依赖到所有 6 个模块。但注意：
- `quartz` 和 `generator` 之间没有互相依赖
- `system` 和 `quartz`/`generator` 之间没有直接依赖
- `framework` 不依赖 `quartz` 和 `generator`

## 四、版本仲裁机制

### 4.1 父 POM dependencyManagement

根 `pom.xml` 通过 `<dependencyManagement>` 统一管理所有依赖版本：

```xml
<!-- 根 pom.xml -->
<dependencyManagement>
    <dependencies>
        <!-- SpringBoot的依赖配置 -->
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-dependencies</artifactId>
            <version>${spring-boot.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>

        <!-- 阿里数据库连接池 -->
        <dependency>
            <groupId>com.alibaba</groupId>
            <artifactId>druid-spring-boot-4-starter</artifactId>
            <version>${druid.version}</version>
        </dependency>

        <!-- pagehelper 分页插件 -->
        <dependency>
            <groupId>com.github.pagehelper</groupId>
            <artifactId>pagehelper-spring-boot-starter</artifactId>
            <version>${pagehelper.boot.version}</version>
        </dependency>

        <!-- ... 其他依赖 ... -->

        <!-- 项目内部模块 -->
        <dependency>
            <groupId>com.ruoyi</groupId>
            <artifactId>ruoyi-framework</artifactId>
            <version>${ruoyi.version}</version>
        </dependency>
        <dependency>
            <groupId>com.ruoyi</groupId>
            <artifactId>ruoyi-system</artifactId>
            <version>${ruoyi.version}</version>
        </dependency>
        <dependency>
            <groupId>com.ruoyi</groupId>
            <artifactId>ruoyi-common</artifactId>
            <version>${ruoyi.version}</version>
        </dependency>
        <!-- ... -->
    </dependencies>
</dependencyManagement>
```

### 4.2 版本仲裁策略

1. **Spring Boot BOM 导入**：通过 `spring-boot-dependencies` POM 导入，继承 Spring Boot 的版本管理，所有 Spring Boot Starter 无需指定版本号
2. **第三方库版本集中管理**：Druid、PageHelper、FastJson2 等版本号在 `<properties>` 中定义，在 `<dependencyManagement>` 中引用
3. **内部模块版本统一**：所有子模块版本统一为 `${ruoyi.version}`（3.9.2）
4. **子模块无需指定版本**：子模块 POM 中引入依赖时无需写 `<version>`，由父 POM 仲裁

### 4.3 版本仲裁优先级

```
1. 子模块中显式指定的版本号（最高优先级）
2. 父 POM dependencyManagement 中指定的版本
3. Spring Boot BOM 中管理的版本
4. Maven 依赖调解规则（最近路径优先）
```

## 五、模块设计思想

### 5.1 为什么这样拆分？

**分层解耦原则**：

```
┌─────────────────────────────────────────────────┐
│              表现层 (Controller)                 │  ruoyi-admin
│  只负责接收请求、参数校验、返回响应               │
├─────────────────────────────────────────────────┤
│              框架层 (Config/AOP)                 │  ruoyi-framework
│  安全配置、数据源、缓存、切面、拦截器            │
├─────────────────────────────────────────────────┤
│              业务层 (Service/Mapper)              │  ruoyi-system
│  核心业务逻辑、数据访问                          │
├─────────────────────────────────────────────────┤
│              基础层 (Utils/Annotation)           │  ruoyi-common
│  工具类、注解、常量、异常、过滤器                  │
├─────────────────────────────────────────────────┤
│         扩展模块 (quartz/generator)              │  独立功能
│  定时任务、代码生成，按需引入                     │
└─────────────────────────────────────────────────┘
```

### 5.2 设计优势

1. **职责单一**：每个模块只做一件事，便于维护
2. **按需引用**：如果不需要定时任务，可以去掉 `ruoyi-quartz` 依赖；如果不需要代码生成，可以去掉 `ruoyi-generator` 依赖
3. **独立演进**：common 模块可以单独抽取为公共 JAR 供其他项目使用
4. **团队协作**：不同团队成员可以独立开发不同模块
5. **编译效率**：修改 common 模块不会导致 quartz 和 generator 不必要的重编译（虽然传递依赖仍会触发）

### 5.3 潜在改进方向

1. **ruoyi-common 依赖过重**：common 模块引入了 Spring Security、Redis、POI 等重量级依赖，如果只需使用工具类，会引入不必要的依赖
2. **可考虑进一步拆分**：将 `ruoyi-common` 拆分为 `ruoyi-core`（纯工具类）和 `ruoyi-security`（安全相关）
3. **ruoyi-generator 的 Druid 依赖**：generator 模块直接依赖 Druid，与 framework 模块的 Druid 配置存在重复

  ├── filter/                        # 过滤器
  ├── utils/                         # 工具类

## 七、细节留神

1. **ruoyi-admin 的打包方式是 `jar`**：虽然配置了 `maven-war-plugin`，但主打包方式仍是 `jar`，说明默认以可执行 JAR 方式部署，同时保留了 WAR 部署的兼容性
2. **Kaptcha 的 exclusion**：`ruoyi-framework` 中排除了 Kaptcha 自带的 `javax.servlet:servlet-api`，因为 Spring Boot 4.x 使用 `jakarta.servlet`，如果不排除会产生冲突
3. **ruoyi-generator 额外引入 Druid**：代码生成器需要通过 Druid 的 `DatabaseMetaData` 获取表结构信息，这是一个独立于 framework 中 Druid 配置的使用场景
4. **所有子模块都没有指定版本号**：子模块 POM 中的依赖均未写 `<version>`，全部由父 POM 的 `<dependencyManagement>` 仲裁
5. **ruoyi-common 中 Jackson 的 groupId**：使用的是 `tools.jackson.core` 而非传统的 `com.fasterxml.jackson.core`，这是 Spring Boot 4.x 中的变化

## 八、提问方向

1. **"RuoYi-Vue 的 6 个模块为什么这样划分？如果让你重新设计模块结构，你会怎么调整？"**

   > 参考思路：讨论职责单一原则、按需引用、common 模块是否应该进一步拆分

2. **"ruoyi-common 模块引入了 Spring Security、Redis、POI 等重量级依赖，如果只想使用其中的 StringUtils 工具类，是否会产生不必要的依赖污染？如何解决？"**

   > 参考思路：讨论模块拆分策略，将纯工具类与框架集成类分离

3. **"ruoyi-framework 依赖了 ruoyi-system，而 ruoyi-system 依赖了 ruoyi-common。如果 framework 中的 AOP 切面只需要 common 中的注解，是否可以打破 framework->system 的依赖？"**

   > 参考思路：讨论依赖倒置、是否需要引入接口抽象层

4. **"父 POM 中通过 `spring-boot-dependencies` 导入 BOM，如果某个第三方库的版本与 Spring Boot BOM 管理的版本冲突，Maven 会如何处理？"**

   > 参考思路：讨论 Maven 依赖调解的"最近路径优先"和"先声明优先"策略

5. **"ruoyi-quartz 和 ruoyi-generator 都依赖 ruoyi-common，但它们之间没有互相依赖。如果代码生成器需要调用定时任务，应该如何设计这种跨模块调用？"**

   > 参考思路：讨论模块间通信方式，通过 admin 模块编排、事件驱动、或引入共享接口模块

6. **"项目中 ruoyi-admin 的 `spring-boot-devtools` 设置了 `<optional>true</optional>`，这个配置的实际效果是什么？在生产环境中是否会包含这个依赖？"**

   > 参考思路：`optional=true` 表示依赖不会传递，生产打包时不会包含 devtools

7. **"如果要在项目中新增一个 `ruoyi-message`（消息通知模块），应该放在依赖图的什么位置？需要依赖哪些现有模块？"**

   > 参考思路：应该依赖 ruoyi-common，被 ruoyi-admin 依赖，与 ruoyi-system 平级

## 一、Vite 构建配置

### 1.1 构建命令

在项目根目录执行：

```bash
npm run build
```

这条命令实际上执行的是 `vite build`。Vite 会完成以下工作：

1. **编译转换**：将 `.vue` 单文件组件编译为 JavaScript 和 CSS
2. **代码压缩**：使用 Terser/esbuild 对 JS 代码进行压缩和混淆
3. **CSS 提取**：将组件中的 CSS 提取为独立的 `.css` 文件
4. **资源处理**：对图片、字体等资源进行内联或拷贝
5. **代码分割**：根据路由和动态导入自动分割代码块

构建成功后，项目根目录下会生成 `dist/` 文件夹。

### 1.2 构建产物结构

```
dist/
├── index.html                  # 入口 HTML
├── assets/
│   ├── index-a1b2c3d4.js       # 主 JS 文件（入口模块）
│   ├── vendor-e5f6g7h8.js      # 第三方库（vendor chunk）
│   ├── element-plus-i9j0k1.js  # Element Plus（单独分包）
│   ├── index-a1b2c3d4.css      # 主 CSS 文件
│   ├── logo-x1y2z3.png         # 图片资源
│   └── ...                     # 其他 chunk 文件
├── favicon.ico
└── vite.svg
```

文件名的哈希值（如 `a1b2c3d4`）是内容哈希——只有文件内容发生变化时，哈希值才会改变。这意味着浏览器可以长期使用强缓存，内容不变就不需要重新下载。

### 1.3 核心构建选项

在项目根目录的 `vite.config.js` 中配置 `build` 选项：

```javascript
// vite.config.js
import { defineConfig, loadEnv } from 'vite'
import vue from '@vitejs/plugin-vue'
import { resolve } from 'path'

export default defineConfig(({ mode }) => {
  const env = loadEnv(mode, process.cwd())

  return {
    plugins: [vue()],
    // 生产环境使用相对路径，部署到任意子路径都不会出问题
    base: './',
    resolve: {
      alias: {
        '@': resolve(__dirname, 'src')
      }
    },
    build: {
      // 输出目录（默认 dist）
      outDir: 'dist',
      // 静态资源存放的子目录（默认 assets）
      assetsDir: 'assets',
      // 单个 chunk 文件超过此值（单位 kB）会发出警告，默认 500
      chunkSizeWarningLimit: 1000,
      // Rollup 输出配置
      rollupOptions: {
        output: {
          // 手动代码分割——将不同模块打包到不同的 chunk 中
          manualChunks(id) {
            if (id.includes('node_modules')) {
              // Element Plus 单独打包（体积最大）
              if (id.includes('element-plus')) {
                return 'element-plus'
              }
              // Vue 核心库打包在一起
              if (id.includes('/vue@') || id.includes('/vue-router@') || id.includes('/pinia@')) {
                return 'vue-vendor'
              }
              // Axios 单独打包
              if (id.includes('axios')) {
                return 'axios'
              }
              // 其他第三方库
              return 'vendor'
            }
          },
          // 为 chunk 文件设置命名规则
          chunkFileNames: 'assets/js/[name]-[hash].js',
          entryFileNames: 'assets/js/[name]-[hash].js',
          assetFileNames: (assetInfo) => {
            // 根据资源类型放入不同子目录
            if (/\.(png|jpe?g|gif|svg|webp|ico)$/.test(assetInfo.name)) {
              return 'assets/images/[name]-[hash][extname]'
            }
            if (/\.(woff|woff2|ttf|eot)$/.test(assetInfo.name)) {
              return 'assets/fonts/[name]-[hash][extname]'
            }
            if (/\.css$/.test(assetInfo.name)) {
              return 'assets/css/[name]-[hash][extname]'
            }
            return 'assets/[name]-[hash][extname]'
          }
        }
      },
      // 生产环境去除 console.log 和 debugger
      minify: 'terser',
      terserOptions: {
        compress: {
          drop_console: true,
          drop_debugger: true
        }
      }
    }
  }
})
```

**配置要点说明：**

| 配置项 | 作用 | 推荐值 |
|--------|------|--------|
| `base` | 公共路径前缀 | `'./'`（相对路径，适合部署到任意子目录） |
| `outDir` | 构建输出目录 | `'dist'`（默认即可） |
| `assetsDir` | 资源子目录名 | `'assets'`（默认即可） |
| `chunkSizeWarningLimit` | chunk 体积警告阈值 | `1000`（避免频繁报警） |
| `manualChunks` | 手动代码分割 | 按模块职责分组 |
| `terserOptions` | 代码压缩选项 | 去除 console 和 debugger |

### 1.4 环境变量配置

项目根目录下创建 `.env.production` 文件，用于生产环境的变量配置：

```bash
# .env.production

# 应用标题
VITE_APP_TITLE=Vue Admin 后台管理系统

# API 基础路径（生产环境通常走代理或同域）
VITE_APP_BASE_API=/api

# 是否启用 Mock 数据（生产环境关闭）
VITE_USE_MOCK=false

# 生产环境 API 地址
VITE_APP_API_URL=https://api.your-domain.com
```

同时确认 `.env.development` 中的配置：

```bash
# .env.development

VITE_APP_TITLE=Vue Admin（开发环境）
VITE_APP_BASE_API=/dev-api
VITE_USE_MOCK=true
VITE_APP_API_URL=http://localhost:3000
```

在代码中通过 `import.meta.env.VITE_APP_BASE_API` 读取变量，Vite 会根据构建模式自动加载对应的 `.env` 文件。

### 1.5 Base URL 配置详解

`base` 选项决定了构建产物中资源引用的路径前缀，这是部署时最容易踩坑的地方：

```javascript
// 场景一：部署到域名根目录（https://example.com/）
base: '/'

// 场景二：部署到子目录（https://example.com/admin/）
base: '/admin/'

// 场景三：部署到任意路径（推荐，最灵活）
base: './'
```

> **实用建议**：如果你的项目不确定会部署到哪个路径，使用 `base: './'` 是最安全的选择。它生成的资源引用都是相对路径，不会因为路径不匹配导致白屏。

## 二、构建产物分析

### 2.1 安装可视化工具

在优化之前，先要搞清楚"哪些包占了多大体积"。使用 `rollup-plugin-visualizer` 生成可视化报告：

```bash
npm install -D rollup-plugin-visualizer
```

### 2.2 配置分析插件

在 `vite.config.js` 中添加插件配置：

```javascript
// vite.config.js
import { visualizer } from 'rollup-plugin-visualizer'

export default defineConfig({
  plugins: [
    vue(),
    // 仅在分析构建时启用，正常构建不需要
    visualizer({
      open: true,                  // 构建完成后自动打开报告
      filename: 'dist/stats.html', // 报告文件路径
      gzipSize: true,              // 显示 gzip 后体积
      brotliSize: true             // 显示 brotli 后体积
    })
  ]
})
```

> **实用技巧**：不建议把 `visualizer` 常驻在配置中。推荐的做法是在 `package.json` 中添加一个独立的分析脚本：

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "build:analyze": "ANALYZE=true vite build",
    "preview": "vite preview"
  }
}
```

然后在 `vite.config.js` 中判断环境变量：

```javascript
import { visualizer } from 'rollup-plugin-visualizer'

export default defineConfig(({ mode }) => {
  const isAnalyze = process.env.ANALYZE === 'true'

  return {
    plugins: [
      vue(),
      isAnalyze && visualizer({
        open: true,
        filename: 'dist/stats.html',
        gzipSize: true,
        brotliSize: true
      })
    ]
  }
})
```

Windows 用户使用分析命令时，环境变量设置方式不同：

```bash
# Linux / macOS
ANALYZE=true vite build

# Windows CMD
set ANALYZE=true && vite build

# Windows PowerShell
$env:ANALYZE="true"; vite build

# 或者安装 cross-env 统一处理（推荐）
npm install -D cross-env
# package.json 中："build:analyze": "cross-env ANALYZE=true vite build"
```

### 2.3 解读可视化报告

执行 `npm run build:analyze` 后，浏览器会自动打开一个树状图（Treemap）：

```
报告中的关键信息：

┌─────────────────────────────────────────────────────────┐
│  element-plus   ████████████████████   750 kB (gzip: 200kB)  │
│  vue-vendor     ██████████             130 kB (gzip: 45kB)   │
│  vendor         ████████               90 kB  (gzip: 30kB)   │
│  axios          ████                   45 kB  (gzip: 15kB)   │
│  index (入口)   ██                     25 kB  (gzip: 8kB)    │
│  路由 chunk × 5 █ × 5                 10~30kB each          │
└─────────────────────────────────────────────────────────┘
```

**重点关注：**

- **面积最大的色块**：体积最大的依赖，是优化的首要目标
- **Gzip 体积**：实际传输体积，这才是用户真实下载的体积
- **重复依赖**：如果看到同一个库出现在多个 chunk 中，需要调整 `manualChunks`

### 2.4 常见优化策略

#### 策略一：路由懒加载（本教程已实现）

```javascript
// src/router/index.js
// 每个路由对应一个独立的 chunk，只在访问时才加载
{
  path: '/system/user',
  component: () => import('@/views/system/user/index.vue'),
  meta: { title: '用户管理' }
}
```

#### 策略二：Element Plus 按需导入

如果使用了全量导入，`element-plus` 的 chunk 会非常大。按需导入只引入用到的组件：

```javascript
// 全量导入（不推荐）
import ElementPlus from 'element-plus'
import 'element-plus/dist/index.css'

// 按需导入（推荐）
// 借助 unplugin-vue-components 和 unplugin-auto-import 实现自动按需导入
npm install -D unplugin-vue-components unplugin-auto-import
```

```javascript
// vite.config.js
import AutoImport from 'unplugin-auto-import/vite'
import Components from 'unplugin-vue-components/vite'
import { ElementPlusResolver } from 'unplugin-vue-components/resolvers'

export default defineConfig({
  plugins: [
    vue(),
    AutoImport({
      resolvers: [ElementPlusResolver()]
    }),
    Components({
      resolvers: [ElementPlusResolver()]
    })
  ]
})
```

#### 策略三：图片压缩

大图片是包体积的隐形杀手。推荐以下处理方式：

```bash
# 使用 TinyPNG 等工具在线压缩
# 或使用 sharp 等 Node 工具批量压缩

# 对于小图标，使用 SVG 替代 PNG
# 对于大背景图，考虑使用 CDN 外链
```

```javascript
// vite.config.js 中配置小图片自动转 Base64 内联
build: {
  // 小于 4KB 的图片自动转 Base64（减少 HTTP 请求）
  assetsInlineLimit: 4096
}
```

#### 策略四：开启 Gzip / Brotli 压缩

除了依赖 Nginx 的动态压缩外，还可以在构建阶段预生成压缩文件：

```bash
npm install -D vite-plugin-compression
```

```javascript
// vite.config.js
import viteCompression from 'vite-plugin-compression'

export default defineConfig({
  plugins: [
    vue(),
    // 生成 .gz 文件
    viteCompression({
      algorithm: 'gzip',
      threshold: 1024,   // 大于 1KB 才压缩
      ext: '.gz'
    }),
    // 生成 .br 文件（Brotli 压缩率更高）
    viteCompression({
      algorithm: 'brotliCompress',
      threshold: 1024,
      ext: '.br'
    })
  ]
})
```

构建后会生成对应的 `.gz` 和 `.br` 文件，配合 Nginx 的 `gzip_static` 指令可以直接返回预压缩文件，避免运行时压缩的开销。

## 三、Nginx 部署（最常用方案）

Nginx 是部署 Vue SPA 应用最常用的方案，轻量、高效、配置灵活。

### 3.1 安装 Nginx

**Windows：**

```powershell
# 方式一：官网下载
# 访问 http://nginx.org/en/download.html 下载 Windows 版本
# 解压到任意目录（如 C:\nginx）即可使用

# 方式二：使用 Scoop 包管理器
scoop install nginx

# 方式三：使用 Chocolatey 包管理器
choco install nginx
```

**Linux（Ubuntu/Debian）：**

```bash
# 更新包索引
sudo apt update

# 安装 Nginx
sudo apt install nginx -y

# 启动并设置开机自启
sudo systemctl start nginx
sudo systemctl enable nginx

# 验证安装
nginx -v
```

**Linux（CentOS/RHEL）：**

```bash
# 安装 EPEL 源
sudo yum install epel-release -y

# 安装 Nginx
sudo yum install nginx -y

# 启动并设置开机自启
sudo systemctl start nginx
sudo systemctl enable nginx
```

### 3.2 部署步骤

**第一步：构建生产版本**

```bash
npm run build
```

**第二步：将 `dist/` 目录上传到服务器**

```bash
# 方式一：使用 scp 上传（Linux/Mac）
scp -r dist/* user@your-server:/var/www/vue-admin/dist/

# 方式二：使用 rsync（增量同步，更快）
rsync -avz --delete dist/ user@your-server:/var/www/vue-admin/dist/

# 方式三：Windows 上使用 WinSCP / FileZilla 等工具手动上传

# 方式四：通过 Git 拉取代码后在服务器上构建（适合服务器配置较好的场景）
```

**第三步：配置 Nginx**

创建或编辑 Nginx 配置文件：

```bash
# Linux 上创建站点配置
sudo vim /etc/nginx/conf.d/vue-admin.conf
```

### 3.3 完整 Nginx 配置

```nginx
# /etc/nginx/conf.d/vue-admin.conf

server {
    listen 80;
    server_name your-domain.com;   # 替换为你的域名或 IP

    # 网站根目录指向构建产物的 dist 目录
    root /var/www/vue-admin/dist;
    index index.html;

    # ========== SPA 路由支持 ==========
    # Vue Router 使用 history 模式时，所有路径都需要返回 index.html
    # 否则刷新页面会返回 404
    location / {
        try_files $uri $uri/ /index.html;
    }

    # ========== 静态资源缓存 ==========
    # 构建产物的文件名包含内容哈希，可以放心使用强缓存
    location ~* \.(js|css)$ {
        expires 1y;
        add_header Cache-Control "public, immutable";
        access_log off;
    }

    # 图片和字体资源
    location ~* \.(png|jpg|jpeg|gif|ico|svg|webp|woff|woff2|ttf|eot)$ {
        expires 30d;
        add_header Cache-Control "public";
        access_log off;
    }

    # ========== API 反向代理 ==========
    # 将前端 /api/ 开头的请求代理到后端服务器
    location /api/ {
        proxy_pass http://backend-server:8080/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 超时设置
        proxy_connect_timeout 30s;
        proxy_send_timeout 60s;
        proxy_read_timeout 60s;

        # 支持大文件上传
        client_max_body_size 10m;
    }

    # ========== Gzip 压缩 ==========
    gzip on;
    gzip_vary on;
    gzip_proxied any;
    gzip_comp_level 6;
    gzip_min_length 1024;
    gzip_types
        text/plain
        text/css
        text/xml
        text/javascript
        application/json
        application/javascript
        application/xml
        application/rss+xml
        image/svg+xml;

    # 如果构建阶段已生成 .gz 文件，启用静态压缩文件支持
    # gzip_static on;

    # ========== 安全相关 ==========
    # 禁止访问隐藏文件
    location ~ /\. {
        deny all;
        access_log off;
        log_not_found off;
    }

    # 自定义错误页面（可选）
    error_page 404 /index.html;
    error_page 500 502 503 504 /50x.html;
    location = /50x.html {
        root /usr/share/nginx/html;
    }
}
```

### 3.4 关键配置详解

#### `try_files` 指令（最重要）

这是 Vue Router history 模式正常工作的关键：

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

**工作原理：**

```
用户访问 /system/user 时：

1. Nginx 先找文件：/var/www/vue-admin/dist/system/user   → 不存在
2. Nginx 再找目录：/var/www/vue-admin/dist/system/user/   → 不存在
3. Nginx 返回：    /var/www/vue-admin/dist/index.html     → 找到！

然后 Vue Router 接管，根据 /system/user 路径渲染对应组件。
```

**如果没有这条配置**，用户直接访问或刷新 `/system/user` 时，Nginx 找不到对应文件，会返回 404 错误。这是 Vue SPA 部署中最常见的坑。

#### API 反向代理

```nginx
location /api/ {
    # 注意末尾的 /，它决定了路径如何拼接
    # proxy_pass http://backend:8080/;
    # 请求 /api/users → 转发到 http://backend:8080/users（去掉了 /api 前缀）

    # proxy_pass http://backend:8080;
    # 请求 /api/users → 转发到 http://backend:8080/api/users（保留 /api 前缀）
    proxy_pass http://backend-server:8080/;
}
```

> **常见错误**：`proxy_pass` 末尾有没有 `/` 的区别非常大。如果后端接口路径不包含 `/api` 前缀，`proxy_pass` 末尾必须加 `/` 来去掉前缀。

### 3.5 HTTPS 配置（Let's Encrypt）

生产环境强烈建议启用 HTTPS。使用 Let's Encrypt 可以免费获取 SSL 证书：

```bash
# 安装 Certbot
sudo apt install certbot python3-certbot-nginx -y

# 自动获取证书并配置 Nginx
sudo certbot --nginx -d your-domain.com

# Certbot 会自动修改 Nginx 配置并设置自动续期
```

配置后的 Nginx 文件大致如下：

```nginx
server {
    listen 80;
    server_name your-domain.com;
    # HTTP 自动重定向到 HTTPS
    return 301 https://$server_name$request_uri;
}

server {
    listen 443 ssl http2;
    server_name your-domain.com;

    ssl_certificate /etc/letsencrypt/live/your-domain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/your-domain.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;

    root /var/www/vue-admin/dist;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    # ... 其他配置同上
}
```

### 3.6 常用 Nginx 命令

```bash
# 测试配置文件语法是否正确（改完配置先测试，再重启！）
nginx -t
# 或者
sudo nginx -t

# 重新加载配置（不中断服务，推荐）
sudo nginx -s reload

# 重启 Nginx（会短暂中断服务）
sudo systemctl restart nginx

# 查看 Nginx 运行状态
sudo systemctl status nginx

# 查看访问日志和错误日志
sudo tail -f /var/log/nginx/access.log
sudo tail -f /var/log/nginx/error.log

# Windows 上的命令（在 Nginx 安装目录下执行）
start nginx           # 启动
nginx -s reload       # 重新加载
nginx -s stop         # 快速停止
nginx -s quit         # 优雅停止
tasklist /fi "imagename eq nginx.exe"  # 查看 Nginx 进程
```

> **实用建议**：每次修改 Nginx 配置后，一定先执行 `nginx -t` 测试语法是否正确，确认无误后再 `nginx -s reload`。直接重启可能导致配置错误时服务中断。

## 四、Docker 容器化部署

Docker 可以将应用及其运行环境打包成镜像，实现"一次构建，到处运行"。

### 4.1 创建 Dockerfile

在项目根目录创建 `Dockerfile`：

```dockerfile
# ============ 第一阶段：构建 ============
FROM node:18-alpine AS builder

# 设置工作目录
WORKDIR /app

# 先复制依赖描述文件（利用 Docker 层缓存加速构建）
COPY package.json package-lock.json ./

# 安装依赖
RUN npm ci --registry=https://registry.npmmirror.com

# 再复制项目源码
COPY . .

# 执行构建
RUN npm run build

# ============ 第二阶段：运行 ============
FROM nginx:alpine

# 从构建阶段复制产物到 Nginx 目录
COPY --from=builder /app/dist /usr/share/nginx/html

# 复制自定义 Nginx 配置
COPY nginx.conf /etc/nginx/conf.d/default.conf

# 暴露端口
EXPOSE 80

# 容器启动命令（Nginx 镜像默认已配置，可省略）
CMD ["nginx", "-g", "daemon off;"]
```

**两阶段构建的好处：**

```
第一阶段（builder）：
  node:18-alpine 镜像 ≈ 120MB
  包含 Node.js、npm、源代码、node_modules
  这些在运行时都不需要

第二阶段（运行）：
  nginx:alpine 镜像 ≈ 25MB
  只包含 dist/ 构建产物和 Nginx
  最终镜像体积小，启动快
```

### 4.3 准备 Nginx 配置

在项目根目录创建 `nginx.conf`：

```nginx
server {
    listen 80;
    server_name localhost;

    root /usr/share/nginx/html;
    index index.html;

    # SPA 路由支持
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 静态资源缓存
    location ~* \.(js|css)$ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    location ~* \.(png|jpg|jpeg|gif|ico|svg|woff|woff2|ttf)$ {
        expires 30d;
        add_header Cache-Control "public";
    }

    # API 代理（根据实际后端地址修改）
    location /api/ {
        proxy_pass http://backend:8080/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    # Gzip 压缩
    gzip on;
    gzip_types text/plain text/css application/json application/javascript text/xml image/svg+xml;
    gzip_min_length 1024;
    gzip_comp_level 6;
}
```

### 4.5 Docker Compose（前端 + 后端一起部署）

当项目需要前端和后端一起部署时，使用 Docker Compose 管理多个容器：

```yaml
# docker-compose.yml
version: '3.8'

services:
  # ---- 前端服务 ----
  frontend:
    build:
      context: ./frontend
      dockerfile: Dockerfile
    container_name: vue-admin-web
    ports:
      - "80:80"

      - backend
    restart: unless-stopped

      - app-network

  # ---- 后端服务 ----
  backend:
    build:
      context: ./backend
      dockerfile: Dockerfile
    container_name: vue-admin-api
    ports:
      - "8080:8080"
    environment:
      - SPRING_PROFILES_ACTIVE=prod
      - DB_HOST=mysql
      - DB_PORT=3306
      - DB_NAME=vue_admin
    depends_on:
      - mysql
    restart: unless-stopped
    networks:
      - app-network

  # ---- 数据库 ----
  mysql:
    image: mysql:8.0
    container_name: vue-admin-db
    ports:
      - "3306:3306"
    environment:
      MYSQL_ROOT_PASSWORD: your_secure_password
      MYSQL_DATABASE: vue_admin
    volumes:
      - mysql-data:/var/lib/mysql
      - ./backend/sql/init.sql:/docker-entrypoint-initdb.d/init.sql

    networks:
      - app-network

volumes:
  mysql-data:

networks:
  app-network:
    driver: bridge
```

## 五、CI/CD 自动化部署（GitHub Actions 示例）

### 5.1 什么是 CI/CD

```
CI/CD 流程概览：

  开发者 push 代码
        │
        ▼
  ┌─────────────┐
  │   自动构建    │   CI（持续集成）
  │  npm build   │
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐
  │  自动化测试   │   CI（持续集成）
  │  npm test    │
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐
  │  部署到服务器  │   CD（持续部署）
  │  scp / rsync │
  └──────┬──────┘
         │
         ▼
    用户可访问新版本
```

**核心价值**：每次 push 代码后自动完成构建、测试、部署，不需要手动操作，减少人为错误。

### 5.2 前置准备

在 GitHub 仓库中配置 Secrets（加密变量），用于部署时连接服务器：

```
Settings → Secrets and variables → Actions → New repository secret

需要添加的 Secrets：

DEPLOY_HOST      服务器 IP 或域名（如 47.100.xxx.xxx）
DEPLOY_USER      SSH 登录用户名（如 root）
DEPLOY_KEY       SSH 私钥（整个私钥文件内容）
DEPLOY_PATH      部署目录（如 /var/www/vue-admin/dist）
```

> **安全提示**：永远不要在代码中硬编码服务器密码或密钥。使用 GitHub Secrets 存储敏感信息，它们会在日志中自动脱敏。

### 5.3 GitHub Actions 工作流

在项目根目录创建 `.github/workflows/deploy.yml`：

```yaml
# .github/workflows/deploy.yml
name: Deploy to Production

# 触发条件：push 到 main 分支时执行
on:
  push:
    branches:
      - main

# 环境变量
env:
  NODE_VERSION: '18'

jobs:
  build-and-deploy:
    name: Build and Deploy
    runs-on: ubuntu-latest

    steps:
      # 第一步：检出代码
      - name: Checkout code
        uses: actions/checkout@v4

      # 第二步：设置 Node.js 环境
      - name: Setup Node.js ${{ env.NODE_VERSION }}
        uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: 'npm'

      # 第三步：安装依赖
      - name: Install dependencies
        run: npm ci

      # 第四步：构建项目
      - name: Build project
        run: npm run build
        env:
          NODE_ENV: production

      # 第五步：部署到服务器（使用 SCP）
      - name: Deploy to server via SCP
        uses: appleboy/scp-action@v0.1.7
        with:
          host: ${{ secrets.DEPLOY_HOST }}
          username: ${{ secrets.DEPLOY_USER }}
          key: ${{ secrets.DEPLOY_KEY }}
          source: "dist/*"
          target: ${{ secrets.DEPLOY_PATH }}
          strip_components: 1
```

### 5.4 带测试和通知的完整工作流

```yaml
# .github/workflows/deploy.yml（完整版）
name: CI/CD Pipeline

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

env:
  NODE_VERSION: '18'

jobs:
  # ============ 构建与测试 ============
  build:
    name: Build and Test
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Lint code
        run: npm run lint
        continue-on-error: true

      - name: Run tests
        run: npm run test
        continue-on-error: true

      - name: Build project
        run: npm run build

      # 将构建产物传递给下一个 job
      - name: Upload build artifact
        uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/
          retention-days: 7

  # ============ 部署到生产环境 ============
  deploy:
    name: Deploy to Production
    needs: build    # 依赖 build job 成功后才执行
    runs-on: ubuntu-latest
    # 仅 main 分支的 push 触发部署
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'

    steps:
      - name: Download build artifact
        uses: actions/download-artifact@v4
        with:
          name: dist
          path: dist/

      - name: Deploy via rsync
        uses: burnett01/rsync-deployments@6.0.0
        with:
          switches: -avzr --delete
          path: dist/
          remote_path: ${{ secrets.DEPLOY_PATH }}
          remote_host: ${{ secrets.DEPLOY_HOST }}
          remote_user: ${{ secrets.DEPLOY_USER }}
          remote_key: ${{ secrets.DEPLOY_KEY }}

      - name: Reload Nginx
        uses: appleboy/ssh-action@v1.0.3
        with:
          host: ${{ secrets.DEPLOY_HOST }}
          username: ${{ secrets.DEPLOY_USER }}
          key: ${{ secrets.DEPLOY_KEY }}
          script: |
            nginx -t && nginx -s reload
            echo "Deployment completed at $(date)"
```

### 5.5 其他 CI/CD 方案

| 平台 | 配置文件 | 特点 |
|------|---------|------|
| **GitHub Actions** | `.github/workflows/*.yml` | 与 GitHub 深度集成，生态丰富 |
| **GitLab CI** | `.gitlab-ci.yml` | 自托管 Runner，适合内网项目 |
| **Jenkins** | `Jenkinsfile` | 老牌 CI/CD，插件丰富，可定制性强 |
| **Gitee Go** | `.gitee/pipelines/*.yml` | 国内访问快，适合 Gitee 仓库 |
| **Vercel** | 自动识别 | 零配置部署，适合个人项目和演示站点 |

**GitLab CI 示例（`.gitlab-ci.yml`）：**

```yaml
stages:
  - build
  - deploy

build:
  stage: build
  image: node:18-alpine
  script:
    - npm ci
    - npm run build
  artifacts:
    paths:
      - dist/
    expire_in: 1 hour

deploy:
  stage: deploy
  image: alpine
  before_script:
    - apk add --no-cache rsync openssh
    - mkdir -p ~/.ssh
    - echo "$SSH_PRIVATE_KEY" > ~/.ssh/id_rsa
    - chmod 600 ~/.ssh/id_rsa
    - ssh-keyscan -H $DEPLOY_HOST >> ~/.ssh/known_hosts
  script:
    - rsync -avz --delete dist/ $DEPLOY_USER@$DEPLOY_HOST:$DEPLOY_PATH
  only:
    - main
```

## 六、常见问题排查

### 6.1 部署后白屏

**现象**：页面打开后一片空白，浏览器控制台报错。

**排查步骤：**

```bash
# 1. 打开浏览器开发者工具 → Network 面板
#    检查 JS / CSS 文件是否 404

# 2. 查看请求的资源路径
#    如果请求的是 /assets/index-xxx.js 而实际部署在子目录
#    说明 base 配置不对
```

**常见原因与解决方案：**

```javascript
// 原因一：base 路径配置错误
// 解决：vite.config.js 中设置 base: './'

// 原因二：路由模式问题
// 如果使用 hash 模式，URL 带 # 号，不需要 try_files 配置
// 如果使用 history 模式，必须配置 try_files

// src/router/index.js
import { createRouter, createWebHistory, createWebHashHistory } from 'vue-router'

// history 模式（URL 更美观，但需要服务器配置支持）
const router = createRouter({
  history: createWebHistory(),
  routes
})

// hash 模式（URL 带 #，不需要服务器配置，兼容性更好）
const router = createRouter({
  history: createWebHashHistory(),
  routes
})
```

### 6.2 页面刷新后 404

**现象**：在 `/system/user` 页面刷新浏览器，显示 404。

**原因**：Nginx 没有配置 `try_files`，导致直接查找文件系统中的 `/system/user` 路径。

**解决方案：**

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

> **注意**：修改配置后执行 `sudo nginx -s reload` 重新加载。

### 6.3 API 请求失败

**现象**：页面能正常加载，但数据请求全部失败（Network 面板显示 502/504/CORS 错误）。

**排查清单：**

```
1. 确认后端服务是否正在运行
   → curl http://backend-server:8080/api/health

2. 确认 proxy_pass 地址是否正确
   → 检查 Nginx 配置中的后端地址和端口

3. 确认 proxy_pass 末尾的 / 是否匹配后端接口路径
   → /api/users 代理后是 /users 还是 /api/users

4. 确认防火墙是否放行了后端端口
   → sudo ufw allow 8080/tcp（Ubuntu）
   → sudo firewall-cmd --add-port=8080/tcp --permanent（CentOS）

5. 确认后端是否有跨域配置（如果 Nginx 代理则不需要后端配置跨域）
   → Nginx 代理是同源请求，不存在跨域问题
```

### 6.4 静态资源加载失败

**现象**：页面显示正常但图片/字体无法加载，控制台报 MIME type 错误。

**解决方案：**

```nginx
# 确认 Nginx 配置中包含了 MIME 类型文件
# 通常在 /etc/nginx/nginx.conf 的主配置中：
http {
    include /etc/nginx/mime.types;   # 确保这行存在
    default_type application/octet-stream;
    # ...
}
```

如果字体文件加载失败（跨域问题），添加 CORS 头：

```nginx
location ~* \.(woff|woff2|ttf|eot)$ {
    add_header Access-Control-Allow-Origin *;
    expires 30d;
}
```

### 6.5 构建报错

**常见构建错误与解决方案：**

```bash
# 错误一：内存不足（JavaScript heap out of memory）
# 解决：增加 Node 内存限制
export NODE_OPTIONS="--max-old-space-size=4096"
npm run build

# 错误二：依赖版本冲突
# 解决：删除 node_modules 和 lock 文件后重新安装
rm -rf node_modules package-lock.json
npm install
npm run build

# 错误三：某些包不支持 ESM
# 解决：在 vite.config.js 中添加预构建优化
optimizeDeps: {
  include: ['problematic-package']
}

# 错误四：环境变量未生效
# 检查 .env 文件的变量名是否以 VITE_ 开头
# Vite 只暴露 VITE_ 前缀的变量到客户端代码
```

### 6.6 构建产物体积过大

**优化清单：**

```
□ 路由是否使用了懒加载？
□ Element Plus 是否按需导入？
□ 是否有未使用的第三方库？（检查 package.json）
□ 大图片是否已压缩或转为 CDN 外链？
□ 是否配置了 manualChunks 进行代码分割？
□ 是否开启了 Gzip / Brotli 压缩？
□ 是否使用 rollup-plugin-visualizer 分析过包体积？
```

### 6.7 部署后旧版本缓存

**现象**：部署新版本后，部分用户看到的还是旧版本。

**解决方案：**

```nginx
# index.html 不缓存（确保每次都获取最新版本）
location = /index.html {
    add_header Cache-Control "no-cache, no-store, must-revalidate";
    add_header Pragma "no-cache";
    add_header Expires "0";
}

# 带哈希 的资源文件长期缓存
location ~* \.(js|css)$ {
    expires 1y;
    add_header Cache-Control "public, immutable";
}
```

```javascript
// 可选：在代码中添加版本检测，提示用户刷新
// src/utils/version.js
const CURRENT_VERSION = import.meta.env.VITE_APP_VERSION || '1.0.0'

export function checkVersion() {
  const storedVersion = localStorage.getItem('app_version')
  if (storedVersion && storedVersion !== CURRENT_VERSION) {
    // 检测到新版本，清除缓存并刷新
    localStorage.clear()
    window.location.reload(true)
  }
  localStorage.setItem('app_version', CURRENT_VERSION)
}
```

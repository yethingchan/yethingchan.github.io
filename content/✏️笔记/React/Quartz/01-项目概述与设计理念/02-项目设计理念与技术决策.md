Odyssey 项目的设计不是随意的功能堆砌，而是围绕几个核心原则展开的工程决策。这篇文章将深入分析项目的设计理念、每一个关键技术选型的权衡过程，以及实现中最具挑战性的技术难点。

## 核心设计理念

### 内容与展示分离

这是整个项目最基础的架构原则。你的所有笔记和文章都存放在 `content/` 目录下，以纯 Markdown 文件的形式存在，不包含任何展示逻辑。框架负责将这些内容转换为 HTML 页面，所有的样式、交互、布局都由 Quartz 的组件和样式系统处理。

这种分离带来的好处是显而易见的：你可以随时将笔记迁移到任何支持 Markdown 的平台，而不用担心丢失格式；你也可以在不触碰内容文件的前提下，完全重构博客的视觉设计。在本项目中，所有自定义组件（星空背景、光标发光、浮动时钟等）都是展示层的实现，与 `content/` 目录下的 Markdown 文件完全解耦。

### SSG 静态生成 + SPA 客户端路由

Quartz 采用了一种"混合模式"：**构建时生成静态 HTML，运行时以 SPA 方式导航**。

构建时（`npx quartz build`），Quartz 将所有 Markdown 文件转换为完整的 HTML 页面，输出到 `public/` 目录。这些页面可以被任何静态文件服务器托管——GitHub Pages、Nginx、Vercel 都可以。

但在浏览器中，当用户点击站内链接时，Quartz 不会触发完整的页面刷新。取而代之的是，SPA 路由拦截了点击事件，通过 `fetch` 获取目标页面的 HTML，然后用 DOM morphing 技术将当前页面"变形"为目标页面。这种设计的优势在于：首屏加载是纯静态的（SEO 友好、速度快），而站内导航体验又如同单页应用般流畅。

### 渐进增强

项目遵循渐进增强的原则：核心内容（文章文本）在任何环境下都能正常显示，而增强功能（星空背景、光标发光、SPA 导航等）作为附加层逐步加载。如果 JavaScript 加载失败，页面仍然能正常阅读。

## 技术选型决策分析

### Preact vs React 的权衡

在组件层的技术选型上，本项目继承 Quartz 的选择——使用 Preact。这是一个经过深思熟虑的决策：

**选 Preact 的理由：**
- 3KB vs React 的 40KB，对于博客这种首屏性能敏感的场景，差距是数量级的
- API 完全兼容 React，学习成本为零
- 构建时使用 `preact-render-to-string` 渲染为静态 HTML，不依赖客户端 JavaScript
- 博客 UI 的复杂度不需要 React 的高级特性（Concurrent Mode、Suspense 等）

**如果选 React 会怎样：**
- 每个 HTML 页面会多出约 10KB 的 JavaScript 体积（gzipped）
- 需要额外的 Babel 插件来兼容 JSX
- 对移动端用户来说，额外的 JavaScript 意味着更长的白屏时间

在 `quartz.layout.ts` 中可以看到组件的声明方式与 React 完全一致：

```typescript
// quartz.layout.ts -- 布局声明，纯声明式配置
export const defaultContentPageLayout: PageLayout = {
  beforeBody: [
    Component.ConditionalRender({
      component: Component.Breadcrumbs(),
      condition: (page) => page.fileData.slug !== "index",
    }),
    Component.ArticleTitle(),
    Component.ContentMeta(),
    Component.TagList(),
  ],
  left: [
    Component.PageTitle(),
    Component.Flex({
      components: [
        { Component: Component.Search(), grow: true },
        { Component: Component.Darkmode() },
        { Component: Component.ReaderMode() },
      ],
    }),
    Component.Explorer(),
  ],
  right: [
    Component.Graph(),
    Component.DesktopOnly(Component.TableOfContents()),
    Component.Backlinks(),
  ],
  // ...
}
```

### remark/rehype AST 处理管道

选择 unified 生态（remark/rehype）而非手写正则解析器，是因为 Markdown 的语法规则极其复杂，特别是当需要兼容多种 Markdown 方言时。unified 提供了统一的 AST 抽象，让所有处理步骤都在树结构上操作，而不是在文本上做正则匹配。

以本项目的 Transformer 插件配置为例：

```typescript
// quartz.config.ts -- 插件链的配置
plugins: {
  transformers: [
    Plugin.FrontMatter(),                                    // 提取 YAML frontmatter
    Plugin.CreatedModifiedDate({ priority: ["frontmatter", "git", "filesystem"] }),
    Plugin.SyntaxHighlighting({ theme: { light: "github-light", dark: "github-dark" } }),
    Plugin.ObsidianFlavoredMarkdown({ enableInHtmlEmbed: false }),
    Plugin.GitHubFlavoredMarkdown(),                         // 表格、任务列表、脚注
    Plugin.TableOfContents(),                                // 生成 TOC
    Plugin.CrawlLinks({ markdownLinkResolution: "shortest" }),
    Plugin.Description(),                                    // 提取描述
    Plugin.Latex({ renderEngine: "katex" }),                 // LaTeX 公式
    Plugin.HardLineBreaks(),                                 // 硬换行
  ],
  filters: [Plugin.RemoveDrafts()],                          // 过滤草稿
  emitters: [
    Plugin.ContentPage(),                                    // 生成 HTML 页面
    Plugin.FolderPage(),                                     // 生成文件夹页
    Plugin.TagPage(),                                        // 生成标签页
    Plugin.ContentIndex({ enableSiteMap: true, enableRSS: true }),
    Plugin.Assets(),                                         // 拷贝静态资源
    // ...
  ],
}
```

每个 Transformer 插件都可以在 MD 层或 HTML 层注入处理逻辑，这种方式的优势在于：插件之间完全解耦，顺序可配置，且每个插件只关注自己的转换逻辑。

### 插件化架构：三层设计模式

Quartz 的插件系统采用 **Transformer / Filter / Emitter** 三层设计：

```
内容文件 ──→ [Transformer 链] ──→ [Filter 链] ──→ [Emitter 链] ──→ 输出文件
             修改内容              决定是否发布       生成输出
```

- **Transformer** -- 负责内容转换，修改 AST 或文本。每个 Transformer 可以注册三个阶段的处理器：`textTransform`（文本级）、`markdownPlugins`（MDAST 级）、`htmlPlugins`（HAST 级）
- **Filter** -- 负责决定哪些内容应该被发布，返回布尔值
- **Emitter** -- 负责将处理后的内容转化为输出文件（HTML、JSON、RSS 等），每个 Emitter 返回生成的文件路径列表

这种设计让每个插件只做一件事，职责清晰。添加新功能只需要编写一个符合接口定义的插件，然后在配置中注册即可。

### 静态生成 + SPA 的混合模式

这是 Quartz 最独特的架构特征。SPA 导航的核心是 `quartz/components/scripts/spa.inline.ts`，它使用 micromorph 库实现 DOM morphing：

```typescript
// quartz/components/scripts/spa.inline.ts -- 核心导航逻辑
async function _navigate(url: URL, isBack: boolean = false) {
  isNavigating = true
  startLoading()
  const contents = await fetchCanonical(url)  // 获取目标页面 HTML
    .then((res) => {
      const contentType = res.headers.get("content-type")
      if (contentType?.startsWith("text/html")) {
        return res.text()
      } else {
        window.location.assign(url)  // 非页面请求则交给浏览器处理
      }
    })

  // 通知即将导航
  const event = new CustomEvent("prenav", { detail: {} })
  document.dispatchEvent(event)

  // 清理旧页面的事件监听器和定时器
  cleanupFns.forEach((fn) => fn())
  cleanupFns.clear()

  const html = p.parseFromString(contents, "text/html")
  normalizeRelativeURLs(html, url)

  // DOM morphing：将当前页面"变形"为目标页面
  await micromorph(document.body, html.body)

  // 更新 <head> 中的资源
  document.head.querySelectorAll(":not([data-persist])").forEach((el) => el.remove())
  html.head.querySelectorAll(":not([data-persist])").forEach((el) => document.head.appendChild(el))

  // 更新浏览器历史
  history.pushState({}, "", url)
  notifyNav(getFullSlug(window))
}
```

micromorph 的工作原理是对新旧两棵 DOM 树进行差异比较，然后只修改发生变化的部分。与传统的 `innerHTML` 替换相比，DOM morphing 能保留不变节点的状态——视频不会重新播放、滚动位置不会丢失、动画不会被中断。这就是为什么 Quartz 的页面切换如此流畅。

## 内容组织策略

### 基于文件夹的层级结构

Odyssey 项目采用文件夹层级来组织内容。在 `content/` 目录下，文件夹本身就是分类——如 `content/✏️笔记/C sharp/` 存放 C# 相关笔记，`content/✏️笔记/若依/` 存放若依框架的分析文章。这种方式直观且易于管理。

### Trie 树数据结构

Quartz 将文件夹结构映射为一棵 **Trie 树（前缀树）**，由 `quartz/util/fileTrie.ts` 实现。Trie 树天然适合表示文件路径的层级关系：

```typescript
// quartz/util/fileTrie.ts -- Trie 树节点定义
export class FileTrieNode<T extends FileTrieData = ContentDetails> {
  isFolder: boolean
  children: Array<FileTrieNode<T>>
  private slugSegments: string[]
  private data: T | null

  // 插入文件到 Trie
  add(file: T) {
    this.insert(file.slug.split("/"), file)
  }

  // 查找路径对应的节点
  findNode(path: string[]): FileTrieNode<T> | undefined {
    if (path.length === 0 || (path.length === 1 && path[0] === "index")) {
      return this
    }
    return this.children.find((c) => c.slugSegment === path[0])?.findNode(path.slice(1))
  }

  // 获取祖先链（用于面包屑导航）
  ancestryChain(path: string[]): Array<FileTrieNode<T>> | undefined {
    if (path.length === 0 || (path.length === 1 && path[0] === "index")) {
      return [this]
    }
    const child = this.children.find((c) => c.slugSegment === path[0])
    if (!child) return undefined
    const childPath = child.ancestryChain(path.slice(1))
    if (!childPath) return undefined
    return [this, ...childPath]
  }
}
```

Explorer 组件、面包屑导航、文件夹页面都依赖这棵 Trie 树来理解文件之间的关系。

## 构建时 vs 运行时的划分

Quartz 对"什么在构建时做、什么在浏览器中做"有明确的划分原则：

| 职责 | 构建时（Node.js） | 运行时（浏览器） |
|:---|:---|:---|
| Markdown 解析 | 是 | 否 |
| 语法高亮 | 是（Shiki） | 否 |
| LaTeX 渲染 | 是（KaTeX） | 否 |
| HTML 页面生成 | 是（Preact SSR） | 否 |
| 搜索索引构建 | 是（FlexSearch 索引） | 否 |
| SPA 导航 | 否 | 是（micromorph） |
| 搜索交互 | 否 | 是（FlexSearch 查询） |
| 图谱渲染 | 否 | 是（D3.js） |
| 暗色模式切换 | 否 | 是（CSS 变量） |
| 星空粒子动画 | 否 | 是（tsParticles CDN） |

原则很简单：**能预先计算的绝不放到浏览器中做**。文章渲染、语法高亮、数学公式这些计算密集型任务全部在构建时完成，浏览器只需要处理交互逻辑。

## 项目的技术难点

### 增量构建（partialEmit）

当开发服务器处于 watch 模式时，每次文件变更不需要重新构建整个站点。Quartz 通过 `partialEmit` 机制实现了增量构建。在 `quartz/build.ts` 的 `rebuild` 函数中：

```typescript
// quartz/build.ts -- 增量构建核心逻辑
for (const emitter of cfg.plugins.emitters) {
  // 优先使用 partialEmit，否则退回完整 emit
  const emitFn = emitter.partialEmit ?? emitter.emit
  const emitted = await emitFn(ctx, processedFiles, staticResources, changeEvents)
  // ...
}
```

每个 Emitter 可以选择实现 `partialEmit` 方法来只处理变更的文件。例如，内容索引（ContentIndex）在增量构建时只需要更新被修改的条目，而不需要重新序列化整个索引。

### 多线程 Markdown 解析

Markdown 解析是 CPU 密集型操作。Quartz 使用 workerpool 将文件分块后分配给多个 Worker 线程并行处理：

```typescript
// quartz/processors/parse.ts -- 多线程解析
const CHUNK_SIZE = 128
const concurrency = ctx.argv.concurrency ?? clamp(fps.length / CHUNK_SIZE, 1, 4)

const pool = workerpool.pool("./quartz/bootstrap-worker.mjs", {
  minWorkers: "max",
  maxWorkers: concurrency,
  workerType: "thread",
})

// 将文件按 128 个一组分块，分发给 Worker 线程
for (const chunk of chunks(fps, CHUNK_SIZE)) {
  textToMarkdownPromises.push(pool.exec("parseMarkdown", [serializableCtx, chunk]))
}
```

分块大小 128 是一个经验值，足以让 V8 的 JIT 编译器优化解析代码路径。Worker 线程的构建上下文需要可序列化（`WorkerSerializableBuildCtx`），因为它需要通过 `postMessage` 传递到子线程。

### 文件夹层级到 Trie 树的映射

将文件系统的文件夹结构映射到 Trie 树并非简单的一对一映射。需要处理特殊情况：`index.md` 文件代表文件夹本身的"首页"；没有 `index.md` 的文件夹需要从路径段推断显示名称；slug 的规范化处理（去除日期前缀、处理中文字符等）。这些边界条件都在 `FileTrieNode.insert` 方法中处理。

### 移动端 Explorer 的全屏覆盖与滚动锁定

Explorer 组件在桌面端是侧边栏的一部分，而在移动端则变成全屏覆盖层。这需要同时处理：触摸滑动的交互、背景内容的滚动锁定（`overflow: hidden`）、以及展开/收起的状态同步。这是一个典型的跨端适配难题，需要在 CSS 和 JavaScript 之间协调。

## i18n 国际化的设计思路

Quartz 的国际化采用"构建时翻译"的策略。翻译文件存放在 `quartz/i18n/locales/` 目录下，每个语言一个文件（如 `zh-CN.ts`、`en-US.ts`）。配置中指定 `locale` 后，构建过程会自动选择对应的翻译：

```typescript
// quartz.config.ts -- 语言配置
configuration: {
  locale: "zh-CN",  // 使用简体中文翻译
  // ...
}

// quartz/i18n/index.ts -- 翻译查找
export const i18n = (locale: ValidLocale): Translation =>
  TRANSLATIONS[locale ?? defaultTranslation]
```

翻译系统支持 locale 回退——例如 `zh-CN` 会精确匹配 `zh-CN`，而 `zh-HK` 如果没有专门的翻译文件，会回退到默认的 `en-US`。整个翻译定义了 UI 中所有文本字符串，包括搜索框占位符、按钮文字、日期格式等，确保所有面向用户的文本都可以被翻译。

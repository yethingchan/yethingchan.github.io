Quartz 的内容管道（Content Pipeline）是将一堆 Markdown 文件转化为静态 HTML 网站的核心引擎。理解这条管道的工作方式，是深入定制和优化 Quartz 的基础。本文将逐层剖析从文件发现到最终输出的完整流程。

## 一、内容管道总览

Quartz 的构建流程可以用一条清晰的管道来表示：

```
Markdown 文件 (.md)
    |
    v
[Glob 文件发现] --> 收集所有 .md 文件路径
    |
    v
[Parse] --> 文本 -> MDAST -> HAST (HTML AST)
    |
    v
[Transform] --> 通过 transformer 插件链修改 AST
    |
    v
[Filter] --> 通过 filter 插件链决定哪些文件需要发布
    |
    v
[Emit] --> 通过 emitter 插件链生成最终 HTML/JSON/静态资源
    |
    v
静态网站输出 (public/)
```

这条管道由 `build.ts` 中的 `buildQuartz` 函数驱动，三个处理器（`processors/` 目录下的 `parse.ts`、`filter.ts`、`emit.ts`）各司其职。下面我们逐一拆解。

## 二、buildQuartz 函数逐步分析

`quartz/build.ts` 中的 `buildQuartz` 是整个构建流程的入口函数。它的执行步骤如下：

**第一步：构建上下文初始化**

```ts
async function buildQuartz(argv: Argv, mut: Mutex, clientRefresh: () => void) {
  const ctx: BuildCtx = {
    buildId: randomIdNonSecure(),
    argv,
    cfg,
    allSlugs: [],
    allFiles: [],
    incremental: false,
  }
  // ...
}
```

`BuildCtx` 是贯穿整个构建过程的上下文对象，包含了构建 ID（用于标识同一次构建）、命令行参数、配置对象、所有 slug 列表和所有文件列表。`incremental` 标志位用于区分全量构建和增量构建。

**第二步：清理输出目录**

```ts
const release = await mut.acquire()
perf.addEvent("clean")
await rm(output, { recursive: true, force: true })
```

使用 `Mutex` 互斥锁确保同一时间只有一个构建过程在执行（这在 watch 模式下尤为重要，防止并发重写）。`rm` 递归删除整个输出目录，保证每次构建都是干净的。

**第三步：Glob 文件发现**

```ts
const allFiles = await glob("**/*.*", argv.directory, cfg.configuration.ignorePatterns)
const markdownPaths = allFiles.filter((fp) => fp.endsWith(".md")).sort()
```

`glob` 函数（位于 `quartz/util/glob.ts`）封装了 `globby` 库，支持 glob 模式匹配和 `.gitignore` 规则：

```ts
export async function glob(
  pattern: string,
  cwd: string,
  ignorePatterns: string[],
): Promise<FilePath[]> {
  const fps = (
    await globby(pattern, {
      cwd,
      ignore: ignorePatterns,
      gitignore: true,
    })
  ).map(toPosixPath)
  return fps as FilePath[]
}
```

这里做了两件关键的事：一是使用 `ignorePatterns`（在本项目中配置为 `["private", "templates", ".obsidian"]`）过滤掉不需要的目录；二是启用 `gitignore: true`，自动尊重 `.gitignore` 中的规则。收集到的结果会经过 `.sort()` 排序，保证构建结果的确定性。

**第四步：核心管道执行**

```ts
const filePaths = markdownPaths.map((fp) => joinSegments(argv.directory, fp) as FilePath)
ctx.allFiles = allFiles
ctx.allSlugs = allFiles.map((fp) => slugifyFilePath(fp as FilePath))

const parsedFiles = await parseMarkdown(ctx, filePaths)
const filteredContent = filterContent(ctx, parsedFiles)
await emitContent(ctx, filteredContent)
```

这段代码体现了管道模式的核心：每个处理器的输出就是下一个处理器的输入。注意 `allSlugs` 和 `allFiles` 在这一步被写入上下文，后续的 transformer 和 emitter 都可以通过 `ctx.allSlugs` 获取所有文件的 slug 列表，用于链接解析和去重判断。

## 三、多线程 Markdown 解析（workerpool）

`parseMarkdown` 是构建过程中最耗时的环节。Quartz 通过 `workerpool` 实现了多线程解析，显著提升了构建速度。

解析过程分为两个阶段：

1. **Text -> Markdown AST**：使用 `createMdProcessor` 创建 unified 处理器，结合 `remarkParse` 和各 transformer 的 `markdownPlugins`，将原始文本解析为 MDAST。
2. **Markdown AST -> HTML AST**：使用 `createHtmlProcessor`，结合 `remarkRehype` 和各 transformer 的 `htmlPlugins`，将 MDAST 转换为 HAST。

多线程策略的关键在于分块（chunking）：

```ts
const CHUNK_SIZE = 128
const concurrency = ctx.argv.concurrency ?? clamp(fps.length / CHUNK_SIZE, 1, 4)
```

默认块大小为 128 个文件，并发度根据文件数量动态计算，上限为 4 个线程。这个值是经过测试得出的经验值——128 个文件足以让 V8 引擎的 JIT 编译器优化解析代码路径。

工作线程的通信流程：

```
主线程                          工作线程池 (N 个线程)
  |-- transpileWorkerScript()
  |     (用 esbuild 将 worker.ts 编译为 .mjs)
  |
  |-- 分块发送文件路径 -------->  parseMarkdown() [Text -> MDAST]
  |                              processHtml()    [MDAST -> HAST]
  |<-------- 返回解析结果 --------
  |
  |-- 汇总结果 (results.flat())
  |-- pool.terminate()
```

`worker.ts` 中的工作线程函数非常简洁，它只是重建 `BuildCtx` 然后调用与主线程相同的处理器工厂：

```ts
export async function parseMarkdown(
  partialCtx: WorkerSerializableBuildCtx,
  fps: FilePath[],
): Promise<MarkdownContent[]> {
  const ctx: BuildCtx = { ...partialCtx, cfg }
  return await createFileParser(ctx, fps)(createMdProcessor(ctx))
}
```

值得注意的是，工作线程只接收可序列化的上下文（`WorkerSerializableBuildCtx`），不包含完整的 cfg 对象——cfg 是在工作线程内部通过 `import cfg` 重新加载的。

## 四、过滤器处理器

`filter.ts` 是三个处理器中最简单的一个：

```ts
export function filterContent(ctx: BuildCtx, content: ProcessedContent[]): ProcessedContent[] {
  const { cfg, argv } = ctx
  const initialLength = content.length
  for (const plugin of cfg.plugins.filters) {
    const updatedContent = content.filter((item) => plugin.shouldPublish(ctx, item))
    content = updatedContent
  }
  console.log(`Filtered out ${initialLength - content.length} files in ${perf.timeSince()}`)
  return content
}
```

每个 filter 插件通过 `shouldPublish` 方法判断文件是否应该被发布。所有 filter 依次执行，形成一个过滤链——文件必须通过所有 filter 才能进入 emit 阶段。本项目使用的 `RemoveDrafts` filter 会检查 frontmatter 中的 `draft` 字段：

```ts
export const RemoveDrafts: QuartzFilterPlugin<{}> = () => ({
  name: "RemoveDrafts",
  shouldPublish(_ctx, [_tree, vfile]) {
    const draftFlag: boolean =
      vfile.data?.frontmatter?.draft === true || vfile.data?.frontmatter?.draft === "true"
    return !draftFlag
  },
})
```

## 五、输出处理器

`emit.ts` 使用 `Promise.all` 并行执行所有 emitter：

```ts
await Promise.all(
  cfg.plugins.emitters.map(async (emitter) => {
    const emitted = await emitter.emit(ctx, content, staticResources)
    // ... 统计输出文件数
  }),
)
```

每个 emitter 可以返回 `Promise<FilePath[]>` 或 `AsyncGenerator<FilePath>`。使用 AsyncGenerator 的好处是 emitter 可以在生成文件的同时让主线程收集结果，不必等待全部完成后再返回。

## 六、增量构建（partialEmit）

当 `--watch` 模式启用时，Quartz 进入增量构建模式。增量构建的核心思路是：只重新生成发生变化的页面，而非全量重建。

`contentMap` 是增量构建的状态管理中枢：

```ts
type ContentMap = Map<
  FilePath,
  | { type: "markdown"; content: ProcessedContent }
  | { type: "other" }
>
```

它维护了从文件路径到解析后内容的映射。每次文件变化时：

1. **新增文件（add）**：重新解析该文件，更新 contentMap
2. **修改文件（change）**：重新解析该文件，更新 contentMap
3. **删除文件（delete）**：从 contentMap 中移除

在 rebuild 函数中，增量构建优先使用 emitter 的 `partialEmit` 方法：

```ts
const emitFn = emitter.partialEmit ?? emitter.emit
const emitted = await emitFn(ctx, processedFiles, staticResources, changeEvents)
```

以 `ContentPage` 为例，它的 `partialEmit` 只处理发生变化的 slug：

```ts
async *partialEmit(ctx, content, resources, changeEvents) {
  const changedSlugs = new Set<string>()
  for (const changeEvent of changeEvents) {
    if (!changeEvent.file) continue
    if (changeEvent.type === "add" || changeEvent.type === "change") {
      changedSlugs.add(changeEvent.file.data.slug!)
    }
  }
  for (const [tree, file] of content) {
    const slug = file.data.slug!
    if (!changedSlugs.has(slug)) continue  // 跳过未变化的文件
    yield processContent(ctx, tree, file.data, allFiles, opts, resources)
  }
}
```

## 七、chokidar 文件监视与热重载

文件监视由 `chokidar` 驱动，配置如下：

```ts
const watcher = chokidar.watch(".", {
  awaitWriteFinish: { stabilityThreshold: 250 },  // 文件写入稳定 250ms 后才触发
  persistent: true,
  cwd: argv.directory,
  ignoreInitial: true,  // 不处理初始扫描，只监视后续变化
})
```

`stabilityThreshold: 250` 是一个关键的防抖参数。编辑器保存文件时可能产生多次写入事件（例如先写空文件再写内容），这个阈值确保只有在文件停止写入 250ms 后才触发重新构建。

监视器监听三种事件：`add`（新文件）、`change`（文件修改）、`unlink`（文件删除）。每个事件都会触发 `rebuild` 函数，但通过 `Mutex` 互斥锁保证同一时间只有一个构建在执行。如果后续的构建 ID 与当前不匹配（说明有更新的构建请求排队），当前构建会主动退出：

```ts
const buildId = randomIdNonSecure()
ctx.buildId = buildId
const release = await mut.acquire()
if (ctx.buildId !== buildId) {
  release()
  return  // 让更新的构建接管
}
```

构建完成后调用 `clientRefresh()` 通知客户端浏览器刷新。

## 八、构建性能优化策略

Quartz 在构建性能方面采取了多项优化措施：

1. **分块多线程解析**：将文件分成 128 个一组，分配到最多 4 个工作线程并行处理
2. **增量构建**：watch 模式下只重新解析和生成变化的文件
3. **partialEmit**：emitter 级别的增量支持，跳过未变化的页面
4. **esbuild 预编译工作线程脚本**：避免每次构建都重新编译 worker 脚本（缓存到 `.quartz-cache/transpiled-worker.mjs`）
5. **文件写入防抖**：chokidar 的 `stabilityThreshold` 避免重复构建
6. **构建 ID 去重**：通过 `buildId` 机制，让过时的构建请求自动退出
7. **并行 emit**：所有 emitter 通过 `Promise.all` 并行执行

理解了这套管道，你就能明白 Quartz 为什么能在几百个 Markdown 文件的情况下仍然保持亚秒级的构建速度。后续章节将深入管道中的各个环节，讲解插件系统、页面渲染和路由系统的实现细节。

Quartz 的插件系统是整个框架的灵魂。从 frontmatter 解析到代码高亮、从链接爬取到 LaTeX 渲染，几乎所有核心功能都由插件实现。本文将深入分析插件系统的架构设计、三种插件类型的工作原理，以及本项目实际使用的完整插件链。

## 一、插件系统的设计模式

Quartz 的插件系统采用了经典的 **管道模式（Pipeline Pattern）**，同时融入了 **责任链模式（Chain of Responsibility）** 的思想。

在管道模式中，数据沿着一条固定的路径流经一系列处理器，每个处理器对数据进行特定的转换或过滤。Quartz 的内容管道就是这条固定的路径：

```
Text -> [textTransform] -> MDAST -> [markdownPlugins] -> MDAST -> HAST -> [htmlPlugins] -> HAST
                                                                        |
                                                                   [filters]
                                                                        |
                                                                   [emitters]
```

而责任链的体现则在于 filter 插件链——每个 filter 都有权决定文件是否继续往下传递。

这种设计使得每个插件都可以独立开发、独立测试、独立配置。要增加新功能，只需在配置中添加对应的插件即可。

## 二、插件接口详解

Quartz 的插件类型定义在 `quartz/plugins/types.ts` 中。所有插件都遵循工厂函数模式——每个插件是一个返回插件实例的函数：

```ts
// 插件类型 = 一个接受 Options 的工厂函数，返回插件实例
export type QuartzTransformerPlugin<Options extends OptionType = undefined> = (
  opts?: Options,
) => QuartzTransformerPluginInstance
```

这种设计的好处在于：插件的使用和配置被分离了。你在配置文件中调用 `Plugin.FrontMatter()` 获取实例，传参时可以覆盖默认选项。

## 三、三种插件类型

### 3.1 QuartzTransformer -- 修改 AST

Transformer 是最复杂也最强大的插件类型，它负责在解析过程中修改内容。一个 transformer 实例的接口定义如下：

```ts
export type QuartzTransformerPluginInstance = {
  name: string
  textTransform?: (ctx: BuildCtx, src: string) => string        // 纯文本变换
  markdownPlugins?: (ctx: BuildCtx) => PluggableList             // MDAST 级别的插件
  htmlPlugins?: (ctx: BuildCtx) => PluggableList                // HAST 级别的插件
  externalResources?: (ctx: BuildCtx) => Partial<StaticResources>
}
```

Transformer 拥有三个变换钩子，分别作用于内容处理的不同阶段：

1. **textTransform**：在 Markdown 被解析之前对原始文本进行修改。这个阶段还没有 AST，操作对象是纯字符串。
2. **markdownPlugins**：在 MDAST（Markdown Abstract Syntax Tree）阶段操作。此时已经解析了 Markdown 的结构，但还没有转换为 HTML。适合处理 Markdown 特有的语法（如 frontmatter、Wiki 链接、数学公式标记等）。
3. **htmlPlugins**：在 HAST（HTML Abstract Syntax Tree）阶段操作。此时 Markdown 已经转换为 HTML 结构。适合处理 HTML 级别的变换（如代码高亮、链接处理、描述提取等）。

### 3.2 QuartzFilter -- 过滤文件

Filter 插件的接口非常简洁：

```ts
export type QuartzFilterPluginInstance = {
  name: string
  shouldPublish(ctx: BuildCtx, content: ProcessedContent): boolean
}
```

它只做一件事：决定一个文件是否应该被发布到最终输出。返回 `true` 表示保留，返回 `false` 表示过滤掉。

### 3.3 QuartzEmitter -- 生成输出

Emitter 是管道的最后一环，负责将处理后的内容转化为实际的输出文件：

```ts
export type QuartzEmitterPluginInstance = {
  name: string
  emit: (ctx, content, resources) => Promise<FilePath[]> | AsyncGenerator<FilePath>
  partialEmit?: (ctx, content, resources, changeEvents) => Promise<FilePath[]> | AsyncGenerator<FilePath> | null
  getQuartzComponents?: (ctx: BuildCtx) => QuartzComponent[]
  externalResources?: ExternalResourcesFn
}
```

- `emit`：全量输出，构建时调用
- `partialEmit`：增量输出，watch 模式下只处理变化的文件。返回 `null` 表示该 emitter 不支持增量输出，回退到全量 emit
- `getQuartzComponents`：声明该 emitter 使用了哪些 UI 组件，用于资源优化（只注入用到的组件的 CSS/JS）

## 五、关键 Transformer 工作原理

### 5.1 FrontMatter -- YAML 解析与 DataMap 注入

FrontMatter 是所有 transformer 中最先执行的，它负责解析 Markdown 文件顶部的 YAML 元数据块。

工作流程：首先通过 `remark-frontmatter` 插件将 YAML 块从文本中提取为 MDAST 节点，然后使用 `gray-matter` 库解析 YAML/JSON 内容，最后将解析结果注入到 `file.data.frontmatter` 中。

关键的数据处理逻辑：

```ts
// 标题处理：优先使用 frontmatter 中的 title，否则使用文件名
if (data.title != null && data.title.toString() !== "") {
  data.title = data.title.toString()
} else {
  data.title = file.stem ?? i18n(cfg.configuration.locale).propertyDefaults.title
}

// 标签处理：统一 "tags"/"tag" 别名，去重，生成 slug
const tags = coerceToArray(coalesceAliases(data, ["tags", "tag"]))
if (tags) data.tags = [...new Set(tags.map((tag: string) => slugTag(tag)))]

// 日期处理：合并 "created"/"date"、"modified"/"lastmod"/"updated" 等别名
const created = coalesceAliases(data, ["created", "date"])
const modified = coalesceAliases(data, ["modified", "lastmod", "updated", "last-modified"])
data.modified ||= created  // 如果没有修改日期，使用创建日期
```

`coalesceAliases` 函数体现了 Obsidian 兼容性设计——它接受多个别名，按优先级取第一个非空值。

### 5.2 CreatedModifiedDate -- 日期提取的优先级机制

日期插件的配置选项定义了日期来源的优先级：

```ts
interface Options {
  priority: ("frontmatter" | "git" | "filesystem")[]
}

const defaultOptions: Options = {
  priority: ["frontmatter", "git", "filesystem"],
}
```

本项目的配置是 `priority: ["frontmatter", "git", "filesystem"]`，含义是：

1. 优先使用 frontmatter 中指定的日期（如 `created: 2024-01-15`）
2. 如果 frontmatter 没有指定，尝试从 git 历史中获取（使用 `@napi-rs/simple-git` 查询文件的首次提交时间和最后修改时间）
3. 如果 git 也不可用（如文件未被追踪），回退到文件系统的 `birthtime` 和 `mtime`

代码中使用 `||=` 运算符实现了优先级机制——只有当前优先级的来源没有提供值时，才会尝试下一个优先级：

```ts
for (const source of opts.priority) {
  if (source === "filesystem") {
    const st = await fs.promises.stat(fullFp)
    created ||= st.birthtimeMs
    modified ||= st.mtimeMs
  } else if (source === "frontmatter" && file.data.frontmatter) {
    created ||= file.data.frontmatter.created as MaybeDate
    modified ||= file.data.frontmatter.modified as MaybeDate
  } else if (source === "git" && repo) {
    modified ||= await repo.getFileLatestModifiedDateAsync(relativePath)
  }
}
```

此外，日期解析还处理了 ISO 8601 纯日期格式（`YYYY-MM-DD`）的特殊情况——JavaScript 的 `Date` 构造函数会将纯日期解析为 UTC 午夜，所以需要手动追加 `T00:00:00` 来使用本地时区。

### 5.3 SyntaxHighlighting -- 双主题代码高亮

语法高亮插件使用 `rehype-pretty-code`（基于 `shiki`）实现：

```ts
export const SyntaxHighlighting: QuartzTransformerPlugin<Partial<Options>> = (userOpts) => {
  const opts: CodeOptions = { ...defaultOptions, ...userOpts }
  return {
    name: "SyntaxHighlighting",
    htmlPlugins() {
      return [[rehypePrettyCode, opts]]
    },
  }
}
```

这是一个 **htmlPlugins** 阶段的插件，因为它需要在 HAST 层面操作代码块元素。`rehype-pretty-code` 会在 HTML AST 中找到 `<pre><code>` 元素，使用 shiki 进行语法高亮，然后替换为带样式的 HTML。

双主题通过 `theme` 配置实现：

```ts
theme: {
  light: "github-light",
  dark: "github-dark",
}
```

生成的 HTML 会同时包含亮色和暗色两套样式，通过 CSS `prefers-color-scheme` 媒体查询或 Quartz 的暗色模式切换来显示对应的主题。

### 5.4 TableOfContents -- 锚点生成

TOC 插件工作在 **markdownPlugins** 阶段，遍历 MDAST 中的 heading 节点：

```ts
visit(tree, "heading", (node) => {
  if (node.depth <= opts.maxDepth) {
    const text = toString(node)
    highestDepth = Math.min(highestDepth, node.depth)
    toc.push({
      depth: node.depth,
      text,
      slug: slugAnchor.slug(text),
    })
  }
})
```

使用 `github-slugger` 的 `slug()` 方法为每个标题生成 URL 友好的锚点 ID。这个库会自动处理重复标题的情况——如果两个标题文本相同，会追加 `-1`、`-2` 等后缀。

TOC 的深度会进行标准化处理，`depth: entry.depth - highestDepth`，使最高层级的标题深度为 0，方便前端渲染时正确缩进。TOC 数据存储在 `file.data.toc` 中，最终由 `TableOfContents` 组件在右侧边栏渲染。

### 5.5 CrawlLinks -- 内部链接解析与校验

链接爬取是一个 **htmlPlugins** 阶段的插件，它的职责是处理 HTML AST 中所有的 `<a>` 和 `<img>` 等元素的链接属性。

核心逻辑：

1. **链接分类**：区分内部链接和外部链接，分别添加 `internal` 和 `external` CSS 类
2. **外部链接**：可选添加外链图标 SVG、设置 `target="_blank"`
3. **内部链接**：调用 `transformLink` 将 Obsidian 风格的链接转换为标准 URL，同时记录 outgoing links 到 `file.data.links`（用于 backlinks 计算）
4. **Pretty Links**：可选地用文件名（去掉路径前缀）替换链接文本

`transformLink` 函数支持三种策略：`relative`（相对路径）、`absolute`（从站点根目录的绝对路径）、`shortest`（如果文件名唯一则使用最短路径）。本项目配置为 `shortest`：

```ts
Plugin.CrawlLinks({ markdownLinkResolution: "shortest" }),
```

`shortest` 策略的逻辑是：如果目标文件名在整个站点中是唯一的，就只使用文件名；如果同名文件存在多个，则使用完整路径。这样可以在保证链接正确性的前提下让链接尽可能简洁。

### 5.6 Description -- Meta Description 生成

Description 插件工作在 **htmlPlugins** 阶段，为每个页面生成 `<meta name="description">` 的内容：

1. 如果 frontmatter 中有 `description` 字段，直接使用
2. 否则，从 HTML AST 中提取文本内容，按句子分割，逐句累加直到达到 `descriptionLength`（默认 150 字符）的限制
3. 最终结果会被截断到 `maxDescriptionLength`（默认 300 字符）

还有一个实用功能：可选地移除外部链接 URL，只保留域名和路径部分：

```ts
if (opts.replaceExternalLinks) {
  frontMatterDescription = frontMatterDescription?.replace(urlRegex, "$<domain>$<path>")
  text = text.replace(urlRegex, "$<domain>$<path>")
}
```

### 5.7 Latex -- 数学公式渲染

LaTeX 插件跨越两个阶段：

- **markdownPlugins** 阶段：使用 `remark-math` 解析 Markdown 中的数学公式语法（`$...$` 行内公式、`$$...$$` 块级公式）
- **htmlPlugins** 阶段：使用 `rehype-katex`（或 `rehype-mathjax`、`rehype-typst`）将解析出的数学公式节点渲染为 HTML

```ts
export const Latex: QuartzTransformerPlugin<Partial<Options>> = (opts) => {
  const engine = opts?.renderEngine ?? "katex"
  return {
    name: "Latex",
    markdownPlugins() {
      return [remarkMath]        // 解析数学公式标记
    },
    htmlPlugins() {
      return [[rehypeKatex, { output: "html", macros, ...(opts?.katexOptions ?? {}) }]]
    },
    externalResources() {
      return {
        css: [{ content: "https://cdn.jsdelivr.net/npm/katex@0.16.11/dist/katex.min.css" }],
        js: [{
          src: "https://cdn.jsdelivr.net/npm/katex@0.16.11/dist/contrib/copy-tex.min.js",
          loadTime: "afterDOMReady",
          contentType: "external",
        }],
      }
    },
  }
}
```

`externalResources` 方法声明了 KaTeX 需要的外部 CSS 和 JS 资源。Quartz 的资源系统会收集所有插件声明的资源，在构建时注入到页面中。

## 六、插件配置的灵活性

每个插件都有自己的 `Options` 接口，允许通过配置文件进行定制。以 `SyntaxHighlighting` 为例：

```ts
interface Options {
  theme?: Theme           // 可选：自定义主题
  keepBackground?: boolean  // 可选：是否保留代码块背景
}

const defaultOptions: Options = {
  theme: {
    light: "github-light",
    dark: "github-dark",
  },
  keepBackground: false,
}
```

插件通过 `Partial<Options>` 类型接受配置，与默认值合并：

```ts
export const SyntaxHighlighting: QuartzTransformerPlugin<Partial<Options>> = (userOpts) => {
  const opts: CodeOptions = { ...defaultOptions, ...userOpts }
  // ...
}
```

`Partial<Options>` 意味着所有配置项都是可选的，未指定的会使用默认值。这种模式让用户可以只覆盖需要修改的选项，其余保持默认。

## 七、如何编写自己的 Transformer

编写一个新的 transformer 插件只需实现工厂函数，返回一个符合 `QuartzTransformerPluginInstance` 接口的对象。以下是一个简化的示例——一个在文章标题前添加前缀的 transformer：

```ts
import { QuartzTransformerPlugin } from "../plugins/types"

interface PrefixTitleOptions {
  prefix: string
}

export const PrefixTitle: QuartzTransformerPlugin<Partial<PrefixTitleOptions>> = (userOpts) => {
  const opts = { prefix: "[Note] ", ...userOpts }
  return {
    name: "PrefixTitle",
    markdownPlugins(ctx) {
      return [
        () => {
          return (_tree, file) => {
            // 在 frontmatter 处理之后，可以直接修改 frontmatter
            if (file.data.frontmatter) {
              file.data.frontmatter.title = opts.prefix + file.data.frontmatter.title
            }
          }
        },
      ]
    },
  }
}
```

然后在 `quartz.config.ts` 中注册：

```ts
transformers: [
  Plugin.FrontMatter(),           // 先执行 FrontMatter 确保 frontmatter 已解析
  Plugin.PrefixTitle({ prefix: "[Blog] " }),  // 然后添加前缀
  // ... 其他 transformers
],
```

如果你需要在 HAST 层面操作（例如修改 HTML 元素），可以使用 `htmlPlugins` 钩子：

```ts
htmlPlugins(ctx) {
  return [
    () => {
      return (tree, file) => {
        visit(tree, "element", (node) => {
          if (node.tagName === "img") {
            // 给所有图片添加 loading="lazy"
            node.properties.loading = "lazy"
          }
        })
      }
    },
  ]
}
```

掌握了插件系统的架构，你就能轻松地为 Quartz 添加自定义的文档处理逻辑。

# 10 主键策略与雪花算法

> 上接：[[MyBatis-Plus/09-分页插件]]
> 主键怎么生成？MP 的 `IdType` 一行搞定，核心是 **`ASSIGN_ID`（雪花算法）**——分布式不怕重复。

## 10.1 IdType 一览

| 值 | 含义 | 适用 |
|----|------|------|
| `AUTO` | 数据库自增（`AUTO_INCREMENT`） | 单库、ID 连续（易被猜） |
| `NONE` | 无策略，自己 set | 主键自己管 |
| `INPUT` | 自己输入，MP 不生成 | 业务单号作主键 |
| **`ASSIGN_ID`** | **MP 用雪花算 19 位 Long** | **★ 默认推荐，分布式安全** |
| `ASSIGN_UUID` | 生成 UUID（无中划线） | 不要递增场景 |

## 10.2 用法

```java
// 实体字段
@TableId(type = IdType.AUTO)          // 数据库自增
private Long userId;

// 或全局默认（yml，见 [[MyBatis-Plus/01-核心概念与快速集成]] 1.3）
// mybatis-plus.global-config.db-config.id-type: ASSIGN_ID
```
> 不写 `@TableId(type)` 时，取**全局 `id-type`**（默认 `ASSIGN_ID`）。

## 10.3 雪花算法（ASSIGN_ID）原理

```
64 位 Long：
  1 位符号(恒0) | 41 位时间戳(ms,可用69年) | 10 位机器ID | 12 位序列号
        └ 同毫秒同机器最多 4096 个不重复 ┘
```
- **趋势递增**：按时间，索引友好（MySQL B+Tree 喜欢递增主键，减少页分裂）。
- **不依赖数据库**：多服务各自生成，**全局唯一**，不怕分库分表。
- **19 位 Long**：前端 JS 的 `Number` 最大安全整数 `2^53-1`，19 位 Long（≈9.2e18）**可能越界**！

> ⚠️ **JS 精度坑**（本 Spring 教程也踩过）：后端 Long id 转 JSON 到前端，超过 `2^53` 会被截断（如 `19223372036854775807` → `19223372036854776000` 末尾变 0）。**解决**：ID 字段加 `@JsonSerialize(using = ToStringSerializer.class)` 转成字符串传前端，或前端用 `json-bigint`。

## 10.4 自定义机器 ID（多实例不撞）

```yaml
mybatis-plus:
  global-config:
    worker-id: 1        # 机器 ID（0~31），每台部署实例不同
    datacenter-id: 1    # 数据中心 ID（0~31）
```
> 雪花靠 `机器ID` + `数据中心ID` 区分不同进程。容器/K8s 里通常通过环境变量注入不同 `worker-id`，避免多副本生成重复 ID。

## 10.5 选型的经验

| 场景 | 推荐 |
|------|------|
| 单库后台、要 ID 连续可读 | `AUTO` |
| 微服务 / 分库分表 / 高并发 | **`ASSIGN_ID`**（+ 前端字符串化防精度丢失） |
| 业务主键就是单号（如 `B+时间戳`） | `INPUT`（自己 set） |

## 验证清单

- [ ] 用 `ASSIGN_ID`，插入后主键是 19 位 Long 且趋势递增。
- [ ] 多实例/多库各插一条，ID 不重复。
- [ ] 主键 Long 传给前端前已转字符串（`ToStringSerializer`），审查元素里不是整数而是 `"1922..."`。
- [ ] `AUTO` 时数据库表 `id` 列确实是 `AUTO_INCREMENT`。

# 09 · 索引设计与优化实战

> 进阶路线：[[00-总览与学习路线]] → L3 性能原理 ｜ 前置：[[07-索引原理B+Tree]] ｜ 配合：[[08-执行计划EXPLAIN]]

建对索引 = 解决 80% 慢查询。这篇是「企业级调优」的日常。

## 1. 索引设计原则

1. **高选择性列优先**：`COUNT(DISTINCT col)/COUNT(*)` 越接近 1 越适合建索引（性别这种低选择性不值当单列索引）。
2. **WHERE / JOIN / ORDER BY 列**是候选。
3. **组合索引把等值条件放前面、范围放后面**（避免最左前缀断掉，见 [[07-索引原理B+Tree]]）。
4. **尽量覆盖索引**：把查询列也放进去，免回表。

```sql
-- 查询常是：WHERE dept_id=? AND status=? ORDER BY create_time
-- 设计组合索引（等值在前，排序列在后）：
CREATE INDEX idx_dept_status_time ON sys_user(dept_id, status, create_time);
```

## 2. 索引失效的 8 大场景（面试/排错高频）

| 写法 | 为什么失效 |
|------|------------|
| `WHERE DATE(create_time) = ...` | 对列用函数，破坏有序性 |
| `WHERE amount + 1 = 100` | 对列做运算 |
| `WHERE phone = 13800000000` | **隐式类型转换**（phone 是字符串，传了数字） |
| `WHERE name LIKE '%张'` | **前导模糊**，B+Tree 无法定位 |
| `WHERE a = 1 OR b = 2` | OR 连接无共同索引时全扫（可改 UNION） |
| `WHERE NOT IN (...)` / `!=` | 优化器认为绝大多数行 |
| `WHERE col IS NULL`（少数情况） | 视索引与数据分布 |
| 组合索引跳过最左列 | 违反最左前缀 |

```sql
-- 错误（函数）
SELECT * FROM t WHERE YEAR(create_time)=2026;
-- 正确（范围）
SELECT * FROM t WHERE create_time >= '2026-01-01' AND create_time < '2027-01-01';

-- 字符串列务必传字符串，避免隐式转换
SELECT * FROM t WHERE phone = '13800000000';   -- ✅
SELECT * FROM t WHERE phone =  13800000000 ;   -- ❌ 索引失效
```

## 3. 覆盖索引实战

```sql
-- 只需 id/name/dept_id 时，组合索引覆盖这三列：
CREATE INDEX idx_cover ON sys_user(dept_id, user_name, id);
-- Extra 显示 Using index，无需回表
```

## 4. 索引下推 ICP（Index Condition Pushdown，8.0 默认）

把 WHERE 过滤**下推到存储引擎层**在索引遍历时就过滤，减少回表。看到 `Extra: Using index condition` 是好事。

## 5. 冗余/无用索引治理

- 重复索引：同一列上既有 `(a)` 又有 `(a,b)` 的 `a` 部分 → 删单列。
- 低选择性单列索引（如 `status` 只有 0/1）→ 改成组合索引的一部分。
- 工具：`:sys.schema_unused_indexes`（8.0）、`pt-index-usage`。

## 6. 大表在线加索引

```sql
-- 8.0 多数 DDL 默认 INPLACE/ONLINE，但仍建议低峰
ALTER TABLE big_table ADD INDEX idx_x(col), ALGORITHM=INPLACE, LOCK=NONE;
```
> 超大表用 `gh-ost` / `pt-online-schema-change`，避免长时间锁。

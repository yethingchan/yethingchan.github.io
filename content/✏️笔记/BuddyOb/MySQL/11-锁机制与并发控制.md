# 11 · 锁机制与并发控制

> 进阶路线：[[00-总览与学习路线]] → L3 性能原理 ｜ 前置：[[10-事务ACID与隔离级别]]

隔离级别是「结果」，锁是「手段」。InnoDB 锁是性能与并发的命脉。

## 1. 锁的粒度

| 粒度 | 说明 |
|------|------|
| 全局锁 | `FLUSH TABLES WITH READ LOCK`，整库只读（备份用） |
| 表级锁 | `MyISAM` 默认；InnoDB 也有（DDL、意向锁） |
| **行级锁** | InnoDB 核心，锁数据行，并发高 |

> InnoDB **行锁是基于索引的**：锁的是索引记录，没走索引的更新会**升级成表锁** ⚠️。

## 2. InnoDB 行锁的三种

| 锁 | 作用 |
|----|------|
| **记录锁 Record Lock** | 锁单条索引记录 |
| **间隙锁 Gap Lock** | 锁「两条记录之间的空隙」，防插入 |
| **临键锁 Next-Key Lock** | = 记录锁 + 间隙锁（**默认**，`REPEATABLE READ` 下防幻读） |

```
索引值:  10     20     30
间隙:   (-∞,10) (10,20) (20,30) (30,+∞)
Next-Key 锁住: 记录本身 + 它左边的间隙
```

## 3. 共享锁 vs 排他锁

| 锁 | 语法 | 兼容 |
|----|------|------|
| **S 共享锁**（读锁） | `SELECT ... LOCK IN SHARE MODE` | 多个 S 可共存 |
| **X 排他锁**（写锁） | `SELECT ... FOR UPDATE` / DML 自动加 | X 与任何锁互斥 |

```sql
BEGIN;
SELECT * FROM t WHERE id=1 FOR UPDATE;   -- 当前读, 加 X 锁
-- 别的事务此时 UPDATE id=1 会被阻塞
COMMIT;
```

## 4. 当前读 vs 快照读

- **快照读**（普通 `SELECT`）：走 MVCC，读历史版本，不加锁（[[10-事务ACID与隔离级别]]）。
- **当前读**（`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`、`INSERT`）：读最新+加锁，保证不幻读。

## 5. 死锁

- 两个事务互相等待对方持有的锁 → 死锁。
- InnoDB 有**死锁检测**，自动回滚代价小的一方并报错 `Deadlock found`。
- **规避**：
  - 事务内**固定访问表的顺序**（都先锁 A 再锁 B）。
  - 缩短事务、减少锁范围。
  - 用 `SELECT ... FOR UPDATE` 提前串行化热点。

```sql
-- 排查
SHOW ENGINE INNODB STATUS;   -- 看最近死锁信息
SELECT * FROM performance_schema.data_lock_waits;  -- 8.0 锁等待
```

## 6. 乐观锁 vs 悲观锁（应用层选型）

| 方案 | 实现 | 适用 |
|------|------|------|
| 悲观锁 | `SELECT ... FOR UPDATE` | 强一致、冲突频繁 |
| **乐观锁** | 加 `version` 字段，`UPDATE ... SET ... WHERE id=? AND version=?` | 冲突少、高并发（推荐） |

```sql
UPDATE t SET sal=sal+100, version=version+1
WHERE id=1 AND version=3;   -- 版本不符=被别人改过, 重试
```

## 7. 大事务 / 长事务危害

- 占着锁不放 → 阻塞、死锁概率高。
- undo log 堆积 → 膨胀、回滚慢。
- MVCC 老版本无法清理 → 表膨胀。

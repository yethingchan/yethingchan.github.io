# 13 · 主从复制与读写分离

> 进阶路线：[[00-总览与学习路线]] → L4 企业级 ｜ 前置：[[10-事务ACID与隔离级别]] ｜ [[12-慢查询分析与调优]]

单实例扛不住读流量 / 怕单点宕机 → 主从架构。

## 1. 为什么主从

- **读写分离**：主库写、从库读，分散压力。
- **高可用**：主挂了切从，减少停机。
- **备份/分析**：从库做备份、跑报表，不扰主库。

## 2. 复制原理（基于 binlog）

```
主库                          从库
写操作 ──binlog──┐
                    ↓ (IO线程拉取)
                 relay log (中继日志)
                    ↓ (SQL线程重放)
                  从库数据 = 主库
```
- 主库把变更写 **binlog**。
- 从库 `IO 线程` 拉 binlog → 存 `relay log`。
- 从库 `SQL 线程` 重放 relay log → 同步数据。

## 3. binlog 三种格式

| 格式 | 内容 | 优缺点 |
|------|------|---------|
| `STATEMENT` | 记 SQL 语句 | 省空间，但 `NOW()`/`UUID()` 主从可能不一致 |
| `ROW`（**推荐**） | 记每行前后值 | 安全、可闪回，日志大 |
| `MIXED` | 混合 | 折中 |

```sql
SHOW VARIABLES LIKE 'binlog_format';   -- 一般设 ROW
```

## 4. 复制模式

| 模式 | 说明 |
|------|------|
| 异步（默认） | 主提交即返回，不等企业确认；可能丢数据 |
| 半同步 | 主等至少一个从收到 relay log 才返回；折中 |
| 全同步 | 全从确认；强一致但慢 |

> 金融级用半同步 / Group Replication（MGR）保数据安全。

## 5. 读写分离实现

- **应用层**：框架按 SQL 类型路由（如 MyBatis 多数据源 + AOP）。
- **中间件**（企业主流）：
  - **ShardingSphere-Proxy**：分库分表 + 读写分离一体。
  - **ProxySQL** / **MaxScale**：MySQL 协议层代理，自动路由。
  - **MyCat**：老牌，逐渐被 ShardingSphere 取代。

```yaml
# ShardingSphere 读写分离示意
rules:
  - !READWRITE_SPLITTING
    dataSources:
      pr: ds_master        # 写
      rr: ds_slave0,ds_slave1   # 读(负载)
```

## 6. 主从延迟（最常见坑）

- 现象：刚写入主库，立刻从从库读读不到（延迟几秒）。
- 原因：从库 SQL 线程重放慢 / 大事务 / 从库硬件差。
- 对策：
  - 写后强一致读 → 强制走主库（关键路径如「下单后查订单」）。
  - 避免大事务（[[10-事务ACID与隔离级别]]）。
  - 从库提升配置、并行复制（`slave_parallel_workers`）。

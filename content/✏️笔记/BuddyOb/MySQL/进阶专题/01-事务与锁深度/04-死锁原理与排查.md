# 01-事务与锁深度 · 死锁原理与排查

> 前置：[[MySQL/进阶专题/01-事务与锁深度/03-锁的底层record-gap-nextkey意向锁]]

## 死锁的四个必要条件（Coffman）

1. **互斥**：锁排他。
2. **占有且等待**：持有一把锁，等另一把。
3. **不可抢占**：锁不能强行抢，只能等释放。
4. **循环等待**：A 等 B、B 等 A（成环）。

四个**同时**满足 → 死锁。打破任一即可避免。

## 经典死锁（加锁顺序相反）

```
时刻1: T1 UPDATE id=5 (拿 lock5)        T2 UPDATE id=10 (拿 lock10)
时刻2: T1 UPDATE id=10 (等 lock10)     T2 UPDATE id=5  (等 lock5)
→ T1等T2，T2等T1 → 循环等待 → 死锁
```
**解法**：所有事务**按固定顺序加锁**（都先锁小 id 再锁大 id）→ 不会成环。

## MySQL 怎么检测与处理

- InnoDB 有**死锁检测（deadlock detection）**：等待图（wait-for graph）成环即发现。
- 发现后**回滚"代价最小"的事务**（通常是持有锁最少/改动最少的那个），让另一个继续。
- 报错：`ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction`。
- 应用层应**捕获 1213，重试**（RuoYi 等框架一般有重试逻辑）。

## 排查：`SHOW ENGINE INNODB STATUS`

发生死锁后立刻查（信息只保留最近一次）：
```sql
SHOW ENGINE INNODB STATUS\G
```
重点看 `LATEST DETECTED DEADLOCK` 段：
```
*** (1) TRANSACTION:
TRX id 123, ACTIVE ...
*** (1) HOLDS THE LOCK(S):   -- 事务1持有
RECORD LOCKS space id 1 page 3 n bits 80 index PRIMARY of `test`.`t`
*** (1) WAITING FOR THIS LOCK:  -- 事务1在等
RECORD LOCKS ... index PRIMARY ... lock_mode X locks rec but not gap
*** (2) TRANSACTION:
*** (2) HOLDS THE LOCK(S):    -- 事务2持有（正是事务1在等的）
*** (2) WAITING FOR THIS LOCK: -- 事务2在等（正是事务1持有的）
```
把 `(1) HOLDS` 和 `(2) WAITING` 对照，就能还原"谁拿了什么、在等什么" → 找到加锁顺序冲突。

## 其他死锁来源

1. **间隙锁冲突**：RR 下两个事务都 `INSERT` 到同一间隙，一个拿到插入意向锁，另一个被 gap 阻塞 → 配合其他锁可能死锁。
2. **外键**：子表 INSERT 会给父表相关行加 S 锁，跨表加锁顺序易错。
3. **二级索引**：加锁先锁二级索引记录，再锁聚簇索引行 → 多索引时加锁顺序复杂。
4. **大事务**：持锁时间长，更易撞上别人 → 缩小事务（见 05）。

## 避免死锁的工程手段

- **固定加锁顺序**（最管用）。
- **缩短事务**：尽快提交，减少持锁窗口。
- **降低隔离级别到 RC**：RC 无 gap 锁，很多死锁天然消失（代价：有幻读，需自己加锁）。
- **一次锁定所需全部行**：避免"先查后改"两次访问顺序不一致。
- **应用层重试**：捕获 1213 重试（幂等前提）。

## 结论

- 死锁 = 循环等待，打破加锁顺序最关键。
- 查 `SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 段还原现场。
- MySQL 自动回滚小事务 + 应用重试是标准应对。

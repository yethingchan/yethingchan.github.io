# 03 缓存与数据库一致性（Canal）

> 前置：[[MySQL/进阶专题/07-企业级SQL与架构实战/00-索引]] ｜ 二级缓存参考：[[MyBatis Mapper XML/进阶专题/03-缓存机制深度/03-Redis二级缓存集成(接本仓库)]]

"先更新 DB 还是先删缓存？"——这是缓存架构里被问烂、却依然天天出事的问题。本篇给出可落地的方案，并用 **Canal 订阅 binlog** 做最终兜底。

## 一、为什么"缓存双写"必然有洞

经典 Cache-Aside（旁路缓存）读流程：`读缓存 miss → 读 DB → 写回缓存`。写流程有两种 naive 做法，都有不一致窗口：

### 方案 A：先更新 DB，再删缓存（推荐，仍有极小窗口）

```
1. UPDATE db SET ...
2. DELETE cache
```

问题：步骤 1、2 之间若**恰好**有读请求，会读到旧 DB 值并写回缓存（脏数据），直到缓存过期。但概率极低（要求读发生在写提交后、删缓存前，且缓存恰 miss），工程上可接受。

### 方案 B：先删缓存，再更新 DB（更危险）

```
1. DELETE cache
2. UPDATE db
```

问题：步骤 1、2 之间若有读请求，缓存 miss → 读**旧 DB 值** → 写回缓存。结果缓存长期是脏的，直到 TTL 过期。**比 A 更糟，不推荐。**

## 二、把洞堵小：延迟双删

在"更新 DB 后删缓存"的基础上，**延迟再删一次**：

```java
updateDb(data);          // 1. 更新数据库
deleteCache(key);        // 2. 立即删
// 3. 短暂延迟后（如 500ms~1s，覆盖"读回脏缓存"的窗口）再删一次
executor.schedule(() -> deleteCache(key), 500, TimeUnit.MILLISECONDS);
```

- 双删能把"方案 A 的脏写"再清掉一次。
- 延迟时间要**大于**业务读平均耗时（否则第二次删在脏写前，白删）。本质是"用延迟换最终一致"，不优雅但实用。

## 三、根治方案：Canal 订阅 binlog 异步刷新

延迟双删还是"业务代码里掺缓存逻辑"。更干净的做法：**让缓存在数据库真正变更后，由 binlog 驱动更新**。

```
MySQL ──(binlog)──> Canal Server ──(解析)──> MQ ──> 消费者 ──> 更新/删除 Redis
```

```java
// Canal 消费者伪代码：监听 wms_stock 表的 UPDATE
@StreamListener("canal-stock")
public void onStockChange(CanalEntry entry) {
    String sku = entry.getBeforeAfterColumn("sku");
    // 只动缓存，不碰业务逻辑
    redisTemplate.delete("stock:" + sku);
    // 或：直接把新值写回 redisTemplate.opsForValue().set("stock:"+sku, newValue)
}
```

为什么这是最优：

- **单一真相源是 DB**：缓存更新完全由 DB 的 binlog 触发，业务代码不再负责"删缓存"，彻底解耦。
- **顺序保证**：Canal 按 binlog 顺序投递，天然保证"后发生的变更后到缓存"，避免并发乱序。
- **最终一致**：即使中间漏删，下一次变更或 TTL 兜底都会修正。

> 这正好呼应 [[MyBatis Mapper XML/进阶专题/03-缓存机制深度/03-Redis二级缓存集成(接本仓库)]] 里 `RedisMybatisCache implements Cache` 的思路——把"缓存更新"这件事，从业务方法里抽出来，交给统一的机制。Canal 更进一层：连 Mapper 层都不用管，DB 一变就刷。

## 四、读写一致性：强一致 vs 最终一致

| 场景 | 策略 |
|------|------|
| 余额、库存余量（不能脏读） | 关键读**强制读主库/直接读 DB**，或读前删缓存再读 |
| 商品详情、用户资料（可接受秒级延迟） | 正常读缓存；Canal 异步维护即可 |
| 刚写完马上读自己（写后读） | 该请求内直接读 DB，不走缓存，避免"自己写的还没刷到缓存" |

> "刚写完马上读"的坑：用方案 A，写后立刻读走缓存会 miss 再读 DB——此时 DB 已提交，反而能读到新值；但若写事务还没提交（读在提交前），会读到旧值。本质是**事务可见性**问题，见 [[MySQL/进阶专题/01-事务与锁深度/05-隔离级别实现与长事务危害]]。

## 五、避坑清单

- ❌ 不要在业务代码里又更新 DB 又更新缓存（双写）——并发下谁先谁后难保证，且缓存里要算最新值更麻烦。**"更新 DB + 删缓存"比"更新 DB + 更新缓存"稳。**
- ❌ 不要给缓存设置过长的 TTL 当"最终一致兜底"却忘了主动删——长 TTL 意味着脏数据活很久。
- ✅ 读多写少：Canal 异步删/写缓存 + 短 TTL 双保险。
- ✅ 强一致读：走主库或旁路直读。
- ✅ Canal 消费侧做**幂等**（同一 binlog 可能被重投），用 `entry.getExecuteTime()+pk` 去重。

## 小结

- 写缓存用"更新 DB + 删缓存"，别双写。
- 想堵洞用延迟双删；想根治用 **Canal 订阅 binlog 异步维护缓存**。
- 强一致场景（余额/库存）强制读主库；弱一致场景交给 Canal + TTL。
- 缓存一致性没有银弹，靠"单一真相源（DB）+ 异步驱动 + 幂等 + TTL 兜底"四件套。

# 04 冷热分离归档与读写分离一致性

> 前置：[[MySQL/进阶专题/07-企业级SQL与架构实战/00-索引]] ｜ 读写分离基础：[[MySQL/进阶专题/04-高可用复制与集群/04-读写分离中间件]]

数据量到千万/亿级，"一张大表扛所有"就崩了。本篇讲两块：① 冷热分离给表瘦身；② 读写分离下如何避免"读到了旧数据"。

## 一、冷热分离：把历史数据搬走

**热数据**：近期、频繁访问（如近 3 个月订单）。**冷数据**：历史归档、审计用（如 3 年前订单）。

### 1.1 三种归档手段

| 手段 | 做法 | 适用 |
|------|------|------|
| 分区表 | 按时间 `RANGE` 分区，冷分区可 `ALTER TABLE ... DROP/EXCHANGE PARTITION` | 单实例内仍需 InnoDB 管理冷数据，但能快速"剔掉"冷分区 |
| 归档表 + 定时迁移 | `INSERT INTO order_archive SELECT ... WHERE create_time < ?` 后 `DELETE` 原表 | 归档表可放廉价存储/另一实例 |
| `pt-archiver` | Percona 工具，分批 `DELETE`+`INSERT`，对线上影响小 | 大表在线归档，避免一次性 `DELETE` 锁表/长事务 |

```sql
-- 分区表演示：按月分区，旧分区直接 EXCHANGE 出去归档
CREATE TABLE orders (
  id BIGINT, user_id BIGINT, amount DECIMAL(10,2),
  create_time DATETIME,
  PRIMARY KEY (id, create_time)
) PARTITION BY RANGE (TO_DAYS(create_time)) (
  PARTITION p202401 VALUES LESS THAN (TO_DAYS('2024-02-01')),
  PARTITION p202402 VALUES LESS THAN (TO_DAYS('2024-03-01')),
  PARTITION pmax     VALUES LESS THAN MAXVALUE
);
-- 归档 2024-01：把分区换成普通表，原表瞬间"瘦身"
ALTER TABLE orders EXCHANGE PARTITION p202401 WITH TABLE orders_202401_archive;
```

### 1.2 归档的代价与注意

- 归档后**冷数据查询要路由到归档源**，应用层需有"热表查不到再去冷表/冷库"的逻辑（或用视图/中间件统一）。
- 不要用 `DELETE FROM big WHERE create_time < ?` 一次性删——产生巨量 undo/redo、锁表、主从延迟（见 [[MySQL/进阶专题/01-事务与锁深度/05-隔离级别实现与长事务危害]] 与 [[MySQL/进阶专题/05-备份恢复与容灾/03-PITR时间点恢复与闪回]]）。用 `pt-archiver` 分批。
- 归档要考虑**索引失效**：热表按 `create_time` 查询快，冷表若换了存储/结构，相关报表 SQL 要重新验证（见 [[MySQL/进阶专题/02-索引底层与优化器执行计划/05-索引失效全场景]]）。

## 二、读写分离下的一致性陷阱

读写分离（[[MySQL/进阶专题/04-高可用复制与集群/04-读写分离中间件]]）把读打到从库，但**从库有复制延迟**，可能读到"还没同步过来的旧值"。

### 2.1 典型事故

```
1. 主库 INSERT 订单（用户刚下单）
2. 页面跳转"我的订单" → 读从库
3. 从库还没收到这条 binlog → 显示"无订单"
→ 用户以为下单失败，重复下单
```

### 2.2 五种解法

1. **强制主库读（关键路径）**：下单后"查自己刚下的单"这类场景，Hint 路由到主库。MyBatis 可加注解/拦截器（参考 [[MyBatis Mapper XML/进阶专题/05-插件与拦截器/03-数据权限SQL拦截注入]] 的拦截器思路）给方法打标。
2. **写后短暂读主**：写入后一小段时间内的读强制主库（"写后读窗口"），过期后回归从库。
3. **半同步复制缩短延迟**：[[MySQL/进阶专题/04-高可用复制与集群/02-GTID与半同步无损复制]] 的 `rpl_semi_sync_*` 让主库等至少一个从库收妥再提交，延迟窗口大幅缩小（但仍非零）。
4. **会话级读主**：同一会话内刚写过，后续读都走主，直到超时。
5. **业务容忍 + 轮询**：非关键展示（如"销量""评论数"）允许秒级延迟，前端轮询最终一致。

### 2.3 中间件如何做

- **ProxySQL / MyCat**：通过 `mysql_query_rules` 的 `destination_hostgroup` 按 SQL 特征/注解路由；可在 SQL 里加 `/* FORCE_MASTER */` 这类 hint 让中间件识别。
- **ShardingSphere**：`HintManager.getInstance().setWriteRouteOnly()` 强制主库（见 [[MySQL/进阶专题/03-分库分表与分布式事务/03-ShardingSphere实战]]）。

## 三、与本仓库/进阶其他篇的衔接

- 冷热分离的分区表，和 [[MySQL/进阶专题/06-参数调优与运维实战/04-碎片整理与表空间]] 的表空间管理配合，能控制 `ibd` 文件大小。
- 读写分离的一致性，本质是 [[MySQL/进阶专题/04-高可用复制与集群/01-主从复制原理binlog三格式]] 的"异步复制延迟"问题在应用层的表现。
- 归档迁移的大量 DELETE，要受 [[MySQL/进阶专题/05-备份恢复与容灾]] 的备份策略保护，避免误删又无 PITR。

## 小结

- 冷热分离：分区表 `EXCHANGE PARTITION` / 归档表迁移 / `pt-archiver` 分批删，别一次性大 `DELETE`。
- 读写分离一致性：靠"关键读强制主库 + 半同步缩短延迟 + 写后读窗口 + 中间件 hint 路由"组合解决。
- 没有"零延迟"的读写分离，只有"按业务容忍度分级处理"。
- 归档和读写分离都服务于一个目标：让热数据又快又小，冷数据便宜可查。

# 05 线上事故复盘（深分页/大事务/索引错配）

> 前置：[[MySQL/进阶专题/07-企业级SQL与架构实战/00-索引]]
> 关联：[[MySQL/进阶专题/02-索引底层与优化器执行计划/04-EXPLAIN逐列精讲与key_len]] ｜ [[MySQL/进阶专题/01-事务与锁深度/05-隔离级别实现与长事务危害]]

这一篇把前面六个专题踩过的坑，按"真实事故"的样子统一归档。每一类都给出**成因 → 现场特征 → 救法 → 长效防护**。

## 事故一：深分页把数据库拖垮

### 现场
运营后台翻到第 10000 页，接口超时；DB CPU 飙到 100%。

### 成因
```sql
-- ❌ 深分页：MySQL 要先读出前 1000000 行再丢弃，IO + 排序爆炸
SELECT * FROM orders
ORDER BY create_time DESC
LIMIT 1000000, 20;
```
`LIMIT offset, n` 的 offset 越大，MySQL 越要扫描并丢弃前 offset 行。`type=ALL` 或 `type=index` 全扫 + `Using filesort`，百万行直接卡死。

### 救法（即时）
```sql
-- ✅ 游标/Keyset 分页：用上一页最后一条的游标值往后取
SELECT * FROM orders
WHERE create_time < #{lastCreateTime}
ORDER BY create_time DESC
LIMIT 20;
```
`create_time` 上有索引时，直接走索引定位，O(20) 而非 O(1000000)。

### 长效防护
- 产品上限制"最大翻页数"（如只允许翻前 100 页），或改成"无限滚动 + 游标"。
- 必须 `ORDER BY` 的列要有索引，且游标列**唯一或组合唯一**（避免漏行/重行），如 `ORDER BY create_time DESC, id DESC`。
- 超大结果导出走**延迟关联/覆盖索引**：先查 ID 再 `JOIN` 回全字段，避免回表百万次（见 [[MySQL/进阶专题/02-索引底层与优化器执行计划/02-覆盖索引ICP与索引合并MRR]] 的覆盖索引）。

## 事故二：大事务锁全表、主从延迟

### 现场
凌晨批量更新，接口大面积超时；从库延迟几小时，读写分离读到极旧数据。

### 成因
```java
@Transactional   // ❌ 一个事务里做 50 万行更新 + 一堆远程调用
public void batchFix() {
    for (Order o : orders) {
        mapper.update(o);          // 行锁逐条加，事务不提交锁不释放
        remoteCall(o);             // 远程调用慢，事务被拖长
    }
}
```
- 长事务持锁久 → 别的写请求**锁等待**超时。
- 大量 undo 累积 → 回滚慢、MVCC 快照老、[[MySQL/进阶专题/01-事务与锁深度/01-MVCC原理undo版本链与ReadView]] 的版本链暴涨。
- 主库 binlog 延迟刷 → 从库追不上（[[MySQL/进阶专题/04-高可用复制与集群/01-主从复制原理binlog三格式]]）。

### 救法（即时）
- kill 掉卡住的事务/长 SQL（`SHOW PROCESSLIST` + `KILL QUERY`）。
- 把批量拆成小批次，每批单独短事务提交。

### 长效防护
- **事务尽量短**：把远程调用、文件 IO 移到事务外。
- 批量用 [[MyBatis Mapper XML/进阶专题/04-批量与性能优化/02-ExecutorType.BATCH手动批处理]] 的 `BATCH` 模式，或 `rewriteBatchedStatements` 真正批处理，减少交互。
- 监控长事务：`information_schema.innodb_trx` 里 `trx_started` 太久的告警（呼应 [[MySQL/进阶专题/06-参数调优与运维实战/05-监控告警与关键指标]]）。
- 设 `lock_wait_timeout` 防止无限等待雪崩。

## 事故三：索引"看似有，实际没走"

### 现场
一条常用查询突从 20ms 变成 3s，没改 SQL、没改数据量。

### 成因（按概率排序）
1. **隐式转换**：`WHERE phone = 13800000000`（phone 是 `VARCHAR`，传入数字）→ 索引失效，全表扫。必须 `WHERE phone = '13800000000'`。
2. **统计信息过期**：表大批量变更后，`ANALYZE TABLE` 没跑，优化器误判走错索引（见 [[MySQL/进阶专题/02-索引底层与优化器执行计划/03-统计信息与直方图optimizer-trace]]）。
3. **前导 `%` 模糊**：`LIKE '%abc'` 无法走 B+ 树前缀，全扫。
4. **优化器选错**：直方图缺失或 cost 估算偏差，`FORCE INDEX(idx_x)` 纠正（临时），根治是补统计信息/调整索引。
5. **最左前缀断裂**：联合索引 `(a,b,c)`，查询只 `WHERE b=?` 用不上。

### 救法（即时）
```sql
-- 用 OPTIMIZER_TRACE 看优化器到底怎么想的
SET optimizer_trace="enabled=on";
SELECT ... ;
SELECT * FROM information_schema.OPTIMIZER_TRACE\G
-- 统计信息过期就
ANALYZE TABLE orders;
-- 临时纠偏
SELECT * FROM orders FORCE INDEX(idx_create_user) WHERE ...;
```

### 长效防护
- 上线前必跑 `EXPLAIN` 逐列核对（[[MySQL/进阶专题/02-索引底层与优化器执行计划/04-EXPLAIN逐列精讲与key_len]]），`type` 至少到 `range`，`Extra` 别有 `Using filesort`/`Using temporary`。
- 建立"慢查询监控"（[[MySQL/进阶专题/06-参数调优与运维实战/05-监控告警与关键指标]] 的 `slow_query_log` + Prometheus），SQL 变慢第一时间告警。
- 大表变更后自动 `ANALYZE TABLE`（运维脚本）。
- 参数化查询务必**类型匹配**：传入字符串就传字符串，别让驱动做隐式转换。

## 小结

- **深分页**：用游标/Keyset 分页替代 `LIMIT offset,n`；限制最大翻页；覆盖索引延迟关联。
- **大事务**：事务要短、远程调用移出事务、批量用 BATCH 模式、监控长事务。
- **索引错配**：先查隐式转换/统计信息/前导模糊/最左前缀，用 `OPTIMIZER_TRACE` 定位，`ANALYZE TABLE` 或 `FORCE INDEX` 救急。
- 三类事故的共同解药：**上线前 EXPLAIN + 慢查询监控 + 长事务告警**，把问题挡在用户前面。
- 复盘不是写检讨，是把"坑"变成"自动防护"。

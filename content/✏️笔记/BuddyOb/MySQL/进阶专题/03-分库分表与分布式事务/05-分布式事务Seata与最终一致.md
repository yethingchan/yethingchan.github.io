# 03-分库分表 · 分布式事务（2PC / TCC / Seata / 最终一致）

> 前置：[[MySQL/进阶专题/03-分库分表与分布式事务/04-跨分片查询与JOIN难题]] ｜ 本地事务：[[MySQL/进阶专题/01-事务与锁深度/05-隔离级别实现与长事务危害]]

## 为什么本地事务不够

`@Transactional` 只能管**一个** MySQL 实例里的一个连接。一旦跨库（分片/多数据源）或多个服务，就要**分布式事务**。

```
下单：扣库存(库A) + 创建订单(库B) + 扣账户(库C)
→ 任何一步失败，前面已提交的怎么办？本地事务管不了
```

## 方案 1：2PC（两阶段提交，强一致）

```
协调者: ① Prepare：各参与者锁资源、写 undo/redo，回 "Ready"
协调者: ② Commit：都 Ready → 统一 Commit；任一 No → 统一 Rollback
```
- 优点：强一致。
- 缺点：**同步阻塞**（Prepare 阶段全程锁资源）、协调者单点、数据锁定时间长 → 性能差。
- MySQL XA 就是 2PC 实现（`XA START/BEGIN/END/PREPARE/COMMIT`），但很少直接用（锁太久）。

## 方案 2：TCC（Try-Confirm-Cancel，业务层）

把每个操作拆成三阶段，**业务自己实现**补偿：

```
Try:   预留资源（如冻结库存 5 件，不直接扣）
Confirm: 真正提交（扣掉冻结的 5 件）—— 必须成功（重试到成功）
Cancel: 释放预留（解冻 5 件）—— 回滚路径
```
- 优点：无长锁、性能好、可控。
- 缺点：**侵入业务**，每个接口要写 Try/Confirm/Cancel 三套，开发重。
- 适合：金融、交易等强一致且能接受开发成本的场景。

## 方案 3：Saga（长事务/补偿链）

把流程拆成一串**本地事务 + 补偿**：
```
T1(扣库存) → T2(创订单) → T3(扣款)
失败则反向: C3(退款) → C2(撤单) → C1(补库存)
```
- 适合**长流程**（跨多个服务、耗时久）。
- 不要求隔离性，靠"正向+逆向补偿"保证最终一致。

## 方案 4：Seata（阿里，最常用框架）

Seata 提供三种模式，对业务侵入从低到高：

| 模式 | 原理 | 侵入 | 说明 |
|------|------|------|------|
| **AT**（默认） | 自动：拦截 SQL，记录**前后镜像**到 `undo_log`，提交走本地事务；回滚用镜像反向 | **几乎零侵入** | 最常用，靠全局锁防脏写 |
| TCC | 同上文 TCC，Seata 编排 | 高（写三阶段） | 强一致、高性能 |
| Saga | 状态机编排补偿链 | 中 | 长流程 |

AT 模式流程：
```
1. TM(事务管理器) 开全局事务 → 拿 XID
2. 各分支 RM(资源管理器) 执行业务 SQL（本地事务提交）
   - 同时记 before/after 镜像到 undo_log
3. 全成功 → 全局提交（删 undo_log）
4. 任一失败 → 全局回滚（按 undo_log 镜像反向更新）
```
> 关键点：AT 的**本地事务是各自提交的**（不等全局），靠 `undo_log` 镜像做补偿回滚 → 性能好但有"脏写"风险（需全局锁）。

## 方案 5：最终一致（消息队列，最松耦合）

不追求"同时成功"，而是**异步保证最终一致**：

```
1. 本地事务：扣库存成功 + 往消息表插"已扣库存"事件（同库事务，原子）
2. 消息投递器把事件发给 MQ（RocketMQ/RabbitMQ）
3. 订单服务消费事件 → 创建订单
4. 消费失败 → MQ 重试（至少一次）→ 消费方要幂等
```
- 优点：**解耦、高性能、无长锁**。
- 代价：**短暂不一致**（库存扣了、订单还没创建的瞬间）。多数业务可接受。
- 幂等：消费方用"已处理事件 ID 去重表"防重复消费（见 [[MyBatis Mapper XML/进阶专题/05-插件与拦截器/04-脱敏加密与慢SQL拦截器]] 的防重思路）。

## 怎么选

| 场景 | 选 |
|------|-----|
| 同库多表、强一致 | 本地 `@Transactional` |
| 跨库但能接受开发量、强一致 | TCC / Seata TCC |
| 跨库、要省事、能容忍镜像补偿 | **Seata AT** |
| 长流程、多服务 | Saga |
| 高并发、能接受短暂不一致 | **MQ 最终一致** |

## 结论

- 本地事务管不了跨库/跨服务 → 要分布式事务。
- 强一致用 2PC/Seata-TCC（代价：锁/开发量）。
- 大多数互联网场景用 **Seata-AT（零侵入）** 或 **MQ 最终一致（高性能）**。
- 最终一致必须配**幂等消费**，防重复。

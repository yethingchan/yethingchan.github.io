# 03-分库分表 · 分片策略与分片键

> 前置：[[MySQL/进阶专题/03-分库分表与分布式事务/00-索引]]

## 两种拆分

| 方式 | 拆什么 | 适用 |
|------|------|------|
| **垂直分库** | 按业务把表分到不同库（用户库/订单库/商品库） | 业务解耦、不同库不同资源 |
| **垂直分表** | 宽表拆成"常用列"+"不常用列"两表（同库） | 减少单行宽度、热数据集中 |
| **水平分表** | 同一张表按行拆分到 N 个结构相同的子表（t_order_0..N） | 单表数据量过大（千万/亿级） |

> 大多数"分库分表"指**水平分片**（单表撑不住才是真问题）。

## 分片键（sharding key）是命根子

分片键 = "按哪一列的值决定这条数据落到哪个分片"。选错 → 热点、跨片查询爆炸。

### 选分片键的原则

1. **高频查询条件列**：`WHERE` 最常带的列，这样大部分查询能**单分片命中**，不用扫全部分片。
2. **区分度高、分布均匀**：避免都落到一个分片（热点）。如用 `user_id` 比 `status` 好（status 只有几个值）。
3. **避免跨片 JOIN**：若订单和订单明细都用 `order_id` 分片 → 同订单的数据在同一分片 → JOIN 不出片。
4. **尽量不变**：分片键改了要迁移数据，极痛。

### 反例

```
订单表按 user_id 分片，但业务常查"商家维度的订单流水"：
  → 商家查询要扫所有 user 分片 → 跨片全扫 → 慢
解法：冗余"商家分片表"或异构同步到商家维度库
```

## 分片算法

| 算法 | 说明 | 例子 |
|------|------|------|
| **取模** | `shard = id % N` | 简单、均匀，但**扩 N 要迁移大量数据** |
| **范围** | `id 1~1000万 → 片0` | 易扩容、但易热点（最新片最忙） |
| **一致性哈希** | 哈希环，扩缩容只迁移邻近数据 | 扩 N 影响小，实现略复杂 |
| **按时间** | `order_202601 / order_202602` | 日志/流水类天然，归档方便 |
| **基因法** | 分片键里嵌入分片位（如雪花 ID 末几位=分片） | 既全局唯一又能直接定位分片 |

> 本仓库雪花 ID（`ASSIGN_ID`）是趋势递增的，若直接按 `id % N` 分片，新数据都会落最新片 → 热点。所以分片键**别直接用自增/雪花**，要么用业务键（user_id），要么用基因法/哈希。

## 热点与扩缩容

- **热点**：某分片 QPS 远高于其他 → 拆更细、或把热点键单独分（如"大 V 用户"独立分片）。
- **扩容**：取模法扩容要 `rehash`（数据大搬移）；一致性哈希/范围法扩容影响小。

## 不分片的信号（别过度设计）

```
单表 < 500万行 且 增长平缓 → 不用分
单表 500万~2000万 → 加索引/归档冷数据/读写分离先撑
单表 > 2000万 或 单行大/写入极高 → 才考虑分片
```
> 本仓库 RuoYi 的表（用户/角色/菜单）量级小，**完全不需要分片**。WMS 的出入库流水若到亿级才考虑。

## 结论

- 水平分片解决"单表过大"，垂直分库解决"业务解耦"。
- **分片键 = 最高频查询列 + 高区分度 + 不变**。
- 优先用业务键或基因法，别直接拿自增/雪花做分片键（热点）。
- 没到千万级别急着分片是过度设计。

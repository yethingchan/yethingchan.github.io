# 03-分库分表 · 全局唯一 ID 方案

> 前置：[[MySQL/进阶专题/03-分库分表与分布式事务/01-分片策略与分片键]] ｜ 本仓库雪花：[[MyBatisPlus/10-主键策略与雪花算法]]

## 为什么不能用数据库自增

分片后每个分片各自 `AUTO_INCREMENT`，会**重复**（片0 出 1，片1 也出 1）。所以必须有一个**全局唯一**的 ID 生成器。

## 方案对比

| 方案 | 优点 | 缺点 | 适用 |
|------|------|------|------|
| **UUID** | 简单、本地生成 | 36 字符长、**无序** → InnoDB 聚簇索引随机插入页分裂严重、索引大 | 不推荐做主键 |
| **雪花算法 Snowflake** | 64 位、**趋势递增**、本地生成高性能 | 依赖时钟，**时钟回拨**会重复；需配 workerId | **最常用** |
| **号段 segment** | 数据库/Redis 发号段，本地自增，入库连续 | 要一次 DB/Redis 访问（批量发段缓减） | 美团 Leaf-segment、阿里 |
| **Redis INCR** | 简单原子递增 | 强依赖 Redis，单点/性能瓶颈 | 小中型 |
| **Leaf（美团）** | segment + snowflake 双模式，高可用 | 要部署 Leaf 服务 | 大厂标准 |

## 雪花算法（本仓库用的）

```
64 位：
  1 bit 符号(0)
 41 bit 时间戳(ms，可用 69 年)
 10 bit 机器/workerId(1024 台)
 12 bit 序列号(每 ms 4096 个)
= 大致递增的 Long
```
- 本仓库 MyBatis-Plus `ASSIGN_ID` 就是这个（见 [[MyBatisPlus/10-主键策略与雪花算法]]）。
- **趋势递增**：对 B+ 树友好（插入在末尾，少页分裂），比 UUID 好。
- **JS Long 精度**：前端 JS 的 `Number` 只有 53 位精度，64 位雪花传过去会丢 → 必须 `ToStringSerializer` 转字符串（见 MyBatisPlus 10）。

### 时钟回拨问题

机器时钟往回跳（NTP 校准）→ 可能生成和过去重复的 ID。
- 解法：workerId 配 ZooKeeper/Redis 保证唯一；检测到回拨时**等待/报警/换 workerId**。
- 美团 Leaf-snowflake 用 **ZK 顺序节点**分配 workerId，规避回拨冲突。

## 号段 segment 思路

```
DB 表: biz_tag=order, max_id=1000, step=1000
1) 取号: UPDATE 把 max_id 改成 2000（原子）
2) 本服务拿到 [1001, 2000] 号段，本地自增分配
3) 用完再取下一个号段
```
- 入库 ID **连续**（对索引友好），DB 访问降到 1/step。
- 双 buffer：一个号段快用完时异步预取下一个，不阻塞。

## 分片键 vs 主键

注意区分：
- **主键（ID）**：保证全局唯一，雪花/号段都行。
- **分片键**：决定数据落哪个分片，选业务键或基因法。
- 二者**可以不同**！常见：主键用雪花（唯一+递增），分片键用 `user_id`（查询维度）。
- 基因法：让**主键的低位 = 分片号**，这样"按主键查"也能直接算分片（不用反查）。

## 结论

- 分片后自增不可用 → 必须全局 ID 生成器。
- 首选**雪花**（趋势递增、本地高性能），配好 workerId 防回拨。
- JS 前端要把 Long 转字符串（精度坑）。
- 主键（唯一）和分片键（落片）可不同；基因法让两者兼得。

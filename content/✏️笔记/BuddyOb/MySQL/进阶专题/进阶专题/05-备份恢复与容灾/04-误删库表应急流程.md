# 05-备份恢复 · 误删库表应急流程

> 前置：[[MySQL/进阶专题/05-备份恢复与容灾/03-PITR时间点恢复与闪回]]

## 黄金法则：误删后第一件事 = 停写、别动！

```
❌ 错误：发现删了 → 立刻重启/各种操作 → 覆盖现场
✅ 正确：发现删了 → 立刻停业务写 → 保护现场 → 评估恢复方案
```

## 通用应急 5 步

```
1) 立刻停写：断开应用 / 关写入端口 / 设只读
2) 保护现场：别重启、别覆盖 binlog、对当前库做个紧急快照备份
3) 评估：删了什么（DML/DDL）？有全量备份吗？binlog 还在吗？
4) 选方案：闪回 / PITR / 从库回退 / 直接恢复备份
5) 恢复 + 校验数据 + 复盘（加防护）
```

## 场景 A：误 `DELETE`（DML，表还在）

- 有 ROW binlog → **闪回**（见 03）最快，影响最小。
- 无 binlog → 只能从最近全量备份 + 之后 binlog（若有）PITR。

## 场景 B：误 `UPDATE`（改错值，表还在）

- 同 DELETE，闪回反向（把旧值 UPDATE 回去）。
- 若改的是"状态/金额"类，闪回前**先确认影响行数**再放。

## 场景 C：误 `TRUNCATE` / `DROP TABLE`（DDL，表没了）

- **闪回无效**（表结构都没了）。
- 方案：
  1. 若有**全量备份 + binlog** → PITR 恢复到删前（整库/单库）。
  2. 若有**从库/延迟从库**（故意延迟 1 小时回放）→ 从延迟从库**立刻摘流量、停回放**，从它导出表 → 导回主库（最快，不依赖备份链）。
  3. 若有 **MGR** → 同组数据还在其他节点，但 DROP 已同步过去 → 还是要靠备份。

> **延迟从库**是救误删的神器：故意让从库比主库"慢 1 小时"，误删 1 小时内能直接从延迟从库捞回。

## 场景 D：误 `DROP DATABASE`（整个库没了）

- 同上，靠全量 + binlog PITR，或延迟从库。
- 主从/MGR 都**同步了 DROP**，不能指望它们。

## 从库能救命的几种"特殊从库"

| 类型 | 作用 |
|------|------|
| **延迟从库**（delayed replica） | 故意慢 N 分钟回放，误删 N 分钟内可捞 |
| **备份专用从库** | 不扛读，纯做备份源，误删主库不影响它（在它被同步前摘流） |
| **冷备实例** | 每日全量恢复好的隔离实例，应急时直接用 |

## 防误删的工程手段

1. **权限最小化**：生产账号**无 DROP/TRUNCATE** 权限，只有 DBA 有。
2. **危险操作审批 + 二次确认**：`DROP` 前强制备份。
3. **回收站（soft delete）**：业务用 `del_flag` 逻辑删，物理删走定时任务（可兜底）。
4. **延迟从库**：误删兜底（见上）。
5. **SQL 审计**：所有 DDL/DML 留痕，谁删的、删了啥可追溯。
6. **定期恢复演练**：备份"能不能恢复"必须演练验证（见 05）。

## 恢复后必做

- **校验数据**：行数、关键金额、最近记录是否完整。
- **业务对账**：和上游/下游系统核对（如订单数和支付数）。
- **复盘**：怎么删的、为什么防护没拦住、补什么措施。

## 结论

- 误删**第一要务 = 停写、保现场**，别乱动。
- DML 误删 → 闪回最快；DDL 误删 → PITR / 延迟从库捞。
- 主从/MGR **都同步误删**，别指望它们。
- **延迟从库 + 权限最小化 + 逻辑删 + 定期演练** 是防误删四件套。

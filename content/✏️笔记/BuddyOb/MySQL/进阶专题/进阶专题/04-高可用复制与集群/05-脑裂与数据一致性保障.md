# 04-高可用复制 · 脑裂与数据一致性保障

> 前置：[[MySQL/进阶专题/04-高可用复制与集群/04-读写分离中间件]]

## 脑裂（Split-Brain）是什么

```
主库 A（原主）           主库 B（被误切的新主）
  都在接受写入！
```
网络分区/切换误判 → **出现两个"主"同时写** → 数据分叉，再也合不拢。这是高可用最可怕的事故。

## 脑裂怎么发生的

- 原主其实还活着（只是和切换器网络断了），切换器以为它死了 → 提升新主。
- 原主网络恢复 → 它不知道自己已被"下课"，继续接受写入。
- 两个主各自写 → 主键冲突、数据不一致、GTID 分叉。

## 防脑裂的手段

### 1)  fencing（ fencing / 围栏）

切换新主**之前**，先**强制干掉原主**：
```
- 电源围栏：IPMI/云 API 直接断电原主机器
- 存储围栏：revoke 原主对共享存储的锁
- 网络围栏：把原主从网络隔离（iptables 丢包）
```
> 原则："不让两个主同时活"。围栏比"信任心跳"可靠。

### 2) 多数派（Paxos / 租约）

MGR / etcd 这类**共识协议**天生防脑裂：少于多数派的节点**不允许写**（自动降级只读）。
```
3 节点：断网一个 → 剩 2 个仍是多数 → 继续服务、原主（孤立）被踢出
断网两个 → 剩 1 个不是多数 → 全体停写（宁可不可用，也不脑裂）
```
- 这就是为什么 MGR 用多数派而非"主从+心跳"。
- 租约（Lease）：主定期续租，超时自动失去主身份（防"假死主"）。

### 3) 仲裁节点（Arbiter）

偶数节点（如 2 节点）易平票 → 加一个**只投票不存数据**的仲裁节点凑成奇数，避免平票脑裂。

### 4) 切换工具的正确性

用成熟工具（MHA / Orchestrator / MySQL Router + MGR），它们内置"先围栏旧主再提升新主"逻辑。手写切换脚本极易漏围栏 → 脑裂。

## 数据一致性保障（多层）

```
第1层：主库本地 ACID（redo/undo/MVCC）         → 单库不丢不错
第2层：binlog + 双1 + 半同步/无损                   → 主从不强丢
第3层：GTID 自动续传                              → 切换不重不漏
第4层：MGR 多数派 /  fencing 围栏                     → 防脑裂分叉
第5层：定期数据校验（pt-table-checksum）             → 发现漂移
```

## 数据漂移检测与修复

```
pt-table-checksum   主从跑校验 → 发现不一致的行
pt-table-sync       把从库和主库对不上的行补齐/纠正
```
- 定期跑，发现"从库被直写/复制中断导致的漂移"。
- 从库**严禁业务直写**，漂移几乎都来自此。

## 故障切换的"正确性"清单

```
1. 检测主挂（超时/心跳丢失）
2. 确认不是网络抖动误判（多次探测 / 多数派确认）
3. 围栏旧主（断电/网络隔离）
4. 提升新主（GTID 自动定位续传点）
5. 把 VIP / 中间件 / 应用指向新主
6. 旧主恢复后，以"从"身份重新加入（避免双主）
```

## 结论

- 脑裂 = 两个主同时写 → 数据分叉、不可恢复。
- 防脑裂：**fencing 围栏**（先杀旧主）+ **多数派共识**（MGR/Paxos）+ **仲裁节点**。
- 一致性多层：本地 ACID → 半同步/双1 → GTID → 围栏/多数派 → 定期校验。
- 从库**只读**，漂移检测用 pt-table-checksum/sync。

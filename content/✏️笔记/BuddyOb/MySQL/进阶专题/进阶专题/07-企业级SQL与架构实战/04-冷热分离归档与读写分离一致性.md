## 冷热分离（让热表小、查询快）

```
热数据：最近 90 天订单（高频查、要快）
冷数据：90 天前订单（归档到历史库/归档表，偶发查）
```
- 热表小 → 索引小、备份快、查询快。
- 冷数据归档到**独立库/表/分区**，甚至 ES/ClickHouse（见 [[MySQL/进阶专题/03-分库分表与分布式事务/04-跨分片查询与JOIN难题]]）。

### 实现方式

| 方式 | 做法 |
|------|------|
| **归档任务**（应用层） | 定时把"过期数据"搬去历史表，原表 `DELETE` |
| **分区表**（MySQL 原生） | 按时间 `PARTITION BY RANGE`，冷热落在不同分区，可 `DROP PARTITION` 秒删 |
| **分表**（按时间） | `order_202601` / `order_202602`，旧表整体归档 |

## 分区表（MySQL 原生冷热）

```sql
CREATE TABLE wms_order (
  id BIGINT,
  order_date DATE,
  ...
) PARTITION BY RANGE (TO_DAYS(order_date)) (
  PARTITION p202601 VALUES LESS THAN (TO_DAYS('2026-02-01')),
  PARTITION p202602 VALUES LESS THAN (TO_DAYS('2026-03-01')),
  PARTITION pmax      VALUES LESS THAN MAXVALUE
);
-- 删 1 月数据：秒级（只删分区，不逐行 DELETE）
ALTER TABLE wms_order DROP PARTITION p202601;
```
- **`DROP PARTITION` 比 `DELETE` 快几个量级**（不写 undo/redo 大量行）。
- 查询带 `order_date` 条件 → **分区裁剪**（只扫相关分区）。
- 限制：分区键要进 WHERE，否则扫全部分区。

## 归档任务的坑

```
❌ 一次性 DELETE 1000 万行 → 大事务、锁表、主从延迟爆
✅ 分批 DELETE（每批 1 万）+ 搬去历史表（见 [[MySQL/进阶专题/01-事务与锁深度/05-隔离级别实现与长事务危害]]）
```
- 归档也是写，要**分批小事务**，别一次干 1000 万。
- 归档过程产生的 binlog 也会同步从库 → 控制速率避免从库延迟。

## 读写分离下的一致性（复习关键坑）

```
事务内：写订单 → 立刻查这单（状态）
  若查被路由到从库 → 从库延迟 → 查不到刚写的 → 业务错
```
- **事务内读、刚写的读、强一致读 → 强制走主库**（见 [[MySQL/进阶专题/04-高可用复制与集群/04-读写分离中间件]]）。
- 读写分离中间件（ProxySQL/ShardingSphere）规则：事务内 / 带 hint 的 → 主库。

## 归档 + 读写分离的组合

```
热表（主库 + 从库读）  ← 高频
冷归档表（独立，可只读库） ← 低频
应用按"查询时间范围"路由到热/冷
```
- 热表小、从库同步快、读快。
- 冷数据偶尔查，放低成本存储。

## 冷热不分的代价

```
单表 5 亿行、不分冷热 → 索引巨大、备份 8 小时、慢查询、主从延迟
拆冷热 → 热表 5000 万、备份 20 分钟、查询毫秒
```

## 结论

- 冷热分离让**热表小** → 快、好备份、低延迟。
- 原生用**分区表**（`DROP PARTITION` 秒删冷数据）。
- 归档用**分批小事务**，别一次 DELETE 千万行。
- 读写分离下：**事务内/刚写/强一致读 → 走主库**。

## 事故一：深分页拖垮数据库

### 现象
"订单列表翻到第 5000 页，接口 30 秒超时，DB CPU 100%"。

### 根因
```sql
SELECT * FROM wms_order ORDER BY id DESC LIMIT 1000000, 20;
-- 要先扫 100 万行、排序、丢掉前 100 万、取 20 → 全扫 + filesort
```
- `LIMIT offset, n` 的 offset 越大越慢（见 [[MySQL/进阶专题/02-索引底层与优化器执行计划/05-索引失效全场景]] 深分页）。
- 分库分表下更惨（每片都扫 100 万，见 [[MySQL/进阶专题/03-分库分表与分布式事务/04-跨分片查询与JOIN难题]]）。

### 修复
- **游标分页**：`WHERE id < ? ORDER BY id DESC LIMIT 20`（每片只查 20 行）。
- 或复杂检索走 **ES**（不接受深跳页）。
- 前端限制"最多翻到第 N 页"。

## 事故二：大事务锁全表 + 主从延迟

### 现象
"下午 3 点，下单接口全卡，从库延迟飙升到 5 分钟"。

### 根因
```java
@Transactional   // 整个方法一个事务
public void importOrders(List<Order> list) {
    for (Order o : list) {            // 10 万行
        orderMapper.insert(o);        // 每行都在这长事务里
        callRemoteWMS(o);            // ❌ 还夹了外部 RPC 调用！
    }
}
```
- 长事务持行锁/间隙锁 → 别的写入阻塞。
- 夹了 RPC → 事务持续几十秒 → 锁更久。
- 提交时 binlog 一次性写 → 从库要 5 分钟回放 → 主从延迟。

### 修复
- **分批小事务**（每 1000 行一个事务，见 [[MySQL/进阶专题/01-事务与锁深度/05-隔离级别实现与长事务危害]]）。
- **RPC/HTTP 移出事务**（见 [[MyBatis Mapper XML/进阶专题/04-批量与性能优化/02-ExecutorType.BATCH手动批处理]]）。
- 导入类任务走**异步 + 独立连接**，不占主业务事务。

## 事故三：索引"看起来有，实际没用"

### 现象
"就加了个 `WHERE status = ?`，原来毫秒，现在全表扫 8 秒"。

### 根因（常见之一：隐式转换）
```sql
-- status 是 VARCHAR
SELECT * FROM order WHERE status = 0;     -- ❌ 传了数字 → 列被转数字 → 索引失效
SELECT * FROM order WHERE status = '0';   -- ✅ 字符串 → 走索引
```
- 参数类型与列不一致 → 优化器对列做函数转换 → 索引失效（见 [[MySQL/进阶专题/02-索引底层与优化器执行计划/05-索引失效全场景]]）。
- MyBatis 里就是"参数类型与列类型不匹配"（见 [[MyBatis Mapper XML/进阶专题/06-企业实战与疑难排查/04-诡异Bug排查与Locations坑根源]]）。

### 其他根因
- 对列用函数：`DATE(create_time) = ?` → 失效，改参数侧范围。
- 前导 `%`：`LIKE '%张'` → 失效。
- 违反最左：`INDEX(a,b)` 但只查 `b` → 失效。
- 优化器认为"回表太贵"弃用 → 建覆盖索引。

### 定位流程
```
1) EXPLAIN → type=ALL / key=NULL → 全扫
2) EXPLAIN FORMAT=JSON → 看优化器为什么弃用
3) 查参数类型 / 函数 / 模糊 / 最左 → 对齐
4) ANALYZE TABLE 更新统计（若过期）
5) 建覆盖索引消除回表
```

## 事故四：误删（最惨）

### 现象
"运营手滑 `DELETE FROM wms_stock` 没加 WHERE，库存全没"。

### 根因与修复
- DML 没 WHERE → 全表删（见 [[MySQL/进阶专题/05-备份恢复与容灾/04-误删库表应急流程]]）。
- 救：停写 → ROW binlog 闪回（见 [[MySQL/进阶专题/05-备份恢复与容灾/03-PITR时间点恢复与闪回]]）。
- 防：生产账号无 DROP/DELETE 大权限、危险操作审批、**延迟从库**兜底、逻辑删（`del_flag`）。

## 事故复盘清单（SOP）

```
收到告警（慢查询/连接满/主从延迟）→ 
1) SHOW PROCESSLIST 看谁占连接、State 卡哪
2) EXPLAIN 慢 SQL 看是不是全扫/没走索引
3) SHOW ENGINE INNODB STATUS 看锁/死锁
4) information_schema.innodb_trx 看长事务
5) 止血：杀掉问题会话 / 临时限流 / 摘流量
6) 修复：加索引 / 改 SQL / 分批 / 游标分页
7) 复盘：加防护（权限/审批/监控/演练）
```

## 结论

- **深分页**：游标分页 / ES，别用 `LIMIT offset`。
- **大事务**：分批小事务 + RPC 移出事务 + 异步导入。
- **索引失效**：先 EXPLAIN，再查类型/函数/模糊/最左，建覆盖索引。
- **误删**：应急停写 → 闪回/PITR；防护靠权限/审批/延迟从库/逻辑删。
- 所有事故都有**可提前的监控**（见 [[MySQL/进阶专题/06-参数调优与运维实战/05-监控告警与关键指标]]）。

# 07-企业实战 · 缓存与数据库一致性（Canal）

> 前置：[[MySQL/进阶专题/07-企业级SQL与架构实战/02-高并发扣减防超卖(WMS)]] ｜ 缓存：[[MyBatis Mapper XML/进阶专题/03-缓存机制深度/04-缓存三大问题与事务脏读]]

## 为什么"加了缓存还是脏"

缓存和 DB 是两份数据，任何"写"都要决定**先写谁、怎么保一致**。不一致就出现"列表看到旧库存"。

## 方案 1：Cache Aside（旁路，最常用）

```
读：缓存有 → 返回；没有 → 查 DB → 写入缓存
写：先更新 DB → 再删除缓存（不是更新缓存！）
```
**为什么删缓存而不是更新缓存**：
- 更新缓存可能算错（如 `qty-1` 并发重复减）。
- 删缓存 = "下次读再重建"，简单且无并发算错。

**不一致窗口**：
```
T1: 更新 DB（新值）
T2: 删缓存
→ 这之间若有读，读到旧值并可能回写旧缓存 → 短暂不一致
```
概率极低（要"写删之间刚好有读"），多数业务可接受。

## 方案 2：先删缓存再更新 DB（更稳但仍有窗）

```
写：先删缓存 → 再更新 DB
```
- 若删缓存后、更新 DB 前，有读 → 读 DB 旧值写回缓存 → 不一致。
- 两种顺序都有窗，Cache Aside 更主流（因为"更新 DB 比删缓存"慢，窗更短）。

## 方案 3：延迟双删（补窗）

```
写：删缓存 → 更新 DB → sleep(500ms) → 再删一次缓存
```
- 第二次删消化掉"期间误写的旧缓存"。
- 500ms 是经验值（覆盖"读重建缓存"的耗时）。

## 方案 4：Canal 订阅 binlog（本仓库风格，最彻底）

**核心思想**：不靠应用"记得删缓存"，而是**监听 MySQL binlog，数据一变就自动删/更新缓存**。

```
MySQL binlog ── Canal 客户端订阅 ──> 投递到 MQ/直接调用 ──> 删缓存 / 更新缓存
```
- 业务代码**只管写 DB**，缓存一致性由 Canal 兜底。
- 解耦：任何途径改了 DB（含直接 SQL、别的微服务）→ 缓存都跟着变。
- 本仓库若做"库存/字典缓存强一致"，用 Canal 监听 `wms_stock` 变更 → 删对应 Redis key。

### Canal 配置思路

```yaml
# canal.properties：伪装成 MySQL 从库，拉 binlog
canal.instance.master.address = 127.0.0.1:3306
canal.instance.dbUsername = canal
canal.instance.dbPassword = xxx
# 客户端：收到 RowChange → 解析出 表+主键 → 删 redis key: stock:{skuId}
```
> 前提：binlog = ROW 格式（见 [[MySQL/进阶专题/04-高可用复制与集群/01-主从复制原理binlog三格式]]）。

## 方案 5：强一致（读写锁 / 分布式锁）

对"绝对不能脏"的数据（余额）：
- 读也加分布式锁 / 强制走 DB（不查缓存）。
- 或写时 `RedissonLock` 锁住 sku → 读写互斥 → 强一致（性能低）。

## 方案选择

| 场景 | 选 |
|------|-----|
| 普通业务（库存/列表） | **Cache Aside + 延迟双删** |
| 多服务/多途径改同一表 | **Canal 订阅 binlog** 兜底 |
| 绝对不能脏（余额） | 强一致锁 / 读写走 DB |
| 极高并发读 | 缓存 + 防穿透/击穿（见 [[MyBatis Mapper XML/进阶专题/03-缓存机制深度/04-缓存三大问题与事务脏读]]） |

## 三个必防

1. **缓存穿透**：查不存在的 key → 空值缓存 / 布隆。
2. **缓存击穿**：热点 key 过期 → 互斥锁。
3. **缓存雪崩**：大量 key 同过期 → TTL 抖动。

## 结论

- 最常用 **Cache Aside**：写时"更新 DB + 删缓存"（删不是更新）。
- 防不一致窗用**延迟双删**。
- 多服务/直接改 DB 场景用 **Canal 订阅 binlog** 自动删缓存，最彻底。
- 强一致数据用锁 / 读写走 DB。

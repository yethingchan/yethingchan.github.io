# 06-参数调优 · 碎片整理与表空间

> 前置：[[MySQL/进阶专题/06-参数调优与运维实战/03-大表DDL-gh-ost与instant]]

## 碎片是什么

频繁 `DELETE` / `UPDATE`（变长字段变短）/ 大量归档后，表里出现**空洞**：
- 数据行删了，但页/区的空间没还给 OS。
- 二级索引的"标记删除"也留空洞。
- 结果：**.ibd 文件很大，但实际数据很少**，查询要扫更多页 → 变慢。

```
原：100 万行，数据 2GB
DELETE 掉 80 万行 → 数据剩 0.4GB，但 .ibd 还是 ~2GB（全是无用空洞）
```

## 怎么看碎片

```sql
-- 数据长度 vs 索引长度 vs 分配空间
SELECT
  table_name,
  data_length,            -- 数据字节
  index_length,           -- 索引字节
  data_free              -- 碎片（空闲未回收）字节
FROM information_schema.tables
WHERE table_schema='mydb' AND data_free > 0
ORDER BY data_free DESC;
```
- `data_free` 大（比如几百 MB、比 `data_length` 还大）→ 碎片严重。

## 整理方式 1：`OPTIMIZE TABLE`

```sql
OPTIMIZE TABLE big_order;
-- 等价于：ALTER TABLE ... FORCE（重建表，回收空洞）
```
- 实质是**重建表**（拷贝数据到新表、改名），会**锁表一段时间**（大表慎用）。
- 5.6+ InnoDB 的 `OPTIMIZE` 走 Online DDL（仍可能短暂锁）。

## 整理方式 2：`ALTER TABLE ... ENGINE=INNODB`（等价重建）

```sql
ALTER TABLE big_order ENGINE=INNODB;   -- 重建表，回收碎片
-- 加安全声明：
ALTER TABLE big_order ENGINE=INNODB, ALGORITHM=INPLACE, LOCK=NONE;
```
- 和 `OPTIMIZE` 本质一样，是"原地重建"。
- 大表用 gh-ost 式的重建更安全（见 03）。

## 整理方式 3：`TRUNCATE` + 重导（极端）

表可重建时，最彻底：导出真数据 → `TRUNCATE` → 导入。最干净但停机。

## 表空间：独立 vs 共享

```
innodb_file_per_table = ON    # 默认 ON：每表一个 .ibd 文件
```
- **ON（独立表空间）**：`OPTIMIZE` 后 `.ibd` 能缩小（空间还给 OS）。
- **OFF（共享 ibdata1）**：所有表混在 `ibdata1`，**碎片永远还不了 OS**（ibdata1 只增不减）→ 必须独立表空间才能收缩。

> 老版本默认 OFF 是个大坑，现代默认 ON 已解决。确认 `innodb_file_per_table=ON`。

## 碎片预防（比整理重要）

1. **用 `del_flag` 逻辑删 + 定时物理归档**：避免业务表频繁物理 DELETE 出空洞（见 [[MySQL/进阶专题/07-企业级SQL与架构实战/04-冷热分离归档与读写分离一致性]]）。
2. **自增主键**：插入在末尾，少页分裂（见 [[MySQL/进阶专题/02-索引底层与优化器执行计划/01-B+树页结构与回表]]）。
3. **变长字段别频繁缩短**：`VARCHAR` 改短会留空洞，尽量定长或可接受。
4. **定期整理**：低频大表每季度 `OPTIMIZE` 一次（低峰）。

## 整理时机判断

```
data_free > 数据本身大小的 30%~50%  → 值得整理
整理在低峰 + 用 gh-ost/Online DDL（LOCK=NONE）
小表不值得（成本 > 收益）
```

## 结论

- 碎片 = DELETE/UPDATE 留下的页空洞，`.ibd` 大但数据少、查询变慢。
- 看 `information_schema.tables.data_free` 判断严重度。
- 整理：`OPTIMIZE TABLE` / `ALTER ... ENGINE=INNODB`（本质重建表）。
- **必须 `innodb_file_per_table=ON`** 才能把空间还给 OS。
- 预防（逻辑删+归档、自增主键）比事后整理更划算。

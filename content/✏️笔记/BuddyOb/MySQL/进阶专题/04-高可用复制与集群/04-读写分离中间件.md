# 04-高可用复制 · 读写分离中间件

> 前置：[[MySQL/进阶专题/04-高可用复制与集群/03-MGR组复制Paxos]] ｜ 基础：[[MySQL/13-主从复制与读写分离]]

## 读写分离的目的

主库扛写，多个从库扛读 → **读扩展**（读多写少场景，如报表、列表查询）。中间件负责把 `SELECT` 路由到从库、`INSERT/UPDATE/DELETE` 路由到主库。

## 方案 1：ProxySQL（最常用，C 写的高性能代理）

```
应用 ──> ProxySQL(6033) ──写入──> 主库
                         └─查询──> 从库(负载均衡)
```
特点：
- 规则引擎：按 SQL 类型 / 正则 / 用户 / 注释 hint 路由。
- **连接池 + 复用**：挡在应用和 MySQL 之间，减少后端连接。
- 健康检查：从库挂了自动摘流量。
- 读写分离规则示例（概念）：
  ```
  匹配 SELECT 且非事务内 → 路由读组（从库）
  匹配写语句 / 事务内 → 路由写组（主库）
  ```

## 方案 2：MyCat（Java，国产老牌）

- 更像"数据库中间件"，支持分库分表 + 读写分离。
- 配置 XML 路由规则。
- 历史项目多见，新项目多转向 ProxySQL / ShardingSphere-Proxy。

## 方案 3：ShardingSphere-Proxy

- 和 [[MySQL/进阶专题/03-分库分表与分布式事务/03-ShardingSphere实战]] 的 Sharding-JDBC 同生态，可同时做**分片 + 读写分离**。
- 一套配置管分库分表 + 读写分离，省维护。

## 方案 4：应用层（不推荐大用）

```java
// 自己根据方法名路由不同数据源
@DataSource("slave") public List<Order> list() {...}   // 读走从
@Transactional @DataSource("master") public void create() {...}  // 写走主
```
- 简单场景可用（如本仓库 RuoYi 若接从库可注解切换）。
- 但规则散在代码里、事务内读走从易错，**大规模不如中间件**。

## 🔴 读写分离的"一致性坑"

```
事务内：INSERT 一行 → 立刻 SELECT 这一行
  若 SELECT 被路由到从库 → 从库还没同步到（有延迟）→ 查不到！
```
**解法**：
- **事务内强制走主库**（ProxySQL 规则：事务内全走主）。
- 或"刚写的Session 本事务内读主"。
- 关键业务（余额、订单状态）**永远走主库**，别为了省而读从。

## 延迟敏感的读怎么处理

| 读类型 | 路由 |
|------|------|
| 刚写的读（事务内） | **主库** |
| 强一致要求（余额） | **主库** |
| 容忍秒级延迟（列表、报表、统计） | 从库 |

> "写后立刻读"是最常踩的坑，务必事务内读主。

## 负载均衡与权重

- 多个从库可配权重（性能高的多分流量）。
- 从库延迟过大（Seconds_Behind > 阈值）自动降权/摘流。

## 结论

- 读写分离 = 写走主、读走从，扩读能力。
- 中间件首选 **ProxySQL**（高性能）或 **ShardingSphere-Proxy**（分片+读写一体）。
- **事务内读、刚写的读、强一致读 → 必须走主库**，否则延迟导致查不到。
- 从库延迟大自动摘流。

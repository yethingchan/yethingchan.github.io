# 02-索引底层 · B+ 树页结构与回表

> 前置：[[MySQL/进阶专题/02-索引底层与优化器执行计划/00-索引]]

## InnoDB 的"页"（16KB）

InnoDB 所有数据**最小管理单位 = 页（page）**，默认 **16KB**。B+ 树的一个节点 = 一个页。
- 一个页能存很多行（取决于行宽）。
- 一次 IO 读一页（或连续几页，靠预读）。
- 索引的"高度"= 从根页到叶页的页数。**3 层 B+ 树能存千万级数据**，查一次只要 3 次 IO。

## 聚簇索引（Clustered Index）

- **主键**就是聚簇索引，**叶子节点存整行数据**。
- 一张表**只有一个**聚簇索引（没显式主键就用唯一非空，再没有用隐式 `DB_ROW_ID`）。
- 所以"按主键查"最快——直接定位到叶子页就拿到了整行。

## 二级索引（Secondary Index）

- 普通索引/唯一索引/联合索引都是二级索引。
- **叶子节点不存整行**，只存 **索引列的值 + 主键值**。
- 例：`INDEX(age)` 的叶子存 `(age, id)`。

## 回表（Bookmark Lookup）—— 核心代价

当用二级索引查、但 `SELECT` 列**不全在索引里**，要再拿主键回聚簇索引取其余列：

```
SELECT name FROM user WHERE age = 20;
-- 1) 走 age 二级索引，找到 age=20 的叶子 → 拿到 id 列表
-- 2) 用 id 回聚簇索引（再查一遍）→ 拿到 name
→ "回表"发生
```
- 回表 = **再走一次 B+ 树**（多一次 IO/行）。
- 大结果集回表 → 性能杀手。

## 例子说明聚簇 vs 二级

```
表 user(id PK, name, age, email)
INDEX idx_age (age)

主键查：WHERE id=5        → 聚簇索引一次定位 → 最快
二级查：WHERE age=20      → age 索引找 id → 回表拿 name/email → 多了回表
```

## 联合索引的"最左前缀"

`INDEX(a, b, c)` 在 B+ 树里按 **a → b → c** 排序存储：
```
(a) 有序
(a,b) 有序
(a,b,c) 有序
但 (b,c) 无序 → 不能跳过 a 直接用 b
```
- 能用到索引：`WHERE a=?` / `a=? AND b=?` / `a=? AND b=? AND c=?` / `a=? AND c=?`（c 用上但 b 断，部分）。
- 用不到：`WHERE b=?` / `WHERE c=?`（跳过最左 a）。

## 主键设计对 B+ 树的影响

- **自增主键（推荐）**：插入永远在末尾追加 → 页分裂少、碎片低。
- **UUID/随机主键（不推荐）**：插入位置随机 → 频繁页分裂、页填充率低 → 索引更大、更慢。
- 本仓库雪花 ID（`ASSIGN_ID`）是**趋势递增**的，接近自增效果，比纯随机 UUID 好。

## 结论

- 一表一聚簇（主键），二级索引叶子只存"索引列 + 主键"。
- 回表 = 二级索引查完还要拿主键回聚簇再查一次 → 大结果集慢。
- 减少回表 = 建**覆盖索引**（见 02）。
- 主键用自增/趋势递增，避免随机主键的页分裂。

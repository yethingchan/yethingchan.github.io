# 07 · 索引原理（B+Tree）

> 进阶路线：[[00-总览与学习路线]] → L3 性能原理 ｜ 前置：[[04-表设计与约束]]

索引是 MySQL 性能的第一杠杆。先懂结构，才会建索引。

## 1. 为什么需要索引

- 无索引：全表扫描（`EXPLAIN` 显示 `ALL`），数据量大时灾难。
- 有索引：把「随机磁盘查找」变成「有序树查找」，复杂度从 O(N) 降到 O(log N)。

## 2. InnoDB 用 B+Tree（不是二叉树/红黑树/哈希）

为什么不是别的：
- 二叉树/红黑树：**高度太高**，百万数据要几十层，磁盘 IO 多。
- Hash：等值快，但**不支持范围 / 排序**。
- **B+Tree**：多路平衡树，**矮胖**（一页 16KB，三五百子节点），高度通常 3~4 层；且**叶子节点用双向链表串起，天然支持范围查询**。

```
        [根节点: 只存键值+指针]
       /        |        \
  [分支]    [分支]    [分支]
     |           |           |
[叶子]→[叶子]→[叶子]→[叶子]   (链表串联, 存真实数据/主键)
```

## 3. 聚簇索引 vs 二级索引（InnoDB 核心）

- **聚簇索引（主键）**：叶子节点**直接存整行数据**。一张表**只有一个**，默认是主键。
- **二级索引（普通/唯一索引）**：叶子节点存的是**主键值**，不是行数据。

> 由此引出两个关键概念：
> - **回表**：用二级索引查到主键后，再拿主键去聚簇索引找整行 → 多了一次 B+Tree 查找。
> - **覆盖索引**：查询列**刚好都在二级索引里** → 不用回表，性能翻倍（详见 [[09-索引设计与优化实战]]）。

## 4. 索引的类型

| 类型 | 说明 |
|------|------|
| 普通索引 `INDEX` | 最基础，加速查询 |
| 唯一索引 `UNIQUE` | 值不重复（可含 NULL） |
| 主键索引 `PRIMARY KEY` | 聚簇，唯一非空 |
| **组合索引** | 多列联合 `(a,b,c)`，有最左前缀规则 |
| 前缀索引 | 长字符串取前 N 字符建索引 |
| 全文索引 | `FULLTEXT`，替代 `LIKE '%xx%'` |
| 空间索引 | GIS 数据 |

## 5. 组合索引的最左前缀（必考）

索引 `(a, b, c)` 相当于建了 `(a)`、`(a,b)`、`(a,b,c)` 三个索引：
```sql
WHERE a=1 AND b=2 AND c=3   -- ✅ 命中完整索引
WHERE a=1 AND b=2           -- ✅ 命中 (a,b)
WHERE b=2 AND c=3           -- ❌ 没 a，索引失效（除非有单独索引）
WHERE a=1 AND c=3           -- ⚠️ 只用到 a，c 失效
```

> 范围查询（`>`, `<`, `BETWEEN`）后的列**会失效**：`WHERE a=1 AND b>2 AND c=3` → 仅用到 `(a,b)`。

## 6. 索引的代价

- 占空间；写操作（INSERT/UPDATE/DELETE）要维护索引 → 拖慢写入。
- **不是越多越好**：只对「高频查询、高选择性」列建索引（详见 [[09-索引设计与优化实战]]）。

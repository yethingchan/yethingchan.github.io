# 14 · 分库分表与高可用架构

> 进阶路线：[[00-总览与学习路线]] → L4 企业级 ｜ 前置：[[13-主从复制与读写分离]] ｜ [[04-表设计与约束]]

单机到瓶颈（单表千万级/单库连接数/IPOS 上限）→ 拆分 + 高可用。

## 1. 垂直拆分 vs 水平拆分

| 维度 | 垂直（按业务） | 水平（按数据行） |
|------|----------------|----------------|
| 分库 | 用户库/订单库/商品库 | 同结构多库（按分片键） |
| 分表 | 大字段拆出去（主表+扩展表） | 同表结构拆多张（user_0..user_31） |
| 解决 | 业务解耦、单库过大 | 单表过大、写入热点 |

## 2. 分片键（sharding key）是核心

- 选**高频过滤且分布均匀**的列（如 `user_id`），避免跨分片查询。
- 错误选择 → 查询被迫广播到所有分片（全库扫），比不分还慢。
- 常见：用户域用 `user_id`，订单域用 `order_id` 或 `user_id`。

## 3. 常见拆分策略

- **取模**：`id % 32` → 32 张表。扩容麻烦（要迁移）。
- **范围**：按时间/ID 段。易产生热点（最新段最忙）。
- **一致性哈希**：节点增减只迁移少量数据，扩缩容友好。
- **基因法**：分片键里嵌入分表位（如 `user_id` 末位决定表），避免查两次。

## 4. 中间件（企业主流）

| 组件 | 角色 |
|------|------|
| **ShardingSphere**（JDBC / Proxy） | 国产、活跃，分库分表+读写分离+加密，首选 |
| MyCat | 老牌 Proxy，配置重 |
| Vitess | YouTube 出品，K8s 友好，偏大型 |

> 优先 **ShardingSphere**：入侵低（JDBC 模式改配置即可），功能全。

## 5. 高可用架构

| 方案 | 说明 |
|------|------|
| **MHA** | 经典主从故障自动切换（Manager+Node） |
| **MGR / InnoDB Cluster** | 官方组复制，多数派一致，原生高可用 |
| **Orchestrator** | 开源拓扑管理与自动 failover |
| **Keepalived + VIP** | 虚拟 IP 漂移，对应用透明 |

```
      应用 → 代理(ProxySQL/ShardingSphere/Keepalived-VIP)
                   ↓
        [主 Master] ←半同步→ [从 Slave1] [从 Slave2]
              ↓ binlog                       ↑
          [MGR / MHA 自动选主切换]
```

## 6. 分布式 ID

分库分表后自增主键冲突 → 用**全局唯一 ID**：
- **雪花算法**（Twitter Snowflake）：时间戳+机器+序列，趋势递增。
- 美团 Leaf、百度 UidGenerator、UUID（不推荐当主键，见 [[04-表设计与约束]]）。

## 7. 分库分表的代价（必须权衡）

- 跨分片 JOIN、分布式事务（2PC / 最终一致）变复杂。
- 分页、排序、聚合需各分片算再归并。
- **能不分就不分**：先索引优化、主从、升级硬件，真到瓶颈再拆。

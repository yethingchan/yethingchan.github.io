# 03 · 数据类型与字符集

> 进阶路线：[[00-总览与学习路线]] → L1 基础 ｜ 上接：[[02-SQL分类与基础查询]]

字段类型选错 = 浪费空间 + 索引失效 + 隐式转换坑。这一篇是「基础里的硬核」。

## 1. 数值类型

| 类型 | 字节 | 范围/说明 |
|------|------|-----------|
| `TINYINT` | 1 | -128~127（状态/布尔常用） |
| `SMALLINT` | 2 | 短整型 |
| `INT` / `INTEGER` | 4 | 普通整数 |
| `BIGINT` | 8 | 主键/雪花 ID 常用 |
| `DECIMAL(M,D)` | 变长 | **精确小数**（金额必用！） |
| `FLOAT` / `DOUBLE` | 4/8 | 浮点，**有精度丢失，禁止存钱** |

> **金额一律用 `DECIMAL(18,2)`**，`FLOAT/DOUBLE` 存钱会丢分（0.1+0.2≠0.3）。

## 2. 字符串类型

| 类型 | 说明 | 场景 |
|------|------|------|
| `CHAR(N)` | 定长，不足补空格 | 定长编码（如 MD5、身份证号理论可，但建议 VARCHAR） |
| `VARCHAR(N)` | **变长**，存 1~N | 绝大多数文本，用户名/邮箱/地址 |
| `TEXT` / `MEDIUMTEXT` / `LONGTEXT` | 大文本 | 文章正文、日志（不进行格式，单独存） |
| `JSON` | MySQL 8.0 原生 | 半结构化数据，可建函数索引 |

> `VARCHAR` 长度单位：**字符**（非字节）。`utf8mb4` 下中文占 1 字符（存储按 3~4 字节）。
> 经验：`VARCHAR(255)` 是常用上界；超过用 `TEXT`。

## 3. 日期时间类型

| 类型 | 格式 | 说明 |
|------|------|------|
| `DATETIME` | `2026-07-19 14:00:00` | 与时区无关，存储空间大 |
| `TIMESTAMP` | 时间戳 | **与时区有关**，范围 1970~2038（有 2038 问题） |
| `DATE` | `2026-07-19` | 只存日期 |
| `TIME` | `14:00:00` | 只存时间 |
| `YEAR` | `2026` | 年份 |

> 企业实践：**统一用 `DATETIME`** 存业务时间（避免时区/2038 坑）；`TIMESTAMP` 仅用于「最后修改时间」这类自动维护字段。
> 与 Java 对应：`DATETIME` → `LocalDateTime`；日期 → `LocalDate`。

## 4. 字符集与排序规则（极易踩坑）

- **字符集**：`utf8mb4`（**不是 `utf8`**！MySQL 的 `utf8` 是阉割版，最多 3 字节，存不了 emoji/部分生僻字）。
  ```sql
  CREATE DATABASE db CHARSET utf8mb4;
  ```
- **排序规则 `COLLATION`**：
  - `utf8mb4_general_ci`：ci=不区分大小写，老默认，排序快但不够准。
  - `utf8mb4_unicode_ci` / `utf8mb4_0900_ai_ci`（8.0 默认）：更准。
  - `..._bin`：按二进制比，区分大小写。
- **坑**：两张表/两个库的字符集或 collation 不一致时，JOIN 会**无法用索引**（隐式转换），详见 [[09-索引设计与优化实战]]。

## 5. 选型原则（面试/规范常考）

1. 最小够用：状态用 `TINYINT` 别用 `INT`。
2. 金额 `DECIMAL`，禁 `FLOAT/DOUBLE`。
3. 固定长度小字段可 `CHAR`，其余 `VARCHAR`。
4. 时间 `DATETIME`，库级 `utf8mb4`。
5. 大文本 `TEXT` 单独表，别和主表混。

# 03 后端基础框架 · 技术细节与难点

> 配套原教程：[[../03-后端基础框架/00-索引]]（统一返回/全局异常/MP+Redis/Security+JWT/CORS+XSS）
> 本篇是**全工程的"地基"**，也是坑最密的一章——Spring Security 6 和 JWT 0.12 的 API 都和网上 90% 的老例子对不上。

## 一、技术细节

### 3.1 统一返回 `AjaxResult` / `R<T>`
- 约定：`code=200` 成功，非 200 是业务异常；`data` 装载荷，`R<T>` 额外带 `rows/total` 给分页。
- 前端 `request.js` 只认 `code`：200 取 `data`，否则 `message` 弹错，401 跳登录。

### 3.2 全局异常（**Filter 边界是大坑**）
`@RestControllerAdvice` + `@ExceptionHandler` 能兜住 `BusinessException` / `MethodArgumentNotValidException` / 兜底 `Exception`。
**但**：它只在 **`DispatcherServlet` 之后**（Controller/Service 层）生效。而 **JWT 过滤器在 `DispatcherServlet` 之前**——过滤器里抛的异常，`@RestControllerAdvice` 根本看不到，结果前端收到的是 Tomcat 默认 HTML 错误页，`request.js` 解析不了 JSON。

### 3.3 Spring Security 6（最大变化）
- **不再继承 `WebSecurityConfigurerAdapter`**（已弃用）。改成写一个 `@Bean SecurityFilterChain`。
- 方法级鉴权用 **`@EnableMethodSecurity`**（替代老的 `@EnableGlobalMethodSecurity`），配合 `@PreAuthorize("hasPermi('system:user:add')")`。

### 3.4 JWT jjwt **0.12**（API 全改）
- 签发：`Jwts.builder().signWith(key, JwTSAlgorithm.HS256).setSubject(...).compact()`
- 解析：`Jwts.parser().verifyWith(key).build().parseSignedClaims(token)`
- **`key` 是 `SecretKey` 对象**（不是老式的 `String` + `SignatureAlgorithm.HS512`）。HMAC 密钥必须 **≥256 bit**，否则 `WeakKeyException`。
- 老式 0.9.1 的 `Jwts.builder().setClaims(...).signWith(SignatureAlgorithm.HS512)` 在本项目直接编译不过。

### 3.5 Redis 序列化
默认 `RedisTemplate` 用 **JDK 序列化**（二进制、redis-cli 看不懂、占空间）。改成 `StringRedisTemplate` + **手动 JSON 字符串**最稳，避开泛型擦除带来的反序列化头疼。

### 3.6 CORS 与鉴权链顺序
`CorsConfigurationSource` 必须放在过滤链**最前**，且对 `OPTIONS` 预检 `permitAll`——否则浏览器预检失败，跨域红字。

## 二、技术难点

1. **Security 6 老代码编译失败**：全网 80% 例子是 `extends WebSecurityConfigurerAdapter` + `antMatchers`，在 Boot 3 下整段红。本项目用 `SecurityFilterChain` + `authorizeHttpRequests` + `@EnableMethodSecurity`。
2. **JWT 0.12 写法对不上**：`setClaims/signWith(SignatureAlgorithm)` 已弃用；`key` 必须用 `Keys.hmacShaKeyFor(secret.getBytes())` 造 `SecretKey`，密钥长度不够直接抛 `WeakKeyException`。
3. **全局异常管不到 Filter**：如上，JWT 过滤器抛的 401/403 走不到 `@RestControllerAdvice`。**必须**在 `AuthenticationEntryPoint`（未认证→401 JSON）和 `AccessDeniedHandler`（无权限→403 JSON）里**手写 JSON 响应**，否则前端拿到 HTML。
4. **Redis 二进制乱码**：默认 JDK 序列化存进去是 `\xac\xed\x00...`，排查时一头雾水。改用 `StringRedisTemplate` + JSON。
5. **MP 分页拦截器顺序**：多个拦截器（分页/乐观锁/多租户/数据权限）顺序敏感，**分页必须排最前**，否则 `count` 语句拼错、分页总数算错。
6. **CORS 预检被拦**：带 `Authorization` 的非简单请求，浏览器先发 `OPTIONS`；若 Security 把它当普通请求拦了，预检失败。需 `requestMatchers(HttpMethod.OPTIONS,"/**").permitAll()`。

## 三、本项目的解法（代码落点）

| 难点 | 本项目做法 |
|------|--------------|
| Security 6 | `@Bean SecurityFilterChain` + `@EnableMethodSecurity` + `authorizeHttpRequests` |
| JWT 0.12 | `Jwts.builder().signWith(key,HS256)` + `Keys.hmacShaKeyFor` 造 `SecretKey`（≥256bit） |
| Filter 异常边界 | `AuthenticationEntryPoint`→401 JSON、`AccessDeniedHandler`→403 JSON，不走 `@RestControllerAdvice` |
| Redis 序列化 | `StringRedisTemplate` + JSON 字符串，规避 JDK 二进制 |
| 分页拦截器 | `PaginationInnerInterceptor` 排拦截器链**第一位** |
| CORS | `CorsConfigurationSource` 置链首，`OPTIONS` `permitAll` |
| 全局异常 | `@RestControllerAdvice` 兜 Controller 层；`BusinessException/ErrorCode` 统一码 |

> 一句话：**这章的难点本质是"版本迁移"——Security 6 弃了 Adapter、JWT 0.12 弃了 setClaims，而 Filter 异常边界是独立的一篇**。本项目全部用 Boot 3 原生写法落地。

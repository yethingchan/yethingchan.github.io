# 05 字典与基础数据 · 技术细节与难点

> 配套原教程：[[../05-字典与基础数据/00-索引]]（字典管理 / 参数配置与公告）
> 本篇讲**为什么下拉框千万别硬编码、字典缓存怎么才不"改了不生效"、参数怎么才能热更新**。

## 一、技术细节

### 5.1 字典两张表
- `sys_dict_type`（类型：如 `sys_user_sex`）+ `sys_dict_data`（数据：`dict_type` 外键，含 `label/value`）。
- 下拉框**统一读字典**：按 `dict_type` 拉 `list`，前端 `el-select` 渲染。**告别硬编码** `男/女` 写死在前端。

### 5.2 字典缓存
启动时或首次访问加载到 **Redis / 本地 Map**，下拉渲染前从缓存取，避免每次 `SELECT`。

### 5.3 参数配置 `sys_config`
`config_key / config_value` 存系统参数（分页大小、上传路径、限流阈值）。两种用法：
- `@Value("${...}")` 注入（绑定在启动时，**改了不自动刷**）；
- 实时从 **Redis / DB** 读（改了马上生效）。

### 5.4 公告 `sys_notice`
富文本 `content` + 状态（草稿/发布）+ 已读未读。

## 二、技术难点

1. **字典缓存一致性（最经典）**：后台改了字典数据，但**缓存没清** → 页面下拉还是旧值。解法：改字典后**主动 `DEL` Redis 缓存 key**（或短 TTL + 主动失效），下次拉重新加载。
2. **字典 vs 枚举用混**：经常变的下拉（订单状态、审批结果）用**字典**（后台可改）；不变的技术枚举（性别、布尔）可用 Java `enum`。混用会让"到底改代码还是改库"说不清。
3. **参数热更新坑**：用 `@Value` 注入的字段，**配置在应用启动时绑定一次**，运行时改 `application.yml` 或 DB 都不会让这个 Bean 字段变。要热更新只能：**每次实时从 Redis/DB 读**，或用 Spring Cloud 的 `@RefreshScope`。
4. **富文本公告的 XSS**：公告 `content` 是 HTML，存库前若全转义会丢格式，不处理又会被 XSS（见 [[技术细节与难点/10-安全防护]]）。本项目走**白名单标签过滤**（Jsoup）而非裸转义。
5. **字典数据量大**：一个 `dict_type` 下几百条时，每次全量拉影响性能 → 缓存 + 按 `dict_type` 细粒度 key。

## 三、本项目的解法

| 难点 | 本项目做法 |
|------|--------------|
| 缓存一致性 | 字典变更后清 Redis 缓存 key，下次拉重新加载 |
| 字典 vs 枚举 | 易变 → 字典；不变 → 枚举，明确分工 |
| 参数热更新 | 参数走 Redis/DB **实时读**，不写死到 `@Value` 字段 |
| 公告 XSS | Jsoup 白名单过滤（允许 `b/p/img` 等安全标签） |
| 下拉不硬编码 | 前端 `el-select` 统一 `dict API` 按 type 拉 |

> 一句话：**字典的难点不是"建表"，是"缓存一致性 + 参数热更新"——本项目用"变更清缓存 + 参数实时读"化解，下拉从此不硬编码。**
